Lo que vas a lograr

JavaScript confía en ti. Te deja multiplicar un texto, llamar a una función con argumentos de menos o leer una propiedad mal escrita, y solo descubres el problema cuando el programa ya está funcionando, a veces en la pantalla de otra persona. TypeScript añade a JavaScript una capa de tipos que una herramienta revisa antes de ejecutar nada. Es como tener a alguien leyendo tu código por encima del hombro todo el tiempo, que te avisa de muchos errores en el momento en que los escribes.

  • Explicar qué es TypeScript, cómo se relaciona con JavaScript y por qué sus tipos desaparecen antes de ejecutar.
  • Crear un proyecto con TypeScript, configurarlo en modo estricto con tsconfig.json y compilarlo con tsc.
  • Ejecutar TypeScript de tres formas (tsc y node, node archivo.ts y tsx) y saber cuál de ellas revisa los tipos.
  • Anotar variables, arrays, tuplas, objetos y funciones, y dejar que la inferencia haga el resto.
  • Describir datos con type e interface, y transformarlos con Partial, Pick, Omit, Record y compañía.
  • Modelar valores que pueden ser de varias formas con uniones y tipos literales, y estrecharlos con typeof, in y discriminantes.
  • Escribir funciones genéricas que sirven para muchos tipos sin perder información.
  • Distinguir any, unknown y never, y elegir entre enums y uniones de literales.
  • Tipar el DOM y las respuestas de una API, y validar en tiempo de ejecución lo que llega de fuera.
  • Leer un mensaje de error de TypeScript, entender qué dice y saber por dónde empezar a corregirlo.

Por qué tipos: errores antes de ejecutar

En la Estación 7 aprendiste que cada valor tiene un tipo: número, texto, booleano… Y en la Estación 12 viste las tres familias de errores: de sintaxis, de ejecución y lógicos. JavaScript solo te avisa de los primeros antes de empezar. Todo lo demás lo descubres mientras el programa corre, o no lo descubres nunca.

Mira este programa de una tienda. Antes de pulsar «Ejecutar», predice qué va a imprimir cada línea. Escríbelo en un papel.

Cuatro líneas y ningún mensaje rojo. Repasa lo que pasó:

  • precioConIva(entrada) dio 115.99999999999999. Casi bien, y por casualidad: * solo funciona con números, así que JavaScript convirtió el texto "100" por su cuenta. (Los decimales raros son los de la Estación 7: un precio se redondea antes de mostrarse.)
  • entrada + 50 dio 10050: con un texto a un lado, + pega en vez de sumar. Es la trampa que viste en la Estación 7.
  • aplicarDescuento(200) dio NaN: faltaba el porcentaje, así que valía undefined, y cualquier cuenta con undefined da NaN.
  • jugador.vida dio undefined: la propiedad se llama vidas. JavaScript no te dice «esa propiedad no existe»; te devuelve undefined y sigue adelante.

Ninguno de estos fallos detuvo el programa. En una tienda real, el cliente vería un precio de NaN o un carrito con 10050 productos. Estos son los errores más caros: los que el programa no nota.

Tipado dinámico y tipado estático

JavaScript es un lenguaje de tipado dinámico: los tipos pertenecen a los valores y se descubren mientras el programa se ejecuta. Una misma variable puede guardar un número y, dos líneas después, un texto. Nadie comprueba nada por adelantado.

En un lenguaje de tipado estático, los tipos se conocen antes de ejecutar. Una herramienta lee todo el código, averigua qué tipo tiene cada cosa y rechaza el programa si encuentra una mezcla imposible, como pasar un texto donde se esperaba un número. Java, C#, Go, Rust o Kotlin funcionan así.

Qué es TypeScript

TypeScript es un lenguaje creado por Microsoft y publicado en 2012. Lo diseñó Anders Hejlsberg, el mismo ingeniero que creó C#. Es JavaScript con una capa de tipos encima: se dice que es un superconjunto de JavaScript (en inglés, superset). Todo lo que ya sabes escribir sigue valiendo, y además puedes añadir anotaciones de tipo: pequeñas etiquetas que dicen qué tipo espera cada cosa. Se escriben con dos puntos después del nombre: precio: number significa «precio es un número».

Este es el mismo programa de la tienda en TypeScript. Los archivos de TypeScript terminan en .ts en vez de .js:

function precioConIva(precio: number): number {
  return precio * 1.16;
}
function aplicarDescuento(precio: number, porcentaje: number): number {
  return precio - precio * porcentaje / 100;
}

const entrada = "100";   // llegó de un formulario: es texto
console.log(precioConIva(entrada));
console.log(entrada + 50);
console.log(aplicarDescuento(200));

const jugador = { nombre: "Lyra", vidas: 3 };
console.log(jugador.vida);

La herramienta que revisa los tipos se llama tsc (de TypeScript Compiler, «compilador de TypeScript»). Esto es lo que responde, sin ejecutar ni una línea:

Recuerda esta lección desde ya: TypeScript detecta muchos errores, no todos. Los errores lógicos siguen siendo cosa tuya.

Los tipos se borran

Aquí está la idea más importante de toda la estación. Ni el navegador ni Node.js ejecutan los tipos. El camino de un archivo .ts hasta la pantalla tiene dos fases muy distintas:

A la fase de revisión se le llama tiempo de compilación (lo que pasa antes de ejecutar) y a la otra, tiempo de ejecución (lo que pasa mientras el programa corre). Compilar es traducir un programa de un lenguaje a otro; aquí, de TypeScript a JavaScript. Los compiladores e intérpretes los viste con detalle en la Estación 22: Cómo se ejecuta el código. Como tsc traduce de un lenguaje de alto nivel a otro, a lo que hace también se le llama transpilar.

Idea clave

Los tipos de TypeScript solo existen antes de ejecutar. TypeScript revisa tu código, pero no los datos que llegan cuando el programa ya está funcionando: lo que escribe una persona en un formulario, lo que responde un servidor, lo que lees de un archivo. Si una API te manda un texto donde tu tipo decía número, TypeScript no puede enterarse. Para eso necesitas comprobaciones de JavaScript normal, y las aprenderás en la sección El DOM y las APIs.

Para entenderlo

TypeScript es como el inspector que revisa los planos de un edificio antes de construirlo: descubre que una puerta da a una pared o que falta una escalera, y te ahorra construir algo que no funciona. Pero el inspector revisa los planos, no los ladrillos que llegan el día de la obra. Si el camión trae ladrillos defectuosos, eso hay que comprobarlo en la obra. Los datos externos son esos ladrillos.

Lo que TypeScript no hace

No hace que tu programa sea más rápido: el JavaScript que produce es prácticamente el mismo que habrías escrito tú. No cambia cómo se comporta tu código al ejecutarse. Y no reemplaza a las pruebas (Estación 26): un programa puede tener todos los tipos correctos y calcular mal un descuento.

Instalar y ejecutar TypeScript

Hay tres formas de trabajar con TypeScript, de menos a más preparación: probar en el navegador sin instalar nada, crear un proyecto en tu computadora que se compila con tsc, y ejecutar archivos .ts directamente. Vas a conocer las tres.

Sin instalar nada: el Playground

El equipo de TypeScript mantiene una página oficial para practicar: el Playground («patio de juegos»), en typescriptlang.org/play. A la izquierda escribes TypeScript; los errores aparecen subrayados en rojo mientras escribes, y si dejas el ratón encima de una variable ves su tipo. En el panel de la derecha, la pestaña .JS muestra el JavaScript que resulta de borrar los tipos, y la pestaña Errors lista los errores.

Ábrelo ahora en otra pestaña y tenlo a mano: cada bloque de código TypeScript de esta estación se puede copiar allí para ver sus errores en vivo. Es la mejor forma de acompañar la lectura.

Dato

El Playground trae el modo estricto activado (verás qué es en unos minutos) y permite elegir la versión de TypeScript en el menú de arriba. Si algún ejemplo no te marca el error que esperas, revisa en el menú TS Config que la casilla strict esté marcada.

Tu primer proyecto con TypeScript

Para programar de verdad, TypeScript se instala dentro de cada proyecto con npm, el gestor de paquetes que viene con Node.js (lo comprobaste en la Estación 5). Aquí usarás solo cuatro comandos de npm; lo verás a fondo en la Estación 29. Abre una terminal y sigue los pasos:

  1. Comprueba que tienes Node.js. Debe ser la versión LTS más reciente (en septiembre de 2026, la 24):

    $ node --version
v24.21.0

  2. Crea la carpeta del proyecto y entra en ella:

    $ mkdir -p ~/proyectos/hola-ts
$ cd ~/proyectos/hola-ts

  3. Crea el archivo package.json, la ficha del proyecto: su nombre, su versión y de qué paquetes depende. La opción -y acepta todas las respuestas por defecto:

    $ npm init -y

  4. Indica que el proyecto usa módulos modernos de JavaScript (los import y export de la Estación 22). Este comando escribe "type": "module" dentro de package.json. Sin él, tsc generaría un JavaScript de estilo antiguo con líneas de más:

    $ npm pkg set type=module

  5. Instala TypeScript en el proyecto:

    $ npm install --save-dev typescript
added 2 packages, and audited 3 packages in 2s

found 0 vulnerabilities

    npm descarga TypeScript en una carpeta nueva, node_modules, y lo anota en package.json. La opción --save-dev lo guarda como dependencia de desarrollo: algo que necesitas mientras programas, pero no para que el programa funcione, porque lo que se ejecuta al final es JavaScript.

  6. Comprueba la versión con npx, que ejecuta un programa instalado dentro del proyecto:

    $ npx tsc --version
Version 7.0.2

    Tu número puede ser mayor. Lo importante es que empiece por 7 o más.

  7. Crea el archivo de configuración:

    $ npx tsc --init
Created a new tsconfig.json

    Ábrelo en VS Code (code .). Verás muchas líneas, varias desactivadas con //. Reemplaza todo su contenido por esta versión corta, que es la que usaremos en el curso (en la siguiente sección se explica línea por línea):

    {
  "compilerOptions": {
    "rootDir": "./src",
    "outDir": "./dist",
    "target": "esnext",
    "module": "nodenext",
    "types": [],
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true,
    "moduleDetection": "force",
    "skipLibCheck": true
  },
  "include": ["src"]
}

  8. Crea la carpeta src (de source, «código fuente») y dentro un archivo hola.ts con este contenido:

    function saludar(nombre: string): string {
  return `Hola, ${nombre}`;
}

const invitados: string[] = ["Ana", "Leo"];
for (const invitado of invitados) {
  console.log(saludar(invitado));
}

  9. Compila y ejecuta el resultado:

    $ npx tsc
$ ls dist
hola.js
$ node dist/hola.js
Hola, Ana
Hola, Leo

    Si npx tsc no imprime nada, es una buena noticia: no hay errores. Abre dist/hola.js y compáralo con src/hola.ts: es el mismo programa sin las anotaciones.

¿Por qué no instalarlo para todo el sistema?

Podrías instalar TypeScript una sola vez para toda la computadora, pero en la industria se instala dentro de cada proyecto. Así cada proyecto fija su versión en package.json y cualquier persona del equipo que lo descargue obtiene exactamente la misma, con npm install. npx tsc usa siempre la del proyecto.

Para fijar el orden, ordena los comandos que acabas de ver. Algunas líneas dependen de otras: no puedes instalar nada antes de tener package.json, ni ejecutar dist/hola.js antes de compilar.

  1. mkdir -p ~/proyectos/hola-ts
  2. cd ~/proyectos/hola-ts
  3. npm init -y
  4. npm pkg set type=module
  5. npm install --save-dev typescript
  6. npx tsc --init
  7. npx tsc
  8. node dist/hola.js

tsconfig.json: las reglas del proyecto

El archivo tsconfig.json le dice a tsc dónde está tu código, dónde dejar el resultado y qué tan exigente debe ser. Cuando ejecutas npx tsc sin nada más, busca este archivo en la carpeta actual y obedece lo que dice. Estas son las opciones del curso:

OpciónQué hace
"include": ["src"]Qué archivos revisar: todo lo que esté dentro de src.
rootDir y outDirDónde está el código TypeScript (src) y dónde escribir el JavaScript resultante (dist, de distribution).
targetQué versión de JavaScript generar. esnext significa «la más moderna»: sirve para Node.js 24 y navegadores actuales.
moduleCómo tratar import y export. nodenext sigue las reglas de Node.js.
typesQué paquetes de tipos extra cargar. Vacío de momento; cuando uses cosas propias de Node.js, como process, añadirás "node" (Estación 29).
strictEl modo estricto. Activa todas las comprobaciones importantes. Es la opción que más importa del archivo.
noUncheckedIndexedAccessAl leer lista[0], te recuerda que ese elemento podría no existir. Lo verás en la sección de tipos básicos.
erasableSyntaxOnlyTe avisa si usas algo que no se puede borrar sin más (como enum). Así tu código también funciona con node archivo.ts.
verbatimModuleSyntax, moduleDetection, skipLibCheckDetalles técnicos recomendados por el propio tsc --init: tratan cada archivo como un módulo independiente y ahorran tiempo al no revisar los tipos de las librerías instaladas.

El modo estricto ("strict": true) activa un grupo de comprobaciones. Las dos que más vas a notar: noImplicitAny, que te obliga a decir el tipo de los parámetros de una función cuando TypeScript no puede adivinarlo, y strictNullChecks, que te obliga a contemplar los casos en que un valor puede ser null o undefined. Sin modo estricto, TypeScript deja pasar muchísimos errores y pierde buena parte de su gracia.

Según la versión

Desde TypeScript 6.0 (marzo de 2026), strict está activado aunque no lo escribas. Aun así, déjalo escrito: quien lea el archivo sabrá cómo se revisa el proyecto, sin depender de la versión instalada. Y desde TypeScript 7.0 (julio de 2026), tsc es un programa nativo reescrito en el lenguaje Go, unas diez veces más rápido que antes. Se instala y se usa igual. Para saber qué versión tienes: npx tsc --version.

Error común

Si escribes npx tsc src/hola.ts (con el nombre del archivo) en una carpeta que tiene tsconfig.json, obtienes error TS5112: tsconfig.json is present but will not be loaded if files are specified on commandline. Es decir: «hay un tsconfig.json, pero no lo usaré si me das archivos sueltos». La solución es escribir solo npx tsc: el propio tsconfig.json ya dice qué archivos revisar.

tsc genera el .js aunque haya errores

Esto sorprende a casi todo el mundo: si tsc encuentra errores, los muestra, pero igualmente escribe el archivo .js. Un error de tipos no impide generar JavaScript, porque borrar los tipos siempre es posible. Por eso es importante mirar la salida de tsc y no solo si apareció el archivo en dist. Tres variantes útiles:

Ejecutar un .ts directamente: node y tsx

Compilar a dist y después ejecutar es el camino clásico, y sigue siendo el que se usa para publicar un proyecto. Pero mientras aprendes o pruebas algo rápido, hay dos atajos.

Node.js puede ejecutar archivos .ts. Desde Node.js 22.18 y en toda la versión 24, basta con escribir node archivo.ts. Node hace un borrado de tipos (en inglés, type stripping): quita las anotaciones y ejecuta lo que queda. En Node.js 24 esta función es estable desde la versión 24.12.0 y ya no muestra avisos de «experimental» desde la 24.3.0. Pero fíjate en lo que pasa con un error de tipos:

// src/prueba.ts
function saludar(nombre: string): string {
  return `Hola, ${nombre}`;
}
console.log(saludar("Ana"));
console.log(saludar(42));   // error de tipos
$ node src/prueba.ts
Hola, Ana
Hola, 42

Se ejecutó sin quejarse. Node.js borra los tipos, pero no los revisa: para él, las anotaciones son decoración que hay que quitar. Además, solo sabe borrar lo que es puramente decorativo. Si usas algo de TypeScript que genera código, como un enum (lo verás en la sección any, unknown y enums), Node se niega:

$ node src/direcciones.ts
file:///home/tu/proyectos/hola-ts/src/direcciones.ts:1
enum Direccion { Arriba, Abajo }
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode

(La salida real sigue con varias líneas que empiezan por at: es la pila de llamadas que conociste en la Estación 12. La línea importante es la del error: «los enum de TypeScript no están soportados en el modo que solo borra tipos».)

Para eso sirve la opción erasableSyntaxOnly de nuestro tsconfig.json: el editor te avisa en cuanto escribes algo que Node.js no sabría borrar.

tsx (de TypeScript Execute) es un paquete que ejecuta TypeScript con Node.js usando por dentro esbuild, un traductor muy rápido. Entiende todo TypeScript, incluidos los enums, y tiene un modo que vuelve a ejecutar el archivo cada vez que guardas. Tampoco revisa los tipos.

$ npm install --save-dev tsx
$ npx tsx src/hola.ts
Hola, Ana
Hola, Leo
$ npx tsx watch src/hola.ts
Forma¿Revisa los tipos?¿Genera .js?Cuándo usarla
npx tsc y después node dist/…SíSí, en distPara publicar o entregar el proyecto, y para revisarlo entero.
node archivo.tsNoNoProbar rápido con Node.js 22.18 o posterior, si usas solo sintaxis borrable.

Un flujo de trabajo cómodo

La propia documentación de Node.js recomienda esta combinación: ejecutar con node archivo.ts para ver resultados rápido y, en otra terminal, npx tsc --noEmit --watch para que te avise de cualquier error de tipos. Además, VS Code trae TypeScript integrado y subraya los errores mientras escribes, sin ejecutar ningún comando. En los equipos, tsc --noEmit también se ejecuta automáticamente antes de aceptar cambios (lo verás en la Estación 35).

  3. Lee lo que generó tsc con cat dist/hola.js. ¿Qué desapareció?

Todo lo que tenía que ver con tipos desapareció: la línea type Invitado = … entera, : Invitado, : string e Invitado[]. El resto es idéntico, salvo la sangría (tsc usa cuatro espacios) y un export {}; al final, que marca el archivo como módulo. Esa es toda la magia: TypeScript es JavaScript más tipos, y compilar es, sobre todo, quitar los tipos.

Tipos básicos e inferencia

Ya tienes dónde escribir TypeScript. Empieza por lo más pequeño: decirle a TypeScript qué tipo tiene una variable. La anotación de tipo se escribe después del nombre, con dos puntos:

let titulo: string = "Aventura en el bosque";
let nivel: number = 1;
let terminado: boolean = false;

Los nombres de los tipos básicos coinciden con los que devuelve typeof en JavaScript (Estación 7), con una excepción: el tipo de null se llama null, aunque typeof null dé "object".

TipoQué valores admiteEjemplo
stringCualquier textolet nombre: string = "Ana";
numberCualquier número, entero o decimal (también NaN e Infinity)let precio: number = 9.99;
booleantrue o falselet pausado: boolean = false;
nullSolo el valor nullCasi siempre se combina con otro tipo, como verás
undefinedSolo el valor undefinedIgual que null

Existen también bigint y symbol, que casi no vas a necesitar.

Error común

Los tipos se escriben en minúscula: string, number, boolean. String, Number y Boolean con mayúscula existen, pero son otra cosa (los objetos «envoltorio» de JavaScript) y TypeScript no te avisará si los usas por error. La documentación oficial lo dice sin rodeos: usa siempre la versión en minúscula.

La inferencia: TypeScript deduce los tipos

Las anotaciones de arriba sobran. Si escribes let nivel = 1;, TypeScript ve que el valor inicial es un número y decide que nivel es de tipo number para siempre. A esto se le llama inferencia de tipos: TypeScript deduce el tipo a partir del valor. Si en VS Code o en el Playground dejas el ratón encima de nivel, verás let nivel: number.

Sigue cómo lee TypeScript este programa. No lo ejecuta: lo recorre de arriba abajo y va anotando el tipo de cada variable, igual que tú anotabas valores en la prueba de escritorio.

let puntos = 0;
const nombre = "Lyra";
let enLinea: boolean = false;
puntos = puntos + 10;
enLinea = "sí";
const mensaje = `${nombre}: ${puntos}`;

La conclusión práctica: no anotes lo que TypeScript ya sabe. Escribir const nombre: string = "Ana" no añade información y hace el código más largo. Anota solo donde TypeScript no puede adivinar o donde quieres dejar clara tu intención:

  • Los parámetros de las funciones. TypeScript no sabe con qué valores llamarán a tu función. Si no los anotas, en modo estricto te avisa: error TS7006: Parameter 'n' implicitly has an 'any' type («el parámetro n tiene implícitamente el tipo any», un tipo comodín que verás en la sección any, unknown y enums).
  • Las variables que empiezan vacías, como una lista que se llenará después: const pendientes: string[] = [];
  • Lo que devuelve una función, cuando quieres que TypeScript compruebe que el resultado es el que planeabas (lo verás en Funciones y genéricos).

Arrays: listas de un tipo

Un array (Estación 11) se anota con el tipo de sus elementos seguido de corchetes. Hay una segunda forma que significa lo mismo: Array<tipo>. Los signos < > indican que Array es un tipo que necesita otro tipo para estar completo; lo entenderás del todo en la sección de genéricos.

const nombres: string[] = ["Ana", "Leo"];
const puntuaciones: Array<number> = [120, 95, 300];   // igual que number[]
const pendientes: string[] = [];                       // vacía: hay que anotarla

const niveles = [1, 2, 3];        // TypeScript infiere number[]
const mezcla = [1, "dos", 3];     // infiere (string | number)[]: números o textos

nombres.push("Maya");   // bien
nombres.push(7);        // error TS2345: Argument of type 'number' is not assignable
                        // to parameter of type 'string'.

El tipo (string | number)[] se lee «array de elementos que son string o number». Esa barra vertical es una unión, y tiene su propia sección más adelante.

Con el tsconfig.json del curso, leer un elemento por su posición tiene una sorpresa:

const primero = nombres[0];       // tipo: string | undefined
console.log(primero.toUpperCase());
// error TS18048: 'primero' is possibly 'undefined'.

if (primero !== undefined) {
  console.log(primero.toUpperCase());   // aquí sí: dentro del if, primero es string
}

for (const nombre of nombres) {
  console.log(nombre.toUpperCase());    // for...of nunca da undefined: sin error
}

¿Por qué string | undefined? Porque TypeScript no sabe cuántos elementos tendrá la lista cuando el programa se ejecute. Si la lista está vacía, nombres[0] vale undefined, y undefined.toUpperCase() es el clásico TypeError: Cannot read properties of undefined que cazaste en la Estación 12. La opción noUncheckedIndexedAccess te obliga a contemplar ese caso. Sin ella, TypeScript supondría que el elemento siempre existe.

Tuplas: arrays de tamaño fijo

A veces un array tiene siempre la misma cantidad de elementos, y cada posición significa algo distinto: una coordenada [x, y], o un par [nombre, puntos]. Para eso existe la tupla: un array con un tipo para cada posición.

const posicion: [number, number] = [3, 4];
const registro: [string, number] = ["Ana", 120];

const [x, y] = posicion;              // desestructuración: x e y son number
const [quien, puntos] = registro;     // quien es string, puntos es number

const malo: [number, number] = [3, 4, 5];
// error TS2322: Type '[number, number, number]' is not assignable to type '[number, number]'.
//   Source has 3 element(s) but target allows only 2.

Al ejecutarse, una tupla es un array normal de JavaScript: la restricción de tamaño solo existe para TypeScript. La desestructuración es la que viste en la Estación 11. En la Estación 32 verás que React devuelve tuplas: const [cuenta, setCuenta] = useState(0).

Objetos: type e interface

Casi todos los datos de un programa real son objetos: un producto, un jugador, un mensaje (Estación 11). Describir su forma es donde TypeScript empieza a ahorrarte trabajo de verdad. Puedes escribir la forma de un objeto directamente en la anotación:

function mostrar(producto: { nombre: string; precio: number }) {
  console.log(`${producto.nombre}: ${producto.precio} €`);
}

Funciona, pero si la misma forma aparece en diez funciones, tendrías que repetirla diez veces. Mejor ponerle nombre.

Alias de tipo con type

La palabra type crea un alias de tipo: un nombre para una forma que vas a reutilizar. Por costumbre, los nombres de tipos empiezan con mayúscula (Producto, Jugador), para distinguirlos de las variables.

type Producto = {
  readonly id: number;        // readonly: no se puede cambiar después de crearlo
  nombre: string;
  precio: number;
  descripcion?: string;       // ?: propiedad opcional, puede no estar
  etiquetas: string[];
};

const taza: Producto = {
  id: 1,
  nombre: "Taza de cerámica",
  precio: 8.5,
  etiquetas: ["cocina", "regalo"],
};

function resumen(p: Producto): string {
  const extra = p.descripcion ?? "sin descripción";
  return `${p.nombre} (${p.precio} €): ${extra}`;
}

Dos marcas nuevas:

  • descripcion?: string es una propiedad opcional. Su tipo real es string | undefined: puede ser un texto o no estar. Por eso resumen usa ?? (Estación 8) para dar un valor por defecto. Si escribieras p.descripcion.length sin comprobar, TypeScript diría 'p.descripcion' is possibly 'undefined'.
  • readonly id es una propiedad de solo lectura: se asigna al crear el objeto y después no se puede cambiar. Ideal para identificadores.

Ahora mira todo lo que tsc detecta con ese tipo:

const plato: Producto = { id: 2, nombre: "Plato", etiquetas: [] };
// error TS2741: Property 'precio' is missing in type '{ id: number; nombre: string;
// etiquetas: never[]; }' but required in type 'Producto'.

const vaso: Producto = { id: 3, nombre: "Vaso", precio: 3, etiquetas: [], color: "azul" };
// error TS2353: Object literal may only specify known properties, and 'color' does
// not exist in type 'Producto'.

taza.id = 5;
// error TS2540: Cannot assign to 'id' because it is a read-only property.

Traducidos: «falta la propiedad precio, que es obligatoria en Producto»; «un objeto escrito así solo puede tener propiedades conocidas, y color no existe en Producto»; «no se puede asignar a id porque es de solo lectura». El segundo error protege de las erratas: si escribes precoi: 3, TypeScript te avisa en vez de crear una propiedad nueva que nadie leerá.

readonly no congela nada al ejecutarse

readonly es una regla para TypeScript, no para JavaScript: después del borrado de tipos, el objeto se puede modificar como cualquier otro. Si necesitas impedir cambios mientras el programa corre, existe Object.freeze(), que sí es JavaScript.

Objetos dentro de objetos, y listas de objetos

Los tipos se combinan igual que los datos. Un tipo puede usar otros tipos, y una lista de productos es Producto[]:

type Direccion = { ciudad: string; codigoPostal: string };

type Cliente = {
  nombre: string;
  direccion: Direccion;
  pedidos: Producto[];
};

const cliente: Cliente = {
  nombre: "Ana",
  direccion: { ciudad: "Lima", codigoPostal: "15001" },
  pedidos: [taza],
};
console.log(cliente.direccion.ciudad);   // al escribir el punto, el editor te sugiere ciudad y codigoPostal

Ese último comentario es una ventaja que se nota desde el primer día: como el editor conoce la forma de cada objeto, te ofrece las propiedades al escribir el punto (autocompletado). Dejas de ir y venir entre archivos para recordar si era codigoPostal o cp.

TypeScript compara formas, no nombres

Una pregunta natural: si tengo un objeto que no creé con el tipo Producto, ¿puedo pasarlo a una función que pide un Producto? Sí, si tiene la forma correcta. TypeScript solo mira qué propiedades hay y de qué tipo son. A esto se le llama tipado estructural:

type Personaje = { nombre: string; vida: number };

function curar(p: Personaje) {
  p.vida += 10;
}

const datos = { nombre: "Ana", vida: 50, color: "rojo" };
curar(datos);   // bien: datos tiene nombre (string) y vida (number); color sobra y no molesta

¿Y el error de color de antes? Esa comprobación de propiedades de más solo se aplica cuando escribes el objeto directamente en la anotación, porque ahí una propiedad desconocida casi siempre es una errata. Si el objeto ya existía en una variable, TypeScript acepta que tenga más cosas de las necesarias.

Para entenderlo

Es como un casting para una obra de teatro que pide «alguien que sepa cantar y bailar». No importa cómo te llames ni de qué escuela vengas: si cantas y bailas, sirves. Y si además tocas la guitarra, no te descartan por eso. El límite de la analogía: en TypeScript, «saber cantar» es tener una propiedad con el nombre y el tipo exactos.

interface: la otra forma de describir objetos

Hay una segunda palabra para describir la forma de un objeto: interface («interfaz»). Se escribe sin el signo =:

interface Personaje {
  nombre: string;
  vida: number;
}

interface Mago extends Personaje {   // un Mago es un Personaje con algo más
  mana: number;
}

const lyra: Mago = { nombre: "Lyra", vida: 80, mana: 120 };

extends («extiende») crea una interfaz nueva a partir de otra, añadiendo propiedades. Con type se consigue lo mismo usando &, que se llama intersección y significa «todo lo de este tipo y todo lo de este otro»:

type ConPosicion = { x: number; y: number };
type Enemigo = Personaje & ConPosicion;   // nombre, vida, x e y

const slime: Enemigo = { nombre: "Slime", vida: 20, x: 3, y: 7 };

¿Cuál usar? Para describir objetos, las dos sirven casi siempre. Estas son las diferencias reales:

typeinterface
Describir objetosSíSí
Ampliar otro tipoCon &Con extends
Uniones ("a" | "b"), tuplas, tipos básicosSíNo
Reabrirla para añadir propiedades más tardeNo: el nombre queda fijadoSí: dos interface con el mismo nombre se fusionan

Consejo de oficio

El manual oficial dice que en la mayoría de los casos puedes elegir según tu preferencia, y propone una regla: usa interface hasta que necesites algo que solo type puede hacer. Muchos equipos prefieren lo contrario, type para todo, porque sirve para más cosas. Lo que importa de verdad es que el equipo elija una convención y la mantenga. En este curso usaremos type casi siempre, porque también lo necesitarás para uniones.

Las clases de la Estación 21 también se pueden tipar: TypeScript añade a las clases propiedades con tipo y la palabra implements, para prometer que una clase cumple una interfaz. La idea es la misma que acabas de ver.

Tipos de utilidad: transformar un tipo en otro

Imagina un formulario para editar un producto. La persona puede cambiar solo el precio, o solo el nombre. La función que aplica los cambios no recibe un Producto completo, sino «algunas propiedades de Producto». Podrías escribir un tipo nuevo con todo opcional, pero entonces tendrías que mantener dos tipos sincronizados a mano.

TypeScript trae tipos de utilidad (en inglés, utility types): tipos que reciben otro tipo entre < > y devuelven una versión transformada. El más usado es Partial, que vuelve opcionales todas las propiedades:

function actualizar(p: Producto, cambios: Partial<Producto>): Producto {
  return { ...p, ...cambios };   // spread: copia p y encima pone los cambios
}

const rebajada = actualizar(taza, { precio: 6 });   // solo el precio: permitido

El ... es el spread de la Estación 11. Estos son los seis tipos de utilidad que más vas a ver:

const borrador: NuevoProducto = { nombre: "Plato", precio: 5, etiquetas: [] };

Fíjate en Record<Dificultad, number>: como Dificultad solo admite tres textos, TypeScript exige exactamente esas tres claves. Si olvidas dificil, te lo dice: Property 'dificil' is missing in type '{ facil: number; normal: number; }' but required in type 'Record<Dificultad, number>'. El contador de votos es el mismo patrón que usaste en el ejercicio «Contar votos» de la Estación 11, ahora con tipo.

Idea clave

Los tipos de utilidad no crean datos ni hacen nada al ejecutarse: transforman descripciones. Te permiten escribir la forma de tus datos una sola vez (Producto) y derivar el resto. Si mañana añades stock a Producto, NuevoProducto y Partial<Producto> lo incluyen solos.

Uniones, tipos literales y estrechamiento

En la vida real, muchos valores pueden ser de más de una forma. Un código de pedido puede llegar como número o como texto. Una búsqueda puede encontrar un producto o no encontrar nada. Una descarga puede estar «cargando», «lista» o en «error». TypeScript tiene una herramienta precisa para esto, y es probablemente la que más vas a usar.

Uniones: esto o aquello

Una unión es un tipo que admite valores de varios tipos. Se escribe separándolos con una barra vertical |, que se lee «o»:

type Id = number | string;

let pedido: Id = 1042;
pedido = "A-1042";      // también vale
pedido = true;          // error TS2322: Type 'boolean' is not assignable to type 'Id'.

La contrapartida: con una unión, TypeScript solo te deja usar lo que tienen en común todos sus miembros. Si valor es string | number, no puedes llamar a valor.toUpperCase(), porque si resulta ser un número, el programa fallaría:

function grita(valor: string | number) {
  return valor.toUpperCase();
}
// error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
//   Property 'toUpperCase' does not exist on type 'number'.

La segunda línea del error explica el motivo: «no existe en el tipo number». Para usar toUpperCase primero tienes que averiguar qué es valor en ese momento. Enseguida verás cómo.

Tipos literales: solo estos valores exactos

En la traza de la sección anterior viste que const nombre = "Lyra" tiene el tipo "Lyra". Un tipo literal es un tipo que admite un único valor exacto. Solo, no sirve de mucho. Combinado en una unión, es una herramienta excelente para describir opciones cerradas:

type Estado = "cargando" | "listo" | "error";
type Direccion = "arriba" | "abajo" | "izquierda" | "derecha";
type Dado = 1 | 2 | 3 | 4 | 5 | 6;

let estado: Estado = "cargando";
estado = "listo";         // bien
estado = "terminado";     // error TS2322: Type '"terminado"' is not assignable to type 'Estado'.

const rumbo: Direccion = "arrriba";
// error TS2820: Type '"arrriba"' is not assignable to type 'Direccion'. Did you mean '"arriba"'?

Compara con usar string: cualquier errata ("arrriba", "Arriba", "up") pasaría sin aviso y tu personaje se quedaría quieto sin que nadie supiera por qué. Con la unión de literales, TypeScript rechaza la errata, sugiere la palabra correcta y el editor te ofrece las cuatro opciones al escribir la comilla.

null y undefined: el valor que puede faltar

Con el modo estricto, null y undefined no caben en cualquier sitio: un string es siempre un texto. Si un valor puede faltar, lo dices con una unión. Y muchas funciones de JavaScript ya vienen con esa unión puesta:

let ganador: string | null = null;           // todavía no hay ganador

const encontrado = [3, 8, 12].find((n) => n > 10);   // number | undefined
const boton = document.querySelector("button");       // HTMLButtonElement | null

boton.addEventListener("click", () => {});
// error TS18047: 'boton' is possibly 'null'.

«boton es posiblemente null»: si la página no tuviera ningún botón, querySelector devolvería null y el programa se rompería con el TypeError de siempre. Tony Hoare, que introdujo la referencia nula en 1965, la llamó años después «mi error de mil millones de dólares» por todos los fallos que ha causado. El modo estricto convierte ese error de ejecución en un aviso antes de ejecutar.

Estrechar el tipo: narrowing

¿Cómo se usa entonces un valor de tipo unión? Comprobando qué es con JavaScript normal. TypeScript sigue tus if y, dentro de cada rama, sabe qué tipo queda. A esto se le llama estrechamiento de tipos (en inglés, narrowing): el tipo se va haciendo más estrecho, más preciso, a medida que tu código descarta posibilidades.

TypeScript entiende muchas formas de comprobar, todas de JavaScript normal:

Igualdadif (nombre === null), if (estado === "error")null, undefined o un literal concreto
Veracidadif (boton)null y undefined (cuidado: también descarta 0 y "", como viste con truthy y falsy en la Estación 8)

El operador in es de JavaScript: "nadar" in animal vale true si el objeto tiene una propiedad con ese nombre. TypeScript lo usa para distinguir objetos de formas distintas:

type Pez = { nombre: string; nadar: () => void };
type Pajaro = { nombre: string; volar: () => void };

function mover(animal: Pez | Pajaro) {
  console.log(animal.nombre);   // bien: los dos tienen nombre
  if ("nadar" in animal) {
    animal.nadar();             // aquí animal es Pez
  } else {
    animal.volar();             // aquí animal es Pajaro
  }
}

Consejo de oficio

Las guardas que aprendiste en la Estación 8 (salir pronto de la función con return cuando algo no cuadra) encajan de maravilla con TypeScript: después de if (nombre === null) return 0;, en el resto de la función nombre ya no puede ser null, y el código queda plano y claro.

Uniones discriminadas: objetos con etiqueta

El patrón más potente de esta sección combina todo lo anterior. Imagina figuras geométricas: un círculo tiene radio; un rectángulo, ancho y alto. Les pones a todas una propiedad común con un tipo literal distinto, una especie de etiqueta que dice qué es cada una:

type Figura =
  | { tipo: "circulo"; radio: number }
  | { tipo: "rectangulo"; ancho: number; alto: number };

function area(f: Figura): number {
  switch (f.tipo) {
    case "circulo":
      return Math.PI * f.radio ** 2;      // aquí f es el círculo: tiene radio
    case "rectangulo":
      return f.ancho * f.alto;            // aquí f es el rectángulo
  }
}

Esto se llama unión discriminada, y la propiedad tipo es el discriminante: mirando solo esa propiedad, TypeScript sabe de qué miembro de la unión se trata. Dentro de case "circulo", escribir f.ancho sería un error, porque un círculo no tiene ancho. Es la forma natural de modelar mensajes de un chat (texto, imagen, audio), eventos de un juego (moneda, golpe, subida de nivel) o respuestas de una API (éxito o error).

Y ahora, la parte que convence a cualquiera. Añades el triángulo a la unión y te olvidas de actualizar area:

type Figura =
  | { tipo: "circulo"; radio: number }
  | { tipo: "rectangulo"; ancho: number; alto: number }
  | { tipo: "triangulo"; base: number; altura: number };   // nueva

function area(f: Figura): number {
// error TS2366: Function lacks ending return statement and return type does not
// include 'undefined'.

«La función no termina con un return y su tipo de retorno no incluye undefined». Traducido al caso: hay una figura para la que area no devuelve nada. En un programa grande, con la misma unión usada en veinte sitios, TypeScript te lleva de la mano a cada uno de los lugares que tienes que actualizar. Para ver lo que pasa sin esa ayuda, ejecuta la versión JavaScript. Predice las tres líneas antes de pulsar «Ejecutar»:

JavaScript imprime triangulo undefined sin inmutarse: el switch no encontró su caso y la función terminó sin return. Añade el caso que falta (el área de un triángulo es base por altura entre dos) y vuelve a ejecutar.

never: asegúrate de cubrir todos los casos

Hay una forma todavía más explícita de pedirle a TypeScript que vigile que no olvidas ningún caso. Se añade un default que guarda la figura en una variable de tipo never, un tipo que no admite ningún valor:

function area(f: Figura): number {
  switch (f.tipo) {
    case "circulo":
      return Math.PI * f.radio ** 2;
    case "rectangulo":
      return f.ancho * f.alto;
    default: {
      const imposible: never = f;
      throw new Error(`Figura desconocida: ${JSON.stringify(imposible)}`);
    }
  }
}
// Con el triángulo añadido a Figura y sin su case:
// error TS2322: Type '{ tipo: "triangulo"; base: number; altura: number; }' is not
// assignable to type 'never'.

Si todos los casos están cubiertos, al llegar al default TypeScript ya descartó todas las figuras y f es de tipo never: la asignación encaja. Si falta alguno, lo que queda (el triángulo) no cabe en never, y el error te dice exactamente cuál falta. El throw protege además en tiempo de ejecución, por si llega un dato inesperado desde fuera. A esto se le llama comprobación exhaustiva.

Ordena ahora una función que usa una unión discriminada. Piensa qué líneas solo son válidas después de una comprobación. Las dos opciones de la unión pueden ir en cualquier orden:

  1. type Mensaje =
  2. | { tipo: "texto"; contenido: string }
  3. | { tipo: "imagen"; url: string; ancho: number };
  4. function vistaPrevia(m: Mensaje): string {
  5. if (m.tipo === "texto") {
  6. return m.contenido.slice(0, 20);
  7. }
  8. return `[Imagen de ${m.ancho} px]`;
  9. }

Funciones tipadas y genéricos

En la Estación 10 leíste un aviso: JavaScript nunca comprueba que llames a una función con la cantidad correcta de argumentos ni con el tipo correcto. Con TypeScript, cada función se convierte en un pequeño contrato: qué recibe y qué devuelve.

Parámetros y valor de retorno

function sumar(a: number, b: number): number {
  return a + b;
}

sumar(1, 2);        // bien
sumar(1);           // error TS2554: Expected 2 arguments, but got 1.
sumar(1, 2, 3);     // error TS2554: Expected 2 arguments, but got 3.
sumar("1", 2);      // error TS2345: Argument of type 'string' is not assignable to
                    // parameter of type 'number'.

Los tipos de los parámetros van dentro de los paréntesis; el tipo de lo que devuelve, después, tras dos puntos. TypeScript comprueba las dos direcciones: que quien llama pase lo que la función pide, y que la función devuelva lo que promete:

function edadEnAnios(): number {
  return "30";      // error TS2322: Type 'string' is not assignable to type 'number'.
}

El tipo de retorno se puede omitir, porque TypeScript lo infiere del return. Escribirlo tiene una ventaja: si por error devuelves otra cosa, el error aparece dentro de la función, donde está el fallo, y no en los diez sitios que la usan.

Opcionales, valores por defecto y void

// saludo?: parámetro opcional (puede no pasarse: vale undefined)
function saludar(nombre: string, saludo?: string): string {
  return `${saludo ?? "Hola"}, ${nombre}`;
}
saludar("Ana");              // "Hola, Ana"
saludar("Ana", "Buenas");    // "Buenas, Ana"

// Con valor por defecto no hace falta anotar: vida es number
function crearEnemigo(nombre: string, vida = 100) {
  return { nombre, vida };
}

// Parámetro rest: cualquier cantidad de números, que llegan como array
function promedio(...notas: number[]): number {
  return notas.reduce((a, b) => a + b, 0) / notas.length;
}

// void: la función no devuelve nada útil
function anunciar(mensaje: string): void {
  console.log(`>> ${mensaje}`);
}

Cuidado

Los parámetros opcionales van siempre al final: function f(a?: string, b: number) es un error, porque no habría forma de pasar b sin pasar a.

Funciones flecha y callbacks

Las funciones flecha se anotan igual. Y cuando pasas una función como argumento (un callback, Estación 10), normalmente no hace falta anotar nada, porque TypeScript deduce los tipos por el contexto:

const doble = (n: number): number => n * 2;

const nombres = ["Ana", "Leo", "Maya"];
const largos = nombres.map((nombre) => nombre.length);
// nombre es string (porque nombres es string[]) y largos es number[]

Para describir una función que recibe otra función, se escribe el tipo de la función con una flecha: (parámetros) => retorno. Se lee «una función que recibe esto y devuelve aquello»:

function repetir(veces: number, accion: (vuelta: number) => void): void {
  for (let i = 1; i <= veces; i++) accion(i);
}
repetir(3, (v) => console.log(`Vuelta ${v}`));   // v es number: lo deduce del tipo de accion

type Operacion = (a: number, b: number) => number;
const restar: Operacion = (a, b) => a - b;

Una función async (Estación 16) siempre devuelve una promesa. Su tipo de retorno se escribe Promise<T>, donde T es lo que obtendrás con await: async function cargarNivel(): Promise<string[]> promete que, al esperar, obtendrás un array de textos.

Genéricos: una función, muchos tipos

Quieres una función que devuelva el primer elemento de cualquier lista. ¿Qué tipo le pones al parámetro? Si escribes number[], solo sirve para números. Si escribes any[] (el comodín que verás en la sección siguiente), sirve para todo, pero TypeScript pierde la pista del tipo y deja de protegerte con el resultado.

La solución son los genéricos: funciones (o tipos) con un hueco para un tipo que se decide al usarlas. El hueco se declara entre < > después del nombre, y por costumbre se llama T (de type). Se le llama parámetro de tipo:

function primero<T>(lista: T[]): T | undefined {
  return lista[0];
}

const n = primero([10, 20, 30]);     // T es number  → n es number | undefined
const s = primero(["Ana", "Leo"]);   // T es string  → s es string | undefined
const v = primero<string>([]);       // T indicado a mano, porque [] no da pistas

Se lee: «primero recibe una lista de elementos de cierto tipo T y devuelve un elemento de ese mismo tipo T, o undefined». En cada llamada, TypeScript mira el argumento y deduce qué es T. El genérico conecta la entrada con la salida: lo que entra determina lo que sale.

Para entenderlo

Un genérico es como un formulario con un espacio en blanco: «Devuelve el primer ____ de una lista de ____». Cada vez que lo usas, el mismo tipo rellena los dos huecos. Si metes una lista de canciones, te devuelve una canción. Donde la analogía se queda corta: en TypeScript no rellenas el hueco a mano casi nunca; lo deduce el compilador.

A veces necesitas que T cumpla algo. Con extends pones una restricción: «T puede ser cualquier tipo, siempre que tenga…»:

function masLargo<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
masLargo("hola", "adiós");     // bien: los textos tienen length
masLargo([1, 2], [3]);         // bien: los arrays también
masLargo(10, 20);
// error TS2345: Argument of type 'number' is not assignable to parameter of type
// '{ length: number; }'.

function buscarPorNombre<T extends { nombre: string }>(lista: T[], nombre: string): T | undefined {
  return lista.find((item) => item.nombre === nombre);
}
const heroes = [{ nombre: "Lyra", vida: 80 }, { nombre: "Tor", vida: 120 }];
const tor = buscarPorNombre(heroes, "Tor");   // tor conserva su forma: tiene vida
console.log(tor?.vida);

Fíjate en lo que ganas con buscarPorNombre: sirve para héroes, productos o ciudades, cualquier cosa con nombre, y el resultado no pierde el resto de propiedades. El ?. es el encadenamiento opcional de la Estación 11: tor puede ser undefined.

Los tipos también pueden ser genéricos. Este patrón aparece en muchos proyectos para devolver un resultado que puede haber salido bien o mal, sin lanzar excepciones:

type Resultado<T> =
  | { ok: true; valor: T }
  | { ok: false; error: string };

function dividir(a: number, b: number): Resultado<number> {
  if (b === 0) return { ok: false, error: "No se puede dividir entre 0" };
  return { ok: true, valor: a / b };
}

const r = dividir(10, 2);
if (r.ok) {
  console.log(r.valor);    // aquí r tiene valor
} else {
  console.log(r.error);    // aquí r tiene error
}

Es una unión discriminada: ok es el discriminante, con los tipos literales true y false. La usarás en el proyecto de esta estación.

Y una sorpresa: ya llevas un rato usando genéricos. Array<string>, Promise<Usuario>, Partial<Producto> y Record<string, number> son tipos genéricos que trae TypeScript. También Map<string, number> y Set<string>, las estructuras de la Estación 19:

const inventario = new Map<string, number>();   // claves string, valores number
inventario.set("pocion", 3);
inventario.set("espada", "una");   // error TS2345: Argument of type 'string' is not
                                   // assignable to parameter of type 'number'.

Los genéricos no existen en JavaScript: allí todas las funciones aceptan cualquier cosa. Escribe la versión JavaScript de ultimo, cuyo tipo en TypeScript sería function ultimo<T>(lista: T[]): T | undefined. Debe devolver el último elemento, o undefined si la lista está vacía:

Pista

El último elemento está en la posición lista.length - 1. Si la lista está vacía, esa posición es -1 y leerla da undefined, que es justo lo que quieres. También existe lista.at(-1).

No todo tiene que ser genérico

Una regla del manual oficial: si el parámetro de tipo aparece una sola vez en la firma, probablemente no lo necesitas. function mostrar<T>(x: T): void no gana nada frente a un tipo normal; el genérico sirve cuando conecta dos cosas (la entrada con la salida, o dos parámetros entre sí).

any, unknown, never y enums

Hasta ahora, cada valor tenía un tipo concreto. TypeScript tiene además tres tipos especiales que describen situaciones límite: «me da igual», «no lo sé» y «esto no puede pasar». Conviene conocerlos bien, porque uno de ellos es la puerta por la que se cuelan casi todos los errores.

any: apaga la revisión

any («cualquiera») significa «no revises nada de este valor». Con any puedes hacer lo que quieras, y TypeScript no se queja de nada:

const texto = '{"nombre":"Ana","nivel":7}';
const dato: any = JSON.parse(texto);

console.log(dato.nombre.toUppercase());   // tsc: 0 errores
// Al ejecutar: TypeError: dato.nombre.toUppercase is not a function

La errata (toUppercase en vez de toUpperCase) llega intacta hasta la ejecución. Y any es contagioso: todo lo que sale de un any (dato.nombre, dato.nombre.algo) también es any. Un solo any en el lugar equivocado puede desactivar la revisión de medio programa sin que se note.

Te lo vas a encontrar sin buscarlo: JSON.parse devuelve any, respuesta.json() también, y algunas librerías antiguas lo usan por todas partes. En modo estricto, lo que TypeScript sí prohíbe es el any implícito: un parámetro sin tipo del que no puede deducir nada (el error TS7006 que viste antes).

unknown: no sé qué es, así que compruébalo

unknown («desconocido») también admite cualquier valor, pero con la regla contraria: no te deja usarlo hasta que compruebes qué es. Es la versión segura de any:

const dato: unknown = JSON.parse(texto);

console.log(dato.nombre);
// error TS18046: 'dato' is of type 'unknown'.

if (typeof dato === "object" && dato !== null && "nombre" in dato && typeof dato.nombre === "string") {
  console.log(dato.nombre.toUpperCase());   // aquí sí: TypeScript sabe que nombre es string
}

Es más trabajo, y ese trabajo es justo el que evita el error. Cuando un valor llega de fuera y no sabes qué forma tiene, declararlo unknown te obliga a comprobarlo antes de usarlo. En la siguiente sección escribirás esas comprobaciones de forma ordenada.

never: lo que no puede ocurrir

never («nunca») es el tipo que no admite ningún valor. Aparece en tres sitios:

  • Como tipo de retorno de una función que nunca termina con normalidad, porque siempre lanza un error: function fallar(mensaje: string): never { throw new Error(mensaje); }
  • En la comprobación exhaustiva de la sección de uniones: cuando todas las opciones se han descartado, lo que queda es never.
  • En algunos mensajes de error. Si ves etiquetas: never[], significa «un array vacío del que TypeScript no sabe qué tipo de elementos tendrá».
Tipo¿Qué valores admite?¿Qué te deja hacer?Cuándo usarlo
anyTodosTodo, sin revisarCasi nunca. Como parche temporal al migrar código antiguo.
unknownTodosNada, hasta que compruebes qué esDatos de fuera: JSON, respuestas de APIs, errores capturados.
neverNingunoNo aplica: no puede existirFunciones que siempre lanzan y comprobaciones exhaustivas.

Aserciones de tipo: as y !

Una aserción de tipo es decirle a TypeScript «confía en mí, yo sé qué es esto». Se escribe con as:

const entrada = document.querySelector("#edad") as HTMLInputElement;
console.log(entrada.value);   // TypeScript ya no se queja

Aquí está la trampa: as no convierte ni comprueba nada. Desaparece al compilar, igual que cualquier tipo. Si en la página no hay ningún #edad, entrada será null y el programa se romperá igual; solo que ahora TypeScript no te avisó porque le pediste que no lo hiciera. Lo mismo hace el signo ! detrás de un valor, llamado aserción de no nulo: document.querySelector("#comprar")! significa «te prometo que esto no es null».

Una aserción no es una conversión

const texto = "30";
const edad = texto as unknown as number;
console.log(edad + 1);   // imprime "301"

Convertir de verdad

const texto = "30";
const edad = Number(texto);
console.log(edad + 1);   // imprime 31

En el ejemplo de la izquierda, TypeScript cree que edad es un número, pero al ejecutarse sigue siendo el texto "30", y + concatena. Hizo falta pasar por unknown porque TypeScript rechaza la aserción directa texto as number con el error TS2352 («esta conversión puede ser un error, porque ninguno de los dos tipos se parece lo suficiente al otro»). Para convertir, usa las funciones de la Estación 7.

Error común

El error más común al empezar con TypeScript es «arreglar» los errores escondiéndolos: poner any, añadir as o !, o escribir // @ts-ignore encima de la línea (un comentario que le dice a tsc que ignore el error siguiente). El error desaparece de la pantalla, pero el problema sigue ahí, esperando a ejecutarse. Antes de silenciar, pregúntate qué te está diciendo TypeScript. Casi siempre la solución es una comprobación con if.

Enums o uniones de literales

Un enum (de enumeration, «enumeración») es una lista de constantes con nombre. Es de las pocas cosas de TypeScript que no son solo tipos:

enum Direccion { Arriba, Abajo, Izquierda, Derecha }   // valen 0, 1, 2 y 3
let rumbo = Direccion.Arriba;

enum Color { Rojo = "rojo", Verde = "verde" }          // enum de textos

¿Qué queda de un enum al compilar? No desaparece: tsc lo convierte en código JavaScript que crea un objeto. Esto es exactamente lo que genera para Direccion. Predice qué imprimen las tres últimas líneas y después ejecuta:

Un enum numérico crea un objeto que funciona en las dos direcciones: Direccion.Arriba da 0 y Direccion[2] da "Izquierda". Por eso el objeto tiene 8 claves y no 4. Esto tiene consecuencias:

  • Un enum no se puede borrar sin más, porque genera código. Por eso node archivo.ts lo rechaza con ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX, y la opción erasableSyntaxOnly de nuestro tsconfig.json lo marca como error: error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
  • En un JSON o en la consola verás 0 o 2, que no dicen nada, en vez de "arriba" o "izquierda".

La alternativa moderna es la unión de tipos literales, que se borra del todo y cuyos valores se leen solos:

type Direccion = "arriba" | "abajo" | "izquierda" | "derecha";
let rumbo: Direccion = "arriba";

¿Y si además necesitas la lista de opciones al ejecutar, por ejemplo para rellenar un menú o comprobar lo que escribe alguien? Escribes la lista una vez como array, y sacas el tipo de ella:

const DIFICULTADES = ["facil", "normal", "dificil"] as const;
type Dificultad = (typeof DIFICULTADES)[number];   // "facil" | "normal" | "dificil"

function esDificultad(valor: string): valor is Dificultad {
  return DIFICULTADES.some((d) => d === valor);
}

Tres piezas nuevas, en orden: as const le dice a TypeScript que el array no cambiará nunca, así que guarda cada texto como tipo literal. En una posición de tipo, typeof DIFICULTADES significa «el tipo de esta variable» (no es el typeof de JavaScript, aunque se escriba igual). Y [number] significa «el tipo de cualquiera de sus elementos». El resultado: la lista existe al ejecutar y el tipo se deriva de ella, así que nunca pueden desincronizarse. La función esDificultad es una guarda de tipo; la entenderás del todo en la siguiente sección.

Los enums siguen existiendo

Los enums no están prohibidos ni obsoletos, y los verás en mucho código existente (en proyectos de Angular, por ejemplo). Si trabajas en un proyecto que los usa, sigue su convención y ejecútalo con tsc o tsx. Pero en código nuevo, las uniones de literales hacen lo mismo, se borran sin dejar rastro y funcionan con la ejecución directa de Node.js.

El DOM y las APIs: datos que llegan de fuera

Todo lo que TypeScript revisa está dentro de tu código. Pero un programa real vive rodeado de cosas que no escribiste tú: una página HTML que puede cambiar, formularios donde la gente escribe lo que quiere, servidores que responden lo que pueden. Esta sección trata de esa frontera, donde los tipos dejan de ser una garantía y pasan a ser una promesa que hay que comprobar.

Tipar el DOM

TypeScript conoce todos los elementos de HTML y sus propiedades. Cada etiqueta tiene su tipo: HTMLInputElement para <input>, HTMLButtonElement para <button>, HTMLLIElement para <li>… Todos son casos particulares de HTMLElement, y este, de Element. Lo que devuelven las funciones de búsqueda de la Estación 15 depende de lo que TypeScript puede saber:

CódigoTipo que obtienesPor qué
document.querySelector("button")HTMLButtonElement | nullPor el nombre de la etiqueta, TypeScript sabe qué elemento es.
document.querySelector("#edad")Element | nullPor un id o una clase no puede saber qué etiqueta hay detrás.
document.getElementById("edad")HTMLElement | nullSabe que es un elemento HTML, pero no cuál.

Siempre con | null, porque el elemento podría no existir. Esto produce dos errores muy típicos:

const entrada = document.querySelector("#edad");
console.log(entrada.value);
// error TS18047: 'entrada' is possibly 'null'.
// error TS2339: Property 'value' does not exist on type 'Element'.

El segundo dice que un Element cualquiera no tiene value: solo los campos de formulario lo tienen. Hay tres formas de resolverlo, de más segura a menos:

// 1. Comprobar con instanceof: una comprobación real, que sigue en el .js
const entrada = document.querySelector("#edad");
if (entrada instanceof HTMLInputElement) {
  console.log(entrada.value);    // aquí entrada es HTMLInputElement
}

// 2. Decir el tipo entre < >: querySelector es genérico
const campo = document.querySelector<HTMLInputElement>("#nombre");   // HTMLInputElement | null
if (campo) console.log(campo.value);

// 3. Aserción: sin ninguna comprobación (evítala)
const otro = document.querySelector("#apellido") as HTMLInputElement;

La segunda forma es cómoda y muy común, pero ojo: es una aserción disfrazada. Si en el HTML #nombre resulta ser un <p>, TypeScript no se entera. La primera es la única que comprueba de verdad al ejecutarse.

Con los eventos pasa algo parecido. TypeScript deduce el tipo del evento por su nombre: en "keydown", el evento es un KeyboardEvent y tiene key. Pero evento.target es solo un EventTarget | null, porque el evento puede venir de cualquier elemento:

document.addEventListener("keydown", (evento) => {
  console.log(evento.key);         // bien: evento es KeyboardEvent
});

const lista = document.querySelector("ul");
lista?.addEventListener("click", (evento) => {
  const objetivo = evento.target;
  if (objetivo instanceof HTMLLIElement) {   // la delegación de la Estación 15, con tipos
    objetivo.classList.toggle("hecha");
  }
});

Cuidado

entrada.value es siempre un string, aunque el campo sea type="number". TypeScript lo sabe y no te dejará sumarlo como número sin convertirlo: Number(entrada.value). Es exactamente el error de «30» + 1 = «301» de la Estación 7, cazado antes de ejecutar.

Este taller es la versión JavaScript de un programa escrito en TypeScript. Fíjate en que las comprobaciones que TypeScript exige (que los elementos existan, que el campo sea un input) siguen ahí, porque son JavaScript real. Pruébalo con una edad y después con la casilla vacía: verás que dice «tendrás 1», porque Number("") vale 0. Modifícalo para que, si la casilla está vacía, muestre Escribe un número.

Respuestas de APIs: la promesa que nadie comprueba

En la Estación 16 pediste datos con fetch. En TypeScript, respuesta.json() devuelve Promise<any>: TypeScript no tiene forma de saber qué contestará un servidor. La tentación es escribir esto:

type Usuario = { id: number; nombre: string; correo: string };

async function cargarUsuario(id: number): Promise<Usuario> {
  const respuesta = await fetch(`https://api.ejemplo.com/usuarios/${id}`);
  return (await respuesta.json()) as Usuario;   // «confía en mí»
}

Compila sin errores, y todo el resto del programa tratará el resultado como un Usuario perfecto. Pero si el servidor cambia nombre por name, o manda el id como texto, nadie se entera hasta que algo falla lejos de aquí, en otra función, con un error difícil de rastrear. El as no comprobó nada: solo prometió.

La forma segura trata la respuesta como unknown y la comprueba en la frontera, nada más llegar:

Así queda en código. La función esUsuario tiene un tipo de retorno especial: dato is Usuario. Se llama predicado de tipo, y a una función así se le llama guarda de tipo (type guard): devuelve un booleano, y cuando devuelve true, TypeScript estrecha el tipo del argumento, igual que hacía con typeof.

type Usuario = { id: number; nombre: string; correo: string };

function esUsuario(dato: unknown): dato is Usuario {
  return (
    typeof dato === "object" && dato !== null &&
    "id" in dato && typeof dato.id === "number" &&
    "nombre" in dato && typeof dato.nombre === "string" &&
    "correo" in dato && typeof dato.correo === "string"
  );
}

async function cargarUsuario(id: number): Promise<Usuario> {
  const respuesta = await fetch(`https://jsonplaceholder.typicode.com/users/${id}`);
  if (!respuesta.ok) {
    throw new Error(`Error HTTP ${respuesta.status}`);
  }
  const datos: unknown = await respuesta.json();
  if (!esUsuario(datos)) {
    throw new Error("La respuesta no tiene la forma de un Usuario");
  }
  return datos;   // aquí datos ya es Usuario
}

¿Por qué typeof dato === "object" && dato !== null al principio? Porque typeof null también da "object" (la rareza histórica de la Estación 7). Para probarla con JSONPlaceholder, la API de práctica de la Estación 16, pega el código en el Playground: la pestaña .JS te da la versión sin tipos, lista para copiarla en la consola del navegador y llamar a await cargarUsuario(1). Sorpresa: lanza el error. JSONPlaceholder responde con name y email, en inglés, no con nombre y correo. Es justo el tipo de desajuste que la guarda caza en la frontera. Cambia el tipo y la guarda para usar los nombres del servidor y vuelve a probar.

Una vez compilada, la guarda es JavaScript normal. Sigue paso a paso qué hace con una respuesta mal formada:

function esUsuario(dato) {
  if (typeof dato !== "object") return false;
  if (dato === null) return false;
  if (typeof dato.id !== "number") return false;
  return typeof dato.nombre === "string";
}
const texto = '{"id":"7","nombre":"Ana"}';
const recibido = JSON.parse(texto);
console.log(esUsuario(recibido));

Validar sin escribirlo todo a mano

Escribir guardas para objetos grandes es repetitivo. En proyectos reales se usan bibliotecas de validación como Zod o Valibot: describes la forma de los datos una sola vez (un «esquema»), y la biblioteca te da a la vez la función que valida al ejecutar y el tipo de TypeScript. El principio es el mismo que acabas de aprender: comprobar en la frontera y confiar dentro.

La misma idea vale para cualquier dato que entre desde fuera: JSON.parse (devuelve any: guárdalo como unknown), localStorage.getItem (devuelve string | null, Estación 15), lo que llega en un formulario, o el error que capturas en un catch, que en modo estricto es de tipo unknown. Por eso verás este patrón a menudo:

try {
  const u = await cargarUsuario(1);
  console.log(u.nombre);
} catch (error) {
  if (error instanceof Error) {   // error es unknown: se comprueba antes de usarlo
    console.log(error.message);
  }
}

Tipos de librerías: @types

Muchas librerías de npm traen sus propios tipos. Las que no los traen suelen tener un paquete aparte, mantenido por la comunidad en el proyecto DefinitelyTyped, que se llama igual con el prefijo @types/. Por ejemplo, los tipos de Node.js (process, fs…) se instalan con npm install --save-dev @types/node y se activan con "types": ["node"] en tsconfig.json. Lo usarás en la Estación 29.

Leer los errores de TypeScript

La primera vez que pases un proyecto de JavaScript a TypeScript, verás decenas de líneas rojas. No te asustes: en la Estación 12 aprendiste que un error es información, y los de TypeScript son de los más precisos que existen. Dicen dónde, qué esperaban y qué encontraron. Solo hay que aprender a leerlos.

Anatomía de un error

  • Archivo, línea y columna (src/tienda.ts:9:26): el error empieza en la línea 9, carácter 26. En VS Code, con Ctrl + clic sobre esa ruta en la terminal, saltas directamente allí.
  • El código (TS2345): cada tipo de error tiene un número fijo. No hace falta memorizarlos, pero son perfectos para buscar en internet, porque no dependen del idioma.
  • El mensaje: qué tipo esperaba TypeScript y qué tipo encontró.
  • El fragmento: la línea de código con el culpable subrayado con ~~~.

«is not assignable to»: la frase que más vas a leer

La mitad de los errores de TypeScript tienen esta forma: Type 'A' is not assignable to type 'B', «el tipo A no se puede asignar al tipo B». Tradúcela siempre así: «pusiste un A donde hacía falta un B». El primer tipo es lo que diste; el segundo, lo que se esperaba. Con funciones cambia un poco la frase, pero no el sentido: Argument of type 'string' is not assignable to parameter of type 'number' es «pasaste un texto a un parámetro que pide un número».

La pregunta que sigue es la importante: ¿quién tiene razón? A veces el valor está mal (pasaste el texto sin convertirlo). Pero a veces el que está mal es el tipo: quizá el precio sí puede ser texto porque llega de un formulario, y lo que hay que cambiar es la declaración. TypeScript solo te dice que las dos cosas no encajan; decidir cuál corregir es tu trabajo.

Mensajes largos: lee de fuera hacia dentro

Con objetos grandes, los mensajes crecen hacia abajo, cada línea con más sangría que la anterior:

Un método para corregir

  1. Empieza por el primer error. Un solo fallo puede provocar otros en cadena. Corrige el primero, vuelve a revisar (o deja --watch funcionando) y mira cuántos quedan.

  2. Ve a la línea y mira lo subrayado. El subrayado indica la expresión exacta que no encaja, no toda la línea.

  3. Pregúntale a TypeScript qué cree. Pasa el ratón por encima de cada variable implicada. Muchas veces la sorpresa está ahí: una variable que creías number es number | undefined, o any.

  4. Traduce: «puse un A donde hacía falta un B». Y decide quién tiene razón: el valor o el tipo.

  5. Corrige con código de verdad. Una conversión (Number(...)), una comprobación (if, ?., ??) o un tipo mejor. No con any, as o @ts-ignore.

  6. Si sigues atascado, busca el código («TS2345») o pide ayuda con el mensaje completo copiado, tal como aprendiste en la Estación 12. Si usas una IA, pídele que te explique el error antes que la solución.

Resumen

  • TypeScript es JavaScript con una capa de tipos. tsc revisa los tipos antes de ejecutar y después los borra: lo que se ejecuta es JavaScript normal, y durante la ejecución los tipos ya no existen.
  • Se instala en cada proyecto (npm install --save-dev typescript) y se configura en tsconfig.json, siempre con "strict": true. npx tsc compila; npx tsc --noEmit solo revisa; tsc genera el .js aunque haya errores.
  • Node.js 24 ejecuta archivos .ts directamente y tsx también, pero ninguno de los dos revisa los tipos. Node solo acepta sintaxis borrable: nada de enum.
  • La inferencia deduce casi todos los tipos. Anota los parámetros de las funciones, las variables que empiezan vacías y, si quieres, lo que devuelven las funciones.
  • Describe objetos con type o interface; usa ? para lo opcional y readonly para lo que no cambia. Deriva variantes con Partial, Required, Pick, Omit, Record y Readonly.
  • Las uniones (A | B) y los tipos literales ("arriba" | "abajo") describen opciones. Para usarlas, estrecha el tipo con comprobaciones de JavaScript: typeof, ===, in, instanceof, Array.isArray.
  • Las uniones discriminadas (una propiedad etiqueta como tipo) y la comprobación exhaustiva con never hacen que TypeScript te avise de cada caso olvidado.
  • Los genéricos (<T>) conectan la entrada con la salida de una función sin perder el tipo. Array<T>, Promise<T> y Map<K, V> son genéricos.
  • any apaga la revisión; unknown obliga a comprobar; never es lo imposible. as y ! no comprueban nada. Prefiere uniones de literales a enums.
  • Lo que llega de fuera (DOM, formularios, APIs, JSON) se comprueba en la frontera con guardas de tipo. Un error de tsc se lee así: «pusiste un A donde hacía falta un B», empezando por el primero.

Valida lo que llega de fuera

Semiguiado

En TypeScript, esta guarda tendría la firma function esProducto(dato: unknown): dato is Producto, con type Producto = { nombre: string; precio: number; etiquetas: string[] }. Escribe su cuerpo en JavaScript. Debe devolver true solo si dato es un objeto (y no null) con nombre de tipo texto, precio de tipo número y etiquetas como un array en el que todos los elementos son textos. Las pruebas del final deben imprimir true y después cinco false.

Pista 1

Empieza por descartar lo que no es un objeto: if (typeof dato !== "object" || dato === null) return false; Recuerda que typeof null es "object".

Pista 2

Para las etiquetas, primero Array.isArray(dato.etiquetas) y después dato.etiquetas.every((e) => typeof e === "string"). El método every lo viste en la Estación 11.

Ver una solución 
function esProducto(dato) {
  if (typeof dato !== "object" || dato === null) return false;
  if (typeof dato.nombre !== "string") return false;
  if (typeof dato.precio !== "number") return false;
  if (!Array.isArray(dato.etiquetas)) return false;
  return dato.etiquetas.every((e) => typeof e === "string");
}

const pruebas = [
  { nombre: "Taza", precio: 8.5, etiquetas: ["cocina"] },
  { nombre: "Plato", precio: "5", etiquetas: [] },
  { nombre: "Vaso", precio: 3 },
  { nombre: "Jarra", precio: 12, etiquetas: ["cocina", 7] },
  null,
  "Taza",
];

  console.log(esProducto(p));
}

En TypeScript, el cuerpo sería casi idéntico, añadiendo "nombre" in dato && antes de cada propiedad para que TypeScript acepte leerla de un unknown. Si quieres ser más exigente, añade Number.isFinite(dato.precio) && dato.precio >= 0: un precio NaN o negativo también es un número para typeof.

Eventos del juego

Semiguiado

En TypeScript, los eventos de un juego serían esta unión discriminada:

type Evento =
  | { tipo: "moneda"; valor: number }
  | { tipo: "golpe"; danio: number }
  | { tipo: "nivel"; numero: number };

Completa describir en JavaScript con un switch sobre evento.tipo. Debe devolver +5 monedas, -12 de vida y ¡Nivel 3! para las pruebas, y en el default lanzar un error con el mensaje Evento desconocido: teletransporte (el throw que en TypeScript acompañaría a la comprobación con never).

Pista 1

Cada caso devuelve un texto con una plantilla literal: case "moneda": return `+${evento.valor} monedas`;

Pista 2

El caso por defecto: default: throw new Error(`Evento desconocido: ${evento.tipo}`); Como cada case termina con return, no hace falta break.

Ver una solución 
function describir(evento) {
  switch (evento.tipo) {
    case "moneda":
      return `+${evento.valor} monedas`;
    case "golpe":
      return `-${evento.danio} de vida`;
    case "nivel":
      return `¡Nivel ${evento.numero}!`;
    default:
      throw new Error(`Evento desconocido: ${evento.tipo}`);
  }
}

const eventos = [
  { tipo: "moneda", valor: 5 },
  { tipo: "golpe", danio: 12 },
  { tipo: "nivel", numero: 3 },
];
for (const e of eventos) {
  console.log(describir(e));
}
try {
  describir({ tipo: "teletransporte" });
} catch (error) {
  console.log(error.message);
}

En TypeScript, la llamada con { tipo: "teletransporte" } ni siquiera compilaría, porque ese tipo no está en la unión. El default sirve para los datos que llegan de fuera al ejecutarse, donde TypeScript no puede vigilar. En el default de la versión TypeScript añadirías const imposible: never = evento; para que el compilador te avise si algún día añades un evento y olvidas su caso.

Pick y Omit al ejecutarse

Semiguiado

Pick<T, ...> y Omit<T, ...> solo transforman tipos: desaparecen al compilar. Si necesitas hacer lo mismo con los datos, tienes que escribirlo. Completa dos funciones: elegir(obj, claves) devuelve un objeto nuevo solo con las propiedades de la lista, y omitir(obj, claves) uno nuevo con todas menos las de la lista. El objeto original no debe cambiar. La salida esperada es:

{ nombre: 'Taza', precio: 8.5 }
{ nombre: 'Taza', precio: 8.5, stock: 20 }
{ id: 7, nombre: 'Taza', precio: 8.5, stock: 20 }
Pista 1

En elegir, recorre las claves con for (const clave of claves) y copia cada una: resultado[clave] = obj[clave]; (los corchetes de la Estación 11).

Pista 2

En omitir, resultado ya es una copia gracias al spread. Recorre las claves y bórralas de la copia con delete resultado[clave];

Ver una solución 
function elegir(obj, claves) {
  const resultado = {};
  for (const clave of claves) {
    if (clave in obj) resultado[clave] = obj[clave];
  }
  return resultado;
}

function omitir(obj, claves) {
  const resultado = { ...obj };
  for (const clave of claves) {
    delete resultado[clave];
  }
  return resultado;
}

const producto = { id: 7, nombre: "Taza", precio: 8.5, stock: 20 };
console.log(elegir(producto, ["nombre", "precio"]));
console.log(omitir(producto, ["id"]));
console.log(producto);

En TypeScript, la firma sería function elegir<T, K extends keyof T>(obj: T, claves: K[]): Pick<T, K>. keyof T significa «cualquiera de los nombres de propiedad de T», así que TypeScript rechazaría elegir(producto, ["nombr"]) y sabría que el resultado solo tiene nombre y precio.

Carga una partida guardada

Reto

Una partida guardada llega como texto JSON, desde un archivo o desde localStorage. En TypeScript, la función tendría este tipo:

type Partida = { jugador: string; nivel: number; objetos: string[] };
type Resultado<T> = { ok: true; valor: T } | { ok: false; error: string };

function cargarPartida(texto: string): Resultado<Partida>

Escríbela en JavaScript sin lanzar excepciones hacia fuera. Si el texto no es JSON válido, devuelve { ok: false, error: "JSON inválido" }. Si no tiene la forma de una partida, "Forma incorrecta". Si la forma es buena pero el nivel no es un número entero mayor o igual que 1, "Nivel imposible". Si todo está bien, { ok: true, valor: partida }. Las pruebas deben imprimir:

OK: Lyra, nivel 4, 2 objetos
Error: Forma incorrecta
Error: Nivel imposible
Error: JSON inválido
Error: Forma incorrecta
Pista 1

Divide el trabajo en tres pasos, cada uno con su return temprano: primero JSON.parse dentro de try/catch; después, comprobar la forma (objeto no nulo, jugador texto, nivel número, objetos array de textos); por último, la regla del nivel.

Pista 2

Para la regla del nivel: Number.isInteger(datos.nivel) && datos.nivel >= 1. Un array como [1, 2, 3] es un objeto para typeof, pero no tiene jugador: la comprobación de forma lo descarta sola.

Ver una solución 
function cargarPartida(texto) {
  let datos;
  try {
    datos = JSON.parse(texto);
  } catch {
    return { ok: false, error: "JSON inválido" };
  }

  const formaCorrecta =
    typeof datos === "object" && datos !== null &&
    typeof datos.jugador === "string" &&
    typeof datos.nivel === "number" &&
    Array.isArray(datos.objetos) &&
    datos.objetos.every((o) => typeof o === "string");
  if (!formaCorrecta) {
    return { ok: false, error: "Forma incorrecta" };
  }

  if (!Number.isInteger(datos.nivel) || datos.nivel < 1) {
    return { ok: false, error: "Nivel imposible" };
  }
  return { ok: true, valor: datos };
}

const textos = [
  '{"jugador":"Lyra","nivel":4,"objetos":["espada","poción"]}',
  '{"jugador":"Tor","nivel":"4","objetos":[]}',
  '{"jugador":"Nia","nivel":0,"objetos":[]}',
  '{"jugador":"Kai","nivel":2,',
  '[1, 2, 3]',
];
for (const t of textos) {
  const r = cargarPartida(t);
  if (r.ok) {
    console.log(`OK: ${r.valor.jugador}, nivel ${r.valor.nivel}, ${r.valor.objetos.length} objetos`);
  } else {
    console.log(`Error: ${r.error}`);
  }
}

Esta es la forma de trabajar que se usa en la industria: la frontera convierte un texto desconocido en un Resultado con forma conocida, y el resto del programa solo tiene que mirar r.ok. En TypeScript, dentro del if (r.ok), el editor sabría que r.valor es una Partida y te ofrecería sus propiedades.

Agrupa por clave

Reto

En TypeScript, esta función genérica tendría el tipo function agruparPor<T>(lista: T[], obtenerClave: (item: T) => string): Record<string, T[]>. Léelo con calma: recibe una lista de elementos de tipo T y una función que, para cada elemento, dice en qué grupo va; devuelve un objeto cuyas claves son los grupos y cuyos valores son listas de T. Escríbela en JavaScript para que las pruebas impriman:

hecha, pendiente
Programar salto | Música
{"3":["sol","mar","río"],"4":["luna"],"5":["cielo"]}
Pista 1

Recorre la lista con for (const item of lista). Para cada elemento, const clave = obtenerClave(item);

Pista 2

Si el grupo todavía no existe, créalo vacío antes de añadir: grupos[clave] = grupos[clave] ?? []; y después grupos[clave].push(item); Es el patrón del contador de votos, pero guardando listas en vez de números.

Ver una solución 
function agruparPor(lista, obtenerClave) {
  const grupos = {};
  for (const item of lista) {
    const clave = obtenerClave(item);
    grupos[clave] = grupos[clave] ?? [];
    grupos[clave].push(item);
  }
  return grupos;
}

const tareas = [
  { titulo: "Diseñar nivel", estado: "hecha" },
  { titulo: "Programar salto", estado: "pendiente" },
  { titulo: "Música", estado: "pendiente" },
];
const porEstado = agruparPor(tareas, (t) => t.estado);
console.log(Object.keys(porEstado).join(", "));
console.log((porEstado.pendiente ?? []).map((t) => t.titulo).join(" | "));

const palabras = ["sol", "mar", "luna", "río", "cielo"];
console.log(JSON.stringify(agruparPor(palabras, (p) => String(p.length))));

Por qué el genérico importa: en TypeScript, porEstado.pendiente sería de tipo { titulo: string; estado: string }[] | undefined, así que dentro del map el editor sabría que cada t tiene titulo. Sin genérico (con any), una errata como t.titlo pasaría sin aviso. JavaScript moderno trae Object.groupBy, que hace esto mismo; ahora sabes cómo funciona por dentro.

Proyecto: el inventario tipado de una aventura

Vas a construir en tu computadora el inventario de un juego de aventuras: armas, pociones y llaves con distintos pesos y rarezas, una mochila con capacidad limitada y una partida guardada que se carga desde JSON. Es un programa pequeño, pero usa casi todo lo de esta estación: uniones discriminadas, intersecciones, readonly, genéricos, Record, never, unknown y guardas de tipo. Al terminar, intenta romperlo a propósito: es la mejor forma de ver a TypeScript trabajar.

  1. Crea el proyecto inventario-ts igual que en la sección Instalar y ejecutar: npm init -y, npm pkg set type=module, npm install --save-dev typescript y el tsconfig.json del curso. Crea src/inventario.ts.

  2. Escribe los tipos arriba del archivo. Rareza es una unión de tres literales: "comun", "rara" y "epica". Un tipo Base con id, nombre, rareza y peso. Tres tipos que amplían Base con & y tienen un discriminante tipo: Arma (con danio), Pocion (con curacion) y Llave (con puerta). Objeto es la unión de los tres. Inventario tiene una capacidad de solo lectura y una lista de objetos. Y el Resultado<T> genérico de la sección de funciones.

  3. Escribe describir(o: Objeto): string con un switch sobre o.tipo y la comprobación exhaustiva con never en el default. Comprueba que funciona: añade temporalmente un cuarto tipo a la unión (Escudo) y mira el error de tsc en el default. Después quítalo.

  4. Escribe pesoTotal (con reduce), agregar (devuelve un Resultado<Inventario> y crea un inventario nuevo con spread, sin modificar el original), buscarPorId (genérica, con la restricción T extends { id: number }) y contarPorRareza (devuelve un Record<Rareza, number>).

  5. La frontera: escribe la guarda esObjeto(dato: unknown): dato is Objeto y cargarObjetos(texto: string): Resultado<Objeto[]>, que usa JSON.parse dentro de try/catch, comprueba que el resultado es un array y se queda solo con los elementos válidos (filter(esObjeto)).

  6. El programa principal: crea una mochila de capacidad 10, intenta meter cuatro objetos, muestra el peso y el conteo por rareza, busca un objeto por su id y carga una partida guardada que contiene un objeto con forma incorrecta.

  7. Revisa y ejecuta. Deja npx tsc --noEmit --watch en una terminal y ejecuta con node src/inventario.ts en otra. Cuando no haya errores, compila con npx tsc y ejecuta también node dist/inventario.js. La salida debe ser esta:

+ Poción roja (poción, cura 30)
+ Llave de hierro (llave de: Torre norte)
x No cabe: Hacha de guerra
Peso: 6 / 10
{ comun: 1, rara: 1, epica: 1 }
Encontrado: Llave de hierro (llave de: Torre norte)
Aviso: objetos descartados por forma incorrecta: 1
Cargado: Poción azul (poción, cura 10)

  8. Rómpelo a propósito, un cambio cada vez, y anota qué dice tsc y qué significa: escribe rareza: "rarisima" en un objeto; borra el case "llave"; intenta mochila.capacidad = 50; llama a buscarPorId(mochila.objetos, "3"); cambia peso: 4 por peso: "4". Deshaz cada cambio antes del siguiente.

// ---------- Tipos ----------
type Rareza = "comun" | "rara" | "epica";

type Base = { id: number; nombre: string; rareza: Rareza; peso: number };
type Arma = Base & { tipo: "arma"; danio: number };
type Pocion = Base & { tipo: "pocion"; curacion: number };
type Llave = Base & { tipo: "llave"; puerta: string };
type Objeto = Arma | Pocion | Llave;

type Inventario = { readonly capacidad: number; objetos: Objeto[] };

type Resultado<T> =
  | { ok: true; valor: T }
  | { ok: false; error: string };

// ---------- Funciones ----------
function describir(o: Objeto): string {
  switch (o.tipo) {
    case "arma":
      return `${o.nombre} (arma, ${o.danio} de daño)`;
    case "pocion":
      return `${o.nombre} (poción, cura ${o.curacion})`;
    case "llave":
      return `${o.nombre} (llave de: ${o.puerta})`;
    default: {
      const imposible: never = o;
      throw new Error(`Objeto desconocido: ${JSON.stringify(imposible)}`);
    }
  }
}

function pesoTotal(inv: Inventario): number {
  return inv.objetos.reduce((suma, o) => suma + o.peso, 0);
}

function agregar(inv: Inventario, o: Objeto): Resultado<Inventario> {
  if (pesoTotal(inv) + o.peso > inv.capacidad) {
    return { ok: false, error: `No cabe: ${o.nombre}` };
  }
  return { ok: true, valor: { ...inv, objetos: [...inv.objetos, o] } };
}

function buscarPorId<T extends { id: number }>(lista: T[], id: number): T | undefined {
  return lista.find((item) => item.id === id);
}

function contarPorRareza(inv: Inventario): Record<Rareza, number> {
  const cuenta: Record<Rareza, number> = { comun: 0, rara: 0, epica: 0 };
  for (const o of inv.objetos) {
    cuenta[o.rareza] += 1;
  }
  return cuenta;
}

// ---------- La frontera: datos que llegan de fuera ----------
const RAREZAS: readonly string[] = ["comun", "rara", "epica"];

function esObjeto(dato: unknown): dato is Objeto {
  if (typeof dato !== "object" || dato === null) return false;
  if (!("id" in dato) || typeof dato.id !== "number") return false;
  if (!("nombre" in dato) || typeof dato.nombre !== "string") return false;
  if (!("peso" in dato) || typeof dato.peso !== "number") return false;
  if (!("rareza" in dato) || typeof dato.rareza !== "string" || !RAREZAS.includes(dato.rareza)) return false;
  if (!("tipo" in dato)) return false;
  switch (dato.tipo) {
    case "arma":
      return "danio" in dato && typeof dato.danio === "number";
    case "pocion":
      return "curacion" in dato && typeof dato.curacion === "number";
    case "llave":
      return "puerta" in dato && typeof dato.puerta === "string";
    default:
      return false;
  }
}

function cargarObjetos(texto: string): Resultado<Objeto[]> {
  let datos: unknown;
  try {
    datos = JSON.parse(texto);
  } catch {
    return { ok: false, error: "El texto no es JSON válido" };
  }
  if (!Array.isArray(datos)) {
    return { ok: false, error: "Se esperaba una lista" };
  }
  const validos = datos.filter(esObjeto);
  const descartados = datos.length - validos.length;
  if (descartados > 0) {
    console.log(`Aviso: objetos descartados por forma incorrecta: ${descartados}`);
  }
  return { ok: true, valor: validos };
}

Autoevaluación

Responde sin mirar arriba. Cada opción tiene su explicación: léelas también cuando aciertes, porque los errores de las otras opciones son los que comete de verdad la gente que empieza con TypeScript.

¿Qué pasa con las anotaciones de tipo cuando tsc compila un archivo .ts?

  1. Se convierten en comprobaciones que se ejecutan junto con el programa.

    No. Ninguna comprobación de tipos llega a la ejecución. Si quieres comprobar datos al ejecutar, tienes que escribir tú el código (por ejemplo, una guarda con typeof).

  2. Se borran: el .js resultante es el mismo código sin tipos.

    Correcto. tsc revisa los tipos y después los quita. Durante la ejecución, los tipos ya no existen.

  3. Se guardan en un archivo aparte que Node.js consulta al ejecutar.

    No. Node.js no revisa tipos en ningún momento, ni siquiera cuando ejecuta un .ts directamente.

  4. Hacen que el programa se ejecute más rápido.

    No. El JavaScript generado es prácticamente el que habrías escrito a mano; los tipos no cambian la velocidad.

Con Node.js 24 ejecutas node app.ts. El archivo contiene saludar(42), pero saludar pide un string. ¿Qué ocurre?

  1. Node muestra el error TS2345 y no ejecuta nada.

    Eso haría tsc. Node.js borra los tipos, pero no los revisa.

  2. Node convierte el 42 en "42" porque el parámetro es string.

    Los tipos nunca convierten valores. Para convertir hacen falta String() o Number().

  3. El programa se ejecuta: Node quita las anotaciones sin comprobarlas.

    Correcto. Por eso se combina con npx tsc --noEmit o con el editor, que sí revisan.

  4. Node se niega a ejecutar archivos .ts sin instalar tsx.

    Desde Node.js 22.18 y en toda la versión 24, node archivo.ts funciona sin nada más, siempre que el código solo use sintaxis borrable.

Tienes let puntos = 0; sin anotación. ¿Qué dice tsc de la línea puntos = "diez";?

  1. Error: puntos se infirió como number y no admite un texto.

    Correcto. La inferencia fija el tipo a partir del valor inicial: TS2322, Type 'string' is not assignable to type 'number'.

  2. Nada: sin anotación, la variable es de tipo any.

    No. Sin anotación, TypeScript deduce el tipo del valor inicial. any solo aparece si lo escribes o si no hay forma de deducir nada.

  3. Nada: puntos pasa a ser string | number.

    TypeScript no amplía el tipo por su cuenta. Si quieres una unión, tienes que escribirla.

  4. Solo habría error si puntos se hubiera declarado con const.

    Con const habría otro error (no se puede reasignar). Con let también lo hay, por el tipo.

¿Cuál es la diferencia entre any y unknown?

  1. Ninguna: son dos nombres para lo mismo.

    Los dos admiten cualquier valor, pero te dejan hacer cosas muy distintas con él.

  2. unknown solo admite textos y números.

    No. unknown admite cualquier valor, igual que any.

  3. any obliga a comprobar el valor antes de usarlo; unknown no.

    Es justo al revés: any lo permite todo sin revisar.

  4. Los dos admiten cualquier valor, pero unknown no deja usarlo hasta comprobar qué es.

    Correcto. Por eso unknown es el tipo adecuado para datos que llegan de fuera: te obliga a validarlos.

En function f(v: string | number), dentro de if (typeof v === "number") { … }, ¿qué tipo tiene v?

  1. string | number, porque typeof no afecta a los tipos.

    Sí los afecta: TypeScript entiende las comprobaciones de JavaScript y estrecha el tipo dentro de cada rama.

  2. number

    Correcto. Dentro del if, TypeScript descartó string: eso es el estrechamiento de tipos.

  3. string

    Eso sería fuera del if (si dentro hubiera un return), no dentro.

  4. unknown

    No. La comprobación hace el tipo más preciso, no menos.

¿Qué hace const datos = (await respuesta.json()) as Usuario;?

  1. Comprueba que la respuesta tiene la forma de Usuario y lanza un error si no.

    No comprueba nada. Es un error muy extendido: as desaparece al compilar.

  2. Convierte los datos a la forma de Usuario, renombrando propiedades si hace falta.

    Las aserciones no transforman valores. Si el servidor manda name, seguirás teniendo name.

  3. Le pide a TypeScript que confíe en que los datos son un Usuario, sin comprobarlo al ejecutar.

    Correcto. Si el servidor responde otra cosa, el fallo aparecerá más tarde. Lo seguro es tratarlo como unknown y validarlo con una guarda.

  4. Da error de compilación, porque json() devuelve any.

    No hay error: un any se puede tratar como cualquier tipo. Por eso es peligroso.

Producto tiene id, nombre y precio. ¿Qué tipo describe los datos para crear un producto nuevo, que todavía no tiene id?

  1. Omit<Producto, "id">

    Correcto: todas las propiedades menos id, y nombre y precio siguen siendo obligatorias.

  2. Pick<Producto, "id">

    Pick se queda solo con las propiedades indicadas: tendrías únicamente id, lo contrario de lo que buscas.

  3. Partial<Producto>

    Vuelve todo opcional: permitiría crear un producto sin nombre ni precio.

  4. Readonly<Producto>

    Solo impide modificar las propiedades; id seguiría siendo obligatorio.

Tu función area tiene un switch sobre f.tipo y un default con const imposible: never = f;. Añades el triángulo a la unión Figura y olvidas su case. ¿Qué pasa?

  1. Nada hasta ejecutar; entonces area devuelve undefined.

    Eso pasaría en JavaScript. Con la comprobación exhaustiva, TypeScript lo detecta antes.

  2. TypeScript añade el case que falta al compilar.

    TypeScript nunca escribe lógica por ti: solo revisa y borra tipos.

  3. No hay aviso, pero el programa lanza un error la primera vez que se ejecuta area.

    El throw del default sí actuaría al ejecutar con un triángulo, pero antes de eso tsc ya te habría avisado.

  4. tsc marca un error en el default: el triángulo no se puede asignar a never.

    Correcto. El mensaje nombra el caso que falta, y te lleva a cada switch que debes actualizar.

Con function primero<T>(lista: T[]): T | undefined, ¿qué tipo tiene el resultado de primero(["a", "b"])?

  1. any

    No. El genérico existe justo para no perder el tipo como pasaría con any.

  2. string | undefined

    Correcto. TypeScript deduce que T es string a partir del argumento, y la lista podría estar vacía.

  3. T

    T es el hueco; en cada llamada se rellena con un tipo concreto.

  4. string[]

    Ese es el tipo de la lista, no el de un elemento.

tsc te dice: Argument of type 'string' is not assignable to parameter of type 'number'. ¿Qué significa?

  1. Guardaste un texto en una variable de tipo number.

    Ese sería el error TS2322 (Type 'string' is not assignable to type 'number'). Las palabras argument y parameter indican una llamada a función.

  2. La función devuelve un texto y debería devolver un número.

    Un retorno equivocado también da TS2322, dentro de la función.

  3. Llamaste a una función pasándole un texto donde el parámetro pide un número.

    Correcto: «pusiste un string donde hacía falta un number». Después decide quién tiene razón: el valor o el tipo.

  4. Dentro de la función falta un Number() para convertir el parámetro.

    Eso sería una forma de arreglarlo en algunos casos, no lo que dice el mensaje. El problema está en la llamada.

¿Por qué se recomiendan las uniones de literales ("arriba" | "abajo") en lugar de enum en código nuevo?

  1. Se borran del todo al compilar, funcionan con la ejecución directa de Node.js y sus valores se entienden al leerlos.

    Correcto. Un enum genera código JavaScript, así que node archivo.ts lo rechaza, y en un JSON verías 0 o 2 en vez de palabras.

  2. Porque TypeScript 7 eliminó los enums.

    Falso: los enums siguen funcionando en TypeScript 7 y aparecen en mucho código existente.

  3. Porque los enums no se pueden usar dentro de un switch.

    Sí se pueden usar. El motivo es otro.

  4. Porque las uniones de literales comprueban los valores al ejecutarse.

    No: como todos los tipos, se borran. Si necesitas comprobar al ejecutar, usa una lista con as const y una guarda.

Glosario

TypeScript
Lenguaje creado por Microsoft que añade tipos a JavaScript. Una herramienta revisa esos tipos antes de ejecutar y después los borra para obtener JavaScript normal.
Tipado dinámico
Forma de trabajar de lenguajes como JavaScript o Python: los tipos pertenecen a los valores y solo se descubren al ejecutar.
Tipado estático
Forma de trabajar en la que los tipos se conocen y se revisan antes de ejecutar el programa.
Anotación de tipo
Indicación escrita del tipo de una variable, un parámetro o un valor de retorno, con dos puntos: precio: number.
Inferencia de tipos
Capacidad de TypeScript de deducir un tipo sin anotación, a partir del valor o del contexto.
tsc
El compilador de TypeScript (TypeScript Compiler). Revisa los tipos de un proyecto y genera los archivos JavaScript.
Borrado de tipos
Quitar las anotaciones de un programa TypeScript para obtener JavaScript. Lo hacen tsc, tsx y Node.js (type stripping).
tsconfig.json
Archivo de configuración de un proyecto TypeScript: dónde está el código, dónde va el resultado y qué comprobaciones se activan.
Modo estricto
La opción "strict": true: activa las comprobaciones importantes, como prohibir parámetros sin tipo o exigir que se contemplen null y undefined.
Alias de tipo
Nombre para un tipo, creado con type: type Producto = { … }.
Interfaz
Descripción de la forma de un objeto creada con interface. Se puede ampliar con extends.
Tipado estructural
Regla de TypeScript por la que dos tipos son compatibles si tienen la misma forma, aunque tengan nombres distintos.
Tupla
Array de tamaño fijo con un tipo para cada posición: [number, number].
Unión
Tipo que admite valores de varios tipos, escrito con |: string | number.
Tipo literal
Tipo que admite un único valor exacto, como "arriba" o 3. Unidos, describen opciones cerradas.
Estrechamiento de tipos
Cuando TypeScript deduce un tipo más preciso dentro de una rama gracias a una comprobación como typeof. En inglés, narrowing.
Unión discriminada
Unión de objetos que comparten una propiedad (el discriminante, como tipo) con un valor literal distinto en cada uno.
Genérico
Función o tipo con un parámetro de tipo (<T>) que se decide al usarlo, para servir a muchos tipos sin perder información.
Tipos de utilidad
Tipos genéricos que trae TypeScript para transformar otros tipos: Partial, Required, Pick, Omit, Record, Readonly…
any
Tipo que desactiva la revisión: admite cualquier valor y permite cualquier operación sin comprobarla.
unknown
Tipo que admite cualquier valor pero no deja usarlo hasta comprobar qué es. Ideal para datos externos.
never
Tipo sin ningún valor posible. Aparece en funciones que siempre lanzan un error y en comprobaciones exhaustivas.
Aserción de tipo
Indicación as Tipo (o ! para descartar null) con la que le pides a TypeScript que confíe en ti. No comprueba ni convierte nada.
Guarda de tipo
Función que comprueba un valor al ejecutar y devuelve un predicado de tipo (dato is Usuario), para que TypeScript estreche el tipo si devuelve true.
Enum
Lista de constantes con nombre de TypeScript. A diferencia de los tipos, genera código JavaScript, por lo que no se puede borrar sin más.
