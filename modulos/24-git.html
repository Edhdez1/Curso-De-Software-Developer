Lo que vas a lograr

En la Estación 5 guardaste tus primeros puntos de control con Git. Ahora vas a usarlo como lo usan los equipos profesionales: revisar la historia de un proyecto, deshacer errores sin miedo, trabajar en ramas, fusionar el trabajo de varias personas, resolver conflictos y colaborar en GitHub con pull requests. Al final vas a publicar una página web en internet, gratis, con GitHub Pages.

  • Explicar la diferencia entre Git y GitHub, y qué contiene de verdad un commit.
  • Preparar commits pequeños y precisos, leer git diff y escribir mensajes claros con la convención Conventional Commits.
  • Elegir qué archivos no deben entrar en el repositorio y escribir un .gitignore.
  • Buscar en el historial y deshacer cambios con restore, revert y, con cuidado, reset.
  • Crear ramas, cambiar entre ellas y fusionarlas, y resolver un conflicto paso a paso.
  • Subir un repositorio a GitHub y sincronizarlo con push, fetch y pull, usando una autenticación segura (HTTPS con token o SSH).
  • Proponer cambios con un pull request, revisar el código de otra persona y contribuir a un proyecto ajeno con un fork.
  • Organizar el trabajo con issues y seguir el flujo GitHub flow para trabajar en equipo sin pisarse.
  • Publicar una web estática con GitHub Pages.

Antes de empezar

Necesitas Git instalado y configurado, y haber hecho tus primeros commits con git init, git add, git commit y git log. Todo eso está en la Estación 5: Tu taller; si te lo saltaste, hazlo primero. Para la parte de GitHub Pages te conviene haber hecho la Estación 13: HTML. Casi todo lo vas a practicar en la terminal de práctica de esta página; para GitHub necesitarás una computadora con conexión a internet y una cuenta de correo.

Cómo estudiar esta estación

Es una estación larga y muy práctica. Hazla en tres o cuatro sesiones: primero Git en tu computadora (commits, historial, deshacer), después ramas y conflictos, y por último GitHub (remotos, pull requests y Pages). Escribe tú cada comando en vez de copiarlo: los dedos también aprenden.

Git y GitHub: qué es cada cosa

Imagina que estás haciendo un juego de plataformas con dos amigas. Una dibuja los niveles, otra programa los enemigos y tú el salto del personaje. Si se pasan los archivos por correo o por una carpeta compartida, pronto aparecen las preguntas difíciles: ¿quién tiene la versión buena?, ¿quién borró la función del salto?, ¿cómo junto mis cambios con los tuyos sin perder nada?, ¿cómo vuelvo a como estaba el martes, cuando todo funcionaba?

Un sistema de control de versiones responde a esas preguntas. Ya sabes que Git guarda fotos de tu proyecto, los commits. Esa es solo la primera de sus cuatro capacidades:

  • Historial. Qué cambió, cuándo, quién lo hizo y, si el mensaje es bueno, por qué.
  • Volver atrás. Recuperar un archivo, deshacer un cambio o volver a una versión que funcionaba.
  • Experimentar sin miedo. Probar una idea en una línea paralela (una rama) sin tocar la versión que funciona.
  • Colaborar. Varias personas cambian los mismos archivos a la vez, y Git junta el trabajo.

Git no es GitHub

Mucha gente usa las dos palabras como si fueran lo mismo. No lo son:

  • Git es un programa que instalaste en tu computadora. Funciona sin internet. Guarda la historia en la carpeta oculta .git de cada proyecto.
  • GitHub es un servicio web (en github.com, propiedad de Microsoft desde 2018) que guarda copias de repositorios de Git en internet y les añade herramientas para colaborar: pull requests, revisión de código, issues, publicación de páginas web y automatización. Hay servicios parecidos, como GitLab, Codeberg o Bitbucket. Con todos se usa el mismo Git.

Fíjate en un detalle importante: en Git no hay una copia «principal» por diseño. Cada copia de un repositorio tiene la historia completa, por eso se dice que Git es un sistema de control de versiones distribuido. Si GitHub se cayera mañana, tu computadora seguiría teniendo todos los commits. Los equipos acuerdan usar la copia de GitHub como punto de encuentro, pero es un acuerdo, no una obligación técnica.

Para entenderlo

Git es como la cámara y el álbum de fotos de tu teléfono: funcionan sin conexión y el álbum es tuyo. GitHub es como un álbum compartido en internet donde tu familia sube sus fotos, las comenta y ordena. La analogía falla en algo: GitHub añade herramientas que Git no tiene (pull requests, issues, Pages), y Git junta el trabajo de varias personas de una forma que ningún álbum de fotos sabe hacer.

Qué hay dentro de un commit

En la Estación 5 dijimos que un commit es una foto del proyecto. Veamos qué guarda exactamente:

  • La foto de todos los archivos que Git sigue, tal como estaban al hacer el commit. No solo los que cambiaron: el proyecto entero. Por dentro, Git no duplica los archivos que no cambiaron y comprime todo, así que un repositorio con miles de commits ocupa poco.
  • El autor y la fecha. El nombre y el correo que configuraste con git config.
  • El mensaje que escribiste con -m.
  • El padre: el identificador del commit anterior. Así cada commit sabe de dónde viene y la historia forma una cadena. El primer commit no tiene padre, y un commit que junta dos ramas tiene dos.
  • Un identificador único, como a3f9c2e4b1d0..., de 40 dígitos hexadecimales. Se llama hash y se calcula a partir de todo lo anterior.

El hash funciona como una huella digital: si cambias un solo carácter del mensaje, de un archivo o del padre, sale un identificador completamente distinto. Por eso nadie puede alterar un commit antiguo sin que se note: cambiaría su hash y el de todos los que vienen detrás. Es la misma idea de las funciones hash que viste en la Estación 19, en su versión criptográfica, y los dígitos hexadecimales son los de la Estación 18. Casi siempre verás solo los 7 primeros dígitos, como a3f9c2e: bastan para distinguir un commit de los demás en un proyecto normal.

SHA-1 y SHA-256

Hoy Git calcula los identificadores con un algoritmo llamado SHA-1. El proyecto Git ya anunció que la futura versión 3.0 usará SHA-256 en los repositorios nuevos, y también llamará main a la rama inicial. Cuando llegue, los identificadores serán más largos, pero todo lo que aprendas aquí seguirá valiendo igual.

Dos nombres más que vas a ver todo el tiempo. Una rama (en inglés, branch) es un nombre, como main, que señala un commit y avanza sola cada vez que haces un commit nuevo en ella. HEAD («cabeza») es la marca de «estás aquí»: normalmente apunta a la rama en la que trabajas. Lo verás en detalle en la sección de ramas.

Consejo de oficio

Cuando no sepas qué hace un comando, pregúntale a Git: git help commit abre el manual completo, y git commit -h muestra un resumen corto de sus opciones. Y lee siempre lo que Git escribe: sus mensajes suelen incluir una línea que empieza por (use "git ...") con el comando que probablemente necesitas.

El ciclo del commit, a fondo

Ya conoces el ciclo básico: cambias archivos, los preparas con git add y los guardas con git commit. Parece poca cosa, pero la diferencia entre un historial útil y uno inservible está en los detalles: qué entra en cada commit, qué se queda fuera y qué dice el mensaje. Un buen historial se lee como el diario de un proyecto; uno malo es una lista de «cambios», «más cambios» y «arreglo».

Los estados de un archivo

Para Git, cada archivo de tu carpeta está en uno de estos estados. git status te lo dice, y conviene leerlo con calma:

EstadoQué significaCómo aparece en git statusEn git status -s
Sin seguimientoGit lo ve, pero nunca lo ha guardadoUntracked files??
ModificadoCambió desde el último commit y no está preparadoChanges not staged for commit M (la M a la derecha)
PreparadoEstá en el área de preparación: entrará en el próximo commitChanges to be committedM o A (a la izquierda)
ConfirmadoEstá igual que en el último commitNo aparece: nothing to commit, working tree cleanNo aparece

La versión corta, git status -s (de short), usa dos columnas: la izquierda habla del área de preparación y la derecha de la carpeta de trabajo. Así, MM juego.js significa que preparaste una parte de los cambios de juego.js y después seguiste cambiándolo. Sí, eso es posible: el área de preparación guarda el archivo tal como estaba al hacer git add, no una referencia al archivo.

«Pero si ya hice git add»

Un tropiezo clásico: haces git add juego.js, sigues editando juego.js, haces commit… y el commit no tiene tus últimos cambios. Es correcto: se guardó la versión que preparaste. Antes de cada commit, mira git status: si el archivo aparece a la vez en Changes to be committed y en Changes not staged, te falta otro git add.

Preparar con precisión

El área de preparación existe para que decidas qué entra en cada commit. Estas son las formas de usarla:

ComandoQué prepara
git add juego.jsEse archivo, tal como está ahora
git add sprites/Todo lo que hay dentro de la carpeta sprites
git add .Todo lo nuevo, modificado o borrado en la carpeta actual y sus subcarpetas
git add -p juego.jsTe enseña cada trozo de cambio y te pregunta si lo preparas (y sí, n no, q salir). Útil cuando un mismo archivo tiene dos cambios que no tienen nada que ver
git restore --staged juego.jsLo contrario: saca el archivo del área de preparación. Tus cambios siguen en el archivo; solo dejan de estar preparados

¿Por qué complicarse en vez de hacer siempre git add .? Porque un commit debería contener un solo cambio lógico: «añade el contador de puntos», no «añade el contador de puntos, cambia los colores y arregla un error del menú». Si mañana el contador de puntos resulta ser un problema, podrás deshacer ese commit sin perder los colores ni el arreglo. Y quien revise tu trabajo entenderá cada paso por separado.

Consejo de oficio

Usar git add . está bien cuando sabes exactamente qué hay en la carpeta. Mira siempre git status antes: es la forma más barata de descubrir que ibas a guardar un archivo de contraseñas, una carpeta de 300 MB o un borrador que no querías compartir.

Ver exactamente qué cambió: git diff

git status te dice qué archivos cambiaron. git diff te dice qué líneas. Hay tres comparaciones posibles, según qué dos zonas quieras comparar:

Así se lee la salida de git diff. En este ejemplo cambiaste la velocidad de 5 a 8 y añadiste una línea:

$ git diff
diff --git a/juego.js b/juego.js
index 3b18e51..a1c2f0d 100644
--- a/juego.js
+++ b/juego.js
@@ -1,2 +1,3 @@
 let vidas = 3;
-let velocidad = 5;
+let velocidad = 8;
+let puntos = 0;
  • --- a/juego.js es la versión anterior y +++ b/juego.js la nueva.
  • @@ -1,2 +1,3 @@ dice dónde está el cambio: en la versión anterior, un trozo que empieza en la línea 1 y tiene 2 líneas; en la nueva, empieza en la línea 1 y tiene 3.
  • Las líneas que empiezan con un espacio no cambiaron: están ahí como contexto.
  • Las que empiezan con - se quitaron y las que empiezan con + se añadieron. Git no tiene la idea de «línea modificada»: un cambio en una línea aparece como la línea vieja quitada y la nueva añadida.

Si la salida es más larga que la pantalla, Git la muestra dentro de un visor: bájala con las flechas o con la barra espaciadora y sal con q. VS Code muestra lo mismo con colores si haces clic en un archivo del panel Control de código fuente.

Ahora practica. En esta misión vas a hacer lo que se hace a diario en un proyecto real: tienes dos cambios distintos en dos archivos y los guardas en dos commits separados, cada uno con su mensaje.

  1. Prepara el escenario: cd juego, git init, git add . y git commit -m "feat: primera versión del juego".
  2. Haz dos cambios: echo "let puntos = 0;" >> juego.js y echo "h1 { color: gold; }" >> estilos.css.
  3. Mira qué pasó con git status y qué líneas cambiaron con git diff.
  4. Guarda el cambio de juego.js solo, en un commit: git add juego.js y git commit -m "feat: añade el contador de puntos".
  5. Después guarda el de estilos.css en otro commit con el mensaje style: pinta el título de dorado, y termina con git log --oneline.

Tres commits, cada uno con una sola idea. Dentro de un mes, si el título dorado no gusta, podrás deshacer solo ese commit sin tocar el contador de puntos.

Lo que no debe entrar: .gitignore

Algunos archivos no deben guardarse nunca en el repositorio:

  • Dependencias descargadas, como la carpeta node_modules que crea npm. Pueden ser cientos de megas y cualquiera puede volver a descargarlas con un comando.
  • Secretos: contraseñas, claves de APIs, el archivo .env donde se suelen guardar. Lo que entra en un repositorio lo puede leer cualquiera que tenga acceso a él.
  • Archivos generados: versiones compiladas o empaquetadas (carpetas como dist o build) que se fabrican a partir del código.
  • Basura del sistema y de programas: .DS_Store de macOS, Thumbs.db de Windows, registros *.log, archivos temporales.

Para eso existe el archivo .gitignore: un archivo de texto en la raíz del repositorio con una regla por línea. Git no mostrará como «sin seguimiento» nada de lo que coincida, y git add . lo dejará fuera. El propio .gitignore sí se guarda en el repositorio, para que todo el equipo comparta las mismas reglas.

# Las líneas que empiezan con # son comentarios
node_modules/     # la carpeta node_modules, esté donde esté
.env              # un archivo llamado exactamente .env
*.log             # cualquier archivo que termine en .log
/dist             # dist solo en la raíz del proyecto
sprites/*.psd     # los .psd que estén directamente en sprites
!importante.log   # excepción: este sí se guarda
ReglaSignificado
*Cualquier cantidad de caracteres, excepto /. *.log son todos los archivos que terminan en .log
?Exactamente un carácter cualquiera
**Cualquier cantidad de carpetas: docs/**/*.pdf son los PDF dentro de docs, a cualquier profundidad
Termina en /Solo carpetas: build/ ignora una carpeta build, pero no un archivo llamado build
Empieza con / o tiene / en medioLa ruta se cuenta desde donde está el .gitignore. Sin barra, la regla vale en cualquier carpeta
Empieza con !Excepción: vuelve a incluir algo que una regla anterior ignoraba. Si ignoraste la carpeta entera, no puedes rescatar un archivo de dentro

Este taller imita cómo decide Git. Arriba están las reglas; abajo, los archivos de un proyecto. Predice cuáles se ignorarán antes de ejecutar.

Con las reglas iniciales se ignoran .env, los dos .log (el de la raíz y el de logs, porque *.log no tiene barra y vale en cualquier carpeta) y todo lo que está dentro de node_modules. Para completar el taller añade dist/ y *.psd.

.gitignore no borra el pasado

.gitignore solo afecta a archivos que Git todavía no sigue. Si ya hiciste commit de node_modules o de .env, añadirlos a .gitignore no los saca del repositorio. Tienes que dejar de seguirlos con git rm --cached .env (quita el archivo del repositorio pero lo deja en tu disco) y hacer un commit. Aun así, la versión antigua sigue en el historial.

Impacto

Si subes por error una clave o contraseña a un repositorio público, date por hecho que alguien la copió: hay programas que recorren GitHub buscando claves minutos después de cada push. Borrarla en un commit nuevo no basta, porque sigue en el historial. Lo correcto es anular la clave (cambiar la contraseña o revocar la clave en el servicio que la emitió) y crear una nueva. GitHub revisa los envíos a los repositorios públicos nuevos y bloquea muchos tipos de claves conocidas antes de que se publiquen (push protection), pero no las reconoce todas. Verás más sobre secretos en la Estación 31.

No hace falta escribir el .gitignore desde cero. Al crear un repositorio en GitHub puedes elegir una plantilla para tu lenguaje (por ejemplo, Node), y el repositorio público github/gitignore tiene plantillas para casi cualquier tecnología, incluidos motores de videojuegos como Unity y Godot.

Mensajes que cuentan una historia

El mensaje de un commit es para una persona que no está en tu cabeza: tu equipo, o tú dentro de seis meses. La propia documentación de Git recomienda empezar con una línea corta, de menos de unos 50 caracteres, que resuma el cambio; después una línea en blanco, y después, si hace falta, una explicación más larga. Estas reglas ayudan:

  • La primera línea dice qué hace el commit, con un verbo en presente: «Añade el contador de puntos», «Corrige el doble salto». Imagina que completa la frase «Si aplicas este commit, …».
  • El cuerpo explica por qué, si no es evidente: qué problema había, qué alternativa descartaste. El cómo ya está en el código.
  • Un commit, un cambio lógico. Si el mensaje necesita un «y», probablemente son dos commits.

Con -m puedes escribir los dos párrafos: el primer -m es el título y el segundo, el cuerpo.

$ git commit -m "fix: evita el doble salto en el aire" -m "El personaje podía saltar otra vez antes de tocar el suelo si se pulsaba la tecla muy rápido. Ahora solo salta si enSuelo es true."

Conventional Commits

Muchos equipos siguen una convención llamada Conventional Commits (en español, «commits convencionales»). El mensaje empieza con un tipo que dice qué clase de cambio es:

tipo(ámbito opcional): descripción

cuerpo opcional

notas al pie opcionales
TipoÚsalo cuando…Ejemplo
featAñades una funcionalidad nuevafeat: añade el modo multijugador
fixCorriges un errorfix(menu): el botón Salir no respondía
docsSolo cambias documentacióndocs: explica cómo instalar el juego
styleCambias el formato del código sin cambiar lo que hace (espacios, comas). Muchos equipos lo usan también para cambios visuales de CSSstyle: ordena las propiedades CSS
refactorReorganizas el código sin cambiar lo que hacerefactor: separa la física en su propio archivo
testAñades o corriges pruebastest: prueba el cálculo de puntos
perf, build, ci, choreRendimiento, construcción, automatización, tareas de mantenimientochore: actualiza las dependencias

El ámbito entre paréntesis dice qué parte del proyecto toca: fix(menu):, feat(nivel-2):. Si un cambio rompe algo que funcionaba de otra forma (por ejemplo, las partidas guardadas antiguas dejan de cargarse), se marca con ! antes de los dos puntos, feat!: nuevo formato de partidas, o con una nota al pie que empieza por BREAKING CHANGE:.

¿Para qué tanta regla? Para que las personas y los programas entiendan el historial. Hay herramientas que leen estos mensajes y calculan solas el número de la siguiente versión con el sistema SemVer (versionado semántico, tres números MAYOR.MENOR.PARCHE, como 2.4.1): un fix sube el parche, un feat sube el menor y un cambio que rompe sube el mayor. Lo practicarás en un reto.

¿En español o en inglés?

Los tipos (feat, fix…) se escriben siempre en inglés, porque las herramientas los buscan así. La descripción puede ir en el idioma del equipo. En proyectos de código abierto internacionales se escribe en inglés; en un equipo que habla español, en español. Lo importante es ser constante.

Cuando Git abre un editor (y es Vim)

Si escribes git commit sin -m, Git abre un editor para que escribas el mensaje con calma. En la Estación 5 configuraste VS Code para esto (core.editor "code --wait"): se abre una pestaña, escribes el mensaje en la primera línea, guardas y cierras la pestaña. Las líneas que empiezan con # son explicaciones de Git y no se guardan. Si cierras la pestaña sin escribir nada, Git cancela el commit: Aborting commit due to empty commit message.

Pero si no configuraste el editor, o estás en otra computadora, Git suele abrir Vim, un editor de terminal que no se usa como los demás: al abrirlo no puedes escribir, y ninguna tecla habitual lo cierra. No es tu culpa; es un rito de paso. Así se sale:

Quieres…Pulsa
Empezar a escribir el mensajei (abajo aparece -- INSERT --)
Dejar de escribirEsc
Guardar y salir (el commit se hace)Esc y después escribe :wq y pulsa Enter
Salir sin guardar (el commit se cancela)Esc y después escribe :q! y pulsa Enter

Corregir el último commit: --amend

Acabas de hacer un commit y ves que el mensaje tiene una falta, o que olvidaste un archivo. Si todavía no lo compartiste (no hiciste push, que verás más adelante), puedes rehacerlo:

$ git add sonido-salto.wav          # el archivo que olvidaste (opcional)
$ git commit --amend -m "feat: añade el sonido del salto"

--amend («enmendar») no edita el commit anterior: crea uno nuevo, con otro hash, que lo reemplaza. Por eso solo debe usarse con commits que nadie más tiene. La terminal de práctica de esta página no tiene --amend: pruébalo en tu computadora.
