Lo que vas a lograr

En la Estación 5 guardaste tus primeros puntos de control con Git. Ahora vas a usarlo como lo usan los equipos profesionales: revisar la historia de un proyecto, deshacer errores sin miedo, trabajar en ramas, fusionar el trabajo de varias personas, resolver conflictos y colaborar en GitHub con pull requests. Al final vas a publicar una página web en internet, gratis, con GitHub Pages.

  • Explicar la diferencia entre Git y GitHub, y qué contiene de verdad un commit.
  • Preparar commits pequeños y precisos, leer git diff y escribir mensajes claros con la convención Conventional Commits.
  • Elegir qué archivos no deben entrar en el repositorio y escribir un .gitignore.
  • Buscar en el historial y deshacer cambios con restore, revert y, con cuidado, reset.
  • Crear ramas, cambiar entre ellas y fusionarlas, y resolver un conflicto paso a paso.
  • Subir un repositorio a GitHub y sincronizarlo con push, fetch y pull, usando una autenticación segura (HTTPS con token o SSH).
  • Proponer cambios con un pull request, revisar el código de otra persona y contribuir a un proyecto ajeno con un fork.
  • Organizar el trabajo con issues y seguir el flujo GitHub flow para trabajar en equipo sin pisarse.
  • Publicar una web estática con GitHub Pages.

Antes de empezar

Necesitas Git instalado y configurado, y haber hecho tus primeros commits con git init, git add, git commit y git log. Todo eso está en la Estación 5: Tu taller; si te lo saltaste, hazlo primero. Para la parte de GitHub Pages te conviene haber hecho la Estación 13: HTML. Casi todo lo vas a practicar en la terminal de práctica de esta página; para GitHub necesitarás una computadora con conexión a internet y una cuenta de correo.

Cómo estudiar esta estación

Es una estación larga y muy práctica. Hazla en tres o cuatro sesiones: primero Git en tu computadora (commits, historial, deshacer), después ramas y conflictos, y por último GitHub (remotos, pull requests y Pages). Escribe tú cada comando en vez de copiarlo: los dedos también aprenden.

Git y GitHub: qué es cada cosa

Imagina que estás haciendo un juego de plataformas con dos amigas. Una dibuja los niveles, otra programa los enemigos y tú el salto del personaje. Si se pasan los archivos por correo o por una carpeta compartida, pronto aparecen las preguntas difíciles: ¿quién tiene la versión buena?, ¿quién borró la función del salto?, ¿cómo junto mis cambios con los tuyos sin perder nada?, ¿cómo vuelvo a como estaba el martes, cuando todo funcionaba?

Un sistema de control de versiones responde a esas preguntas. Ya sabes que Git guarda fotos de tu proyecto, los commits. Esa es solo la primera de sus cuatro capacidades:

  • Historial. Qué cambió, cuándo, quién lo hizo y, si el mensaje es bueno, por qué.
  • Volver atrás. Recuperar un archivo, deshacer un cambio o volver a una versión que funcionaba.
  • Experimentar sin miedo. Probar una idea en una línea paralela (una rama) sin tocar la versión que funciona.
  • Colaborar. Varias personas cambian los mismos archivos a la vez, y Git junta el trabajo.

Git no es GitHub

Mucha gente usa las dos palabras como si fueran lo mismo. No lo son:

  • Git es un programa que instalaste en tu computadora. Funciona sin internet. Guarda la historia en la carpeta oculta .git de cada proyecto.
  • GitHub es un servicio web (en github.com, propiedad de Microsoft desde 2018) que guarda copias de repositorios de Git en internet y les añade herramientas para colaborar: pull requests, revisión de código, issues, publicación de páginas web y automatización. Hay servicios parecidos, como GitLab, Codeberg o Bitbucket. Con todos se usa el mismo Git.

Fíjate en un detalle importante: en Git no hay una copia «principal» por diseño. Cada copia de un repositorio tiene la historia completa, por eso se dice que Git es un sistema de control de versiones distribuido. Si GitHub se cayera mañana, tu computadora seguiría teniendo todos los commits. Los equipos acuerdan usar la copia de GitHub como punto de encuentro, pero es un acuerdo, no una obligación técnica.

Para entenderlo

Git es como la cámara y el álbum de fotos de tu teléfono: funcionan sin conexión y el álbum es tuyo. GitHub es como un álbum compartido en internet donde tu familia sube sus fotos, las comenta y ordena. La analogía falla en algo: GitHub añade herramientas que Git no tiene (pull requests, issues, Pages), y Git junta el trabajo de varias personas de una forma que ningún álbum de fotos sabe hacer.

Qué hay dentro de un commit

En la Estación 5 dijimos que un commit es una foto del proyecto. Veamos qué guarda exactamente:

  • La foto de todos los archivos que Git sigue, tal como estaban al hacer el commit. No solo los que cambiaron: el proyecto entero. Por dentro, Git no duplica los archivos que no cambiaron y comprime todo, así que un repositorio con miles de commits ocupa poco.
  • El autor y la fecha. El nombre y el correo que configuraste con git config.
  • El mensaje que escribiste con -m.
  • El padre: el identificador del commit anterior. Así cada commit sabe de dónde viene y la historia forma una cadena. El primer commit no tiene padre, y un commit que junta dos ramas tiene dos.
  • Un identificador único, como a3f9c2e4b1d0..., de 40 dígitos hexadecimales. Se llama hash y se calcula a partir de todo lo anterior.

El hash funciona como una huella digital: si cambias un solo carácter del mensaje, de un archivo o del padre, sale un identificador completamente distinto. Por eso nadie puede alterar un commit antiguo sin que se note: cambiaría su hash y el de todos los que vienen detrás. Es la misma idea de las funciones hash que viste en la Estación 19, en su versión criptográfica, y los dígitos hexadecimales son los de la Estación 18. Casi siempre verás solo los 7 primeros dígitos, como a3f9c2e: bastan para distinguir un commit de los demás en un proyecto normal.

SHA-1 y SHA-256

Hoy Git calcula los identificadores con un algoritmo llamado SHA-1. El proyecto Git ya anunció que la futura versión 3.0 usará SHA-256 en los repositorios nuevos, y también llamará main a la rama inicial. Cuando llegue, los identificadores serán más largos, pero todo lo que aprendas aquí seguirá valiendo igual.

Dos nombres más que vas a ver todo el tiempo. Una rama (en inglés, branch) es un nombre, como main, que señala un commit y avanza sola cada vez que haces un commit nuevo en ella. HEAD («cabeza») es la marca de «estás aquí»: normalmente apunta a la rama en la que trabajas. Lo verás en detalle en la sección de ramas.

Comprueba tu taller

Antes de seguir, abre una terminal (Git Bash en Windows) y comprueba tu versión y tu configuración:

$ git --version
git version 2.56.0
$ git config --global --list
user.name=Ana Pérez
user.email=ana@ejemplo.com
init.defaultbranch=main
core.editor=code --wait

Tu número de versión puede ser otro. Todo lo de esta estación funciona desde Git 2.23 (de 2019), que es cuando aparecieron git switch y git restore. Si tienes una versión anterior, actualízala desde git-scm.com. Si en la lista falta user.name, user.email o init.defaultbranch, vuelve a la Estación 5 y configúralos. El correo lo cambiarás en la sección de GitHub por uno privado.

Consejo de oficio

Cuando no sepas qué hace un comando, pregúntale a Git: git help commit abre el manual completo, y git commit -h muestra un resumen corto de sus opciones. Y lee siempre lo que Git escribe: sus mensajes suelen incluir una línea que empieza por (use "git ...") con el comando que probablemente necesitas.
