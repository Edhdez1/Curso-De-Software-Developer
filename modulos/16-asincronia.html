Lo que vas a lograr

Hasta ahora tus programas tenían todos los datos a mano: en variables, en arrays, en localStorage. Pero las apps que usas cada día (el clima, un mapa, el marcador de un partido, la tienda de un videojuego) piden datos a servidores que están a cientos o miles de kilómetros. Esa respuesta tarda, y mientras llega tu programa no puede quedarse congelado. En esta estación aprendes a esperar bien: promesas, async/await y fetch, la herramienta del navegador para hablar con las APIs de internet.

  • Reconocer los callbacks asíncronos y el problema del «callback hell».
  • Entender qué es una promesa y sus estados, usar then, catch y finally, y crear tus propias promesas.

  • Lanzar varias operaciones a la vez con Promise.all y poner un tiempo límite con Promise.race.
  • Explicar qué es una API y una API REST, y leer la documentación de una API pública.

Síncrono y asíncrono: esperar sin congelarse

Abres una app del clima. Antes de mostrarte nada, la app le pide el pronóstico a un servidor. La respuesta puede tardar 50 milisegundos con buena conexión o 5 segundos en el metro. ¿Qué hace el programa mientras tanto? Si se quedara quieto esperando, no podrías desplazarte, ni tocar un botón, ni ver siquiera un mensaje de «Cargando…». La pantalla estaría congelada.

Hay dos maneras de hacer una tarea que tarda:

  • Síncrona (en inglés, synchronous): cada instrucción espera a que termine la anterior. Es lo que has hecho hasta ahora: línea 1, línea 2, línea 3, y nadie empieza hasta que el de adelante acaba.
  • Asíncrona (asynchronous): empiezas una tarea que tarda, sigues con otras cosas y, cuando la tarea termina, alguien te avisa para que continúes con el resultado.

Para entenderlo

Piensa en dos cafeterías. En la primera, la cajera toma tu pedido y se queda inmóvil mirando la cafetera hasta que tu café está listo; la fila entera espera. En la segunda, la cajera te da un localizador (ese aparatito que vibra), atiende a la siguiente persona y, cuando tu café está listo, el aparato vibra y vas a buscarlo. La segunda cafetería es asíncrona. En JavaScript, la cajera es tu programa y las baristas son el navegador, que se encarga de las esperas. El límite de la analogía: en JavaScript solo hay una cajera. Si se pone a hacer una cuenta larguísima, nadie atiende los localizadores que vibran hasta que termine.

Ya usaste operaciones asíncronas sin llamarlas así. En la Estación 15, addEventListener("click", funcion) no ejecutaba la función en ese momento: la dejaba anotada para cuando alguien hiciera clic. Y setTimeout(funcion, 1000) la dejaba programada para dentro de un segundo. En las dos, tu código sigue de largo y la función se ejecuta después. Lo mismo pasa con pedir datos a internet, leer archivos en Node.js o esperar a que cargue una imagen.

Sale 1, 3 y, un segundo después, 2. setTimeout no pausa el programa: deja la función programada y el programa sigue enseguida con la línea siguiente. Ahora el caso que sorprende a casi todo el mundo: ¿y si el tiempo es 0?

Sale A, C, B. Aunque el tiempo sea 0, la función de setTimeout no puede colarse en medio de tu código: espera a que termine todo lo que está en marcha. Para entender por qué, hay que mirar cómo organiza JavaScript su trabajo.

Por qué JavaScript no se bloquea

JavaScript ejecuta tu código en un solo hilo (en inglés, thread): una única línea de trabajo que hace una cosa a la vez. Entonces, ¿cómo puede esperar la respuesta de un servidor y a la vez responder a tus clics? El truco es que JavaScript no espera. Las esperas las hace el entorno donde corre tu código: el navegador o Node.js. Cuando una espera termina, el entorno deja la función que tenía que ejecutarse en una cola de tareas. Y un mecanismo llamado bucle de eventos (event loop) se encarga de que, cada vez que JavaScript queda libre, tome la siguiente tarea de la cola y la ejecute.

Con este modelo se explica el misterio del 0: aunque el temporizador termine en el acto, la función va a la cola y solo sale de ahí cuando JavaScript acaba el código que estaba ejecutando. El tiempo de setTimeout es un mínimo, no una cita exacta: si JavaScript está ocupado, la tarea espera su turno en la cola.

Esto es una versión simplificada

El bucle de eventos real tiene más piezas: una pila de llamadas, varias colas y una cola especial y prioritaria para las promesas (la de microtareas). Para esta estación basta con la idea de «una cosa a la vez, y lo que está listo espera su turno en una cola». Lo verás a fondo, con ejercicios de «predice el orden», en la Estación 22: Cómo se ejecuta el código.

Bloquear o no bloquear

Si solo hay un hilo, ¿qué pasa si lo ocupas con algo largo? Este taller tiene un contador que sube diez veces por segundo y dos botones que «esperan» 2 segundos de formas distintas. El primero espera con un bucle que da vueltas mirando el reloj (síncrono). El segundo usa setTimeout (asíncrono). Pulsa cada botón y, mientras espera, intenta escribir en el cuadro de texto.

Con el primer botón, el contador se detiene, no puedes escribir y ni siquiera llega a verse el mensaje «Bloqueando…»: la página solo se vuelve a dibujar cuando JavaScript queda libre, y el bucle no lo suelta hasta el final. Es posible que la página entera del curso se quede quieta esos 2 segundos; es lo esperado. Con el segundo botón, todo sigue funcionando mientras pasa el tiempo.

Idea clave

Asíncrono no significa «más rápido» ni «en paralelo». Tu código sigue ejecutándose de a una cosa por vez. Lo que ganas es que las esperas (la red, un temporizador, un archivo) no ocupan el hilo, así que la página sigue respondiendo mientras tanto.

Error común

Creer que setTimeout(funcion, 1000) «pausa el programa un segundo». No pausa nada: programa la función y sigue. Si necesitas que algo ocurra después de la espera, ese algo tiene que ir dentro de la función que le pasas, o, como verás pronto, después de un await.

Callbacks y el «callback hell»

Un callback es una función que le pasas a otra función para que la llame más tarde. Lo viste en la Estación 10. Algunos callbacks se llaman enseguida, como el de map o filter. Otros se llaman cuando termina una espera: son los callbacks asíncronos, como el de setTimeout o el de addEventListener. Durante años fueron la única forma de trabajar con operaciones que tardan.

Cuando algo sale mal

Una petición puede fallar: no hay conexión, el usuario no existe… Con callbacks, la costumbre más extendida (la usa Node.js en sus funciones clásicas) es el callback con error primero: el primer parámetro del callback es el error, o null si todo fue bien, y el segundo son los datos.

function pedirUsuario(id, callback) {
  setTimeout(() => {
    if (id <= 0) {
      callback(new Error("Id no válido"), null);
    } else {
      callback(null, { id: id, nombre: "Ana" });
    }
  }, 500);
}

pedirUsuario(-1, (error, usuario) => {
  if (error) {
    console.log("Falló: " + error.message);
    return;
  }
  console.log("Llegó: " + usuario.nombre);
});

Funciona, pero fíjate en la forma: cada paso empuja el código un nivel más a la derecha. A esto se le llama callback hell («el infierno de los callbacks») o pirámide de la perdición (pyramid of doom). Tiene problemas reales:

  • Se lee mal. Con diez pasos, el código se sale de la pantalla y cuesta seguir qué cierra cada llave.
  • El manejo de errores se repite en cada nivel. Si olvidas uno, el error desaparece en silencio.
  • Hacer cosas a la vez es difícil. Si quisieras pedir el perfil y las noticias al mismo tiempo y seguir cuando lleguen las dos, tendrías que contar a mano cuántas respuestas llegaron.
  • Pierdes el control. Entregas tu función a otro código y confías en que la llame exactamente una vez. Si por un error la llama dos veces, o nunca, tu programa falla de formas difíciles de rastrear.

Los callbacks no son malos

Los callbacks siguen en todas partes y están bien usados: addEventListener, map, filter, setTimeout. El problema es solo encadenar muchas esperas que dependen unas de otras. Para eso se inventaron las promesas.

Promesas

Una promesa (en inglés, promise) es un objeto que representa un resultado que todavía no existe: algo que llegará más adelante, o que fallará. En lugar de recibir un callback, una función asíncrona moderna te devuelve una promesa al instante, y tú decides qué hacer cuando se cumpla.

Para entenderlo

Una promesa es como el ticket que te dan al dejar tu bicicleta en el taller. El ticket no es la bicicleta arreglada: es la garantía de que, cuando termine el trabajo, te van a avisar, con la bici lista o con la noticia de que no tenía arreglo. Mientras tanto, puedes irte a hacer otras cosas con el ticket en el bolsillo. El límite de la analogía: un taller siempre acaba llamando, pero una promesa puede quedarse pendiente para siempre si el código que debía cumplirla nunca lo hace. Por eso existen los tiempos límite, que verás más adelante.

Una promesa siempre está en uno de tres estados:

EstadoEn inglésQué significa
PendientependingLa operación sigue en marcha. Todavía no hay resultado.
CumplidafulfilledTerminó bien. La promesa guarda un valor: los datos que pediste.
RechazadarejectedTerminó mal. La promesa guarda un motivo, normalmente un objeto Error.

Cuando una promesa está cumplida o rechazada se dice que está establecida (settled), y a partir de ahí ya no cambia nunca. En la documentación también verás la palabra resolved («resuelta»). A veces se usa como sinónimo de «cumplida», pero técnicamente significa algo más sutil; para empezar, quédate con pendiente, cumplida y rechazada.

Usar una promesa: then, catch y finally

Una promesa tiene tres métodos para decir qué hacer cuando termine:

  • promesa.then(funcion): la función recibe el valor cuando la promesa se cumple.
  • promesa.catch(funcion): la función recibe el error si la promesa se rechaza.
  • promesa.finally(funcion): la función se ejecuta en los dos casos y no recibe nada. Es el lugar ideal para «limpiar»: ocultar un mensaje de «Cargando…» o reactivar un botón.

Crear una promesa

Para crear tu propia promesa usas new Promise(...) y le pasas una función que recibe dos funciones: resolve (llámala con el valor cuando todo salga bien) y reject (llámala con un error cuando algo falle). Un detalle de los talleres

El taller da por terminado tu programa cuando acaba el código principal y no quedan temporizadores pendientes. Si en ese momento una cadena de promesas sigue en marcha, sus últimos mensajes se perderían. Por eso en algunos talleres verás un await delante de una cadena o de una llamada: le pide al taller que espere a que termine. En la consola del navegador o en Node.js no hace falta, porque siguen atendiendo todo lo pendiente. Qué hace await exactamente lo verás en la próxima sección.

Tres reglas para crear promesas:

  • Llama a resolve o a reject una sola vez. Las llamadas siguientes se ignoran, porque una promesa establecida ya no cambia.
  • Rechaza con objetos Error (reject(new Error("…"))), no con textos sueltos. Así tienes el mensaje en error.message y la pila de llamadas para depurar, como viste en la Estación 12.
  • Si el ejecutor lanza un error con throw, la promesa se rechaza sola.

Hay dos atajos para crear promesas ya establecidas: Promise.resolve(valor) y Promise.reject(error). Y una función de tres líneas que vas a usar en toda la estación para simular esperas:

function esperar(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

esperar(1000).then(() => console.log("Pasó un segundo"));

setTimeout llama a resolve cuando pasan los milisegundos, y la promesa se cumple. Es setTimeout convertido en promesa.

Un detalle que confunde a mucha gente: el ejecutor se ejecuta enseguida, en el momento de crear la promesa. Lo que se ejecuta después es la función del then. Síguelo paso a paso:

console.log("1. Antes");
const promesa = new Promise((resolve) => {
  console.log("2. El ejecutor corre enseguida");
  resolve("pizza");
});
promesa.then((valor) => {
  console.log("4. El then recibe: " + valor);
});
console.log("3. Después");

Encadenar promesas

Aquí está la magia que desarma la pirámide. then devuelve una promesa nueva, así que puedes poner otro then detrás, y otro, formando una cadena. Tres reglas lo explican todo:

  1. Lo que devuelves (return) dentro de un then se convierte en el valor que recibe el then siguiente.
  2. Si devuelves una promesa, la cadena espera a que se cumpla y pasa su valor al siguiente then.
  3. Si algo falla (un throw o una promesa rechazada), la cadena salta directamente al siguiente catch, sin ejecutar los then que hay en medio. Funciona como el try/catch que ya conoces.

Error común

Olvidar el return dentro de un then con llaves es el error más común con promesas. Sin return, la función devuelve undefined, la cadena no espera a la petición y el siguiente then recibe undefined. Las flechas sin llaves, como (sesion) => pedirPerfil(sesion.token), devuelven su valor automáticamente. El segundo error más común es meter un then dentro de otro then: vuelves a construir la pirámide. Devuelve la promesa y sigue la cadena desde fuera.

Consejo de oficio

Termina siempre una cadena con catch. Una promesa rechazada que nadie atiende produce un error «Uncaught (in promise)» en la consola del navegador y, en Node.js (desde la versión 15), detiene el programa entero. Los equipos profesionales configuran herramientas que avisan cuando una promesa queda sin manejar.

async y await: código asíncrono que se lee de arriba abajo

Las cadenas de then son mucho mejores que la pirámide, pero siguen llenas de funciones dentro de funciones. En 2017, JavaScript añadió dos palabras que permiten escribir código asíncrono con el mismo aspecto que el código síncrono de siempre: async y await. No reemplazan a las promesas: funcionan con promesas, por debajo todo sigue siendo lo mismo.

Tres reglas:

  1. async delante de una función hace que siempre devuelva una promesa. Si la función hace return 5, quien la llama recibe una promesa que se cumple con 5. Si la función lanza un error con throw, la promesa se rechaza.
  2. await delante de una promesa pausa esa función hasta que la promesa se establezca. Si se cumple, await te entrega el valor. Si se rechaza, await lanza el error en esa misma línea, como un throw, así que lo atrapas con try/catch.
  3. await solo se puede usar dentro de funciones async, o en el nivel superior de un módulo (lo verás en la Estación 22) y en la consola del navegador. En los talleres de este curso también puedes usarlo fuera de funciones, porque el taller envuelve tu código en una función async por ti.

Los errores más comunes con async y await

1. Olvidar el await. Sin await no recibes los datos, sino la promesa. Y una promesa no tiene la propiedad que buscas, así que obtienes undefined:

const perfil = pedirPerfil();   // falta await
console.log(perfil);            // Promise { <pending> }
console.log(perfil.nombre);     // undefined

Cuando veas Promise { <pending> } o un undefined inesperado cerca de código asíncrono, busca primero un await que falta.

2. Usar await fuera de una función async. El navegador responde con un error de sintaxis parecido a SyntaxError: await is only valid in async functions and the top level bodies of modules. La solución es añadir async a la función que contiene el await.

3. Olvidar que una función async devuelve una promesa. Si calcularTotal es async, const total = calcularTotal(); guarda una promesa, no un número. Lo asíncrono «contagia»: todo lo que necesita un resultado asíncrono también tiene que esperar (con await o con then).

¿then o await?

El código moderno usa sobre todo async/await, porque se lee mejor y el manejo de errores es el mismo try/catch de siempre. Aun así, vas a leer then en documentación, tutoriales y proyectos más antiguos, y a veces una cadena corta queda más clara con then. Las dos son promesas: aprende a leer las dos y, dentro de una misma función, elige un estilo y no los mezcles.

Varias promesas a la vez: Promise.all y Promise.race

La pantalla principal de un juego en línea necesita tu perfil, tu lista de amigos y las noticias del día. Cada petición tarda alrededor de medio segundo. Si las pides una detrás de otra con tres await, la pantalla tarda la suma de las tres. Pero ninguna depende de las otras: puedes lanzarlas todas a la vez y esperar solo lo que tarde la más lenta.

Promise.all recibe un array de promesas y devuelve una sola promesa que se cumple cuando todas se cumplen. Su valor es un array con los resultados, en el mismo orden en que pusiste las promesas (no en el orden en que llegaron). Con la desestructuración de la Estación 11 queda muy limpio:

const [perfil, amigos, noticias] = await Promise.all([
  pedirPerfil(),
  pedirAmigos(),
  pedirNoticias(),
]);

La clave está en un detalle: una operación empieza cuando llamas a la función, no cuando haces await. Al construir el array se llaman las tres funciones seguidas, así que las tres peticiones ya están en marcha antes de esperar a ninguna. Mide la diferencia:

Si una de las promesas se rechaza, Promise.all se rechaza enseguida con ese error, sin esperar a las demás (que siguen su curso, pero sus resultados se ignoran). Es lo que quieres cuando necesitas todos los datos o ninguno. Si prefieres recibir cada resultado aunque alguno falle, usa Promise.allSettled: se cumple cuando todas terminan y te da un objeto por cada una:

const resultados = await Promise.allSettled([pedirPerfil(), pedirAmigos()]);
// [
//   { status: 'fulfilled', value: 'Lyra' },
//   { status: 'rejected', reason: Error: sin conexión }
// ]
for (const r of resultados) {
  if (r.status === "fulfilled") console.log("Bien:", r.value);
  else console.log("Falló:", r.reason.message);
}

Error común

Qué es una API y cómo se lee su documentación

Ya sabes esperar. Ahora, ¿a quién le pides los datos y cómo? Una API (del inglés Application Programming Interface, «interfaz de programación de aplicaciones») es un conjunto de reglas que dice cómo un programa puede pedirle cosas a otro: qué puedes pedir, cómo tienes que pedirlo y qué te van a responder.

Para entenderlo

Una API es como la carta de un restaurante. Te dice qué platos existen y cómo pedirlos, sin que tengas que entrar a la cocina ni saber cómo se preparan. El límite de la analogía: un camarero entiende «una de esas, pero sin cebolla»; una API no. Si escribes una letra mal o pides algo que no está en la carta, recibes un error.

Ya usaste varias APIs. En la Estación 15 viste que el navegador le ofrece a tu código sus APIs web: el DOM (document.querySelector), localStorage, la propia console. En esta estación hablamos de otra clase: las APIs HTTP, las que usas a través de internet. Tu programa envía una petición HTTP a un servidor, como las que viste en la Estación 3, y el servidor responde con datos, casi siempre en formato JSON (Estación 11).

Anatomía de una petición a una API

  • La URL base es la parte común a todas las peticiones de una API: https://api.tvmaze.com.
  • Un endpoint («punto de acceso») es cada dirección concreta que ofrece un servicio: /search/shows busca series, /shows/55138 da los datos de una serie.
  • Los parámetros de consulta (query parameters) van después del ?, en pares nombre=valor separados por &. Sirven para afinar la petición: qué buscar, cuántos resultados, en qué idioma.

Cuando el valor de un parámetro viene de lo que escribe una persona, no lo pegues a mano en la dirección: los espacios, las tildes y símbolos como & o ? tienen significado especial dentro de una URL. API REST: recursos y verbos

Muchas APIs web siguen un estilo llamado REST (Representational State Transfer), que describió Roy Fielding en su tesis doctoral del año 2000. En la práctica, cuando alguien dice «una API REST» se refiere a una API HTTP organizada así:

  • Los datos se organizan en recursos: usuarios, publicaciones, partidas, series. Cada recurso tiene su propia URL: /posts es la colección de publicaciones y /posts/1 es la publicación número 1.
  • El método HTTP dice qué quieres hacer con el recurso. Es el verbo; la URL es el sustantivo.
  • Las respuestas usan los códigos de estado de HTTP para decir cómo fue todo, y casi siempre traen JSON.

Pedir y enviar datos con fetch

Para hablar con una API desde JavaScript, los navegadores (y Node.js desde la versión 18) traen la función fetch («ir a buscar»). Recibe una dirección y devuelve una promesa que se cumple con un objeto Response (la respuesta). Leer los datos de esa respuesta es otra operación que tarda, así que lleva su propio await:

const respuesta = await fetch("https://pokeapi.co/api/v2/pokemon/pikachu");
const datos = await respuesta.json();
console.log(datos.name); // "pikachu"

¿Por qué dos await? Porque la respuesta llega en dos partes: primero el código de estado y las cabeceras, y después el cuerpo con los datos, que puede ser grande y llegar poco a poco. Míralo en cámara lenta:

Idea clave

fetch no considera un error que el servidor responda 404 o 500: para fetch, el servidor respondió y su trabajo terminó bien. Comprueba siempre respuesta.ok (que es true con los códigos del 200 al 299) o respuesta.status antes de usar los datos.

Como vas a repetir siempre los mismos pasos (pedir, comprobar ok, leer el JSON), conviene envolverlos en una función. Esta es probablemente la función más copiada de la web:

async function obtenerJSON(url) {
  const respuesta = await fetch(url);
  if (!respuesta.ok) {
    throw new Error("Error HTTP " + respuesta.status);
  }
  const datos = await respuesta.json();
  return datos;
}

try {
  const pikachu = await obtenerJSON("https://pokeapi.co/api/v2/pokemon/pikachu");
  console.log(pikachu.name);
} catch (error) {
  console.log("No se pudo cargar: " + error.message);
}

Con ella, quien la usa solo tiene que preocuparse de un caso de error (el catch), venga de la red o del servidor. Ordena sus líneas:

  1. async function obtenerJSON(url) {
  2. const respuesta = await fetch(url);
  3. if (!respuesta.ok) throw new Error("Error HTTP " + respuesta.status);
  4. const datos = await respuesta.json();
  5. return datos;
  6. }

Enviar datos: POST, cabeceras y cuerpo

Hasta aquí, fetch hacía peticiones GET, que es lo que hace por defecto. Para enviar datos (publicar una puntuación, crear una cuenta, guardar un comentario) se usa normalmente POST, y se le pasa a fetch un segundo argumento con opciones:

  • method: el método HTTP ("POST", "PUT", "PATCH", "DELETE").
  • headers: las cabeceras, datos extra sobre la petición. "Content-Type": "application/json" le dice al servidor que el cuerpo es JSON.
  • body: el cuerpo. Tiene que ser texto, así que conviertes tu objeto con JSON.stringify.

Pruébalo en la consola con JSONPlaceholder, que acepta publicaciones de práctica:

const respuesta = await fetch("https://jsonplaceholder.typicode.com/posts", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "Hola", body: "Mi primer POST", userId: 1 }),
});
console.log(respuesta.status);       // 201: creado
console.log(await respuesta.json()); // { title: 'Hola', body: 'Mi primer POST', userId: 1, id: 101 }

El servidor responde 201 y te devuelve lo que creó, con un id nuevo. JSONPlaceholder finge que lo guardó (siempre responde con el id 101), pero no guarda nada: es un servidor de práctica. Otras cabeceras frecuentes son Accept: application/json (pides que te respondan en JSON) y Authorization (envías una clave o un token de sesión). Para leer una cabecera de la respuesta: respuesta.headers.get("content-type").

Cuidado

El cuerpo de una respuesta solo se puede leer una vez. Si llamas a respuesta.json() y después a respuesta.text(), la segunda falla con un error que dice que el cuerpo ya se usó (body stream already read o parecido). Guarda el resultado en una variable y úsalo las veces que quieras.

La interfaz mientras esperas: carga, error, vacío y cancelación

Pulsas «Buscar» y no pasa nada durante dos segundos. ¿Funcionó? ¿Se rompió? Pulsas cinco veces más. O algo falla y la pantalla se queda en blanco, sin explicación. Las dos cosas son de las más frustrantes que puede hacer una app. Cuando tu interfaz depende de una petición, tiene que decir en todo momento qué está pasando. Eso significa diseñar cinco estados, no solo el de «todo salió bien»:

En código, el patrón casi siempre es el mismo. try/catch/finally encaja con estos estados como un guante:

  1. Antes de pedir: muestra «Cargando…» y desactiva el botón para que nadie lance la misma petición cinco veces.
  2. Dentro del try: pide los datos con await. Si llega una lista vacía, muestra el estado vacío; si no, dibuja los datos.
  3. En el catch: muestra un mensaje de error claro, que diga qué pasó y qué puede hacer la persona.
  4. En el finally: reactiva el botón. Pase lo que pase, incluso si hubo un return dentro del try.

Tiempos límite con AbortSignal.timeout

fetch acepta una opción signal (señal): un objeto que le puede avisar «abandona esta petición». AbortSignal.timeout(ms) crea una señal que se activa sola pasado ese tiempo. Si salta, fetch se rechaza con un error llamado TimeoutError. Funciona en todos los navegadores actuales desde 2024 y en Node.js.

try {
  const respuesta = await fetch(url, { signal: AbortSignal.timeout(5000) });
  // …
} catch (error) {
  if (error.name === "TimeoutError") {
    estado.textContent = "El servidor tarda demasiado. Inténtalo más tarde.";
  } else {
    estado.textContent = "No se pudo cargar.";
  }
}

Modifica el taller anterior: en la llamada a obtenerJSON, añade un segundo argumento { signal: AbortSignal.timeout(2000) }. Elige «Servidor muy lento» y comprueba que a los 2 segundos aparece el error. Después, en el catch, muestra un mensaje distinto cuando error.name === "TimeoutError".

Cancelar con AbortController

A veces eres tú quien quiere cancelar: la persona cerró la ventana, cambió de pestaña o, el caso más común, escribió una búsqueda nueva antes de que llegara la anterior. Para eso existe AbortController («controlador de cancelación»): creas uno, le das su señal a fetch y, cuando quieras cancelar, llamas a abort(). La petición se abandona y fetch se rechaza con un error llamado AbortError.

const controlador = new AbortController();
const promesa = fetch(url, { signal: controlador.signal });
controlador.abort(); // la petición se cancela; promesa se rechaza con AbortError

  espera = setTimeout(() => buscar(entrada.value), 300); // y empieza otra
});

Una última idea para errores pasajeros, como un 429 (demasiadas peticiones) o un 503 (servidor saturado): reintentar unas pocas veces, esperando un poco entre intento e intento. Algunas APIs incluso te dicen cuánto esperar en la cabecera Retry-After. Lo vas a programar en uno de los retos de la práctica.

Resumen

  • El código síncrono espera a que termine cada paso; el asíncrono empieza una tarea que tarda y sigue, y continúa con el resultado cuando llega.
  • JavaScript hace una cosa a la vez (un solo hilo). Las esperas las hace el navegador o Node.js; lo que está listo espera en una cola y el bucle de eventos lo ejecuta cuando JavaScript queda libre. Por eso un bucle largo congela la página y un setTimeout no.
  • Los callbacks asíncronos funcionan, pero al encadenar esperas forman el «callback hell». Un valor asíncrono no se puede devolver con return desde un callback.
  • Una promesa representa un resultado futuro: pendiente, cumplida (con un valor) o rechazada (con un error). then, catch y finally dicen qué hacer; new Promise((resolve, reject) => …) crea una. En una cadena, recuerda el return.
  • async hace que una función devuelva una promesa; await pausa esa función (no el programa) hasta que la promesa se establece, y los errores se atrapan con try/catch. Cuidado con olvidar await y con await dentro de forEach.
  • Promise.all lanza varias operaciones independientes a la vez y espera a todas; Promise.race se queda con la primera y sirve para tiempos límite; allSettled y any cubren los otros casos.
  • Una API define cómo pedirle cosas a otro programa. Una API REST organiza los datos en recursos con URL y usa métodos HTTP (GET, POST, PUT, PATCH, DELETE) y códigos de estado. Antes de programar, lee su documentación: endpoints, parámetros, forma de la respuesta, límites de uso y licencia.
  • fetch(url, opciones) devuelve una promesa con un Response; los datos se leen con await respuesta.json(). fetch solo se rechaza si no hay respuesta: comprueba siempre respuesta.ok. Para enviar datos: method, headers con Content-Type y body con JSON.stringify.
  • Una interfaz que pide datos tiene cinco estados: inicial, cargando, éxito, vacío y error. try/catch/finally los organiza.
  • AbortSignal.timeout(ms) pone un tiempo límite a fetch y AbortController cancela peticiones, por ejemplo la búsqueda anterior, para evitar condiciones de carrera.

Reto

function esperar(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

  await esperar(ms);
  return dato;
}

function conLimite(promesa, ms) {
  const limite = new Promise((resolve, reject) => {
    setTimeout(() => reject(new Error("Tiempo agotado")), ms);
  });
  return Promise.race([promesa, limite]);
}

} catch (error) {

}

      return await respuesta.json();

    if (intento < intentos) {
      await esperar(200);
    }

Pista 2

Ver una solución 
// ---- Servidor simulado de puntuaciones (no lo cambies) ----
function fetchFalso(url, opciones = {}) {
  return new Promise((resolve) => {
    setTimeout(() => {
      const responder = (status, datos) => resolve({ status: status, ok: status >= 200 && status <= 299, json: async () => datos });
      if (opciones.method !== "POST") return responder(405, { error: "usa el método POST" });
      const cabeceras = opciones.headers || {};
      const tipo = Object.keys(cabeceras).find((k) => k.toLowerCase() === "content-type");
      if (!tipo || cabeceras[tipo] !== "application/json") return responder(415, { error: "falta la cabecera Content-Type: application/json" });
      let cuerpo;
      try { cuerpo = JSON.parse(opciones.body); } catch (e) { return responder(400, { error: "el cuerpo no es JSON válido" }); }
      if (typeof cuerpo.jugador !== "string" || cuerpo.jugador === "") return responder(400, { error: "falta el nombre del jugador" });
      if (typeof cuerpo.puntos !== "number") return responder(400, { error: "puntos debe ser un número" });
      responder(201, { id: 7, jugador: cuerpo.jugador, puntos: cuerpo.puntos });
    }, 200);
  });
}
// ---- Fin del servidor simulado ----

async function enviarPuntuacion(jugador, puntos) {
  const respuesta = await fetchFalso("https://api.example.com/puntuaciones", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ jugador: jugador, puntos: puntos }),
  });
  const datos = await respuesta.json();
  if (respuesta.ok) {
    console.log("Guardada con id " + datos.id + ": " + datos.jugador + ", " + datos.puntos + " puntos");
  } else {
    console.log("Rechazada: " + respuesta.status + " (" + datos.error + ")");
  }
}

// Pruebas (no las cambies)
await enviarPuntuacion("Lyra", 1200);
await enviarPuntuacion("Leo", "muchos");

Aquí leemos el JSON también cuando la respuesta es un error, porque este servidor explica el motivo en el cuerpo. Muchas APIs lo hacen; su documentación te dice cómo. Y fíjate en quién valida: el servidor no confía en lo que le envías. Nunca debería hacerlo (lo verás en la Estación 31).

  const respuesta = await fetchFalso(url, { signal: senal });

    throw new Error("Error HTTP " + respuesta.status);

function pintarResultados(lista) {
  resultados.replaceChildren();
  for (const resultado of lista) {
    const serie = resultado.show;
    const anio = serie.premiered ? serie.premiered.slice(0, 4) : "¿?";
    const generos = serie.genres.length > 0 ? serie.genres.join(", ") : "sin géneros";

    const item = document.createElement("li");
    const nombre = document.createElement("strong");
    nombre.textContent = serie.name;
    const detalles = document.createElement("span");
    detalles.textContent = anio + " · " + generos + " · " + nota;
    item.append(nombre, detalles);
    resultados.append(item);
  }
}

  evento.preventDefault();
  const texto = campo.value.trim();
  if (texto === "") {
    estado.textContent = "Escribe algo para buscar.";
    return;
  }

  controlador = new AbortController();
  resultados.replaceChildren();
  estado.textContent = "Buscando «" + texto + "»…";

  cancelar.disabled = false;

    if (lista.length === 0) {

      estado.textContent = "Búsqueda cancelada.";

});

Autoevaluación

Responde sin mirar arriba. Si fallas alguna, lee la explicación: equivocarse aquí es la forma más barata de aprender.

¿Qué imprime este programa? console.log("A"); setTimeout(() => console.log("B"), 0); console.log("C");

  1. A, B, C

    Sería así si setTimeout con 0 ejecutara la función en el acto. Pero la función va a la cola de tareas y espera a que termine el código en marcha.

  2. B, A, C

    setTimeout nunca adelanta una función: como mucho, la retrasa.

  3. A, C, B

    Correcto. La función de setTimeout espera en la cola hasta que JavaScript termina el código síncrono, aunque el tiempo sea 0.

  4. A, C, y B nunca se imprime

    Con 0 milisegundos la función sí se ejecuta, solo que después del código síncrono.

Pides https://pokeapi.co/api/v2/pokemon/pikachuu con fetch (el nombre está mal escrito) y el servidor responde 404. ¿Qué pasa con la promesa de fetch?

  1. Se rechaza con un error 404.

    Es la confusión más común con fetch. Solo se rechaza cuando no hay respuesta (sin red, dominio inexistente, bloqueo del navegador).

  2. Se cumple con una respuesta que tiene ok: false y status: 404.

    Correcto. El servidor respondió, así que fetch cumplió su trabajo. Te toca comprobar respuesta.ok y lanzar el error tú.

  3. Se queda pendiente para siempre.

    El servidor respondió, así que la promesa se establece. Quedarse pendiente pasa cuando no llega ninguna respuesta y no hay tiempo límite.

  4. Devuelve undefined.

    fetch siempre devuelve una promesa; con un 404 se cumple con un objeto Response.

¿Cuáles son los estados posibles de una promesa?

  1. Pendiente, cumplida y rechazada.

    Correcto. Cuando está cumplida o rechazada se dice que está establecida, y ya no cambia.

  2. Iniciada, en curso y terminada.

    No son esos nombres, y «terminada» no dice lo más importante: si salió bien o mal.

  3. Pendiente y resuelta.

    Falta distinguir entre salir bien y salir mal. Además, «resuelta» (resolved) tiene un significado técnico más sutil.

  4. Síncrona y asíncrona.

    Eso describe formas de ejecutar código, no el estado de una promesa.

Si async function puntos() { return 10; }, ¿qué guarda const p = puntos();?

  1. El número 10.

    Sería así sin async. Una función async siempre envuelve su resultado en una promesa.

  2. undefined.

    La función sí devuelve algo: una promesa.

  3. Un error, porque no hay await dentro de la función.

    Una función async sin await es válida: devuelve una promesa ya cumplida.

  4. Una promesa que se cumple con 10.

    Correcto. Para obtener el 10 escribe const p = await puntos(); dentro de otra función async.

Tu pantalla necesita el perfil, los amigos y las noticias, que no dependen entre sí. ¿Qué es mejor?

  1. Tres await seguidos, uno por petición.

    Funciona, pero tarda la suma de las tres, porque cada petición espera a la anterior sin necesidad.

  2. await Promise.all([pedirPerfil(), pedirAmigos(), pedirNoticias()])

    Correcto. Las tres salen a la vez y esperas solo lo que tarda la más lenta.

  3. await Promise.race([pedirPerfil(), pedirAmigos(), pedirNoticias()])

    race se queda solo con la primera que termine; perderías las otras dos.

  4. Un forEach con una función async.

    forEach no espera a las funciones async: no sabrías cuándo terminó todo.

¿Por qué hay dos await en const r = await fetch(url); const datos = await r.json();?

  1. Por costumbre: el segundo sobra.

    Sin el segundo await, datos sería una promesa, no los datos.

  2. Porque fetch hace dos peticiones al servidor.

    Es una sola petición y una sola respuesta.

  3. Porque la respuesta llega en dos partes: primero el estado y las cabeceras (ahí se cumple fetch) y después se lee el cuerpo, que también tarda.

    Correcto. json() termina de recibir el cuerpo y lo convierte de texto JSON a objeto, y eso es asíncrono.

  4. Porque json() hace otra petición para convertir el texto.

    La conversión ocurre en tu computadora. Lo que tarda es terminar de recibir y leer el cuerpo.

Este código imprime «Listo» antes que las descargas. ¿Por qué? archivos.forEach(async (a) => { await descargar(a); }); console.log("Listo");

  1. Porque forEach no espera a las funciones async que llama: las lanza y sigue.

    Correcto. Usa for...of con await (una por una) o Promise.all con map (todas a la vez).

  2. Porque falta async delante de forEach.

    forEach es un método de los arrays, no una función que puedas marcar como async. El problema es que no espera.

  3. Porque console.log siempre se ejecuta antes que el resto.

    console.log se ejecuta cuando le toca, como cualquier línea. Aquí le toca antes porque nadie esperó a las descargas.

  4. Porque descargar falla en silencio.

    Las descargas se hacen; solo que terminan después de «Listo».

En una API REST, ¿qué método y qué respuesta esperas al crear una publicación nueva?

  1. GET y 200.

    GET es para leer, no para crear.

  2. DELETE y 204.

    DELETE es para borrar.

  3. PUT y 404.

    PUT reemplaza un recurso que ya existe, y 404 significa que no se encontró.

  4. POST y 201 (Created).

    Correcto. POST crea un recurso nuevo y el servidor suele responder 201 con lo que se creó.

En tu buscador escribes «mario», pero la lista muestra resultados de «ma». ¿Qué pasó y cómo se arregla?

  1. El servidor tiene un error; no se puede arreglar desde tu código.

    El servidor respondió bien a cada búsqueda. El problema está en tu código, que dibujó una respuesta vieja.

  2. La respuesta de «ma» llegó después que la de «mario» y se dibujó encima. Se arregla cancelando la búsqueda anterior con AbortController.

    Correcto. Es una condición de carrera: las respuestas no siempre llegan en el orden en que salieron.

  3. Falta un await delante de console.log.

    console.log no devuelve una promesa; el await no cambiaría nada.

  4. Hay que esperar las dos búsquedas con Promise.all.

    Seguirías recibiendo la respuesta vieja. Lo que quieres es descartarla, no esperarla.

La API responde 200 con un array vacío []. ¿Qué debería mostrar tu interfaz?

  1. Un mensaje de error.

    La petición salió bien. «No hay resultados» no es un fallo, y tratarlo como tal confunde a la persona.

  2. Nada: una lista vacía se explica sola.

    Una pantalla en blanco no dice si terminó, si sigue cargando o si falló.

  3. Un estado vacío: «No encontramos resultados», con una sugerencia de qué probar.

    Correcto. El estado vacío es uno de los cinco que toda interfaz que pide datos debe diseñar.

  4. Reintentar hasta que lleguen datos.

    Reintentar sirve para errores pasajeros. Una búsqueda sin resultados va a seguir sin resultados.

¿Dónde pones el código que reactiva el botón «Buscar» para que se ejecute tanto si la búsqueda sale bien como si falla?

  1. En el bloque finally.

    Correcto. finally se ejecuta siempre, incluso si hubo un error o un return dentro del try.

  2. Al final del bloque try.

    Si ocurre un error antes, esa línea nunca se ejecuta y el botón queda desactivado para siempre.

  3. En el bloque catch.

    Solo se ejecutaría cuando hay un error; si todo sale bien, el botón seguiría desactivado.

  4. Justo después de llamar a fetch, sin await.

    Se reactivaría antes de que llegue la respuesta, y la persona podría lanzar la misma búsqueda muchas veces.

Glosario

Síncrono
Forma de ejecutar en la que cada instrucción espera a que termine la anterior.
Asíncrono
Forma de ejecutar en la que una tarea que tarda se empieza, el programa sigue con otras cosas y continúa con el resultado cuando llega.
Hilo (thread)
Una línea de trabajo que ejecuta instrucciones de una en una. JavaScript ejecuta tu código en un solo hilo.
Bucle de eventos (event loop)
Mecanismo que, cada vez que JavaScript queda libre, toma la siguiente tarea lista de la cola y la ejecuta.
Cola de tareas
Lista de funciones que ya pueden ejecutarse (un temporizador que terminó, una respuesta que llegó) y esperan su turno.
Callback hell
Código con muchos callbacks asíncronos anidados, que crece hacia la derecha y es difícil de leer y de mantener. También se llama «pirámide de la perdición».
Promesa (Promise)
Objeto que representa un resultado que todavía no existe: puede estar pendiente, cumplida (con un valor) o rechazada (con un error).
Promesa establecida (settled)
Promesa que ya está cumplida o rechazada. A partir de ese momento no cambia nunca.
Ejecutor
La función que se le pasa a new Promise. Se ejecuta enseguida y recibe resolve y reject para cumplir o rechazar la promesa.
then, catch y finally
Métodos de una promesa: then recibe el valor si se cumple, catch el error si se rechaza, y finally se ejecuta en los dos casos.
async
Palabra que, delante de una función, hace que siempre devuelva una promesa y permite usar await dentro.
await
Palabra que pausa una función async hasta que una promesa se establece; entrega su valor o lanza su error.
Promise.all
Combina varias promesas en una que se cumple cuando todas se cumplen (con un array de valores) y se rechaza si alguna falla.
Promise.race
Combina varias promesas en una que se establece igual que la primera que termina. Se usa para tiempos límite.
API
Conjunto de reglas que define cómo un programa puede pedirle cosas a otro. Las APIs HTTP se usan a través de internet con peticiones HTTP.
API REST
API HTTP organizada en recursos con su propia URL, que usa los métodos HTTP (GET, POST, PUT, PATCH, DELETE) como verbos y responde casi siempre con JSON.
Endpoint
Cada dirección concreta de una API que ofrece un servicio, como /search/shows.
Parámetro de consulta
Par nombre=valor que va después del ? en una URL para afinar la petición, como ?q=arcane.
fetch
Función del navegador y de Node.js para hacer peticiones HTTP. Devuelve una promesa que se cumple con un objeto Response.
response.ok
Propiedad de una respuesta de fetch que vale true si el código de estado está entre 200 y 299.
AbortController
Objeto que permite cancelar una petición de fetch: se le pasa su signal a fetch y se llama a abort().
Tiempo límite (timeout)
Máximo de tiempo que se espera una respuesta antes de abandonarla. Con fetch se pone con AbortSignal.timeout(ms).
Límite de uso (rate limit)
Cantidad máxima de peticiones que una API acepta en un tiempo dado. Si lo superas, suele responder 429.
Clave de API (API key)
Código que identifica a quien usa una API. Las claves secretas nunca van en el código del navegador.
Condición de carrera
Error que aparece cuando el resultado depende del orden en que terminan tareas que van a la vez, por ejemplo respuestas que llegan desordenadas.
