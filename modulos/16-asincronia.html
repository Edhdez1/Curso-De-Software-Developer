Síncrono y asíncrono: esperar sin congelarse

Abres una app del clima. Antes de mostrarte nada, la app le pide el pronóstico a un servidor. La respuesta puede tardar 50 milisegundos con buena conexión o 5 segundos en el metro. ¿Qué hace el programa mientras tanto? Si se quedara quieto esperando, no podrías desplazarte, ni tocar un botón, ni ver siquiera un mensaje de «Cargando…». La pantalla estaría congelada.

Hay dos maneras de hacer una tarea que tarda:

  • Síncrona (en inglés, synchronous): cada instrucción espera a que termine la anterior. Es lo que has hecho hasta ahora: línea 1, línea 2, línea 3, y nadie empieza hasta que el de adelante acaba.
  • Asíncrona (asynchronous): empiezas una tarea que tarda, sigues con otras cosas y, cuando la tarea termina, alguien te avisa para que continúes con el resultado.

Para entenderlo

Piensa en dos cafeterías. En la primera, la cajera toma tu pedido y se queda inmóvil mirando la cafetera hasta que tu café está listo; la fila entera espera. En la segunda, la cajera te da un localizador (ese aparatito que vibra), atiende a la siguiente persona y, cuando tu café está listo, el aparato vibra y vas a buscarlo. La segunda cafetería es asíncrona. En JavaScript, la cajera es tu programa y las baristas son el navegador, que se encarga de las esperas. El límite de la analogía: en JavaScript solo hay una cajera. Si se pone a hacer una cuenta larguísima, nadie atiende los localizadores que vibran hasta que termine.

Ya usaste operaciones asíncronas sin llamarlas así. En la Estación 15, addEventListener("click", funcion) no ejecutaba la función en ese momento: la dejaba anotada para cuando alguien hiciera clic. Y setTimeout(funcion, 1000) la dejaba programada para dentro de un segundo. En las dos, tu código sigue de largo y la función se ejecuta después. Lo mismo pasa con pedir datos a internet, leer archivos en Node.js o esperar a que cargue una imagen.

Antes de ejecutar este programa, predice en qué orden salen los tres mensajes. Escríbelo en un papel.

Sale 1, 3 y, un segundo después, 2. setTimeout no pausa el programa: deja la función programada y el programa sigue enseguida con la línea siguiente. Ahora el caso que sorprende a casi todo el mundo: ¿y si el tiempo es 0?

Sale A, C, B. Aunque el tiempo sea 0, la función de setTimeout no puede colarse en medio de tu código: espera a que termine todo lo que está en marcha. Para entender por qué, hay que mirar cómo organiza JavaScript su trabajo.

Por qué JavaScript no se bloquea

JavaScript ejecuta tu código en un solo hilo (en inglés, thread): una única línea de trabajo que hace una cosa a la vez. Entonces, ¿cómo puede esperar la respuesta de un servidor y a la vez responder a tus clics? El truco es que JavaScript no espera. Las esperas las hace el entorno donde corre tu código: el navegador o Node.js. Cuando una espera termina, el entorno deja la función que tenía que ejecutarse en una cola de tareas. Y un mecanismo llamado bucle de eventos (event loop) se encarga de que, cada vez que JavaScript queda libre, tome la siguiente tarea de la cola y la ejecute.

Con este modelo se explica el misterio del 0: aunque el temporizador termine en el acto, la función va a la cola y solo sale de ahí cuando JavaScript acaba el código que estaba ejecutando. El tiempo de setTimeout es un mínimo, no una cita exacta: si JavaScript está ocupado, la tarea espera su turno en la cola.

Esto es una versión simplificada

El bucle de eventos real tiene más piezas: una pila de llamadas, varias colas y una cola especial y prioritaria para las promesas (la de microtareas). Para esta estación basta con la idea de «una cosa a la vez, y lo que está listo espera su turno en una cola». Lo verás a fondo, con ejercicios de «predice el orden», en la Estación 22: Cómo se ejecuta el código.

Bloquear o no bloquear

Si solo hay un hilo, ¿qué pasa si lo ocupas con algo largo? Este taller tiene un contador que sube diez veces por segundo y dos botones que «esperan» 2 segundos de formas distintas. El primero espera con un bucle que da vueltas mirando el reloj (síncrono). El segundo usa setTimeout (asíncrono). Pulsa cada botón y, mientras espera, intenta escribir en el cuadro de texto.

Con el primer botón, el contador se detiene, no puedes escribir y ni siquiera llega a verse el mensaje «Bloqueando…»: la página solo se vuelve a dibujar cuando JavaScript queda libre, y el bucle no lo suelta hasta el final. Es posible que la página entera del curso se quede quieta esos 2 segundos; es lo esperado. Con el segundo botón, todo sigue funcionando mientras pasa el tiempo.

Idea clave

Asíncrono no significa «más rápido» ni «en paralelo». Tu código sigue ejecutándose de a una cosa por vez. Lo que ganas es que las esperas (la red, un temporizador, un archivo) no ocupan el hilo, así que la página sigue respondiendo mientras tanto.

Error común

Creer que setTimeout(funcion, 1000) «pausa el programa un segundo». No pausa nada: programa la función y sigue. Si necesitas que algo ocurra después de la espera, ese algo tiene que ir dentro de la función que le pasas, o, como verás pronto, después de un await.

Callbacks y el «callback hell»

Un callback es una función que le pasas a otra función para que la llame más tarde. Lo viste en la Estación 10. Algunos callbacks se llaman enseguida, como el de map o filter. Otros se llaman cuando termina una espera: son los callbacks asíncronos, como el de setTimeout o el de addEventListener. Durante años fueron la única forma de trabajar con operaciones que tardan.

Cuando algo sale mal

Una petición puede fallar: no hay conexión, el usuario no existe… Con callbacks, la costumbre más extendida (la usa Node.js en sus funciones clásicas) es el callback con error primero: el primer parámetro del callback es el error, o null si todo fue bien, y el segundo son los datos.

function pedirUsuario(id, callback) {
  setTimeout(() => {
    if (id <= 0) {
      callback(new Error("Id no válido"), null);
    } else {
      callback(null, { id: id, nombre: "Ana" });
    }
  }, 500);
}

pedirUsuario(-1, (error, usuario) => {
  if (error) {
    console.log("Falló: " + error.message);
    return;
  }
  console.log("Llegó: " + usuario.nombre);
});

El problema aparece cuando una espera depende de otra. Funciona, pero fíjate en la forma: cada paso empuja el código un nivel más a la derecha. A esto se le llama callback hell («el infierno de los callbacks») o pirámide de la perdición (pyramid of doom). Tiene problemas reales:

  • Se lee mal. Con diez pasos, el código se sale de la pantalla y cuesta seguir qué cierra cada llave.
  • El manejo de errores se repite en cada nivel. Si olvidas uno, el error desaparece en silencio.
  • Hacer cosas a la vez es difícil. Si quisieras pedir el perfil y las noticias al mismo tiempo y seguir cuando lleguen las dos, tendrías que contar a mano cuántas respuestas llegaron.
  • Pierdes el control. Entregas tu función a otro código y confías en que la llame exactamente una vez. Si por un error la llama dos veces, o nunca, tu programa falla de formas difíciles de rastrear.

Así queda el mismo proceso con las herramientas que vas a aprender en las próximas dos secciones. Todavía no hace falta que entiendas cada palabra, solo compara la forma:

Callbacks anidados

iniciarSesion("ana", "1234", (e, sesion) => {

    pedirPartidas(perfil.id, (e, partidas) => {
      pedirPuntuacion(partidas[0].id, (e, puntos) => {
        console.log(puntos);
      });
    });
  });
});

Promesas con async/await

const sesion = await iniciarSesion("ana", "1234");
const perfil = await pedirPerfil(sesion.token);
const partidas = await pedirPartidas(perfil.id);
const puntos = await pedirPuntuacion(partidas[0].id);
console.log(puntos);

Mismo orden de pasos, pero se lee de arriba abajo, como el código síncrono de siempre.

Los callbacks no son malos

Los callbacks siguen en todas partes y están bien usados: addEventListener, map, filter, setTimeout. El problema es solo encadenar muchas esperas que dependen unas de otras. Para eso se inventaron las promesas.

Promesas

Una promesa (en inglés, promise) es un objeto que representa un resultado que todavía no existe: algo que llegará más adelante, o que fallará. En lugar de recibir un callback, una función asíncrona moderna te devuelve una promesa al instante, y tú decides qué hacer cuando se cumpla.

Para entenderlo

Una promesa es como el ticket que te dan al dejar tu bicicleta en el taller. El ticket no es la bicicleta arreglada: es la garantía de que, cuando termine el trabajo, te van a avisar, con la bici lista o con la noticia de que no tenía arreglo. Mientras tanto, puedes irte a hacer otras cosas con el ticket en el bolsillo. El límite de la analogía: un taller siempre acaba llamando, pero una promesa puede quedarse pendiente para siempre si el código que debía cumplirla nunca lo hace. Por eso existen los tiempos límite, que verás más adelante.

Una promesa siempre está en uno de tres estados:

EstadoEn inglésQué significa
PendientependingLa operación sigue en marcha. Todavía no hay resultado.
CumplidafulfilledTerminó bien. La promesa guarda un valor: los datos que pediste.
RechazadarejectedTerminó mal. La promesa guarda un motivo, normalmente un objeto Error.

Cuando una promesa está cumplida o rechazada se dice que está establecida (settled), y a partir de ahí ya no cambia nunca. En la documentación también verás la palabra resolved («resuelta»). A veces se usa como sinónimo de «cumplida», pero técnicamente significa algo más sutil; para empezar, quédate con pendiente, cumplida y rechazada.

Usar una promesa: then, catch y finally

Una promesa tiene tres métodos para decir qué hacer cuando termine:

  • promesa.then(funcion): la función recibe el valor cuando la promesa se cumple.
  • promesa.catch(funcion): la función recibe el error si la promesa se rechaza.
  • promesa.finally(funcion): la función se ejecuta en los dos casos y no recibe nada. Es el lugar ideal para «limpiar»: ocultar un mensaje de «Cargando…» o reactivar un botón.

Crear una promesa

Para crear tu propia promesa usas new Promise(...) y le pasas una función que recibe dos funciones: resolve (llámala con el valor cuando todo salga bien) y reject (llámala con un error cuando algo falle). Esa función que le pasas se llama ejecutor (executor). Predice qué imprime este programa y después ejecútalo:

Tres reglas para crear promesas:

  • Llama a resolve o a reject una sola vez. Las llamadas siguientes se ignoran, porque una promesa establecida ya no cambia.
  • Rechaza con objetos Error (reject(new Error("…"))), no con textos sueltos. Así tienes el mensaje en error.message y la pila de llamadas para depurar, como viste en la Estación 12.
  • Si el ejecutor lanza un error con throw, la promesa se rechaza sola.

Hay dos atajos para crear promesas ya establecidas: Promise.resolve(valor) y Promise.reject(error). Y una función de tres líneas que vas a usar en toda la estación para simular esperas:

function esperar(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

esperar(1000).then(() => console.log("Pasó un segundo"));

setTimeout llama a resolve cuando pasan los milisegundos, y la promesa se cumple. Es setTimeout convertido en promesa.

Un detalle que confunde a mucha gente: el ejecutor se ejecuta enseguida, en el momento de crear la promesa. Lo que se ejecuta después es la función del then. Síguelo paso a paso:

console.log("1. Antes");
const promesa = new Promise((resolve) => {
  console.log("2. El ejecutor corre enseguida");
  resolve("pizza");
});
promesa.then((valor) => {
  console.log("4. El then recibe: " + valor);
});
console.log("3. Después");

Encadenar promesas

Aquí está la magia que desarma la pirámide. then devuelve una promesa nueva, así que puedes poner otro then detrás, y otro, formando una cadena. Tres reglas lo explican todo:

  1. Lo que devuelves (return) dentro de un then se convierte en el valor que recibe el then siguiente.
  2. Si devuelves una promesa, la cadena espera a que se cumpla y pasa su valor al siguiente then.
  3. Si algo falla (un throw o una promesa rechazada), la cadena salta directamente al siguiente catch, sin ejecutar los then que hay en medio. Funciona como el try/catch que ya conoces.

Error común

Olvidar el return dentro de un then con llaves es el error más común con promesas. Sin return, la función devuelve undefined, la cadena no espera a la petición y el siguiente then recibe undefined. Las flechas sin llaves, como (sesion) => pedirPerfil(sesion.token), devuelven su valor automáticamente. El segundo error más común es meter un then dentro de otro then: vuelves a construir la pirámide. Devuelve la promesa y sigue la cadena desde fuera.

Consejo de oficio

Termina siempre una cadena con catch. Una promesa rechazada que nadie atiende produce un error «Uncaught (in promise)» en la consola del navegador y, en Node.js (desde la versión 15), detiene el programa entero. Los equipos profesionales configuran herramientas que avisan cuando una promesa queda sin manejar.

async y await: código asíncrono que se lee de arriba abajo

Las cadenas de then son mucho mejores que la pirámide, pero siguen llenas de funciones dentro de funciones. En 2017, JavaScript añadió dos palabras que permiten escribir código asíncrono con el mismo aspecto que el código síncrono de siempre: async y await. No reemplazan a las promesas: funcionan con promesas, por debajo todo sigue siendo lo mismo.

Tres reglas:

  1. async delante de una función hace que siempre devuelva una promesa. Si la función hace return 5, quien la llama recibe una promesa que se cumple con 5. Si la función lanza un error con throw, la promesa se rechaza.
  2. await delante de una promesa pausa esa función hasta que la promesa se establezca. Si se cumple, await te entrega el valor. Si se rechaza, await lanza el error en esa misma línea, como un throw, así que lo atrapas con try/catch.
  3. await solo se puede usar dentro de funciones async, o en el nivel superior de un módulo (lo verás en la Estación 22) y en la consola del navegador. En los talleres de este curso también puedes usarlo fuera de funciones, porque el taller envuelve tu código en una función async por ti.

Así queda la historia de la sesión y las puntuaciones. Las funciones simuladas también están escritas con async: fíjate en que pueden hacer return de un valor o throw de un error, como cualquier función.

await no congela el programa: pausa solo la función donde está escrito. Mientras esa función espera, JavaScript queda libre para todo lo demás (clics, animaciones, otras funciones). Cuando la promesa se establece, la función continúa justo donde se quedó.

Los errores más comunes con async y await

1. Olvidar el await. Sin await no recibes los datos, sino la promesa. Y una promesa no tiene la propiedad que buscas, así que obtienes undefined:

const perfil = pedirPerfil();   // falta await
console.log(perfil);            // Promise { <pending> }
console.log(perfil.nombre);     // undefined

Cuando veas Promise { <pending> } o un undefined inesperado cerca de código asíncrono, busca primero un await que falta.

2. Usar await fuera de una función async. El navegador responde con un error de sintaxis parecido a SyntaxError: await is only valid in async functions and the top level bodies of modules. La solución es añadir async a la función que contiene el await.

3. Olvidar que una función async devuelve una promesa. Si calcularTotal es async, const total = calcularTotal(); guarda una promesa, no un número. Lo asíncrono «contagia»: todo lo que necesita un resultado asíncrono también tiene que esperar (con await o con then).

4. Usar await dentro de forEach. forEach llama a tu función para cada elemento, pero no espera a que termine, aunque sea async. Ejecuta este taller y mira qué mensaje sale primero:

¿then o await?

El código moderno usa sobre todo async/await, porque se lee mejor y el manejo de errores es el mismo try/catch de siempre. Aun así, vas a leer then en documentación, tutoriales y proyectos más antiguos, y a veces una cadena corta queda más clara con then. Las dos son promesas: aprende a leer las dos y, dentro de una misma función, elige un estilo y no los mezcles.

Varias promesas a la vez: Promise.all y Promise.race

La pantalla principal de un juego en línea necesita tu perfil, tu lista de amigos y las noticias del día. Cada petición tarda alrededor de medio segundo. Si las pides una detrás de otra con tres await, la pantalla tarda la suma de las tres. Pero ninguna depende de las otras: puedes lanzarlas todas a la vez y esperar solo lo que tarde la más lenta.

Promise.all recibe un array de promesas y devuelve una sola promesa que se cumple cuando todas se cumplen. Su valor es un array con los resultados, en el mismo orden en que pusiste las promesas (no en el orden en que llegaron). Con la desestructuración de la Estación 11 queda muy limpio:

const [perfil, amigos, noticias] = await Promise.all([
  pedirPerfil(),
  pedirAmigos(),
  pedirNoticias(),
]);

La clave está en un detalle: una operación empieza cuando llamas a la función, no cuando haces await. Al construir el array se llaman las tres funciones seguidas, así que las tres peticiones ya están en marcha antes de esperar a ninguna. Mide la diferencia:

Si una de las promesas se rechaza, Promise.all se rechaza enseguida con ese error, sin esperar a las demás (que siguen su curso, pero sus resultados se ignoran). Es lo que quieres cuando necesitas todos los datos o ninguno. Si prefieres recibir cada resultado aunque alguno falle, usa Promise.allSettled: se cumple cuando todas terminan y te da un objeto por cada una:

const resultados = await Promise.allSettled([pedirPerfil(), pedirAmigos()]);
// [
//   { status: 'fulfilled', value: 'Lyra' },
//   { status: 'rejected', reason: Error: sin conexión }
// ]
for (const r of resultados) {
  if (r.status === "fulfilled") console.log("Bien:", r.value);
  else console.log("Falló:", r.reason.message);
}

Así se ve la misma comparación en una terminal, como la verás en tu computadora cuando uses Node.js. Entra en la carpeta carga, mira los archivos con cat y ejecuta los dos con node. Fíjate en el orden en que llegan las respuestas en cada caso.

En paralelo.mjs las respuestas llegan en otro orden (la más rápida primero), pero el array que devuelve Promise.all respeta siempre el orden en que pediste las cosas.

Promise.race («carrera») se establece con la primera promesa que termine, bien o mal. Su uso más común es poner un tiempo límite (en inglés, timeout): haces competir tu petición contra una promesa que se rechaza pasado cierto tiempo.

Error común

Dos errores opuestos. El primero: encadenar await para cosas que no dependen entre sí, y hacer esperar a la persona sin motivo. El segundo: intentar lanzar a la vez cosas que sí dependen una de otra. No puedes pedir las partidas de un jugador antes de saber su identificador: ahí el orden importa y los await en serie son lo correcto.

Cuidado

«A la vez» no significa «todas las que quieras». Si lanzas cientos de peticiones juntas a una API, lo más probable es que te bloquee por superar su límite de uso (lo verás en la próxima sección). Con listas largas se piden por tandas: por ejemplo, de diez en diez.

Qué es una API y cómo se lee su documentación

Ya sabes esperar. Ahora, ¿a quién le pides los datos y cómo? Una API (del inglés Application Programming Interface, «interfaz de programación de aplicaciones») es un conjunto de reglas que dice cómo un programa puede pedirle cosas a otro: qué puedes pedir, cómo tienes que pedirlo y qué te van a responder.

Para entenderlo

Una API es como la carta de un restaurante. Te dice qué platos existen y cómo pedirlos, sin que tengas que entrar a la cocina ni saber cómo se preparan. El límite de la analogía: un camarero entiende «una de esas, pero sin cebolla»; una API no. Si escribes una letra mal o pides algo que no está en la carta, recibes un error.

Ya usaste varias APIs sin llamarlas así: el DOM (document.querySelector), localStorage y la propia console son APIs que el navegador le ofrece a tu código. En esta estación hablamos de las APIs web (o APIs HTTP): las que usas a través de internet. Tu programa envía una petición HTTP a un servidor, como las que viste en la Estación 3, y el servidor responde con datos, casi siempre en formato JSON (Estación 11).

Anatomía de una petición a una API

  • La URL base es la parte común a todas las peticiones de una API: https://api.tvmaze.com.
  • Un endpoint («punto de acceso») es cada dirección concreta que ofrece un servicio: /search/shows busca series, /shows/55138 da los datos de una serie.
  • Los parámetros de consulta (query parameters) van después del ?, en pares nombre=valor separados por &. Sirven para afinar la petición: qué buscar, cuántos resultados, en qué idioma.

Cuando el valor de un parámetro viene de lo que escribe una persona, no lo pegues a mano en la dirección: los espacios, las tildes y símbolos como & o ? tienen significado especial dentro de una URL. Deja que URL y URLSearchParams (que ya asomaron en la Estación 3) los codifiquen por ti:

API REST: recursos y verbos

Muchas APIs web siguen un estilo llamado REST (Representational State Transfer), que describió Roy Fielding en su tesis doctoral del año 2000. En la práctica, cuando alguien dice «una API REST» se refiere a una API HTTP organizada así:

  • Los datos se organizan en recursos: usuarios, publicaciones, partidas, series. Cada recurso tiene su propia URL: /posts es la colección de publicaciones y /posts/1 es la publicación número 1.
  • El método HTTP dice qué quieres hacer con el recurso. Es el verbo; la URL es el sustantivo.
  • Las respuestas usan los códigos de estado de HTTP para decir cómo fue todo, y casi siempre traen JSON.
MétodoPara quéEjemploRespuesta típica
GETLeerGET /posts/1200 y la publicación
POSTCrearPOST /posts con los datos en el cuerpo201 y lo que se creó
PUTReemplazar enteroPUT /posts/1 con la publicación completa200
PATCHCambiar una partePATCH /posts/1 con solo el título200
DELETEBorrarDELETE /posts/1200 o 204

Y los códigos de estado que más vas a ver, con lo que tu app debería hacer en cada caso:

CódigoNombreQué significa para tu app
200OKTodo bien; en el cuerpo vienen los datos.
201CreatedSe creó lo que enviaste (típico después de un POST).
204No ContentBien, pero la respuesta no trae cuerpo. No intentes leer JSON.
400Bad RequestTu petición está mal: revisa los datos que envías.
401UnauthorizedFalta identificarse (una clave o una sesión).
403ForbiddenTe identificaste, pero no tienes permiso para eso.
404Not FoundEse recurso no existe: revisa la URL o muestra «no encontrado».
429Too Many RequestsSuperaste el límite de uso: espera un poco y vuelve a intentar.

503Service UnavailableEl servidor está caído o saturado por un rato.

Los códigos 3xx (redirecciones) casi nunca los verás en tu código: el navegador sigue la redirección solo y te entrega la respuesta final.

REST en sentido estricto

REST original es un conjunto de reglas de diseño bastante exigente, y muchas APIs que se llaman «REST» no las cumplen todas. La documentación de MDN lo dice así: para empezar, puedes entender «API REST» como un servicio HTTP que se usa con herramientas web estándar. Cómo diseñar tu propia API REST lo verás en la Estación 29: Backend.

Leer la documentación de una API

Cada API es distinta, y todo lo que necesitas saber está en su documentación. Leerla bien antes de escribir código te ahorra horas. Así se lee la de TVmaze, la API de series que vas a usar en el proyecto (está en https://www.tvmaze.com/api, en inglés):

  1. URL base y endpoints. Busca la lista de servicios. Para buscar series: GET https://api.tvmaze.com/search/shows?q=texto.

  2. Autenticación. ¿Hace falta registrarse? TVmaze no pide nada para leer. Otras APIs piden una clave de API (API key): un código que te identifica y que envías en cada petición.

  3. Parámetros. Qué acepta cada endpoint y si son obligatorios. Aquí, q con el texto a buscar.

  4. Forma de la respuesta. Busca un ejemplo. TVmaze devuelve un array de objetos { score, show }, donde show tiene los datos de la serie. Si no hay resultados, devuelve un array vacío [].

  5. Límites de uso (rate limit). TVmaze permite «al menos 20 peticiones cada 10 segundos» por dirección IP; si te pasas, responde 429 y recomienda esperar y reintentar.

  6. Condiciones y licencia. Los datos de TVmaze usan la licencia CC BY-SA: puedes usarlos si enlazas a TVmaze desde tu app.

  7. Uso desde el navegador. La documentación dice que todos sus endpoints tienen CORS habilitado. Eso significa que una página web de otro dominio (la tuya) puede leer sus respuestas. Qué es CORS y por qué existe lo verás en la Estación 31: Seguridad.

Impacto

Las claves de API son como contraseñas: identifican a quien paga o responde por el uso. Todo lo que pones en el código de una página web lo puede ver cualquiera con las herramientas de desarrollo, así que una clave secreta nunca va en el código del navegador. Las APIs de esta estación no necesitan clave. Cómo se guardan los secretos en un servidor lo verás en la Estación 31.
