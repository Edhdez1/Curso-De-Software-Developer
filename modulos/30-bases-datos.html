Lo que vas a lograr

Cierra una app y vuelve a abrirla: tus mensajes, tus compras y tu progreso en el juego siguen ahí. Detrás de casi todas las aplicaciones hay una base de datos que guarda la información de forma ordenada, segura y rápida de consultar. En esta estación aprenderás a diseñarlas y a hablarles en SQL, el mismo lenguaje que usan desde una app de tareas hasta un banco.

  • Explicar qué es una base de datos y qué problemas resuelve frente a guardar todo en un archivo.
  • Leer y crear tablas con columnas, tipos, clave primaria y restricciones.
  • Consultar datos con SELECT, WHERE, ORDER BY y LIMIT, y tratar bien los valores NULL.
  • Insertar, actualizar y borrar filas sin estropear datos por accidente, protegiendo los cambios con transacciones.
  • Relacionar tablas con claves foráneas y combinarlas con INNER JOIN y LEFT JOIN.
  • Resumir datos con GROUP BY, funciones de agregación, HAVING y subconsultas.
  • Diseñar una base de datos con un diagrama entidad-relación, normalizarla hasta la tercera forma normal y decidir qué índices necesita.
  • Elegir entre SQLite, PostgreSQL, MySQL o una base de datos NoSQL según el proyecto.
  • Usar una base de datos desde Node.js con consultas parametrizadas, y saber qué son los ORMs, las migraciones y las copias de seguridad.

Por qué una base de datos

En la Estación 29 tu API guardaba los datos en un array, dentro de la memoria del servidor. Funciona hasta que el servidor se reinicia: la memoria RAM se borra al apagar, como viste en la Estación 2, y con ella todas las puntuaciones. Necesitas que los datos sobrevivan. A eso se le llama persistencia: que la información quede guardada de forma permanente, en disco.

La primera idea suele ser guardar todo en un archivo JSON: leerlo al arrancar y reescribirlo en cada cambio. Para un proyecto de fin de semana, sirve. Pero en cuanto la app tiene personas usándola de verdad aparecen cinco problemas:

  1. Dos personas a la vez. Si dos peticiones leen y reescriben el archivo al mismo tiempo, una borra el cambio de la otra.
  2. Un apagón a mitad. Si el servidor se apaga mientras escribe, el archivo queda a medias y puedes perderlo entero, no solo el último cambio.
  3. Buscar es lento. Para encontrar a una persona entre un millón tienes que leer y recorrer el archivo completo cada vez.
  4. Nadie vigila las reglas. Nada impide guardar un precio negativo o una compra de un cliente que no existe.
  5. Cada pregunta nueva es un programa nuevo. «¿Cuánto vendimos por género este mes?» te obliga a escribir bucles y acumuladores para cada consulta.

Qué es una base de datos

Una base de datos es una colección de datos organizada y guardada de forma permanente, pensada para consultarse y modificarse de forma segura. El programa que la administra se llama sistema gestor de bases de datos (SGBD; en inglés, database management system, DBMS). SQLite, PostgreSQL y MySQL son sistemas gestores. En el día a día casi todo el mundo dice «la base de datos» para las dos cosas, y aquí haremos lo mismo.

Para entenderlo

Un archivo JSON es como un cuaderno compartido sobre una mesa: cualquiera lo abre, tacha y escribe, y si dos personas escriben en la misma página a la vez, se pisan. Una base de datos es como un archivo con una bibliotecaria en el mostrador. Tú no tocas las fichas: le pides lo que quieres. Ella atiende las escrituras de una en una, anota cada cambio en un registro antes de hacerlo, encuentra una ficha entre un millón en un instante y se niega a archivar una ficha que rompe las reglas. La analogía tiene un límite: la bibliotecaria no entiende qué significan tus datos. Solo hace cumplir las reglas que tú le das.

¿Cómo sobrevive una base de datos a un apagón? Antes de cambiar nada, anota lo que va a hacer en un registro aparte. Si la luz se va a mitad, al arrancar lee ese registro y deshace o termina el cambio, de modo que nunca queda a medias. SQLite llama a ese registro diario (en inglés, journal) y PostgreSQL, registro de escritura anticipada (write-ahead log, WAL). Tú no tienes que programarlo: viene incluido.

Idea clave

Una base de datos no solo guarda: garantiza. Garantiza que dos cambios simultáneos no se pisan, que un apagón no deja datos a medias y que nada que rompa tus reglas entra. Programar esas garantías a mano sobre archivos es dificilísimo; por eso casi nadie lo hace.

¿Y cuándo basta con un archivo?

No todo necesita una base de datos. Un archivo sigue siendo la mejor opción para la configuración de un programa, para exportar datos que otra persona va a abrir en una hoja de cálculo o para la partida guardada de un juego de un solo jugador, donde solo un programa escribe y nunca a la vez. La pregunta útil es: ¿varias personas o procesos van a escribir a la vez, o voy a necesitar buscar y combinar datos de muchas formas? Si la respuesta es sí, usa una base de datos.

Consejo de oficio

La documentación de SQLite lo resume con una frase famosa: SQLite no compite con las bases de datos cliente-servidor, compite con fopen(), la función con la que un programa en C abre un archivo. Muchas aplicaciones usan SQLite como un «archivo con superpoderes»: Android e iOS la incluyen, y navegadores como Firefox y Chrome guardan en ella tu historial. Si tu juego necesita guardar muchas cosas y buscarlas, SQLite puede ser tu formato de partida guardada.

El lenguaje: SQL

La familia de bases de datos más usada es la relacional: guarda los datos en tablas y se consulta con SQL (de Structured Query Language, «lenguaje de consultas estructurado»; se pronuncia «ese-cu-ele» o, a la inglesa, «sícuel»). Nació en IBM en los años setenta y es un estándar internacional desde 1986; la edición más reciente es SQL:2023. Hay otras familias, que se agrupan bajo el nombre NoSQL; las verás en la sección SQLite, PostgreSQL y NoSQL.

En la Estación 21 viste que SQL es declarativo: describes qué datos quieres y la base de datos decide cómo buscarlos. No escribes bucles. Cada motor habla su propio dialecto, con pequeñas diferencias, pero lo básico es igual en todos. En esta estación usarás el de SQLite, y te avisaremos cuando algo cambie en PostgreSQL o MySQL.

Tres convenciones que verás en todos los ejemplos:

  • Las palabras del lenguaje (SELECT, FROM, WHERE) se escriben en MAYÚSCULAS por costumbre, para distinguirlas de tus nombres. SQL no distingue mayúsculas en ellas: select también funciona.
  • Cada instrucción termina en punto y coma (;). Una instrucción puede ocupar varias líneas.
  • Los comentarios empiezan con dos guiones: -- esto no se ejecuta.

Tablas, tipos y claves

En 1970, Edgar F. Codd, un matemático que trabajaba en IBM, publicó un artículo que cambió la informática: proponía organizar los datos en tablas y consultarlos con operaciones matemáticas bien definidas, sin que el programa tuviera que saber cómo estaban guardados en el disco. Es el modelo relacional, y más de cincuenta años después sigue siendo la forma más común de guardar datos. Cada tabla guarda un tipo de cosa: una tabla de juegos, otra de clientes, otra de compras.

Estas son las piezas, con los nombres que vas a leer en todas partes:

  • Una fila (en inglés, row; también se dice registro) es una cosa concreta: un juego, un cliente, una compra.
  • Una columna (en inglés, column; también se dice campo) es una propiedad que tienen todas las filas: el título, el precio. Tiene un nombre y un tipo.
  • El esquema (en inglés, schema) es la descripción de las tablas: qué columnas tienen, de qué tipo y con qué reglas. Es el plano de tu base de datos.

Si vienes de la Estación 11, cada fila es como un objeto { id: 1, titulo: "Bosque Eterno", … } y la tabla es como un array de esos objetos, con una diferencia importante: en una tabla todas las filas tienen exactamente las mismas columnas.

Para entenderlo

Una tabla se parece a una hoja de cálculo, y la comparación sirve para empezar. Pero falla en dos puntos. En una hoja de cálculo puedes escribir cualquier cosa en cualquier celda; en una tabla, cada columna tiene un tipo y unas reglas que la base de datos hace cumplir. Y las filas de una tabla no tienen un orden fijo: si quieres verlas ordenadas, lo pides en cada consulta.

Crear una tabla

La instrucción CREATE TABLE define una tabla nueva: su nombre, sus columnas y las reglas de cada una.

CREATE TABLE juegos (
  id     INTEGER PRIMARY KEY,               -- número que identifica cada juego
  titulo TEXT NOT NULL,                     -- texto obligatorio
  genero TEXT,                              -- texto opcional
  precio REAL NOT NULL CHECK (precio >= 0), -- decimal, obligatorio, nunca negativo
  anio   INTEGER                            -- año de salida, opcional
);

Cada línea dentro de los paréntesis es una columna: primero el nombre, después el tipo y, al final, las restricciones. Los nombres suelen escribirse en minúsculas, sin tildes ni espacios, con guion bajo para separar palabras (precio_pagado). Esa forma se llama snake_case. La columna se llama anio y no año porque la ñ y las tildes funcionan en muchos motores, pero dan problemas en algunas herramientas; es más seguro evitarlas en los nombres, aunque sí puedes usarlas dentro de los datos.

En esta estación los precios son redondos para que los ejemplos se lean fácil.

La clave primaria

La clave primaria (en inglés, primary key) es la columna cuyo valor identifica cada fila: no puede repetirse y no puede faltar. ¿Por qué no usar el nombre? Porque dos clientas pueden llamarse Ana. ¿Y el correo? Porque la gente cambia de correo, y entonces habría que cambiarlo en todas partes. Lo habitual es añadir una columna id con un número que no significa nada más: una clave sustituta (en inglés, surrogate key). Una clave que sí tiene significado, como un DNI, se llama clave natural.

En SQLite, una columna INTEGER PRIMARY KEY se numera sola: si insertas una fila sin id, recibe el siguiente número libre. Cada motor lo escribe a su manera:

-- SQLite
id INTEGER PRIMARY KEY
-- PostgreSQL (forma moderna; en tutoriales antiguos verás SERIAL)
id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY
-- MySQL
id INT AUTO_INCREMENT PRIMARY KEY

¿Y AUTOINCREMENT?

En tutoriales de SQLite verás INTEGER PRIMARY KEY AUTOINCREMENT. No hace falta para que el número se ponga solo: solo impide reutilizar los números de filas borradas. La documentación de SQLite recomienda no usarlo si no lo necesitas, porque gasta más recursos.

Una restricción (en inglés, constraint) es una regla que la base de datos comprueba en cada inserción y en cada cambio. Si una fila la rompe, la operación entera se rechaza con un error.

Insertar filas

Con INSERT INTO añades filas. Primero nombras las columnas que vas a rellenar y después, en VALUES, los valores en el mismo orden. Puedes insertar varias filas en una sola instrucción separándolas con comas:

INSERT INTO juegos (titulo, genero, precio, anio)

Confiar en que SQLite comprueba los tipos. Sin STRICT, una columna INTEGER acepta 'treinta' y el error aparece mucho después, cuando una suma da un resultado raro. En proyectos nuevos con SQLite, usa tablas STRICT o valida los datos antes de guardarlos. PostgreSQL y MySQL, en su configuración habitual, rechazan el valor desde el principio.

Consultar con SELECT

En casi todas las apps se lee mucho más de lo que se escribe: una tienda muestra su catálogo miles de veces por cada juego nuevo que añade. Por eso la instrucción que más vas a escribir es SELECT («seleccionar»). Su forma general, con las partes opcionales entre corchetes, es:

SELECT columnas
FROM tabla
[WHERE condición]

Elegir columnas

Después de SELECT escribes las columnas que quieres, separadas por comas. También puedes calcular columnas nuevas y ponerles un nombre con AS, que se llama alias:

SELECT titulo, precio FROM juegos;                      -- solo dos columnas
SELECT titulo, precio * 0.8 AS rebajado FROM juegos;    -- columna calculada: 20 % menos
SELECT titulo || ' (' || anio || ')' AS ficha FROM juegos; -- une textos: Bosque Eterno (2021)
SELECT DISTINCT genero FROM juegos;                     -- cada género una sola vez

En SQL los textos se unen con ||, no con +. Y DISTINCT quita las filas repetidas del resultado: «rpg» aparece dos veces en la tabla, pero una sola en la respuesta. Las columnas calculadas no cambian nada en la tabla: solo existen en la respuesta.

Consejo de oficio

SELECT * es cómodo para explorar, pero en el código de una app escribe las columnas que necesitas. Traes menos datos por la red, y si mañana alguien añade a la tabla una columna enorme (una imagen, un texto largo) o una columna privada, tu programa no la recibirá sin querer.

Mayúsculas y tildes en los textos

En SQLite, = distingue mayúsculas: 'rpg' no es igual a 'RPG'. LIKE no las distingue, pero solo para las letras sin tilde del alfabeto inglés: 'Ábaco' LIKE 'á%' es falso. En PostgreSQL, LIKE sí distingue mayúsculas y existe ILIKE para ignorarlas. Cuando busques nombres escritos por personas, guarda o compara todo en minúsculas, y comprueba cómo trata tu motor las tildes.

Error común

Usar comillas dobles para los textos. En SQL, las comillas simples son para textos ('rpg') y las dobles, para nombres de columnas o tablas ("genero"). SQLite, por compatibilidad, acepta "rpg" como texto si no hay una columna con ese nombre, así que parece funcionar. Pero WHERE genero = "genero" compara la columna consigo misma y devuelve todas las filas, sin error. PostgreSQL rechaza "rpg" diciendo que esa columna no existe. Acostúmbrate a las simples.

Ordenar y limitar

ORDER BY ordena el resultado por una o varias columnas: de menor a mayor por defecto (ASC, ascendente) o de mayor a menor con DESC (descendente). LIMIT se queda con las primeras filas y OFFSET se salta unas cuantas antes de empezar. Con los dos juntos se hace la paginación: mostrar los resultados de 10 en 10, como las páginas de una tienda.

SELECT titulo, precio FROM juegos ORDER BY precio DESC;          -- del más caro al más barato
SELECT titulo, genero, precio FROM juegos ORDER BY genero, precio; -- por género y, dentro de cada género, por precio
SELECT titulo FROM juegos ORDER BY titulo LIMIT 3;                -- los 3 primeros por orden alfabético
SELECT titulo FROM juegos ORDER BY titulo LIMIT 3 OFFSET 3;       -- la «página 2»: del 4.º al 6.º

Haz tres cambios, ejecutando después de cada uno: muestra los 3 más baratos; después la segunda página de 3 (añade OFFSET 3); por último, los 4 juegos más recientes, usando la columna anio.

Sin ORDER BY no hay orden

Si no escribes ORDER BY, la base de datos devuelve las filas en el orden que le resulte más cómodo. Hoy puede coincidir con el orden en que las insertaste y mañana, tras un cambio interno, no. Un LIMIT sin ORDER BY te da «unas filas cualesquiera». Si el orden importa, pídelo siempre.

NULL: el valor que no es un valor

NULL significa «no se sabe» o «no hay dato». No es cero ni un texto vacío: un cliente con el correo vacío ('') te dio un correo en blanco; un cliente con el correo NULL no te lo dio. Y aquí viene la trampa: cualquier comparación con algo desconocido da como resultado «desconocido». ¿Es un correo desconocido igual a otro correo desconocido? No se sabe. Por eso email = NULL nunca es verdadero, ni siquiera cuando el correo es NULL, y WHERE solo deja pasar las filas cuya condición es verdadera.

NULL también se contagia en los cálculos: 5 + NULL es NULL, y 'Hola ' || NULL también. Tiene sentido: si no sabes cuánto vale algo, tampoco sabes cuánto vale ese algo más 5. Al ordenar, SQLite y MySQL ponen los NULL al principio en orden ascendente y PostgreSQL, al final. Si te importa, dilo tú: ORDER BY email NULLS LAST funciona en SQLite y en PostgreSQL.

Consejo de oficio

Decide columna por columna si un dato puede faltar. Si no puede, márcala NOT NULL desde el principio: cada columna que admite NULL es una pregunta más que tendrás que responder en cada consulta y en cada línea de código que lea ese dato.

Cambiar datos con cuidado

Ya sabes crear filas y leerlas. Cambiarlas y borrarlas es igual de fácil, y justo por eso es peligroso: una sola línea puede modificar un millón de filas, y la base de datos no pregunta «¿estás seguro?». En esta sección aprenderás las dos instrucciones y las redes de seguridad que usan los equipos profesionales.

UPDATE: cambiar filas

UPDATE cambia los valores de las filas que cumplen el WHERE. En SET escribes qué columnas cambian y su valor nuevo, que puede calcularse a partir del actual:

-- Cambiar dos columnas de un juego concreto
UPDATE juegos
SET precio = 18, genero = 'aventura'
WHERE id = 1;

-- Rebajar un 10 % todos los juegos de rol
UPDATE juegos
SET precio = precio * 0.9
WHERE genero = 'rpg';

DELETE: borrar filas

DELETE FROM borra las filas que cumplen el WHERE. No hay papelera de reciclaje: lo borrado desaparece.

DELETE FROM juegos WHERE id = 8;

Error común

Olvidar el WHERE. UPDATE juegos SET precio = 0; pone gratis todos los juegos, y DELETE FROM clientes; borra a todos los clientes. No es un error de sintaxis, así que la base de datos lo ejecuta sin rechistar. Es uno de los accidentes más famosos del oficio: casi toda persona que trabaja con bases de datos tiene una historia sobre él.

Primero SELECT, después UPDATE

Antes de un UPDATE o un DELETE importante, escribe la misma consulta como SELECT con el mismo WHERE. Mira qué filas salen y cuántas son. Solo cuando coincidan con lo que esperas, cambia la primera línea. Además, muchas apps no borran de verdad: añaden una columna borrado_en con la fecha, y las consultas filtran WHERE borrado_en IS NULL. Esto se llama borrado lógico (en inglés, soft delete) y permite deshacer errores y conservar el historial.

SQLite (desde la versión 3.35) y PostgreSQL permiten añadir RETURNING al final de un INSERT, UPDATE o DELETE para que te devuelva las filas afectadas, ya cambiadas. MySQL no lo tiene. Es muy útil desde una API: insertas un juego y en la misma orden recibes el id que le tocó.

En este taller vas a practicar el método completo. COUNT(*) cuenta filas; lo verás a fondo en la sección Agrupar y resumir.

Ahora provoca el accidente a propósito, aquí donde no hace daño: en el paso 2, borra la línea WHERE genero = 'rpg' y ejecuta. RETURNING te enseña las ocho filas rebajadas. En una tienda real, acabas de bajar el precio de todo el catálogo.

Transacciones: todo o nada

Algunos cambios solo tienen sentido juntos. En un juego, Ana le pasa 50 monedas a Leo: hay que restarle 50 a ella y sumárselas a él. Si el servidor se cae entre las dos órdenes, las monedas desaparecen. Una transacción es un grupo de operaciones que la base de datos trata como una sola: o se aplican todas, o ninguna.

  • BEGIN empieza la transacción.
  • COMMIT («confirmar») aplica todos los cambios a la vez, de forma definitiva.
  • ROLLBACK («volver atrás») los descarta todos, como si nunca hubieran ocurrido.

El «borrador» es una forma de imaginarlo. Por dentro, cada motor lo hace a su manera, con el diario o el registro de escritura anticipada que viste al principio de la estación, pero el efecto es el de la animación. Pruébalo. Predice qué mostrarán las dos consultas SELECT:

Después cambia los dos 50 por 150: Ana no tiene tanto, y la restricción CHECK (monedas >= 0) detiene la operación con un error.

Si algo falla dentro, tú decides

Cuando una orden falla dentro de una transacción, la base de datos rechaza esa orden, pero la transacción sigue abierta esperando tu decisión. En SQLite podrías seguir y confirmar el resto; PostgreSQL ya no acepta nada más que ROLLBACK. La regla segura, en cualquier motor, es que tu programa haga ROLLBACK en cuanto algo falle. Verás cómo se escribe en código en la sección Desde tu código.

Cuando no escribes BEGIN, cada instrucción suelta funciona como una transacción de una sola orden: se confirma sola al terminar. Por eso un UPDATE que cambia mil filas nunca se queda a medias: o cambian las mil, o ninguna.

ACID: las cuatro garantías

Las transacciones de las bases de datos relacionales cumplen cuatro propiedades que se conocen por sus iniciales en inglés, ACID:

LetraPropiedadQué garantizaEn la transferencia
AAtomicidadTodo o nada: la transacción no se divideNunca se resta a Ana sin sumar a Leo
CConsistenciaSe pasa de un estado válido a otro válido: todas las restricciones se cumplen al terminarEl CHECK impide saldos negativos

El aislamiento tiene grados. Aislar por completo cada transacción es lo más seguro pero obliga a esperar más, así que los motores ofrecen varios niveles de aislamiento y cada uno elige uno por defecto: PostgreSQL usa read committed (cada orden ve lo que ya estaba confirmado cuando empezó) y SQLite deja escribir a una sola transacción a la vez. Para empezar, los valores por defecto son razonables; cuando trabajes con dinero o inventarios, lee la documentación de tu motor sobre este tema.

La actualización perdida puede volver

Una base de datos no te protege si tu programa lee un valor, lo calcula en JavaScript y escribe el resultado: const n = leerVisitas(); guardarVisitas(n + 1); tiene el mismo problema que el archivo del principio, porque entre la lectura y la escritura otra petición puede colarse. Relacionar tablas: claves foráneas y JOIN

La tienda necesita guardar las compras: quién compró qué juego, cuándo y por cuánto. La primera idea es una tabla con todo junto: el nombre y el correo del cliente, el título del juego, la fecha. Pero si Ana compra diez juegos, su nombre y su correo se repiten diez veces. Si cambia de correo, hay que cambiarlo en diez filas, y si se te olvida una, la base de datos tendrá dos correos distintos para la misma persona.

La solución relacional es guardar cada cosa una sola vez, en su tabla, y conectar las tablas con números. Cada compra no guarda el nombre de la clienta: guarda su id. Una clave foránea (en inglés, foreign key) es una columna cuyo valor debe existir como clave primaria en otra tabla. Se declara con REFERENCES:

CREATE TABLE compras (
  id            INTEGER PRIMARY KEY,
  cliente_id    INTEGER NOT NULL REFERENCES clientes(id),
  juego_id      INTEGER NOT NULL REFERENCES juegos(id),
  fecha         TEXT NOT NULL,
  precio_pagado REAL NOT NULL
);

Con esa declaración, la base de datos rechaza una compra de un cliente que no existe y, si alguien intenta borrar a un cliente que tiene compras, también se niega. Así nunca quedan filas huérfanas: compras que apuntan a nadie.

¿No es repetir el precio?

precio_pagado parece una copia de juegos.precio, pero no lo es: es otro dato. El precio del catálogo cambia con las rebajas; lo que pagó Ana el 1 de septiembre no debe cambiar nunca. Antes de eliminar una columna «repetida», pregúntate si guarda lo mismo o un hecho distinto.

Tipos de relaciones

La cardinalidad de una relación dice cuántas filas de una tabla pueden conectarse con cuántas de la otra. Hay tres casos:

RelaciónSe leeEjemploCómo se guarda
Uno a uno (1:1)Cada A tiene como mucho un BUna cuenta y su perfilClave foránea con UNIQUE, o todo en la misma tabla
Uno a muchos (1:N)Cada A tiene muchos B; cada B es de un solo AUn cliente y sus comprasClave foránea en el lado «muchos»: compras.cliente_id
Muchos a muchos (N:M)Cada A tiene muchos B y cada B, muchos AClientes y juegos; jugadores y logrosUna tabla intermedia con dos claves foráneas

La tabla compras es justamente la tabla intermedia entre clientes y juegos: un cliente compra muchos juegos y un juego lo compran muchos clientes. A veces la tabla intermedia no tiene datos propios, solo las dos claves. Entonces su clave primaria suele ser la pareja de columnas, una clave compuesta:

CREATE TABLE jugador_logros (
  jugador_id INTEGER NOT NULL REFERENCES jugadores(id),
  logro_id   INTEGER NOT NULL REFERENCES logros(id),
  fecha      TEXT NOT NULL,
  PRIMARY KEY (jugador_id, logro_id)   -- el mismo logro no se gana dos veces
);

Aquí SQLite vuelve a sorprender: por compatibilidad con programas antiguos, no comprueba las claves foráneas si no se lo pides. Hay que activarlas en cada conexión con PRAGMA foreign_keys = ON;. Un PRAGMA es una orden especial de SQLite para cambiar su configuración. El módulo node:sqlite de Node.js y la librería better-sqlite3 las activan por defecto; la terminal de SQLite y otras librerías no. PostgreSQL y MySQL las comprueban siempre.

Existen también RIGHT JOIN, que conserva todas las filas de la tabla de la derecha, y FULL OUTER JOIN, que conserva las de ambas. SQLite los admite desde la versión 3.39 (2022). Error común

Olvidar la condición ON. En SQL antiguo verás FROM clientes, compras WHERE clientes.id = compras.cliente_id, que funciona. Pero si se te olvida el WHERE, la base de datos combina cada cliente con cada compra: 5 clientes × 8 compras = 40 filas sin sentido. Se llama producto cartesiano, y con tablas grandes puede generar miles de millones de filas y bloquear el servidor. Si un JOIN devuelve muchas más filas de las que esperabas, revisa el ON.

Agrupar y resumir

Hasta ahora cada consulta devolvía filas de la tabla. Pero muchas preguntas piden un resumen: ¿cuánto vendimos este mes?, ¿cuál es el juego más caro?, ¿cuántas compras hizo cada cliente? En JavaScript lo harías con reduce y un objeto acumulador (Estación 11). En SQL lo hace la base de datos, con una línea.

GROUP BY: un resumen por grupo

GROUP BY reparte las filas en grupos que comparten un valor y calcula las funciones de agregación para cada grupo. El resultado tiene una fila por grupo.

Para entenderlo

Imagina que vacías una bolsa de monedas sobre la mesa y haces montones: uno de monedas de 1, otro de 5, otro de 10. Eso es GROUP BY valor. Después cuentas cada montón: eso es COUNT(*). La analogía cojea en un detalle: en la mesa ves las monedas sueltas dentro de cada montón; en SQL, después de agrupar, solo puedes pedir datos del montón entero (su valor común, cuántas hay, cuánto suman).

SELECT genero, COUNT(*) AS juegos, AVG(precio) AS precio_medio
FROM juegos
GROUP BY genero;
-- aventura | 1 | 20
-- carreras | 1 | 10
-- …
-- rpg      | 2 | 27.5    ← los dos rpg juntos en un grupo

Esa última idea es la regla de oro de GROUP BY: en el SELECT solo pueden aparecer las columnas por las que agrupas y funciones de agregación. Pedir titulo en la consulta anterior no tiene sentido: el grupo «rpg» tiene dos títulos, ¿cuál mostrarías?

SQLite lo deja pasar; PostgreSQL no

Si escribes una columna suelta que no está en el GROUP BY, SQLite no da error: te devuelve el valor de una fila cualquiera del grupo. PostgreSQL, en cambio, responde column "juegos.titulo" must appear in the GROUP BY clause or be used in an aggregate function. Que SQLite lo acepte no significa que esté bien: sigue la regla de oro y tus consultas funcionarán en cualquier motor.

HAVING: filtrar grupos

WHERE filtra filas antes de agrupar. Para filtrar después, según el resultado de cada grupo, se usa HAVING. Por ejemplo, «los géneros con más de un juego» es GROUP BY genero HAVING COUNT(*) > 1: no puedes ponerlo en el WHERE, porque cuando se ejecuta el WHERE todavía no existen los grupos ni sus cuentas.

Eso nos lleva a una idea que resuelve muchas dudas: una consulta no se ejecuta en el orden en que se escribe. Síguela paso a paso sobre una tabla de 10 partidas de un juego:

SELECT jugador, COUNT(*) AS partidas, MAX(puntos) AS record
FROM partidas
WHERE nivel >= 2
GROUP BY jugador
HAVING COUNT(*) >= 2
ORDER BY record DESC;

El orden completo es: FROM (con sus JOIN) → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Comprueba el resultado de la traza y después modifica la consulta: quita la línea del WHERE (¿cuántas partidas tiene ahora cada jugador?) y cambia el HAVING a >= 1 para que Sol aparezca.

Las cláusulas se escriben siempre en el mismo orden, aunque se ejecuten en otro. Ponlas en el orden correcto:

  1. SELECT c.nombre, COUNT(*) AS compras
  2. FROM clientes AS c
  3. JOIN compras AS co ON co.cliente_id = c.id
  4. WHERE co.fecha >= '2026-09-01'
  5. GROUP BY c.nombre
  6. HAVING COUNT(*) >= 2
  7. ORDER BY compras DESC
  8. LIMIT 3;

Subconsultas: una pregunta dentro de otra

A veces, para responder una pregunta primero necesitas la respuesta de otra. «¿Qué juegos cuestan más que la media?» exige calcular antes la media. Una subconsulta es un SELECT entre paréntesis dentro de otra consulta. Se usa de tres formas principales:

  • Como un valor: WHERE precio > (SELECT AVG(precio) FROM juegos). La subconsulta devuelve un solo número.
  • Como una lista: WHERE id IN (SELECT juego_id FROM compras) se queda con los juegos que aparecen en alguna compra.
  • Como una comprobación: WHERE EXISTS (SELECT 1 FROM …) es verdadero si la subconsulta devuelve al menos una fila. Suele mirar la fila de fuera, y entonces se llama subconsulta correlacionada.

Cuando una consulta se complica, WITH permite darle nombre a una subconsulta y usarla después como si fuera una tabla. Se llama expresión de tabla común (en inglés, common table expression, CTE) y hace que la consulta se lea de arriba abajo, como una receta.

Elige la que mejor se lea; si una va lenta, la herramienta del final de la próxima sección te dirá por qué. Modifica la consulta 1 para que muestre los juegos que cuestan menos que la media.

Error común

Usar NOT IN con una subconsulta que puede devolver NULL. Si la lista contiene un solo NULL, x NOT IN (lista) nunca es verdadero, por el mismo motivo que = NULL: «¿es x distinto de un valor desconocido?» no se sabe. La consulta devuelve cero filas sin avisar. Para «los que no tienen…», usa NOT EXISTS o el LEFT JOIN … IS NULL, que no tienen esa trampa.

Diseñar la base de datos

Escribir consultas es la mitad del trabajo. La otra mitad, y la que más cuesta cambiar después, es decidir qué tablas tendrás. Un buen diseño hace que las consultas sean sencillas y que los datos no se contradigan; uno malo te persigue durante años. Por eso los equipos diseñan primero en papel, con un diagrama, y solo después escriben CREATE TABLE.

Del problema al diagrama entidad-relación

El método clásico es el modelo entidad-relación (ER), que propuso Peter Chen en 1976. Tiene tres piezas:

  • Las entidades: las cosas de las que quieres guardar datos. Suelen ser los sustantivos de la descripción del problema: cliente, juego, compra. Cada entidad será una tabla.
  • Los atributos: lo que quieres saber de cada entidad. Serán las columnas.
  • Las relaciones: cómo se conectan las entidades y con qué cardinalidad (1:1, 1:N, N:M). Serán claves foráneas y tablas intermedias.

Una forma práctica de empezar es escribir en frases lo que hace la app y subrayar: «Un cliente hace compras. Cada compra es de un juego, en una fecha y por un precio. Un juego puede comprarse muchas veces». El diagrama de la tienda queda así:

Normalizar: cada dato en un solo lugar

La normalización es un método para repartir los datos en tablas de forma que nada se repita sin necesidad. Se aplica en etapas llamadas formas normales. Para entender por qué importa, parte de la planilla que muchas tiendas pequeñas usan al empezar:

pedidofechaclienteemailjuegos
12026-09-01Anaana@correo.comBosque Eterno (20), Mazmorra 64 (25)

Parece práctica, pero tiene tres problemas que se llaman anomalías:

  • De actualización: si Ana cambia de correo, hay que cambiarlo en todas sus filas. Si se te escapa una, la tabla tiene dos correos para la misma persona y no sabes cuál es el bueno.
  • De inserción: no puedes añadir un juego nuevo al catálogo hasta que alguien lo compre, porque no hay dónde ponerlo.
  • De borrado: si borras el pedido 2, también pierdes que Luis existe y que «Cohete Loco» cuesta 10.

Primera forma normal (1FN): un valor por celda. La columna juegos guarda una lista dentro de una celda, y así no puedes buscar, sumar ni relacionar cada juego. También está prohibido el truco de las columnas juego1, juego2, juego3: ¿qué pasa con el pedido de cuatro juegos? En 1FN, cada juego del pedido va en su propia fila:

Ahora cada fila se identifica por la pareja (pedido, juego): es una clave compuesta. Pero hay aún más repetición que antes.

Segunda forma normal (2FN): todo depende de la clave entera. Mira de qué depende cada columna. La fecha, el cliente y el correo dependen solo del pedido, no del juego: por eso se repiten en las dos filas del pedido 1. El precio de catálogo depende solo del juego. En 2FN, lo que depende de una parte de la clave se va a su propia tabla: pedidos (pedido, fecha, cliente, email), juegos (juego, precio) y lineas_pedido (pedido, juego, precio_pagado), donde queda lo que depende de las dos cosas a la vez.

Tercera forma normal (3FN): nada depende de algo que no sea la clave. En pedidos, el correo depende del cliente, no del pedido: si Ana hace cien pedidos, su correo sigue repitiéndose cien veces. Esa dependencia indirecta se llama dependencia transitiva. En 3FN, los datos del cliente se van a su tabla: clientes (id, nombre, email) y pedidos (id, fecha, cliente_id).

El resultado final son cuatro tablas: clientes, pedidos, juegos y lineas_pedido. Cada dato vive en un solo lugar, y las tres anomalías desaparecen. La tabla compras que usas en esta estación es una versión simplificada en la que cada pedido tiene un solo juego.

Idea clave

Una frase clásica resume las tres formas normales: cada columna debe depender de la clave, de toda la clave y de nada más que la clave. «De la clave» es 1FN (una fila identificable con valores simples), «de toda la clave» es 2FN y «nada más que la clave», 3FN. Existen formas normales superiores, pero en la práctica diaria llegar a la tercera es lo habitual.

Desnormalizar a propósito

A veces se rompe la normalización a sabiendas para leer más rápido: guardar en cada cliente un contador numero_compras ahorra contar sus compras en cada visita a su perfil. Se llama desnormalizar, y tiene un precio: ahora hay que mantener el contador al día en cada compra, y si un día no se actualiza, los datos se contradicen. Normaliza primero; desnormaliza solo cuando midas un problema de velocidad real.

Índices: decidir cuáles crear

En las estaciones 19 y 20 ejecutaste EXPLAIN QUERY PLAN y viste que un índice convierte un SCAN (recorrer toda la tabla, O(n)) en un SEARCH (bajar por un árbol B, O(log n)). Si no lo recuerdas, repasa esos talleres. Aquí toca la parte de diseño: cuáles crear y cuáles no.

CREATE INDEX idx_compras_cliente ON compras (cliente_id);
CREATE UNIQUE INDEX idx_clientes_email ON clientes (email);  -- además impide repetidos
DROP INDEX idx_compras_cliente;                              -- borrarlo
  • Ya tienes algunos gratis. La clave primaria y las columnas UNIQUE llevan un índice automático.
  • Las claves foráneas, no. SQLite y PostgreSQL no crean un índice para ellas (MySQL sí). Como casi todos los JOIN usan esas columnas, indexarlas suele ser lo primero.
  • Indexa lo que buscas a menudo: columnas que aparecen en WHERE, JOIN … ON y ORDER BY de las consultas frecuentes.
  • No indexes todo. Cada índice ocupa espacio y hace más lentas las escrituras, porque cada INSERT, UPDATE o DELETE debe actualizar también todos los índices de la tabla. En tablas pequeñas, un índice no aporta nada.

Un índice puede abarcar varias columnas: es un índice compuesto. El orden de las columnas importa.

Para entenderlo

Una guía telefónica está ordenada por apellido y, dentro de cada apellido, por nombre. Es un índice compuesto (apellido, nombre). Te sirve para buscar a todos los García, o a Ana García. Pero no te sirve para buscar a todas las personas llamadas Ana: tendrías que leer la guía entera. Un índice compuesto solo ayuda si la búsqueda usa sus columnas empezando por la primera.

Fíjate en la columna detail. La consulta 1 hace SCAN y además USE TEMP B-TREE FOR ORDER BY: ordena los resultados en una estructura temporal. La 2 hace SEARCH … USING INDEX y la ordenación desaparece, porque el índice ya guarda los puntos ordenados dentro de cada nivel: es el ranking de un nivel, gratis. La 3 vuelve a SCAN: puntos es la segunda columna del índice, como el nombre en la guía telefónica. Modifica: crea un segundo índice solo sobre puntos antes de la consulta 3 y observa el cambio.

Consultas que no pueden usar un índice

Un índice sobre titulo ayuda con titulo = 'Cohete Loco'. Con LIKE es más delicado: un patrón que empieza con texto fijo, como 'Co%', solo aprovecha el índice en ciertas configuraciones de cada motor, y uno como '%Loco' no puede aprovecharlo nunca: si no sabes cómo empieza, no puedes saltar a esa parte del árbol. Lo mismo pasa si aplicas una función a la columna, como lower(titulo) = 'cohete loco'. Cuando una consulta va lenta, EXPLAIN QUERY PLAN (en PostgreSQL, EXPLAIN ANALYZE) es la primera herramienta: te dice qué está haciendo la base de datos en lugar de obligarte a adivinar.

SQLite, PostgreSQL, MySQL y NoSQL

Todo lo que has aprendido de SQL sirve en cualquier base de datos relacional. Pero al empezar un proyecto hay que elegir un motor concreto (así se suele llamar al sistema gestor), y la primera diferencia entre ellos no es el dialecto: es dónde vive la base de datos.

NoSQL (hoy se interpreta como «no solo SQL», not only SQL) es un nombre paraguas para las bases de datos que no organizan la información en tablas relacionales. No es una tecnología, sino varias familias muy distintas, cada una diseñada para un tipo de problema:

El precio es el que ya conoces: si Ana cambia de correo, hay que actualizarlo en cada documento donde aparece. Diseñar en NoSQL consiste en decidir qué se guarda junto según cómo se va a leer.

En los videojuegos, la familia clave-valor es muy popular para las tablas de clasificación. Redis tiene una estructura llamada sorted set (conjunto ordenado) que mantiene a cada jugador ordenado por su puntuación en todo momento:

ZADD ranking 800 "Ana" 650 "Leo" 900 "Sol"
ZRANGE ranking 0 2 REV WITHSCORES

La primera orden guarda tres puntuaciones y la segunda devuelve los tres mejores, de mayor a menor, con sus puntos. Actualizar una puntuación o pedir el top sigue siendo muy rápido con millones de jugadores, porque la estructura se mantiene siempre ordenada, con un costo O(log n) por operación, como los árboles de la Estación 19.

Tres mitos sobre NoSQL

«NoSQL es más rápido»: depende de la consulta; para lo que fue diseñada, una base NoSQL vuela, y para lo demás puede ser más lenta. «NoSQL no tiene esquema»: los datos siempre tienen una forma; si la base de datos no la vigila, la tiene que vigilar tu código. «NoSQL no tiene transacciones»: MongoDB, por ejemplo, las admite entre varios documentos desde la versión 4.0 (2018).

La recomendación habitual es empezar con una base relacional y añadir otra solo cuando tengas un problema concreto que ella resuelva mejor. Muchos sistemas combinan varias: PostgreSQL como fuente de verdad y Redis como caché y para los rankings, como viste en la Estación 28. Además, PostgreSQL guarda y consulta documentos JSON con su tipo jsonb, así que a menudo puedes tener lo mejor de los dos mundos en una sola base.

Usar la base de datos desde tu código

Hasta aquí has escrito SQL a mano. En una app, quien escribe las consultas es tu programa: la API de la Estación 29 recibe una petición, consulta la base de datos y responde con los resultados en JSON. En esta sección conectarás Node.js con SQLite, aprenderás el error de seguridad más famoso de las bases de datos y conocerás las herramientas que usan los equipos para trabajar con ellas.

Conectar desde Node.js

Node.js trae su propio módulo para SQLite, node:sqlite: no hay que instalar nada. Apareció en la versión 22.5 como experimental, dejó de necesitar una opción especial en la 22.13 y, desde la 24.15, su documentación lo marca como release candidate (candidato a versión estable). Según tu versión, al usarlo puede aparecer un aviso ExperimentalWarning: el módulo funciona igual. Comprueba tu versión con node --version y el estado del módulo en su página de documentación, que tienes al final de la estación. Otras opciones muy usadas son la librería better-sqlite3 para SQLite, pg para PostgreSQL y mysql2 para MySQL, que se instalan con npm.

Sigue este programa paso a paso. Guarda dos jugadores en un archivo y lee el ranking:

import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync("juego.db");
db.exec(`CREATE TABLE IF NOT EXISTS jugadores (
  id INTEGER PRIMARY KEY,
  nombre TEXT NOT NULL,
  puntos INTEGER NOT NULL)`);
const insertar = db.prepare(
  "INSERT INTO jugadores (nombre, puntos) VALUES (?, ?)");
const info = insertar.run("Ana", 120);
insertar.run("Leo", 90);
const ranking = db.prepare(
  "SELECT nombre, puntos FROM jugadores ORDER BY puntos DESC").all();
console.log(info.lastInsertRowid, ranking[0].nombre);
db.close();

Síncrono o asíncrono

DatabaseSync, como su nombre indica, es síncrono: mientras la consulta se ejecuta, tu programa espera y no atiende nada más. Con SQLite suele durar microsegundos, porque el archivo está en la misma máquina, y por eso better-sqlite3 también funciona así. Pero una consulta muy pesada bloquearía el bucle de eventos que viste en la Estación 29. Las librerías de PostgreSQL y MySQL son asíncronas: la base de datos está en otra máquina, así que se usan con await.

Con PostgreSQL, el código se parece mucho. La dirección de la base, con su usuario y contraseña, llega en una variable de entorno para no escribir secretos en el código, y los huecos se escriben $1, $2… en lugar de ?:

import pg from "pg";
const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

const { rows } = await pool.query(
  "SELECT nombre, puntos FROM jugadores WHERE puntos > $1 ORDER BY puntos DESC",
  [100]
);
console.log(rows);   // [ { nombre: 'Ana', puntos: 120 } ]

Un pool de conexiones es un grupo de conexiones abiertas que se reutilizan: abrir una conexión nueva con un servidor por cada petición sería lento, así que el pool presta una libre y la recupera al terminar.

Y así se escribe una transacción desde el código, con el try/catch de la Estación 12: si cualquier orden falla, se deshace todo.

function transferir(de, a, cantidad) {
  db.exec("BEGIN");
  try {
    db.prepare("UPDATE monederos SET monedas = monedas - ? WHERE jugador = ?").run(cantidad, de);
    db.prepare("UPDATE monederos SET monedas = monedas + ? WHERE jugador = ?").run(cantidad, a);
    db.exec("COMMIT");
  } catch (error) {
    db.exec("ROLLBACK");   // algo falló: no queda nada a medias
    throw error;           // y avisamos a quien llamó
  }
}

Vulnerable

// Igual de vulnerable con plantilla literal:
db.prepare(`… WHERE cliente = '${nombre}'`).all();

Parametrizada

const sql = "SELECT fecha, juego FROM compras " +
  "WHERE cliente = ?";
db.prepare(sql).all(nombre);

// En PostgreSQL con pg, los huecos son $1, $2…
await pool.query("… WHERE cliente = $1", [nombre]);

Idea clave

Todo valor que venga de fuera de tu código (formularios, URLs, cuerpos JSON, cabeceras, archivos subidos) va en un parámetro, nunca pegado en el texto de la consulta. Sin excepciones, aunque «ya lo hayas validado». Escapar las comillas a mano tampoco es una defensa fiable: la guía de OWASP, la organización de referencia en seguridad web, lo desaconseja.

Lo que no puede ir en un parámetro

Los parámetros sirven para valores, no para nombres de tablas o columnas ni para palabras como ASC o DESC. Si el usuario elige por qué columna ordenar, compara su elección con una lista cerrada de opciones permitidas: const permitidas = ["precio", "anio"]; if (!permitidas.includes(orden)) orden = "precio";. En la Estación 31: Seguridad verás este y otros ataques, y cómo defenderte en capas.

ORMs y constructores de consultas

Escribir SQL como texto dentro de JavaScript tiene inconvenientes: el editor no sabe si una columna existe, los resultados no tienen tipos de TypeScript (Estación 23) y convertir filas en objetos se vuelve repetitivo. Por eso existen dos tipos de herramientas:

  • Un constructor de consultas (en inglés, query builder) te deja escribir la consulta con funciones de JavaScript que imitan a SQL. Ejemplos: Kysely y Knex.
  • Un ORM (object-relational mapping, «mapeo objeto-relacional») va más allá: describes tus tablas como modelos y trabajas con objetos y métodos; el ORM genera el SQL. Ejemplos: Prisma, Drizzle, TypeORM y Sequelize.

Así se pide «los 3 jugadores con más puntos» con SQL directo, con Drizzle y con Prisma, dos de los más usados con TypeScript. En septiembre de 2026, Prisma va por la versión 7 (con la 8 en fase candidata) y Drizzle por la 0.45, con la 1.0 en fase candidata; comprueba siempre la documentación de la versión que instales, porque la forma de configurarlos cambia entre versiones.

// SQL directo con node:sqlite
const top = db.prepare(
  "SELECT nombre, puntos FROM jugadores ORDER BY puntos DESC LIMIT 3"
).all();
// Drizzle: la tabla se describe en TypeScript…
import { int, sqliteTable, text } from "drizzle-orm/sqlite-core";
export const jugadores = sqliteTable("jugadores", {
  id: int().primaryKey({ autoIncrement: true }),
  nombre: text().notNull(),
  puntos: int().notNull().default(0),
});

// …y la consulta se parece mucho a SQL
import { desc } from "drizzle-orm";
const top = await db.select({ nombre: jugadores.nombre, puntos: jugadores.puntos })
  .from(jugadores).orderBy(desc(jugadores.puntos)).limit(3);
// Prisma: el modelo va en un archivo schema.prisma…
model Jugador {
  id     Int    @id @default(autoincrement())
  nombre String
  puntos Int    @default(0)
}
// …y la consulta usa objetos
const top = await prisma.jugador.findMany({
  select: { nombre: true, puntos: true },
  orderBy: { puntos: "desc" },
  take: 3,
});

El problema N+1

Con un ORM es fácil escribir sin darte cuenta: «trae los 100 clientes» y, dentro de un bucle, «trae las compras de este cliente». Son 1 + 100 consultas donde bastaba una con JOIN. Se llama problema N+1 y es la causa más común de apps lentas con ORM. Los ORMs ofrecen formas de cargar las relaciones de una vez (en Prisma, include); para detectarlo, activa el registro de las consultas que genera tu ORM y cuéntalas.

Idea clave

Aprende SQL antes que cualquier ORM. Un ORM genera SQL, y el día que una consulta vaya lenta o devuelva algo raro, tendrás que leer ese SQL para entender qué pasa. Además, los ORMs cambian cada pocos años; SQL lleva cincuenta.

Migraciones: cambiar el esquema sin perder datos

Tu juego ya tiene usuarios y ahora quieres guardar el país de cada jugador. No puedes borrar la base y crearla de nuevo: perderías todo. Necesitas cambiar el esquema con los datos dentro, y que el cambio se aplique igual en tu computadora, en la de tu equipo y en el servidor. Una migración es un archivo con un cambio del esquema, numerado para aplicarse en orden:

-- migraciones/002_agregar_pais.sql
ALTER TABLE jugadores ADD COLUMN pais TEXT;

ALTER TABLE modifica una tabla existente: añadir columnas, renombrarlas o borrarlas (en SQLite, borrar columnas es posible desde la versión 3.35; otros cambios exigen crear una tabla nueva y copiar los datos). Las reglas del oficio con las migraciones son pocas y estrictas:

  • Cada cambio es un archivo nuevo, con un número o una fecha que fija el orden.
  • Las migraciones van en Git, junto al código que las necesita (Estación 24).
  • La herramienta apunta en una tabla especial de la base de datos cuáles ya se aplicaron, y solo ejecuta las nuevas.
  • Nunca edites una migración que ya se aplicó en otro sitio. Si te equivocaste, escribe otra que lo corrija.

Los ORMs traen su herramienta: con Prisma, npx prisma migrate dev --name agregar_pais compara tu schema.prisma con la base y genera el archivo SQL; con Drizzle, npx drizzle-kit generate genera la migración y npx drizzle-kit migrate la aplica. Sin ORM, basta una carpeta de archivos .sql y un pequeño programa que los ejecute en orden. Practica la organización en esta terminal:

  1. Entra en la carpeta de migraciones del proyecto: cd juego-api/migraciones. Mira qué hay con ls y lee la primera con cat 001_crear_jugadores.sql.
  2. Crea la segunda migración: echo "ALTER TABLE jugadores ADD COLUMN pais TEXT;" > 002_agregar_pais.sql
  3. Crea la tercera, un índice para el ranking: echo "CREATE INDEX idx_jugadores_puntos ON jugadores (puntos);" > 003_indice_puntos.sql
  4. Comprueba con ls que las tres quedan en orden. No toques la 001: ya se aplicó en el servidor.

En un proyecto real, el siguiente paso sería git add migraciones y un commit con un mensaje como «feat: guarda el país del jugador», para que el resto del equipo y el servidor reciban la misma migración.

Copias de seguridad

Los discos se rompen, los servidores se borran por error y alguien, algún día, ejecutará un DELETE sin WHERE. Una copia de seguridad (en inglés, backup) es lo único que te salva de todo eso a la vez.

  • SQLite: no copies el archivo con el explorador mientras la app escribe, porque puedes copiar un estado a medias (y en modo WAL, los últimos cambios están en un archivo aparte, -wal). Usa una copia consistente: VACUUM INTO 'copia.db'; desde SQL (desde la versión 3.27), la orden .backup de la terminal de SQLite o la función backup de node:sqlite en las versiones recientes de Node.
  • PostgreSQL: pg_dump exporta la base a un archivo y pg_restore (o psql, según el formato) la restaura. Los servicios gestionados hacen copias automáticas y permiten volver a cualquier momento de los últimos días, lo que se llama recuperación a un punto en el tiempo (en inglés, point-in-time recovery).
$ sqlite3 juego.db "VACUUM INTO 'copias/juego-2026-09-30.db'"
$ pg_dump --format=custom --file=tienda-2026-09-30.dump tienda
$ pg_restore --dbname=tienda_prueba tienda-2026-09-30.dump

La regla 3-2-1

Ten al menos 3 copias de los datos, en 2 tipos de soporte distintos, con 1 de ellas fuera del lugar donde está el original (otra ciudad, otro proveedor). Automatiza las copias en lugar de confiar en acordarte (lo verás en la Estación 35). Y, sobre todo, prueba a restaurarlas de vez en cuando en una base de prueba, como en la última línea de la consola: una copia que nunca has restaurado es solo una esperanza.

Impacto

Una base de datos con correos, direcciones o compras guarda información sobre personas reales, y las copias también. Guarda solo los datos que de verdad necesitas, protege el acceso a la base y a sus copias, y borra lo que ya no uses. Las leyes de protección de datos, como el Reglamento General de Protección de Datos europeo o las leyes de cada país latinoamericano, obligan a hacerlo. En la Estación 31 verás cómo guardar las contraseñas, que nunca se almacenan tal cual.

Resumen

  • Una base de datos guarda datos de forma permanente y garantiza cosas que un archivo no: escrituras simultáneas sin pisarse, nada a medias tras un apagón, búsquedas rápidas y reglas que siempre se cumplen.
  • El modelo relacional guarda cada tipo de cosa en una tabla: filas (una cosa cada una) y columnas (con nombre, tipo y restricciones). La clave primaria identifica cada fila.
  • CREATE TABLE define, INSERT añade, SELECT consulta, UPDATE cambia y DELETE borra. Antes de cambiar o borrar, prueba el mismo WHERE con un SELECT.
  • WHERE filtra filas, ORDER BY ordena (sin él no hay orden garantizado) y LIMIT/OFFSET pagina. Textos entre comillas simples.
  • NULL es «no se sabe»: nunca es igual a nada. Se pregunta con IS NULL y se sustituye con COALESCE.
  • Las claves foráneas conectan tablas y evitan huérfanos (en SQLite, actívalas con PRAGMA foreign_keys = ON). INNER JOIN combina solo lo que tiene pareja; LEFT JOIN conserva todo lo de la izquierda.
  • GROUP BY hace un resumen por grupo con COUNT, SUM, AVG, MIN y MAX; WHERE filtra antes de agrupar y HAVING, después. Una consulta se ejecuta en otro orden del que se escribe: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
  • Una transacción (BEGIN … COMMIT o ROLLBACK) aplica varios cambios como uno solo. ACID: atomicidad, consistencia, aislamiento y durabilidad.
  • Diseña con un diagrama entidad-relación y normaliza hasta la tercera forma normal: cada dato depende de la clave, de toda la clave y de nada más que la clave. Indexa las columnas que buscas y unes a menudo, empezando por las claves foráneas.
  • SQLite para apps, juegos y proyectos con un solo servidor; PostgreSQL para backends con muchas escrituras simultáneas; NoSQL para problemas concretos. Desde el código, usa siempre consultas parametrizadas, cambia el esquema con migraciones y prueba tus copias de seguridad.

Los tres primeros están casi resueltos, los tres siguientes te piden combinar lo aprendido y los tres últimos son retos. Juegos por menos de 15

Guiado

Muestra el titulo y el precio de los juegos que cuestan menos de 15, del más barato al más caro. Deben salir cuatro juegos. La tabla juegos es la de la sección Consultar con SELECT.

Pista 1

La condición va en WHERE, entre el FROM y el final: WHERE precio < 15.

Pista 2

ORDER BY precio ordena de menor a mayor, porque ASC es el orden por defecto. Va después del WHERE.

Ver una solución 
SELECT titulo, precio
FROM juegos
WHERE precio < 15
ORDER BY precio;

Con <= 15 entraría también «Granja Pixel». Fíjate siempre en si el límite está incluido o no: es uno de los errores más frecuentes, en SQL y en cualquier lenguaje.

Tu tabla de tareas

Guiado

Completa la tabla tareas para una app de pendientes. Además del id, necesita dos columnas: titulo, un texto obligatorio, y hecha, un entero obligatorio que vale 0 si no se indica (0 es pendiente y 1, hecha). Después inserta tres tareas dando solo el título. La consulta final ya está escrita.

Pista 1

Las columnas se separan con comas. Después de id INTEGER PRIMARY KEY pon una coma y escribe titulo TEXT NOT NULL, y en la línea siguiente la columna hecha.

Pista 2

Para insertar solo el título, nombra solo esa columna: INSERT INTO tareas (titulo) VALUES ('Estudiar SQL'), ('Sacar al perro'), ('Llamar a mamá');

Ver una solución 
CREATE TABLE tareas (
  id INTEGER PRIMARY KEY,
  titulo TEXT NOT NULL,
  hecha INTEGER NOT NULL DEFAULT 0
);

INSERT INTO tareas (titulo)
VALUES ('Estudiar SQL'), ('Sacar al perro'), ('Llamar a mamá');

SELECT * FROM tareas;

El id y hecha se rellenan solos. Para marcar la segunda como hecha bastaría UPDATE tareas SET hecha = 1 WHERE id = 2;. En PostgreSQL usarías el tipo boolean con DEFAULT false.

Arregla la consulta: clientes sin correo

Guiado

Esta consulta debería mostrar el nombre y la ciudad de los clientes que no dieron su correo, por orden alfabético. Tiene dos errores. Ejecútala, observa el resultado y corrígela hasta que muestre a Iván y después a Sofía.

Pista 1

Con = NULL la condición nunca es verdadera: por eso no sale nada. Repasa la sección sobre NULL.

Pista 2

DESC ordena de la Z a la A. Para el orden alfabético normal, quítalo o escribe ASC.

Ver una solución 
SELECT nombre, ciudad
FROM clientes
WHERE email IS NULL
ORDER BY nombre;

El primer error es silencioso: = NULL no da error, solo deja la respuesta vacía. Por eso es tan peligroso: parece que no hay clientes sin correo.

Rebajas solo para quien toca

Semiguiado

La tienda quiere rebajar un 20 % (multiplicar el precio por 0.8) los juegos de rol ('rpg') que salieron antes de 2024. El UPDATE que escribió un compañero rebaja demasiado. Corrígelo. El SELECT final muestra todos los precios para que compruebes que nada más cambió.

Pista 1

Un UPDATE sin WHERE cambia todas las filas. Añade un WHERE antes del punto y coma.

Pista 2

Hay dos condiciones que deben cumplirse a la vez: el género y el año. Se unen con AND.

Ver una solución 
UPDATE juegos SET precio = precio * 0.8
WHERE genero = 'rpg' AND anio < 2024;

SELECT titulo, precio FROM juegos ORDER BY id;

Solo «Mazmorra 64» cumple las dos condiciones. Antes de ejecutar un cambio así en una base real, habrías lanzado SELECT titulo FROM juegos WHERE genero = 'rpg' AND anio < 2024; para ver qué filas iba a tocar.

Las compras de Bogotá

Semiguiado

Muestra el nombre del cliente (nombre), el título del juego (titulo) y la fecha (fecha) de cada compra hecha por clientes de Bogotá, de la más antigua a la más reciente. Deben salir cuatro filas. Las tablas son clientes, juegos y compras, las de la sección de relaciones.

Pista 1

Necesitas dos JOIN: uno con clientes (para el nombre y la ciudad) y otro con juegos (para el título). Cada uno con su ON.

Pista 2

Con alias c y j: JOIN clientes AS c ON c.id = co.cliente_id, JOIN juegos AS j ON j.id = co.juego_id y después WHERE c.ciudad = 'Bogotá'.

Ver una solución 
SELECT c.nombre, j.titulo, co.fecha
FROM compras AS co
JOIN clientes AS c ON c.id = co.cliente_id
JOIN juegos   AS j ON j.id = co.juego_id
WHERE c.ciudad = 'Bogotá'
ORDER BY co.fecha;

El WHERE puede filtrar por columnas de cualquiera de las tablas unidas, porque se ejecuta después de los JOIN.

Una transferencia segura

Semiguiado

Leo le paga 15 monedas a Sol. Las dos órdenes ya están escritas, pero van sueltas: si el servidor fallara entre ellas, las monedas se perderían. Mételas en una transacción que se confirme. Al final deben quedar Ana con 100, Leo con 5 y Sol con 65.

Pista 1

Una transacción empieza con BEGIN; y termina con COMMIT; (confirmar) o ROLLBACK; (descartar).

Pista 2

Pon BEGIN; en una línea antes del primer UPDATE y COMMIT; después del segundo. El SELECT puede ir después del COMMIT.

Ver una solución 
BEGIN;
UPDATE monederos SET monedas = monedas - 15 WHERE jugador = 'Leo';
UPDATE monederos SET monedas = monedas + 15 WHERE jugador = 'Sol';
COMMIT;

SELECT jugador, monedas FROM monederos ORDER BY jugador;

El resultado es el mismo que sin transacción cuando nada falla; la diferencia está en lo que pasa cuando algo falla. Prueba a cambiar el primer 15 por 30: Leo no tiene tanto y la restricción CHECK detiene la operación.

¿Qué géneros venden?

Reto

Para cada género con al menos 2 compras, muestra el género (genero), cuántas compras tuvo (ventas) y cuánto se recaudó sumando precio_pagado (total), del que más recaudó al que menos. Usa las tablas de la tienda.

Pista 1

Empieza por el FROM: FROM compras AS co JOIN juegos AS j ON j.id = co.juego_id. Ejecuta con SELECT * para ver qué filas tienes antes de agrupar.

Pista 2

Agrupa con GROUP BY j.genero, calcula COUNT(*) AS ventas y SUM(co.precio_pagado) AS total, y filtra los grupos con HAVING COUNT(*) >= 2. El orden va al final.

Ver una solución 
SELECT j.genero AS genero,
       COUNT(*) AS ventas,
       SUM(co.precio_pagado) AS total
FROM compras AS co
JOIN juegos AS j ON j.id = co.juego_id
GROUP BY j.genero
HAVING COUNT(*) >= 2
ORDER BY total DESC;

Los tres rpg vendidos suman 25 + 30 + 25 = 80. Fíjate en que el HAVING no podía ir en el WHERE: cuando se ejecuta el WHERE, todavía no se han contado las ventas de cada género.

La ficha de cada cliente

Reto

Para todos los clientes, incluidos los que nunca compraron, muestra nombre, cuántas compras hizo (compras) y cuánto gastó en total (gastado), del que más gastó al que menos. Quien no compró nada debe aparecer con 0 compras y 0 gastado, no con NULL. Cuidado: hay una trampa con COUNT.

Pista 1

Para no perder a Iván, cambia JOIN por LEFT JOIN. Ejecuta y mira qué valores recibe.

Pista 2

COUNT(*) cuenta filas, y el LEFT JOIN le da a Iván una fila con las columnas de compras en NULL. COUNT(co.id) solo cuenta valores que no son NULL. Y COALESCE(SUM(…), 0) convierte el NULL de la suma en 0.

Ver una solución 
SELECT c.nombre,
       COUNT(co.id) AS compras,
       COALESCE(SUM(co.precio_pagado), 0) AS gastado
FROM clientes AS c
LEFT JOIN compras AS co ON co.cliente_id = c.id
GROUP BY c.id, c.nombre
ORDER BY gastado DESC;

Agrupar por c.id además de por el nombre evita mezclar a dos clientes que se llamen igual. La combinación LEFT JOIN + COUNT(columna) + COALESCE aparece en cualquier informe que deba incluir a quien tiene cero.

Termina la normalización

Reto

La tabla planilla tiene una fila por compra con el título del juego escrito como texto: fecha, cliente, email, juego y precio_pagado. Sácala a dos tablas: juegos (id y titulo, sin títulos repetidos) y compras (con juego_id apuntando a juegos, además de cliente, fecha y precio_pagado). Rellénalas desde la planilla con INSERT INTO … SELECT. La consulta final, que no debes cambiar, comprueba el resultado. Ojo: «Mazmorra 64» se vendió una vez con descuento.

Pista 1

El precio no va en juegos: «Mazmorra 64» se vendió a 25 y a 20, y un SELECT DISTINCT juego, precio_pagado daría dos filas para el mismo título. El precio pagado es un dato de cada compra. Declara titulo TEXT NOT NULL UNIQUE para que la base de datos impida repetidos.

Pista 2

Para llenar compras, une la planilla con la tabla juegos que acabas de crear por el título: FROM planilla AS p JOIN juegos AS j ON j.titulo = p.juego, y selecciona j.id como juego_id. Revisa el taller «Normaliza con SQL».

Ver una solución 
CREATE TABLE juegos (id INTEGER PRIMARY KEY, titulo TEXT NOT NULL UNIQUE);
INSERT INTO juegos (titulo)
SELECT DISTINCT juego FROM planilla;

CREATE TABLE compras (
  id INTEGER PRIMARY KEY,
  juego_id INTEGER NOT NULL REFERENCES juegos(id),
  cliente TEXT NOT NULL,
  fecha TEXT NOT NULL,
  precio_pagado REAL NOT NULL
);
INSERT INTO compras (juego_id, cliente, fecha, precio_pagado)
SELECT j.id, p.cliente, p.fecha, p.precio_pagado
FROM planilla AS p
JOIN juegos AS j ON j.titulo = p.juego;

SELECT j.titulo, COUNT(*) AS ventas, SUM(co.precio_pagado) AS recaudado
FROM compras AS co
JOIN juegos AS j ON j.id = co.juego_id
GROUP BY j.titulo
ORDER BY ventas DESC, j.titulo;

Los clientes siguen como texto en compras. Para llegar a 3FN, haz lo mismo con ellos: una tabla clientes con su correo y una columna cliente_id en compras, exactamente como en el taller de la sección de diseño.
