Lo que vas a lograr

Cierra una app y vuelve a abrirla: tus mensajes, tus compras y tu progreso en el juego siguen ahí. Detrás de casi todas las aplicaciones hay una base de datos que guarda la información de forma ordenada, segura y rápida de consultar. En esta estación aprenderás a diseñarlas y a hablarles en SQL, el mismo lenguaje que usan desde una app de tareas hasta un banco.

  • Explicar qué es una base de datos y qué problemas resuelve frente a guardar todo en un archivo.
  • Leer y crear tablas con columnas, tipos, clave primaria y restricciones.
  • Consultar datos con SELECT, WHERE, ORDER BY y LIMIT, y tratar bien los valores NULL.
  • Insertar, actualizar y borrar filas sin estropear datos por accidente, protegiendo los cambios con transacciones.
  • Relacionar tablas con claves foráneas y combinarlas con INNER JOIN y LEFT JOIN.
  • Resumir datos con GROUP BY, funciones de agregación, HAVING y subconsultas.
  • Diseñar una base de datos con un diagrama entidad-relación, normalizarla hasta la tercera forma normal y decidir qué índices necesita.
  • Elegir entre SQLite, PostgreSQL, MySQL o una base de datos NoSQL según el proyecto.
  • Usar una base de datos desde Node.js con consultas parametrizadas, y saber qué son los ORMs, las migraciones y las copias de seguridad.

Antes de empezar

Necesitas saber qué es un servidor y una API, que construiste en la Estación 29: Node.js y servidores. Te ayudará recordar los arrays de objetos y JSON de la Estación 11, porque una tabla se parece mucho a un array de objetos. Si pasaste por las estaciones 19 (árboles) y 20 (búsqueda binaria), ya conoces la idea que hace rápidos a los índices.

Todos los talleres de SQL ejecutan SQLite de verdad dentro de tu navegador: no instalas nada. Cada vez que pulsas «Ejecutar», la base de datos se crea de nuevo con los datos de ejemplo, así que puedes borrar, romper y probar sin miedo.

Por qué una base de datos

En la Estación 29 tu API guardaba los datos en un array, dentro de la memoria del servidor. Funciona hasta que el servidor se reinicia: la memoria RAM se borra al apagar, como viste en la Estación 2, y con ella todas las puntuaciones. Necesitas que los datos sobrevivan. A eso se le llama persistencia: que la información quede guardada de forma permanente, en disco.

La primera idea suele ser guardar todo en un archivo JSON: leerlo al arrancar y reescribirlo en cada cambio. Para un proyecto de fin de semana, sirve. Pero en cuanto la app tiene personas usándola de verdad aparecen cinco problemas:

  1. Dos personas a la vez. Si dos peticiones leen y reescriben el archivo al mismo tiempo, una borra el cambio de la otra.
  2. Un apagón a mitad. Si el servidor se apaga mientras escribe, el archivo queda a medias y puedes perderlo entero, no solo el último cambio.
  3. Buscar es lento. Para encontrar a una persona entre un millón tienes que leer y recorrer el archivo completo cada vez.
  4. Nadie vigila las reglas. Nada impide guardar un precio negativo o una compra de un cliente que no existe.
  5. Cada pregunta nueva es un programa nuevo. «¿Cuánto vendimos por género este mes?» te obliga a escribir bucles y acumuladores para cada consulta.

Qué es una base de datos

Una base de datos es una colección de datos organizada y guardada de forma permanente, pensada para consultarse y modificarse de forma segura. El programa que la administra se llama sistema gestor de bases de datos (SGBD; en inglés, database management system, DBMS). SQLite, PostgreSQL y MySQL son sistemas gestores. En el día a día casi todo el mundo dice «la base de datos» para las dos cosas, y aquí haremos lo mismo.

Para entenderlo

Un archivo JSON es como un cuaderno compartido sobre una mesa: cualquiera lo abre, tacha y escribe, y si dos personas escriben en la misma página a la vez, se pisan. Una base de datos es como un archivo con una bibliotecaria en el mostrador. Tú no tocas las fichas: le pides lo que quieres. Ella atiende las escrituras de una en una, anota cada cambio en un registro antes de hacerlo, encuentra una ficha entre un millón en un instante y se niega a archivar una ficha que rompe las reglas. La analogía tiene un límite: la bibliotecaria no entiende qué significan tus datos. Solo hace cumplir las reglas que tú le das.

ProblemaArchivo JSONBase de datos

¿Cómo sobrevive una base de datos a un apagón? Antes de cambiar nada, anota lo que va a hacer en un registro aparte. Si la luz se va a mitad, al arrancar lee ese registro y deshace o termina el cambio, de modo que nunca queda a medias. SQLite llama a ese registro diario (en inglés, journal) y PostgreSQL, registro de escritura anticipada (write-ahead log, WAL). Tú no tienes que programarlo: viene incluido.

Idea clave

Una base de datos no solo guarda: garantiza. Garantiza que dos cambios simultáneos no se pisan, que un apagón no deja datos a medias y que nada que rompa tus reglas entra. Programar esas garantías a mano sobre archivos es dificilísimo; por eso casi nadie lo hace.

¿Y cuándo basta con un archivo?

No todo necesita una base de datos. Un archivo sigue siendo la mejor opción para la configuración de un programa, para exportar datos que otra persona va a abrir en una hoja de cálculo o para la partida guardada de un juego de un solo jugador, donde solo un programa escribe y nunca a la vez. La pregunta útil es: ¿varias personas o procesos van a escribir a la vez, o voy a necesitar buscar y combinar datos de muchas formas? Si la respuesta es sí, usa una base de datos.

Consejo de oficio

La documentación de SQLite lo resume con una frase famosa: SQLite no compite con las bases de datos cliente-servidor, compite con fopen(), la función con la que un programa en C abre un archivo. Muchas aplicaciones usan SQLite como un «archivo con superpoderes»: Android e iOS la incluyen, y navegadores como Firefox y Chrome guardan en ella tu historial. Si tu juego necesita guardar muchas cosas y buscarlas, SQLite puede ser tu formato de partida guardada.

El lenguaje: SQL

La familia de bases de datos más usada es la relacional: guarda los datos en tablas y se consulta con SQL (de Structured Query Language, «lenguaje de consultas estructurado»; se pronuncia «ese-cu-ele» o, a la inglesa, «sícuel»). Nació en IBM en los años setenta y es un estándar internacional desde 1986; la edición más reciente es SQL:2023. Hay otras familias, que se agrupan bajo el nombre NoSQL; las verás en la sección SQLite, PostgreSQL y NoSQL.

En la Estación 21 viste que SQL es declarativo: describes qué datos quieres y la base de datos decide cómo buscarlos. No escribes bucles. Cada motor habla su propio dialecto, con pequeñas diferencias, pero lo básico es igual en todos. En esta estación usarás el de SQLite, y te avisaremos cuando algo cambie en PostgreSQL o MySQL.

Tres convenciones que verás en todos los ejemplos:

  • Las palabras del lenguaje (SELECT, FROM, WHERE) se escriben en MAYÚSCULAS por costumbre, para distinguirlas de tus nombres. SQL no distingue mayúsculas en ellas: select también funciona.
  • Cada instrucción termina en punto y coma (;). Una instrucción puede ocupar varias líneas.
  • Los comentarios empiezan con dos guiones: -- esto no se ejecuta.

Tablas, tipos y claves

En 1970, Edgar F. Codd, un matemático que trabajaba en IBM, publicó un artículo que cambió la informática: proponía organizar los datos en tablas y consultarlos con operaciones matemáticas bien definidas, sin que el programa tuviera que saber cómo estaban guardados en el disco. Es el modelo relacional, y más de cincuenta años después sigue siendo la forma más común de guardar datos. Cada tabla guarda un tipo de cosa: una tabla de juegos, otra de clientes, otra de compras.

Estas son las piezas, con los nombres que vas a leer en todas partes:

  • Una fila (en inglés, row; también se dice registro) es una cosa concreta: un juego, un cliente, una compra.
  • Una columna (en inglés, column; también se dice campo) es una propiedad que tienen todas las filas: el título, el precio. Tiene un nombre y un tipo.
  • El esquema (en inglés, schema) es la descripción de las tablas: qué columnas tienen, de qué tipo y con qué reglas. Es el plano de tu base de datos.

Si vienes de la Estación 11, cada fila es como un objeto { id: 1, titulo: "Bosque Eterno", … } y la tabla es como un array de esos objetos, con una diferencia importante: en una tabla todas las filas tienen exactamente las mismas columnas.

Para entenderlo

Una tabla se parece a una hoja de cálculo, y la comparación sirve para empezar. Pero falla en dos puntos. En una hoja de cálculo puedes escribir cualquier cosa en cualquier celda; en una tabla, cada columna tiene un tipo y unas reglas que la base de datos hace cumplir. Y las filas de una tabla no tienen un orden fijo: si quieres verlas ordenadas, lo pides en cada consulta.

Crear una tabla

La instrucción CREATE TABLE define una tabla nueva: su nombre, sus columnas y las reglas de cada una.

CREATE TABLE juegos (
  id     INTEGER PRIMARY KEY,               -- número que identifica cada juego
  titulo TEXT NOT NULL,                     -- texto obligatorio
  genero TEXT,                              -- texto opcional
  precio REAL NOT NULL CHECK (precio >= 0), -- decimal, obligatorio, nunca negativo
  anio   INTEGER                            -- año de salida, opcional
);

Cada línea dentro de los paréntesis es una columna: primero el nombre, después el tipo y, al final, las restricciones. Los nombres suelen escribirse en minúsculas, sin tildes ni espacios, con guion bajo para separar palabras (precio_pagado). Esa forma se llama snake_case. La columna se llama anio y no año porque la ñ y las tildes funcionan en muchos motores, pero dan problemas en algunas herramientas; es más seguro evitarlas en los nombres, aunque sí puedes usarlas dentro de los datos.

Cada motor tiene su lista de tipos. SQLite tiene muy pocos; PostgreSQL, muchos. Esta tabla muestra los más comunes:

SQLite no tiene tipo de fecha: guarda las fechas como texto con el formato internacional ISO 8601, año-mes-día ('2026-09-30'). Ese orden tiene una ventaja: al ordenar los textos alfabéticamente, quedan ordenados por fecha.

El dinero no va en REAL

En la Estación 7 viste que 0.1 + 0.2 no da exactamente 0.3. REAL tiene el mismo problema. Para dinero de verdad, guarda los céntimos como enteros (1999 para 19,99) o usa numeric en PostgreSQL, que guarda decimales exactos. En esta estación los precios son redondos para que los ejemplos se lean fácil.

La clave primaria

La clave primaria (en inglés, primary key) es la columna cuyo valor identifica cada fila: no puede repetirse y no puede faltar. ¿Por qué no usar el nombre? Porque dos clientas pueden llamarse Ana. ¿Y el correo? Porque la gente cambia de correo, y entonces habría que cambiarlo en todas partes. Lo habitual es añadir una columna id con un número que no significa nada más: una clave sustituta (en inglés, surrogate key). Una clave que sí tiene significado, como un DNI, se llama clave natural.

En SQLite, una columna INTEGER PRIMARY KEY se numera sola: si insertas una fila sin id, recibe el siguiente número libre. Cada motor lo escribe a su manera:

-- SQLite
id INTEGER PRIMARY KEY
-- PostgreSQL (forma moderna; en tutoriales antiguos verás SERIAL)
id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY
-- MySQL
id INT AUTO_INCREMENT PRIMARY KEY

¿Y AUTOINCREMENT?

En tutoriales de SQLite verás INTEGER PRIMARY KEY AUTOINCREMENT. No hace falta para que el número se ponga solo: solo impide reutilizar los números de filas borradas. La documentación de SQLite recomienda no usarlo si no lo necesitas, porque gasta más recursos.

Restricciones: las reglas de la tabla

Una restricción (en inglés, constraint) es una regla que la base de datos comprueba en cada inserción y en cada cambio. Si una fila la rompe, la operación entera se rechaza con un error.

Idea clave

La base de datos es la última línea de defensa. Tu API debería validar los datos antes de guardarlos (lo viste en la Estación 29), pero el código tiene errores y a veces hay varios programas escribiendo en la misma base. Las restricciones se cumplen siempre, venga el dato de donde venga.

Insertar filas

Con INSERT INTO añades filas. Primero nombras las columnas que vas a rellenar y después, en VALUES, los valores en el mismo orden. Puedes insertar varias filas en una sola instrucción separándolas con comas:

INSERT INTO juegos (titulo, genero, precio, anio)
VALUES ('Bosque Eterno', 'aventura', 20, 2021),
       ('Cohete Loco', 'carreras', 10, 2019);

Los textos van entre comillas simples. Si el texto contiene un apóstrofo, se escribe doble: 'Bernardo O''Higgins'. Los números van sin comillas. No hace falta dar el id: la base de datos lo asigna.

La rareza de SQLite: tipos flexibles

SQLite tiene una particularidad que sorprende a casi todo el mundo. Predice qué guardará en cada fila:

La función typeof dice el tipo real de cada valor. El texto '31' se convirtió en el número 31, porque parecía un número. Pero 'treinta' se guardó como texto en una columna de enteros, sin ningún error. SQLite trata el tipo de la columna como una preferencia, no como una obligación; la documentación lo llama afinidad de tipo. Lo hace para ser compatible con programas antiguos.

Desde la versión 3.37 (2021) existe la opción STRICT, que hace que SQLite se comporte como los demás motores. Cambia la primera línea del taller por CREATE TABLE prueba (edad INTEGER) STRICT; y ejecuta: ahora el texto 'treinta' se rechaza con un error. '31', en cambio, se sigue aceptando convertido en número, porque la conversión no pierde nada.

Error común

Confiar en que SQLite comprueba los tipos. Sin STRICT, una columna INTEGER acepta 'treinta' y el error aparece mucho después, cuando una suma da un resultado raro. En proyectos nuevos con SQLite, usa tablas STRICT o valida los datos antes de guardarlos. PostgreSQL y MySQL, en su configuración habitual, rechazan el valor desde el principio.

Consultar con SELECT

En casi todas las apps se lee mucho más de lo que se escribe: una tienda muestra su catálogo miles de veces por cada juego nuevo que añade. Por eso la instrucción que más vas a escribir es SELECT («seleccionar»). Su forma general, con las partes opcionales entre corchetes, es:

SELECT columnas
FROM tabla
[WHERE condición]
[ORDER BY columna]
[LIMIT cantidad];

Cada parte recibe el nombre de su palabra clave: la cláusula WHERE, la cláusula ORDER BY… Una consulta que lee datos se llama, en general, una consulta (en inglés, query). Los talleres de esta sección usan esta tabla juegos de una tienda en línea. Tenla a la vista para predecir los resultados:

Elegir columnas

Después de SELECT escribes las columnas que quieres, separadas por comas. También puedes calcular columnas nuevas y ponerles un nombre con AS, que se llama alias:

SELECT titulo, precio FROM juegos;                      -- solo dos columnas
SELECT titulo, precio * 0.8 AS rebajado FROM juegos;    -- columna calculada: 20 % menos
SELECT titulo || ' (' || anio || ')' AS ficha FROM juegos; -- une textos: Bosque Eterno (2021)
SELECT DISTINCT genero FROM juegos;                     -- cada género una sola vez

En SQL los textos se unen con ||, no con +. Y DISTINCT quita las filas repetidas del resultado: «rpg» aparece dos veces en la tabla, pero una sola en la respuesta. Las columnas calculadas no cambian nada en la tabla: solo existen en la respuesta.

Consejo de oficio

SELECT * es cómodo para explorar, pero en el código de una app escribe las columnas que necesitas. Traes menos datos por la red, y si mañana alguien añade a la tabla una columna enorme (una imagen, un texto largo) o una columna privada, tu programa no la recibirá sin querer.

WHERE (genero = 'rpg' OR genero = 'puzle')
  AND precio < 28;
-- Mazmorra 64, Puzle Cuántico

Mayúsculas y tildes en los textos

En SQLite, = distingue mayúsculas: 'rpg' no es igual a 'RPG'. LIKE no las distingue, pero solo para las letras sin tilde del alfabeto inglés: 'Ábaco' LIKE 'á%' es falso. En PostgreSQL, LIKE sí distingue mayúsculas y existe ILIKE para ignorarlas. Cuando busques nombres escritos por personas, guarda o compara todo en minúsculas, y comprueba cómo trata tu motor las tildes.

Error común

Usar comillas dobles para los textos. En SQL, las comillas simples son para textos ('rpg') y las dobles, para nombres de columnas o tablas ("genero"). SQLite, por compatibilidad, acepta "rpg" como texto si no hay una columna con ese nombre, así que parece funcionar. Pero WHERE genero = "genero" compara la columna consigo misma y devuelve todas las filas, sin error. PostgreSQL rechaza "rpg" diciendo que esa columna no existe. Acostúmbrate a las simples.

Ordenar y limitar

ORDER BY ordena el resultado por una o varias columnas: de menor a mayor por defecto (ASC, ascendente) o de mayor a menor con DESC (descendente). LIMIT se queda con las primeras filas y OFFSET se salta unas cuantas antes de empezar. Con los dos juntos se hace la paginación: mostrar los resultados de 10 en 10, como las páginas de una tienda.

SELECT titulo, precio FROM juegos ORDER BY precio DESC;          -- del más caro al más barato
SELECT titulo, genero, precio FROM juegos ORDER BY genero, precio; -- por género y, dentro de cada género, por precio
SELECT titulo FROM juegos ORDER BY titulo LIMIT 3;                -- los 3 primeros por orden alfabético
SELECT titulo FROM juegos ORDER BY titulo LIMIT 3 OFFSET 3;       -- la «página 2»: del 4.º al 6.º

Haz tres cambios, ejecutando después de cada uno: muestra los 3 más baratos; después la segunda página de 3 (añade OFFSET 3); por último, los 4 juegos más recientes, usando la columna anio.

Sin ORDER BY no hay orden

Si no escribes ORDER BY, la base de datos devuelve las filas en el orden que le resulte más cómodo. Hoy puede coincidir con el orden en que las insertaste y mañana, tras un cambio interno, no. Un LIMIT sin ORDER BY te da «unas filas cualesquiera». Si el orden importa, pídelo siempre.

NULL: el valor que no es un valor

NULL significa «no se sabe» o «no hay dato». No es cero ni un texto vacío: un cliente con el correo vacío ('') te dio un correo en blanco; un cliente con el correo NULL no te lo dio. Y aquí viene la trampa: cualquier comparación con algo desconocido da como resultado «desconocido». ¿Es un correo desconocido igual a otro correo desconocido? No se sabe. Por eso email = NULL nunca es verdadero, ni siquiera cuando el correo es NULL, y WHERE solo deja pasar las filas cuya condición es verdadera.

Error común

Escribir = NULL o <> NULL. No dan error: simplemente no devuelven nada, y crees que no hay datos. Para preguntar por la falta de valor usa siempre IS NULL o IS NOT NULL.

NULL también se contagia en los cálculos: 5 + NULL es NULL, y 'Hola ' || NULL también. Tiene sentido: si no sabes cuánto vale algo, tampoco sabes cuánto vale ese algo más 5. Al ordenar, SQLite y MySQL ponen los NULL al principio en orden ascendente y PostgreSQL, al final. Si te importa, dilo tú: ORDER BY email NULLS LAST funciona en SQLite y en PostgreSQL.

Consejo de oficio

Decide columna por columna si un dato puede faltar. Si no puede, márcala NOT NULL desde el principio: cada columna que admite NULL es una pregunta más que tendrás que responder en cada consulta y en cada línea de código que lea ese dato.

Cambiar datos con cuidado

Ya sabes crear filas y leerlas. Cambiarlas y borrarlas es igual de fácil, y justo por eso es peligroso: una sola línea puede modificar un millón de filas, y la base de datos no pregunta «¿estás seguro?». En esta sección aprenderás las dos instrucciones y las redes de seguridad que usan los equipos profesionales.

UPDATE: cambiar filas

UPDATE cambia los valores de las filas que cumplen el WHERE. En SET escribes qué columnas cambian y su valor nuevo, que puede calcularse a partir del actual:

-- Cambiar dos columnas de un juego concreto
UPDATE juegos
SET precio = 18, genero = 'aventura'
WHERE id = 1;

-- Rebajar un 10 % todos los juegos de rol
UPDATE juegos
SET precio = precio * 0.9
WHERE genero = 'rpg';

DELETE: borrar filas

DELETE FROM borra las filas que cumplen el WHERE. No hay papelera de reciclaje: lo borrado desaparece.

DELETE FROM juegos WHERE id = 8;

Error común

Olvidar el WHERE. UPDATE juegos SET precio = 0; pone gratis todos los juegos, y DELETE FROM clientes; borra a todos los clientes. No es un error de sintaxis, así que la base de datos lo ejecuta sin rechistar. Es uno de los accidentes más famosos del oficio: casi toda persona que trabaja con bases de datos tiene una historia sobre él.

Primero SELECT, después UPDATE

Antes de un UPDATE o un DELETE importante, escribe la misma consulta como SELECT con el mismo WHERE. Mira qué filas salen y cuántas son. Solo cuando coincidan con lo que esperas, cambia la primera línea. Además, muchas apps no borran de verdad: añaden una columna borrado_en con la fecha, y las consultas filtran WHERE borrado_en IS NULL. Esto se llama borrado lógico (en inglés, soft delete) y permite deshacer errores y conservar el historial.

SQLite (desde la versión 3.35) y PostgreSQL permiten añadir RETURNING al final de un INSERT, UPDATE o DELETE para que te devuelva las filas afectadas, ya cambiadas. MySQL no lo tiene. Es muy útil desde una API: insertas un juego y en la misma orden recibes el id que le tocó.

En este taller vas a practicar el método completo. COUNT(*) cuenta filas; lo verás a fondo en la sección Agrupar y resumir.

Ahora provoca el accidente a propósito, aquí donde no hace daño: en el paso 2, borra la línea WHERE genero = 'rpg' y ejecuta. RETURNING te enseña las ocho filas rebajadas. En una tienda real, acabas de bajar el precio de todo el catálogo.

Transacciones: todo o nada

Algunos cambios solo tienen sentido juntos. En un juego, Ana le pasa 50 monedas a Leo: hay que restarle 50 a ella y sumárselas a él. Si el servidor se cae entre las dos órdenes, las monedas desaparecen. Una transacción es un grupo de operaciones que la base de datos trata como una sola: o se aplican todas, o ninguna.

  • BEGIN empieza la transacción.
  • COMMIT («confirmar») aplica todos los cambios a la vez, de forma definitiva.
  • ROLLBACK («volver atrás») los descarta todos, como si nunca hubieran ocurrido.

El «borrador» es una forma de imaginarlo. Por dentro, cada motor lo hace a su manera, con el diario o el registro de escritura anticipada que viste al principio de la estación, pero el efecto es el de la animación. Pruébalo. Predice qué mostrarán las dos consultas SELECT:

Dentro de la transacción ves los cambios, porque son tuyos. Después de ROLLBACK, todo vuelve a como estaba. Modifica: cambia ROLLBACK por COMMIT y comprueba que ahora los cambios se quedan. Después cambia los dos 50 por 150: Ana no tiene tanto, y la restricción CHECK (monedas >= 0) detiene la operación con un error.

Si algo falla dentro, tú decides

Cuando una orden falla dentro de una transacción, la base de datos rechaza esa orden, pero la transacción sigue abierta esperando tu decisión. En SQLite podrías seguir y confirmar el resto; PostgreSQL ya no acepta nada más que ROLLBACK. La regla segura, en cualquier motor, es que tu programa haga ROLLBACK en cuanto algo falle. Verás cómo se escribe en código en la sección Desde tu código.

Cuando no escribes BEGIN, cada instrucción suelta funciona como una transacción de una sola orden: se confirma sola al terminar. Por eso un UPDATE que cambia mil filas nunca se queda a medias: o cambian las mil, o ninguna.

ACID: las cuatro garantías

Las transacciones de las bases de datos relacionales cumplen cuatro propiedades que se conocen por sus iniciales en inglés, ACID:

LetraPropiedadQué garantizaEn la transferencia
AAtomicidadTodo o nada: la transacción no se divideNunca se resta a Ana sin sumar a Leo
CConsistenciaSe pasa de un estado válido a otro válido: todas las restricciones se cumplen al terminarEl CHECK impide saldos negativos
IAislamiento (isolation)Las transacciones simultáneas no ven los cambios a medias de las demásNadie ve a Ana con 50 y a Leo con 20
DDurabilidadLo confirmado sobrevive a un apagónTras COMMIT, el cambio ya está en el disco

El aislamiento tiene grados. Aislar por completo cada transacción es lo más seguro pero obliga a esperar más, así que los motores ofrecen varios niveles de aislamiento y cada uno elige uno por defecto: PostgreSQL usa read committed (cada orden ve lo que ya estaba confirmado cuando empezó) y SQLite deja escribir a una sola transacción a la vez. Para empezar, los valores por defecto son razonables; cuando trabajes con dinero o inventarios, lee la documentación de tu motor sobre este tema.

La actualización perdida puede volver

Una base de datos no te protege si tu programa lee un valor, lo calcula en JavaScript y escribe el resultado: const n = leerVisitas(); guardarVisitas(n + 1); tiene el mismo problema que el archivo del principio, porque entre la lectura y la escritura otra petición puede colarse. Haz la cuenta dentro de la propia orden (SET visitas = visitas + 1), como en el primer taller de la estación.

Relacionar tablas: claves foráneas y JOIN

La tienda necesita guardar las compras: quién compró qué juego, cuándo y por cuánto. La primera idea es una tabla con todo junto: el nombre y el correo del cliente, el título del juego, la fecha. Pero si Ana compra diez juegos, su nombre y su correo se repiten diez veces. Si cambia de correo, hay que cambiarlo en diez filas, y si se te olvida una, la base de datos tendrá dos correos distintos para la misma persona.

La solución relacional es guardar cada cosa una sola vez, en su tabla, y conectar las tablas con números. Cada compra no guarda el nombre de la clienta: guarda su id. Una clave foránea (en inglés, foreign key) es una columna cuyo valor debe existir como clave primaria en otra tabla. Se declara con REFERENCES:

CREATE TABLE compras (
  id            INTEGER PRIMARY KEY,
  cliente_id    INTEGER NOT NULL REFERENCES clientes(id),
  juego_id      INTEGER NOT NULL REFERENCES juegos(id),
  fecha         TEXT NOT NULL,
  precio_pagado REAL NOT NULL
);

Con esa declaración, la base de datos rechaza una compra de un cliente que no existe y, si alguien intenta borrar a un cliente que tiene compras, también se niega. Así nunca quedan filas huérfanas: compras que apuntan a nadie.

¿No es repetir el precio?

precio_pagado parece una copia de juegos.precio, pero no lo es: es otro dato. El precio del catálogo cambia con las rebajas; lo que pagó Ana el 1 de septiembre no debe cambiar nunca. Antes de eliminar una columna «repetida», pregúntate si guarda lo mismo o un hecho distinto.

Tipos de relaciones

La cardinalidad de una relación dice cuántas filas de una tabla pueden conectarse con cuántas de la otra. Hay tres casos:

RelaciónSe leeEjemploCómo se guarda
Uno a uno (1:1)Cada A tiene como mucho un BUna cuenta y su perfilClave foránea con UNIQUE, o todo en la misma tabla
Uno a muchos (1:N)Cada A tiene muchos B; cada B es de un solo AUn cliente y sus comprasClave foránea en el lado «muchos»: compras.cliente_id
Muchos a muchos (N:M)Cada A tiene muchos B y cada B, muchos AClientes y juegos; jugadores y logrosUna tabla intermedia con dos claves foráneas

La tabla compras es justamente la tabla intermedia entre clientes y juegos: un cliente compra muchos juegos y un juego lo compran muchos clientes. A veces la tabla intermedia no tiene datos propios, solo las dos claves. Entonces su clave primaria suele ser la pareja de columnas, una clave compuesta:

CREATE TABLE jugador_logros (
  jugador_id INTEGER NOT NULL REFERENCES jugadores(id),
  logro_id   INTEGER NOT NULL REFERENCES logros(id),
  fecha      TEXT NOT NULL,
  PRIMARY KEY (jugador_id, logro_id)   -- el mismo logro no se gana dos veces
);

Las claves foráneas en SQLite

Aquí SQLite vuelve a sorprender: por compatibilidad con programas antiguos, no comprueba las claves foráneas si no se lo pides. Hay que activarlas en cada conexión con PRAGMA foreign_keys = ON;. Un PRAGMA es una orden especial de SQLite para cambiar su configuración. El módulo node:sqlite de Node.js y la librería better-sqlite3 las activan por defecto; la terminal de SQLite y otras librerías no. PostgreSQL y MySQL las comprueban siempre.

¿Y si de verdad quieres borrar un cliente con compras? Al declarar la clave foránea puedes decidir qué pasa con ON DELETE: con RESTRICT (o sin nada), el borrado se rechaza; con CASCADE, se borran también sus compras; con SET NULL, las compras se quedan con cliente_id vacío. Piensa bien antes de usar CASCADE: borrar a una clienta se llevaría por delante el historial de ventas de la tienda.

JOIN: combinar tablas en una consulta

Guardar cada cosa en su tabla es ordenado, pero para mostrar «Ana compró Bosque Eterno» necesitas juntar datos de dos o tres tablas. Eso hace JOIN («unir»). Mira cómo funciona con una versión reducida de los datos:

Escrito en SQL, el JOIN de la animación es así. JOIN a secas significa INNER JOIN:

SELECT clientes.nombre, compras.fecha
FROM compras
JOIN clientes ON clientes.id = compras.cliente_id;

Como hay columnas con el mismo nombre en varias tablas (las dos tienen id), se escribe tabla.columna para no dejar dudas. Para no repetir nombres largos se usan alias de tabla: FROM compras AS co JOIN clientes AS c ON c.id = co.cliente_id, y después c.nombre. La palabra AS es opcional.

Otros JOIN

Existen también RIGHT JOIN, que conserva todas las filas de la tabla de la derecha, y FULL OUTER JOIN, que conserva las de ambas. SQLite los admite desde la versión 3.39 (2022). Se usan poco: un RIGHT JOIN siempre puede escribirse como un LEFT JOIN con las tablas al revés, y la mayoría de los equipos prefiere leer siempre de izquierda a derecha.

Error común

Olvidar la condición ON. En SQL antiguo verás FROM clientes, compras WHERE clientes.id = compras.cliente_id, que funciona. Pero si se te olvida el WHERE, la base de datos combina cada cliente con cada compra: 5 clientes × 8 compras = 40 filas sin sentido. Se llama producto cartesiano, y con tablas grandes puede generar miles de millones de filas y bloquear el servidor. Si un JOIN devuelve muchas más filas de las que esperabas, revisa el ON.

Agrupar y resumir

Hasta ahora cada consulta devolvía filas de la tabla. Pero muchas preguntas piden un resumen: ¿cuánto vendimos este mes?, ¿cuál es el juego más caro?, ¿cuántas compras hizo cada cliente? En JavaScript lo harías con reduce y un objeto acumulador (Estación 11). En SQL lo hace la base de datos, con una línea.

Funciones de agregación

Una función de agregación recibe muchas filas y devuelve un solo valor:

FunciónDevuelve
COUNT(*)Cuántas filas hay
COUNT(columna)Cuántas filas tienen un valor que no es NULL en esa columna
COUNT(DISTINCT columna)Cuántos valores distintos hay
SUM(columna)La suma
AVG(columna)La media (el promedio)
MIN(columna), MAX(columna)El menor y el mayor

Todas ignoran los NULL, salvo COUNT(*), que cuenta filas enteras. Predice los resultados con la tabla de juegos que ya conoces (precios: 20, 10, 25, 15, 12.5, 30, 5 y 8):

GROUP BY: un resumen por grupo

GROUP BY reparte las filas en grupos que comparten un valor y calcula las funciones de agregación para cada grupo. El resultado tiene una fila por grupo.

Para entenderlo

Imagina que vacías una bolsa de monedas sobre la mesa y haces montones: uno de monedas de 1, otro de 5, otro de 10. Eso es GROUP BY valor. Después cuentas cada montón: eso es COUNT(*). La analogía cojea en un detalle: en la mesa ves las monedas sueltas dentro de cada montón; en SQL, después de agrupar, solo puedes pedir datos del montón entero (su valor común, cuántas hay, cuánto suman).

SELECT genero, COUNT(*) AS juegos, AVG(precio) AS precio_medio
FROM juegos
GROUP BY genero;
-- aventura | 1 | 20
-- carreras | 1 | 10
-- …
-- rpg      | 2 | 27.5    ← los dos rpg juntos en un grupo

Esa última idea es la regla de oro de GROUP BY: en el SELECT solo pueden aparecer las columnas por las que agrupas y funciones de agregación. Pedir titulo en la consulta anterior no tiene sentido: el grupo «rpg» tiene dos títulos, ¿cuál mostrarías?

SQLite lo deja pasar; PostgreSQL no

Si escribes una columna suelta que no está en el GROUP BY, SQLite no da error: te devuelve el valor de una fila cualquiera del grupo. PostgreSQL, en cambio, responde column "juegos.titulo" must appear in the GROUP BY clause or be used in an aggregate function. Que SQLite lo acepte no significa que esté bien: sigue la regla de oro y tus consultas funcionarán en cualquier motor.

HAVING: filtrar grupos

WHERE filtra filas antes de agrupar. Para filtrar después, según el resultado de cada grupo, se usa HAVING. Por ejemplo, «los géneros con más de un juego» es GROUP BY genero HAVING COUNT(*) > 1: no puedes ponerlo en el WHERE, porque cuando se ejecuta el WHERE todavía no existen los grupos ni sus cuentas.

Eso nos lleva a una idea que resuelve muchas dudas: una consulta no se ejecuta en el orden en que se escribe. Síguela paso a paso sobre una tabla de 10 partidas de un juego:

SELECT jugador, COUNT(*) AS partidas, MAX(puntos) AS record
FROM partidas
WHERE nivel >= 2
GROUP BY jugador
HAVING COUNT(*) >= 2
ORDER BY record DESC;

El orden completo es: FROM (con sus JOIN) → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Comprueba el resultado de la traza y después modifica la consulta: quita la línea del WHERE (¿cuántas partidas tiene ahora cada jugador?) y cambia el HAVING a >= 1 para que Sol aparezca.

Las cláusulas se escriben siempre en el mismo orden, aunque se ejecuten en otro. Ponlas en el orden correcto:

  1. SELECT c.nombre, COUNT(*) AS compras
  2. FROM clientes AS c
  3. JOIN compras AS co ON co.cliente_id = c.id
  4. WHERE co.fecha >= '2026-09-01'
  5. GROUP BY c.nombre
  6. HAVING COUNT(*) >= 2
  7. ORDER BY compras DESC
  8. LIMIT 3;

Subconsultas: una pregunta dentro de otra

A veces, para responder una pregunta primero necesitas la respuesta de otra. «¿Qué juegos cuestan más que la media?» exige calcular antes la media. Una subconsulta es un SELECT entre paréntesis dentro de otra consulta. Se usa de tres formas principales:

  • Como un valor: WHERE precio > (SELECT AVG(precio) FROM juegos). La subconsulta devuelve un solo número.
  • Como una lista: WHERE id IN (SELECT juego_id FROM compras) se queda con los juegos que aparecen en alguna compra.
  • Como una comprobación: WHERE EXISTS (SELECT 1 FROM …) es verdadero si la subconsulta devuelve al menos una fila. Suele mirar la fila de fuera, y entonces se llama subconsulta correlacionada.

Cuando una consulta se complica, WITH permite darle nombre a una subconsulta y usarla después como si fuera una tabla. Se llama expresión de tabla común (en inglés, common table expression, CTE) y hace que la consulta se lea de arriba abajo, como una receta.

La consulta 2 da la misma respuesta que el truco del LEFT JOIN: Iván. En SQL suele haber varias formas de llegar al mismo resultado. Elige la que mejor se lea; si una va lenta, la herramienta del final de la próxima sección te dirá por qué. Modifica la consulta 1 para que muestre los juegos que cuestan menos que la media.

Error común

Usar NOT IN con una subconsulta que puede devolver NULL. Si la lista contiene un solo NULL, x NOT IN (lista) nunca es verdadero, por el mismo motivo que = NULL: «¿es x distinto de un valor desconocido?» no se sabe. La consulta devuelve cero filas sin avisar. Para «los que no tienen…», usa NOT EXISTS o el LEFT JOIN … IS NULL, que no tienen esa trampa.
