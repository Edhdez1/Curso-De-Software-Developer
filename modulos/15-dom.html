Lo que vas a lograr

Hasta ahora tus programas escribían en la consola y terminaban. Las páginas que construiste en HTML y CSS se veían bien, pero no hacían nada. En esta estación juntas las dos cosas: JavaScript toma el control de la página, cambia lo que se ve, responde cuando alguien hace clic o pulsa una tecla, revisa formularios y recuerda datos aunque cierres el navegador. Es el paso que convierte una página en una aplicación.

  • Explicar qué es el DOM y cómo el navegador convierte tu HTML en un árbol de objetos que JavaScript puede cambiar.
  • Conectar JavaScript a una página con <script defer> y entender por qué a veces un elemento «no existe» todavía.
  • Encontrar elementos con querySelector, querySelectorAll y getElementById.
  • Cambiar textos, atributos, clases y estilos, y saber por qué textContent es más seguro que innerHTML.
  • Crear, insertar y eliminar elementos a partir de una lista de datos.
  • Reaccionar a clics, teclas y cambios en formularios con addEventListener y el objeto evento.
  • Aprovechar la propagación de eventos para atender muchos elementos con un solo escuchador (delegación).
  • Validar formularios con JavaScript sin que la página se recargue.
  • Guardar datos en el navegador con localStorage y JSON para que sobrevivan a una recarga.
  • Organizar una aplicación pequeña con el patrón «estado → vista» y animar cosas con temporizadores y requestAnimationFrame.

Qué es el DOM

Un archivo HTML es texto. Un texto no puede cambiar mientras lo miras: si quieres que el título de tu tienda diga «Ofertas» en vez de «Tienda», tendrías que editar el archivo y volver a cargarlo. Sin embargo, en cualquier web moderna las cosas cambian delante de ti: el carrito suma productos, aparece un mensaje de error, se marca una tarea como hecha. ¿Cómo lo hacen?

La respuesta es que el navegador no dibuja la pantalla a partir del archivo. Cuando carga una página, lee el HTML de arriba abajo y construye en su memoria una estructura de objetos (fichas con propiedades, como las que viste en la Estación 11), uno por cada etiqueta y cada trozo de texto. Esa estructura se llama DOM, siglas de Document Object Model, «modelo de objetos del documento». La pantalla se dibuja a partir del DOM. Y JavaScript puede cambiar el DOM: cuando lo hace, el navegador vuelve a dibujar la parte afectada.

Para entenderlo

El HTML es el plano de una casa. El DOM es la casa ya construida, con sus muebles. JavaScript es una persona que vive dentro y puede mover los muebles, pintar una pared o añadir una silla mientras tú miras. El plano no cambia. La analogía tiene un límite importante: si recargas la página, el navegador derriba la casa y la vuelve a construir desde el plano, así que todo lo que JavaScript había cambiado se pierde. Para que algo sobreviva a una recarga tendrás que guardarlo aparte (lo harás en la sección Recordar datos).

El DOM tiene forma de árbol, aunque dibujado al revés: la raíz arriba y las ramas hacia abajo. Cada pieza del árbol se llama nodo. Mira cómo se construye:

Padres, hijos y hermanos

Como en un árbol genealógico, cada nodo tiene un padre (el nodo del que cuelga) y puede tener hijos (los que cuelgan de él). Los nodos con el mismo padre son hermanos. En la animación, ul es el padre de los dos li, y esos li son hermanos entre sí. Estas palabras aparecen en los nombres de muchas herramientas del DOM: parentElement, children, nextElementSibling…

En la cima de todo está document. Es un objeto que el navegador crea automáticamente y que tu JavaScript puede usar sin declararlo. Casi todo lo que harás en esta estación empieza escribiendo document. y algo más.

Los espacios también son nodos

Los saltos de línea y los espacios que usas para sangrar tu HTML también se convierten en nodos de texto (invisibles). Por eso existen dos formas de pedir los hijos de un elemento: children devuelve solo los elementos, y childNodes devuelve todos los nodos, incluidos esos textos de espacios. Casi siempre querrás children.

El DOM no es parte de JavaScript

Esto sorprende a mucha gente: document no es parte del lenguaje JavaScript. Es una herramienta que el navegador le presta a JavaScript. A estas herramientas del navegador se les llama API web (Web APIs; una API es un conjunto de funciones y objetos que un programa ofrece para que otros lo usen). Por eso, si escribes document en Node.js, obtienes ReferenceError: document is not defined: Node.js no es un navegador y no tiene página que mostrar.

Los talleres de las estaciones anteriores tampoco tenían document, porque ejecutaban tu código en segundo plano, sin página. Los de esta estación son distintos: se llaman talleres web y tienen tres pestañas (HTML, CSS y JS) y una vista previa donde se ve la página que construyes. La consola sigue debajo, con el rótulo «Consola de la página».

Mira el DOM con tus propios ojos

Las herramientas de desarrollo del navegador (las abriste en la Estación 12 con F12) tienen un panel llamado Elementos (Elements en Chrome; Inspector en Firefox). Conectar el JavaScript y encontrar elementos

Para que tu JavaScript trabaje sobre una página, primero hay que cargarlo desde el HTML, y después tiene que encontrar los elementos que quiere cambiar. Las dos cosas esconden un error clásico, así que vamos por partes.

Dónde va la etiqueta <script>

Lo habitual es escribir el JavaScript en un archivo aparte (por ejemplo, app.js) y enlazarlo desde el <head> con el atributo defer, que significa «aplazar»:

<!doctype html>
<html lang="es">
  <head>
    <meta charset="utf-8">
    <title>Mi tienda</title>
    <link rel="stylesheet" href="estilos.css">
    <script src="app.js" defer></script>
  </head>
  <body>
    <h1>Tienda</h1>
  </body>
</html>

¿Por qué defer? Porque el navegador lee el HTML de arriba abajo. Cuando encuentra un <script> normal, se detiene, lo descarga, lo ejecuta y solo entonces sigue leyendo. Si ese script está en el <head>, se ejecuta cuando el <body> todavía no existe: tu código busca el h1 y no lo encuentra.

Resumen de las opciones:

  • <script src="app.js" defer> en el <head>: la opción recomendada hoy. Se descarga en paralelo mientras se lee el HTML y se ejecuta cuando el documento ya está completo, justo antes del evento DOMContentLoaded («contenido del DOM cargado»). Si hay varios scripts con defer, se ejecutan en el orden en que aparecen.
  • <script> al final del <body>: la forma clásica. Funciona porque, cuando se llega a él, todo lo anterior ya existe. La verás en muchos tutoriales antiguos.
  • <script type="module">: los módulos se aplazan solos, como si tuvieran defer. Los estudiarás en la Estación 22.
  • async: descarga en paralelo y ejecuta en cuanto llega, sin esperar al HTML ni respetar el orden. Sirve para scripts independientes (como un contador de visitas), no para el código que maneja tu página.

Cuidado

defer solo funciona con scripts externos, los que tienen src. En un <script> con el código escrito dentro, defer no tiene ningún efecto. En los talleres de esta estación, tu JavaScript se coloca automáticamente al final del <body>, así que el HTML ya existe cuando se ejecuta.

Encontrar elementos con selectores de CSS

Para cambiar un elemento, primero hay que tenerlo en una variable. La herramienta principal es querySelector («consulta con selector»). Recibe un texto con un selector de CSS, exactamente los mismos que usaste en la Estación 14, y devuelve el primer elemento que coincide:

const titulo = document.querySelector("h1");               // por etiqueta
const carrito = document.querySelector("#carrito");         // por id
const precio = document.querySelector(".precio");           // por clase (el primero)
const boton = document.querySelector("form button");        // descendiente
const tercero = document.querySelector("li:nth-child(3)");  // pseudoclase
const juego = document.querySelector('[data-id="7"]');      // por atributo

Si no hay ningún elemento que coincida, querySelector devuelve null. No da error en ese momento: el error aparece después, cuando intentas usar ese null.

Para obtener todos los que coinciden, usa querySelectorAll. Devuelve una NodeList, una lista de nodos que se parece a un array: tiene length, se accede por posición (lista[0]) y se puede recorrer con forEach o con for...of.

const precios = document.querySelectorAll(".precio");
console.log(precios.length);       // cuántos hay
precios.forEach((p) => {
  console.log(p.textContent);
});

Hay una tercera forma, más antigua y muy común: getElementById. Busca por id y, como ya sabe que es un id, se escribe sin la almohadilla:

const carrito = document.getElementById("carrito");  // sin #

El error más famoso del DOM

Tarde o temprano verás esto en la consola: TypeError: Cannot read properties of null (reading 'addEventListener') (en Firefox dice document.querySelector(...) is null). Significa que intentaste usar un elemento que no se encontró. Las causas, de más a menos frecuente:

  • Olvidaste el # o el . del selector: querySelector("carrito") busca una etiqueta <carrito>, que no existe.
  • El script se ejecutó antes de que existiera el HTML (falta defer).
  • El nombre no coincide: id="Carrito" y "#carrito" son distintos, porque mayúsculas y minúsculas importan.
  • El elemento todavía no existe porque lo crea tu propio código más adelante.

Para investigarlo, imprime el resultado justo después de buscarlo: console.log(boton). Si ves null, el problema está en la búsqueda, no en lo que haces después.

Una lista no es un elemento

querySelectorAll devuelve una lista, aunque solo encuentre un elemento. Si escribes document.querySelectorAll(".precio").textContent = "0" no pasa nada, y document.querySelectorAll("button").addEventListener(...) da TypeError: ... addEventListener is not a function. A una lista hay que recorrerla con forEach y actuar sobre cada elemento.

Una NodeList no es un array

La NodeList tiene forEach, pero no tiene map, filter ni reduce. Si los necesitas, conviértela primero: Array.from(lista) o [...lista]. Además, la lista de querySelectorAll es una foto fija: si después añades más elementos a la página, la lista no se actualiza sola. Existen métodos más antiguos, como getElementsByClassName, que devuelven listas «vivas» que sí cambian; son fuente de sorpresas, así que en código nuevo se prefiere querySelectorAll.

Cambiar lo que se ve

Ya sabes encontrar un elemento. Ahora toca cambiarlo: su texto, sus atributos, sus clases y su estilo. Cada una de estas cosas tiene su herramienta, y elegir la correcta evita errores y problemas de seguridad.

El texto: textContent

textContent es una propiedad de todo elemento que contiene su texto, sin etiquetas. Puedes leerla y puedes asignarle un valor nuevo:

const saldo = document.querySelector("#saldo");
console.log(saldo.textContent);    // lee: "0 monedas"
saldo.textContent = "150 monedas"; // escribe: la pantalla cambia

Al asignar, todo lo que había dentro del elemento se sustituye por ese texto, incluidos otros elementos hijos. Y si el texto contiene algo parecido a una etiqueta, como "<b>hola</b>", se muestra literalmente, con los símbolos < y > a la vista. Eso, que parece una limitación, es justo lo que la hace segura.

¿Y innerText?

Verás también innerText. Se parece, pero tiene en cuenta el CSS: no devuelve el texto de elementos ocultos y, para calcularlo, el navegador tiene que revisar los estilos de la página, lo que lo hace más lento. Para leer y escribir texto, usa textContent salvo que necesites exactamente ese comportamiento.

HTML dentro del elemento: innerHTML y su peligro

innerHTML lee y escribe el contenido de un elemento como HTML. Al asignarle un texto, el navegador lo analiza y crea los elementos que encuentre:

const aviso = document.querySelector("#aviso");
aviso.innerHTML = "Envío <strong>gratis</strong> hoy";  // "gratis" sale en negrita

Es cómodo, y por eso aparece en muchísimos tutoriales. Pero esconde uno de los problemas de seguridad más comunes de la web. Imagina una página de comentarios que muestra lo que escribe cada persona con innerHTML. Alguien escribe esto como «comentario»:

<img src="no-existe.png" onerror="robarSesion()">

El navegador crea una imagen, la imagen no carga, y al fallar ejecuta el código del atributo onerror. Ese código corre en la página de cada persona que lea el comentario, con acceso a todo lo que la página puede hacer. Este ataque se llama XSS (cross-site scripting, «ejecución de código entre sitios»): colar código propio en una página ajena para que se ejecute en el navegador de otras personas.

Compruébalo en un entorno seguro. El «comentario» malicioso de este taller solo cambia el color de fondo, pero podría hacer cualquier cosa:

Con textContent, el comentario aparece tal cual, con sus símbolos, y no hace nada. Con innerHTML, la imagen rota se vuelve invisible y el código se ejecuta. Una curiosidad: un <script> insertado con innerHTML no se ejecuta, y por eso mucha gente cree que innerHTML es seguro. No lo es: atributos como onerror siguen funcionando.

Datos de personas con innerHTML

// nombre viene de un formulario
saludo.innerHTML = "Hola, " + nombre;

Datos de personas con textContent

// nombre viene de un formulario
saludo.textContent = "Hola, " + nombre;

Idea clave

Regla práctica: todo lo que venga de una persona (formularios, comentarios, nombres de usuario, datos de internet) se muestra con textContent o creando elementos (lo verás en la próxima sección). Reserva innerHTML para fragmentos que escribes tú en tu código y que no contienen datos de nadie más. En la Estación 31: Seguridad estudiarás XSS a fondo, junto con herramientas para limpiar HTML de forma segura.

Atributos

Los atributos del HTML (src, href, alt, disabled…) también se pueden leer y cambiar. Los más comunes están disponibles como propiedades con el mismo nombre:

const foto = document.querySelector("img");
foto.src = "gato.png";
foto.alt = "Un gato naranja durmiendo";

const enlace = document.querySelector("a");
enlace.href = "https://developer.mozilla.org/es/";

const boton = document.querySelector("#comprar");
boton.disabled = true;     // el botón se desactiva
boton.hidden = true;       // el botón se oculta

Para cualquier atributo, exista como propiedad o no, hay cuatro métodos genéricos:

boton.setAttribute("aria-label", "Añadir al carrito");  // crea o cambia
boton.getAttribute("aria-label");                         // lee (o null)
boton.hasAttribute("disabled");                           // true o false
boton.removeAttribute("disabled");                        // lo quita

Hay un tipo de atributo pensado para guardar tus propios datos en el HTML: los que empiezan por data-. Desde JavaScript se leen con la propiedad dataset. El nombre pierde el data- y, si tiene guiones, pasa a camelCase:

<button data-producto="42" data-precio-unidad="3.50">Añadir</button>
const boton = document.querySelector("button");
console.log(boton.dataset.producto);       // "42"  (texto, no número)
console.log(boton.dataset.precioUnidad);   // "3.50"
boton.dataset.estado = "en-carrito";       // crea data-estado="en-carrito"

Cuidado

Todo lo que lees de un atributo es texto. dataset.producto vale "42", no 42. Si vas a hacer cuentas, conviértelo con Number(), como aprendiste en la Estación 7.

Clases: la forma recomendada de cambiar el aspecto

En la Estación 14 aprendiste que el aspecto vive en el CSS. La mejor manera de que JavaScript cambie el aspecto de algo es poner o quitar clases, y dejar que el CSS diga cómo se ve cada clase. Para eso existe classList:

const tarjeta = document.querySelector(".tarjeta");
tarjeta.classList.add("seleccionada");      // añade
tarjeta.classList.remove("seleccionada");   // quita
tarjeta.classList.toggle("favorita");       // la pone si no está; la quita si está
tarjeta.classList.contains("favorita");     // true o false
tarjeta.classList.replace("nueva", "vista"); // cambia una por otra

toggle (en español, «alternar», como un interruptor) es perfecto para botones de encender y apagar: modo oscuro, mostrar u ocultar un menú, marcar un favorito. Acepta un segundo argumento opcional que fuerza el resultado: toggle("agotado", stock === 0) pone la clase si la condición es true y la quita si es false.

Error común

Existe también className, que contiene todas las clases en un solo texto. Si escribes tarjeta.className = "seleccionada", borras todas las demás clases que tuviera la tarjeta. Usa classList.

Estilos directos: style

A veces el valor no se puede decidir de antemano en el CSS: el ancho de una barra de vida que depende de los puntos, la posición de un personaje. Para eso está la propiedad style, que escribe estilos directamente en el elemento. Las propiedades de CSS con guion se escriben en camelCase y los valores siempre son textos con su unidad:

const barra = document.querySelector(".barra-vida");
barra.style.width = "75%";              // width: 75%
barra.style.backgroundColor = "gold";   // background-color: gold
barra.style.setProperty("--vida", "75%"); // una variable CSS (Estación 14)

Cuidado

elemento.style.color solo devuelve los estilos escritos directamente en el elemento, no los que vienen de tu hoja de CSS. Si lees style.color de un párrafo pintado de rojo desde el CSS, obtienes "". Para saber el estilo final, se usa getComputedStyle(elemento).color. Y cuidado con hidden: si tu CSS le da display: flex o display: block a ese elemento, ese display gana y el elemento sigue visible aunque tenga hidden.

Consejo de oficio

En los equipos profesionales, JavaScript cambia estados (clases como abierto, error, cargando) y el CSS decide el aspecto de cada estado. Así, quien diseña puede cambiar colores y tamaños sin tocar el JavaScript, y el JavaScript no se llena de colores escritos a mano. Usa style solo para valores que se calculan en el momento.

Crear, insertar y eliminar elementos

Una tienda no escribe a mano en el HTML cada producto: tiene una lista de datos y genera un elemento por cada uno. Un juego crea un elemento cuando aparece un enemigo y lo elimina cuando lo derrotas. Para eso necesitas fabricar elementos desde JavaScript.

El proceso siempre tiene tres pasos: crear, configurar e insertar.

// 1. Crear: el elemento existe, pero todavía no está en la página
const li = document.createElement("li");

// 2. Configurar: texto, clases, atributos...
li.textContent = "Comprar pan";
li.classList.add("tarea");

// 3. Insertar: ahora sí aparece en pantalla
const lista = document.querySelector("#tareas");
lista.append(li);

document.createElement("etiqueta") fabrica un elemento nuevo en la memoria. Hasta que no lo insertas, es como un mueble que compraste pero sigue en la caja: existe, pero no está en la casa. Hay varias formas de insertarlo, según dónde lo quieras:

MétodoDónde queda el nuevo elemento
padre.append(nuevo)Dentro de padre, al final
padre.prepend(nuevo)Dentro de padre, al principio
referencia.before(nuevo)Fuera, justo antes de referencia (como hermano)
referencia.after(nuevo)Fuera, justo después de referencia
padre.appendChild(nuevo)Como append, pero más antiguo: acepta un solo nodo y no acepta textos

append admite varios elementos a la vez, e incluso textos: parrafo.append("Precio: ", fuerte). Para eliminar, cada elemento tiene remove(): li.remove(). Y para vaciar un elemento de golpe, lista.replaceChildren() sin argumentos lo deja sin hijos (también funciona lista.textContent = "").

Un nodo solo puede estar en un sitio

Si haces append de un elemento que ya está en la página, no se copia: se mueve a su nuevo sitio. Si necesitas una copia, usa elemento.cloneNode(true) (el true copia también todo lo que hay dentro).

De una lista de datos a una lista en pantalla

Lo más habitual es recorrer un array y crear un elemento por cada dato. Sigue este programa paso a paso. La memoria de la derecha muestra también en qué estado está la lista de la página:

const compras = ["Pan", "Leche"];
const lista = document.querySelector("#lista");
for (const producto of compras) {
  const li = document.createElement("li");
  li.textContent = producto;
  lista.append(li);
}
console.log(lista.children.length);

Cuando cada elemento tiene varias partes (una tarjeta con nombre, precio y botón), conviene meter la fabricación en una función que recibe un dato y devuelve un elemento. Así el bucle queda corto y la función se puede reutilizar:

function crearTarjeta(producto) {
  const tarjeta = document.createElement("article");
  tarjeta.classList.add("tarjeta");

  const nombre = document.createElement("h3");
  nombre.textContent = producto.nombre;

  const precio = document.createElement("p");
  precio.textContent = producto.precio.toFixed(2) + " €";

  tarjeta.append(nombre, precio);
  return tarjeta;
}

productos.forEach((p) => catalogo.append(crearTarjeta(p)));

innerHTML += dentro de un bucle

Muchos tutoriales construyen listas así: lista.innerHTML += "<li>" + producto + "</li>". Además del riesgo de XSS si producto viene de una persona, cada += obliga al navegador a convertir toda la lista en texto, añadir el trozo nuevo y volver a construir todos los elementos desde cero. Con cien productos es lento, y cualquier escuchador de eventos que tuvieran los elementos anteriores se pierde, porque ya no son los mismos elementos. createElement y append no tienen ninguno de esos problemas.

Ejecuta el taller. Después modifícalo: añade un producto al array, haz que los productos en oferta lleven la clase oferta y, como reto, muestra solo las ofertas usando filter antes de recorrer.

Consejo de oficio

Cuando una pieza tiene mucha estructura, algunos equipos la escriben una sola vez en el HTML dentro de una etiqueta <template> (su contenido no se muestra) y la copian con cloneNode(true) cada vez que la necesitan. Es otra forma válida de separar la estructura del código. Y cuando una aplicación tiene cientos de piezas que cambian, se suele recurrir a bibliotecas como React, que verás en la Estación 32 y que hacen este trabajo por ti.

Eventos: reaccionar a lo que hace la persona

Todos los programas que escribiste hasta ahora se ejecutaban de arriba abajo y terminaban. Una página interactiva funciona de otra manera: carga, prepara todo y después espera. Nadie sabe cuándo vas a pulsar el botón de comprar, ni si lo vas a pulsar. El programa tiene que estar listo para reaccionar en cualquier momento. A esta forma de programar se le llama programación dirigida por eventos.

Un evento es un aviso que da el navegador cuando pasa algo: un clic, una tecla pulsada, un cambio en un campo de texto, el envío de un formulario, el final de la carga de la página. Tú no puedes provocar el clic de la persona, pero puedes decirle al navegador: «cuando pase esto en este elemento, ejecuta esta función». Esa función se llama escuchador de eventos (en inglés, event listener; también verás «manejador» o handler). Se registra con addEventListener:

const boton = document.querySelector("#comprar");

boton.addEventListener("click", () => {
  console.log("¡Clic en comprar!");
});

El primer argumento es el tipo de evento, como texto ("click"). El segundo es la función que se ejecutará cada vez que ocurra. Es un callback, una función que le pasas a otra para que la llame cuando toque, como viste en la Estación 10. Mira qué pasa por dentro:

Pasar la función, no llamarla

Compara boton.addEventListener("click", sumar) con boton.addEventListener("click", sumar()). La primera entrega la función al navegador. La segunda la ejecuta en ese momento, una sola vez, y entrega lo que devuelve (normalmente undefined). Resultado: la función corre al cargar la página y después los clics no hacen nada. Si necesitas pasarle argumentos, envuélvela en una función flecha: addEventListener("click", () => sumar(5)).

Ejecuta el taller, haz clic varias veces y fíjate en qué línea de la consola aparece primero. Después, haz las modificaciones de los comentarios.

La línea «Código terminado» aparece antes que cualquier clic, aunque esté escrita al final. El código de arriba abajo termina enseguida; las funciones de los escuchadores se ejecutan después, cada vez que ocurre el evento.

El objeto evento

Cuando el navegador llama a tu función, le pasa como argumento un objeto evento con información sobre lo que ocurrió. Para usarlo, basta con ponerle nombre al parámetro. Se suele llamar evento, event o, para abreviar, e:

boton.addEventListener("click", (evento) => {
  console.log(evento.type);               // "click"
  console.log(evento.target.textContent); // el texto del botón pulsado
});

Las propiedades más útiles:

evento.targetEl elemento donde ocurrió el evento (el objetivo).
evento.currentTargetEl elemento que tiene el escuchador que se está ejecutando. Lo entenderás en la sección Propagación.

Idea clave

Para acciones, usa siempre un <button> y el evento click. Un botón de verdad ya se puede usar con el teclado (tabulador para llegar, Enter o Espacio para pulsar) y los lectores de pantalla lo anuncian como botón. Si pones un click sobre un <div>, las personas que no usan ratón no podrán activarlo.

input y change: dos momentos distintos

Los dos eventos avisan de cambios en un campo, pero en momentos diferentes. input salta con cada letra que escribes. change salta cuando la persona «confirma» el cambio: en un campo de texto, al salir de él (con el tabulador o haciendo clic fuera); en una casilla de verificación o una lista desplegable, en cuanto eliges. Para leer lo que hay escrito se usa la propiedad value, y para las casillas, checked (true o false).

Predice: si escribes «Ana» en el campo de nombre y después haces clic fuera, ¿cuántas líneas input y cuántas change aparecerán en la consola? Compruébalo.

Al escribir «Ana» sobre un campo vacío verás tres líneas input (una por letra) y una sola change cuando salgas del campo. La lista de equipos y la casilla disparan change en cuanto eliges. Por eso input es el adecuado para vistas previas en vivo, y change para reaccionar a una decisión terminada.

Cuidado

value siempre es un texto, aunque el campo sea type="number". Si escriben 5 en un campo numérico, campo.value vale "5". Para hacer cuentas, conviértelo con Number(campo.value) o usa campo.valueAsNumber, que en los campos numéricos devuelve directamente un número (o NaN si está vacío).

El teclado

Para atajos de teclado y controles de juegos se usa keydown, que salta al bajar una tecla. Normalmente se escucha en document, para que funcione esté donde esté el foco. El objeto evento trae dos propiedades clave:

  • evento.key: el carácter o el nombre de la tecla, según la distribución del teclado y las teclas modificadoras. "a", "A" si se pulsa con Mayús, "Enter", "Escape", "ArrowLeft", y " " (un espacio) para la barra espaciadora.
  • evento.code: la posición física de la tecla, sin importar qué letra tenga impresa: "KeyA", "Space", "ArrowLeft". Es lo que conviene para los controles W, A, S, D de un juego: en un teclado francés (AZERTY), la tecla que ocupa el lugar de la W escribe una Z, pero su code sigue siendo "KeyW".

Si mantienes una tecla pulsada, keydown se repite varias veces por segundo y evento.repeat vale true en las repeticiones. keyup salta al soltar. Quizá veas también keypress en tutoriales antiguos: está obsoleto y no debe usarse.

Cuidado

Los eventos de teclado van al elemento que tiene el foco. En estos talleres, la vista previa es un marco aparte dentro de la página del curso: si el teclado no responde, haz clic dentro de la vista previa antes de pulsar teclas. En tu propia página pasa algo parecido si el foco está, por ejemplo, dentro de un campo de texto.

Quitar un escuchador

A veces un escuchador debe dejar de funcionar: un botón de «empezar partida» que solo sirve una vez, un juego que termina. removeEventListener lo quita, pero necesita la misma función que usaste al registrarlo, así que esa función debe tener nombre:

function mover(evento) { /* ... */ }

document.addEventListener("keydown", mover);
// ...cuando termina la partida:
document.removeEventListener("keydown", mover);

// Para algo que solo debe ocurrir una vez existe una opción directa:
botonEmpezar.addEventListener("click", empezarPartida, { once: true });

Otras formas que verás por ahí

En código antiguo aparecen escuchadores escritos en el propio HTML, como <button onclick="comprar()">, o asignados con una propiedad, como boton.onclick = comprar. Funcionan, pero mezclan HTML y JavaScript, y la propiedad solo admite un escuchador por elemento: si asignas otro, borras el anterior. addEventListener permite varios y mantiene el código ordenado. Úsalo siempre en código nuevo.

Propagación y delegación de eventos

Imagina una lista de tareas con un botón «Borrar» en cada una. Con lo que sabes, pondrías un escuchador en cada botón. Funciona, pero tiene dos problemas: con 300 tareas son 300 escuchadores, y cada tarea nueva que se cree después necesita que le añadas el suyo, porque los escuchadores se registran sobre elementos que ya existen. Hay una solución mucho mejor, y se basa en cómo viajan los eventos por el árbol.

Cuando haces clic en un botón, el evento no se queda en el botón. Después de ocurrir allí, sube por el árbol: pasa por el padre del botón, por el padre de ese padre, y así hasta document. Cada elemento del camino que tenga un escuchador de ese tipo lo ejecuta. Este viaje se llama propagación, y a la fase de subida se le llama burbuja (en inglés, bubbling), porque el evento sube como una burbuja en el agua.

target y currentTarget

Ahora se entiende por qué el objeto evento tiene dos propiedades parecidas:

PropiedadEs…¿Cambia durante el viaje?
evento.targetEl elemento donde ocurrió el evento: el más profundo, el que se pulsó de verdad.No
evento.currentTargetEl elemento cuyo escuchador se está ejecutando ahora mismo.Sí, en cada parada

El target puede ser más pequeño de lo que crees

Si tu botón es <button class="borrar"><span>Borrar</span></button> y la persona hace clic justo sobre el texto, el target es el span, no el botón. Por eso, en lugar de comprobar evento.target directamente, se usa closest(selector): busca, empezando por el propio elemento y subiendo por sus antepasados, el primero que cumple el selector. Si no encuentra ninguno, devuelve null.

La delegación, paso a paso

El patrón de delegación siempre tiene la misma forma: un escuchador en un contenedor que no cambia, y dentro, averiguar qué elemento interesa a partir del target:

const lista = document.querySelector("#tareas");

lista.addEventListener("click", (evento) => {
  const boton = evento.target.closest("button.borrar");
  if (!boton) return;           // el clic no fue en un botón de borrar
  const tarea = boton.closest("li");
  tarea.remove();
});

La línea if (!boton) return; es importante: la lista recibe todos los clics que ocurren dentro de ella, también los que caen sobre el texto de una tarea o en el espacio entre tareas. Si el clic no vino de un botón de borrar, la función termina sin hacer nada.

Ordena las líneas de un escuchador delegado que borra una tarea y actualiza el contador:

  1. lista.addEventListener("click", (evento) => {
  2. const boton = evento.target.closest("button.borrar");
  3. if (!boton) return;
  4. const tarea = boton.closest("li");
  5. tarea.remove();
  6. actualizarContador();
  7. });

Ahora investiga la diferencia con el enfoque de «un escuchador por botón». Este taller usa ese enfoque. Pulsa «Añadir tarea» dos veces e intenta borrar las tareas nuevas. Predice antes: ¿funcionará?

Las tareas nuevas no se borran: el forEach se ejecutó una sola vez, al cargar, y en ese momento solo existían dos botones. Sustituye el enfoque A por el escuchador delegado que ordenaste arriba y vuelve a probar. Ahora todas las tareas se borran, las de antes y las de después, con un solo escuchador.

stopPropagation, con cuidado

evento.stopPropagation() detiene el viaje del evento: los elementos de más arriba no se enteran. A veces es necesario, por ejemplo para que un clic dentro de una ventana emergente no la cierre. Pero úsalo poco: otras partes de la página pueden depender de que los clics lleguen arriba (un menú que se cierra al hacer clic fuera, una herramienta de estadísticas), y cortar la propagación las rompe sin avisar. No lo confundas con preventDefault(), que cancela la acción del navegador pero deja que el evento siga subiendo.

La fase de captura

Antes de subir, el evento baja desde document hasta el objetivo. Esa bajada se llama fase de captura, y puedes escucharla con addEventListener("click", funcion, { capture: true }). Se usa muy poco. Tampoco todos los eventos suben: focus y blur, por ejemplo, no lo hacen (sus versiones focusin y focusout sí). Los que usarás a diario, click, input, change, submit y keydown, suben.

Formularios y validación con JavaScript

En la Estación 13 construiste formularios con <form>, <label> e <input>. Cuando alguien los envía, el navegador hace por defecto algo muy antiguo: empaqueta los datos, navega a la dirección indicada en el atributo action (o vuelve a cargar la misma página si no hay action) y dibuja lo que responda el servidor. Es decir, la página se recarga, y con ella se pierde todo lo que tu JavaScript tenía en memoria. En una aplicación moderna casi siempre quieres otra cosa: recoger los datos con JavaScript, revisarlos y actualizar la página sin recargarla.

Escuchar submit y cancelar el envío

La receta tiene dos piezas. Primero, escucha el evento submit en el formulario, no el click del botón: un formulario se puede enviar pulsando el botón, pero también pulsando Enter dentro de un campo, y submit cubre todos los caminos. Segundo, llama a evento.preventDefault(), que significa «impide la acción por defecto»: el navegador no navega y la página no se recarga.

const formulario = document.querySelector("#registro");

formulario.addEventListener("submit", (evento) => {
  evento.preventDefault();   // la página NO se recarga
  const nombre = formulario.elements.nombre.value.trim();
  console.log("Hola, " + nombre);
});

formulario.elements contiene todos los campos del formulario, y cada uno se encuentra por su atributo name: <input name="nombre"> es formulario.elements.nombre. Hay otra forma muy práctica de recoger todo de una vez: FormData, un objeto que reúne los valores de todos los campos que tienen name. Si lo pasas por Object.fromEntries, obtienes un objeto normal, como los de la Estación 11:

const datos = Object.fromEntries(new FormData(formulario));
// { nombre: "Ana", edad: "29", correo: "ana@ejemplo.com" }

Todo llega como texto, y el vacío engaña

Los valores de un formulario siempre son textos: "29", no 29. Límpialos con trim() (quita espacios de los extremos) y conviértelos con Number() antes de hacer cuentas. Y cuidado con esta trampa: Number("") vale 0, no NaN. Si un campo de edad está vacío, Number(edad) te dirá que la persona tiene 0 años. Comprueba primero si el texto está vacío.

El botón que envía sin querer

Dentro de un <form>, un <button> sin atributo type es un botón de envío. Si pones un botón «Cancelar», «Mostrar contraseña» o «+1» dentro de un formulario, cada clic enviará el formulario. Para los botones que no deben enviar, escribe type="button".

Los talleres y los formularios

La vista previa de los talleres funciona dentro de un marco aislado (un <iframe> con la protección sandbox) para que el código que escribes no pueda tocar el resto del curso. Ese aislamiento hace que el navegador bloquee dos cosas que vas a usar: el envío de formularios y localStorage. Por eso, los talleres que los necesitan llevan al final del HTML un pequeño <script> marcado como «Ayudante de los talleres del curso» que los imita: al pulsar un botón de envío (o Enter) revisa la validación y dispara submit, y si tu código no llama a preventDefault(), recarga la vista previa como lo haría una página de verdad. En tu propia página no hace falta: no lo copies.

Validar: primero el HTML, después JavaScript

Antes de escribir una sola línea de JavaScript, aprovecha lo que el navegador ya sabe hacer. Los atributos de validación que viste en la Estación 13 (required, minlength, maxlength, min, max, type="email", pattern) hacen que el navegador revise el formulario al enviarlo. Si algo no cumple, muestra un mensaje junto al campo y el evento submit ni siquiera ocurre. Tu escuchador solo recibe formularios que ya pasaron esas reglas.

JavaScript entra en juego para las reglas que el HTML no sabe expresar: que las dos contraseñas coincidan, que un nick no tenga espacios, que la fecha de un viaje no esté en el pasado, que el total del pedido llegue al mínimo. Hay dos maneras de mostrar esos errores:

  1. Usar los mensajes del navegador. campo.setCustomValidity("Mensaje") marca el campo como inválido con tu propio texto, y el navegador lo trata igual que a un required incumplido. Para marcarlo como válido otra vez, se llama con un texto vacío: setCustomValidity(""). Suele hacerse en el evento input del campo.
  2. Mostrar tus propios mensajes. Añades el atributo novalidate al <form> para que el navegador no muestre sus globos, validas todo en el submit y escribes los errores en elementos de la página, junto a cada campo. Da más control sobre el aspecto y el texto. Si lo haces, marca los campos erróneos con aria-invalid="true" para que los lectores de pantalla sepan que hay un problema.

Este taller usa la primera manera. Prueba a enviar el formulario vacío, después con un nick que tenga un espacio, y después con datos correctos. Al final, haz el experimento del último comentario.

Sin preventDefault(), el navegador sigue adelante con el envío, la página se recarga y la lista de inscritos desaparece: vivía en el DOM, y el DOM se reconstruyó desde el HTML. Es uno de los errores más frecuentes al empezar, y se reconoce porque la página «parpadea» y todo vuelve a su estado inicial.

Una función que valida y otra que muestra

Cuando las reglas crecen, conviene separar dos trabajos: decidir qué está mal y mostrarlo. La función que decide recibe los datos y devuelve un objeto con los errores; no toca la página. Así se puede leer, probar y reutilizar con facilidad (en la Estación 26 aprenderás a escribirle pruebas automáticas):

function validar(datos) {
  const errores = {};
  if (datos.nick.trim().length < 3) {
    errores.nick = "El nick necesita al menos 3 caracteres.";
  }
  if (datos.edad.trim() === "") {
    errores.edad = "Escribe tu edad.";
  } else if (Number(datos.edad) < 13) {
    errores.edad = "Debes tener al menos 13 años.";
  }
  return errores;   // objeto vacío: todo correcto
}

formulario.addEventListener("submit", (evento) => {
  evento.preventDefault();
  const datos = Object.fromEntries(new FormData(formulario));
  const errores = validar(datos);

  // Mostrar: un <p class="error" id="error-nick"> junto a cada campo
  document.querySelector("#error-nick").textContent = errores.nick ?? "";
  document.querySelector("#error-edad").textContent = errores.edad ?? "";

  if (Object.keys(errores).length > 0) return;   // hay errores: no seguimos
  console.log("Todo correcto:", datos);
});

El operador ?? se llama fusión de nulos: devuelve lo que tiene a la izquierda, salvo que sea null o undefined, en cuyo caso devuelve lo de la derecha. Aquí sirve para escribir un texto vacío cuando ese campo no tiene error. Object.keys(errores).length cuenta cuántos errores hay.

Idea clave

La validación en el navegador es una comodidad para la persona, no una protección. Cualquiera puede desactivar JavaScript, editar la página con las herramientas de desarrollo o enviar datos directamente al servidor sin pasar por tu formulario. Por eso el servidor siempre vuelve a validar todo. Lo harás en la Estación 29, y en la Estación 31 verás por qué nunca hay que confiar en lo que llega del navegador.

Recordar datos: localStorage y JSON

Viste en la primera animación que, al recargar, el navegador reconstruye el DOM desde el HTML y todo lo que JavaScript había hecho desaparece. Las variables también se pierden: cada carga de la página empieza con la memoria vacía. Una lista de tareas que se borra al cerrar la pestaña no sirve de mucho. Necesitas guardar datos en algún sitio que sobreviva.

Una opción es enviarlos a un servidor con una base de datos (lo harás en las estaciones 29 y 30). La más sencilla es guardarlos en el propio navegador con localStorage («almacenamiento local»): un pequeño almacén de textos, organizado por claves (nombres), que el navegador conserva aunque cierres la pestaña, cierres el navegador o apagues la computadora. Los datos siguen ahí hasta que tu código los borre o la persona borre los datos de navegación.

Para entenderlo

Piensa en localStorage como un casillero con etiquetas que el navegador le presta a cada sitio web. Guardas un papel con la etiqueta «tema» y otro con la etiqueta «tareas». Al día siguiente vuelves, pides el papel de la etiqueta «tema» y ahí está. Límite de la analogía: en estos papeles solo se puede escribir texto, y el casillero está en ese navegador de esa computadora; desde el teléfono no lo verás.

Se usa con cuatro métodos:

MétodoQué hace
localStorage.setItem(clave, valor)Guarda valor con ese nombre. Si ya existía, lo reemplaza.
localStorage.getItem(clave)Devuelve el texto guardado, o null si no hay nada con esa clave.
localStorage.removeItem(clave)Borra esa clave.
localStorage.clear()Borra todo lo que este sitio guardó.

Cada sitio tiene su propio casillero, separado por origen: la combinación de protocolo, dominio y puerto que viste en la Estación 3 (por ejemplo, https://mitienda.com). Una página de otro sitio no puede leer lo que guardó el tuyo, y todas las páginas de tu mismo origen comparten el mismo casillero.

Cada vez que pulsas «Ejecutar» en este taller es como si recargaras la página. Predice qué número verás después de pulsar tres veces.

La primera vez, getItem devuelve null porque no hay nada guardado. Después devuelve "1", "2"… siempre como texto (typeof dice string), aunque guardaste un número. Por eso hace falta Number() al leerlo.

En los talleres, la memoria dura menos

El ayudante de los talleres imita localStorage y conserva los datos entre ejecuciones, pero solo mientras no recargues esta página del curso. En tu propia página, localStorage de verdad los conserva durante días, meses o años.

Guardar objetos y listas: JSON

localStorage solo guarda textos. Si le das otra cosa, la convierte en texto a su manera, y con los objetos esa manera es inútil:

Guardar el objeto directamente

const jugador = { nombre: "Ana", nivel: 7 };
localStorage.setItem("jugador", jugador);
localStorage.getItem("jugador");
// "[object Object]"  (los datos se perdieron)

Convertirlo antes a JSON

const jugador = { nombre: "Ana", nivel: 7 };
localStorage.setItem("jugador", JSON.stringify(jugador));
JSON.parse(localStorage.getItem("jugador"));
// { nombre: "Ana", nivel: 7 }

Ya conoces JSON de la Estación 11: JSON.stringify convierte un objeto o un array en texto (a esto se le llama serializar) y JSON.parse hace el camino inverso. Juntos forman un patrón que usarás en cada proyecto que recuerde datos: dos funciones pequeñas, una para guardar y otra para cargar.

const CLAVE = "mis-tareas";

function guardar(tareas) {
  localStorage.setItem(CLAVE, JSON.stringify(tareas));
}

function cargar() {
  try {
    return JSON.parse(localStorage.getItem(CLAVE)) ?? [];
  } catch (error) {
    console.warn("Los datos guardados estaban dañados. Empiezo de cero.");
    return [];
  }
}

let tareas = cargar();   // al arrancar: lo guardado, o una lista vacía

Dos detalles de cargar. Si no hay nada guardado, getItem devuelve null, JSON.parse(null) devuelve null, y el ?? [] lo cambia por una lista vacía. Y si el texto guardado no es JSON válido (alguien lo editó a mano, o lo guardó una versión antigua de tu aplicación), JSON.parse lanza un SyntaxError; el try...catch que viste en la Estación 12 lo atrapa y la aplicación arranca vacía en vez de romperse.

Consejo de oficio

Usa una constante para el nombre de la clave (CLAVE) en lugar de escribir "mis-tareas" en varios sitios: una errata en uno de ellos haría que guardes en una clave y leas de otra. Y guarda siempre justo después de cambiar el estado: si lo dejas para «al cerrar la página», puede que ese momento nunca llegue (el navegador se cierra de golpe, el teléfono se queda sin batería).

Mira el almacén con tus propios ojos

En Chrome y Edge, abre las herramientas de desarrollo y ve a Aplicación (Application) → Almacenamiento local (Local storage) → el origen de tu página. En Firefox está en la pestaña Almacenamiento (Storage). Verás cada clave con su valor, y podrás editarlos o borrarlos a mano: muy útil para probar qué pasa cuando no hay datos o cuando están dañados.

Lo que localStorage no es

  • No es seguro. Cualquier script que se ejecute en tu página puede leerlo, incluido el código que un atacante consiga colar con un XSS. Nunca guardes contraseñas, datos de tarjetas ni información personal delicada.
  • No es infinito. Los navegadores permiten unos 5 MiB por origen. Si te pasas, setItem lanza un error QuotaExceededError, así que en aplicaciones que guardan mucho conviene envolverlo en try...catch. Para grandes cantidades existe otra herramienta del navegador, IndexedDB, que queda fuera de esta estación.
  • No viaja contigo. Vive en un navegador de un dispositivo. Otro navegador, otra computadora o el teléfono tienen su propio almacén, vacío. Y en una ventana de navegación privada, los datos se borran al cerrarla.
  • No es para archivos abiertos con doble clic. Si abres tu index.html directamente (la dirección empieza por file://), cada navegador trata localStorage a su manera y no puedes confiar en el resultado. Abre tus proyectos con un servidor local, por ejemplo con la extensión Live Preview de Microsoft para VS Code.

Estado, vista y tiempo: organizar una aplicación

Ya tienes todas las piezas: encontrar elementos, cambiarlos, crearlos, escuchar eventos y guardar datos. Cuando las juntas en una aplicación de verdad aparece un problema nuevo, que no es de sintaxis sino de organización.

El problema: datos repartidos por la pantalla

Imagina una lista de tareas con un contador «3 pendientes». Al marcar una tarea como hecha, un escuchador tacha el texto. Al borrarla, otro escuchador quita el li. Al añadir, otro crea un li nuevo. Cada uno debe acordarse también de actualizar el contador, de guardar en localStorage y, si hay un filtro «solo pendientes», de esconder lo que toque. Basta con que uno de ellos se olvide de algo para que el contador diga 3 y la lista muestre 2. Y cuando el programa necesita saber cuántas tareas hay, acaba contando elementos de la página o leyendo textos de la pantalla, lo que se rompe en cuanto alguien cambia el HTML.

La solución: el estado manda y la vista obedece

La forma ordenada de construir interfaces separa dos cosas:

  • El estado: los datos que describen cómo está la aplicación ahora mismo. En la lista de tareas, un array de objetos; en un juego, la puntuación, las vidas y las posiciones. Vive en variables de JavaScript y es la única fuente de verdad: si quieres saber algo, lo preguntas al estado, nunca a la pantalla.
  • La vista: lo que se ve. Se construye con una función, que suele llamarse render (renderizar significa generar la imagen o la página a partir de datos), que lee el estado y dibuja la interfaz entera a partir de él.

Con esa separación, cada escuchador hace siempre lo mismo, en este orden: 1) cambia el estado, 2) lo guarda si hace falta y 3) llama a render(). Nunca retoca la pantalla por su cuenta. Así es imposible que el contador y la lista no coincidan, porque los dos salen del mismo array en el mismo momento.

En código, el esqueleto de una aplicación así tiene siempre las mismas partes, en el mismo orden:

// 1. Estado: la única fuente de verdad
let tareas = cargar();

// 2. Referencias a los elementos que no cambian
const lista = document.querySelector("#lista");
const formulario = document.querySelector("#nueva");
const contador = document.querySelector("#contador");

// 3. Render: del estado a la vista
function render() {
  lista.replaceChildren();                 // vacía la lista
  for (const tarea of tareas) {
    const li = document.createElement("li");
    li.textContent = tarea.texto;
    lista.append(li);
  }
  contador.textContent = `${tareas.length} tareas`;
}

// 4. Eventos: cambian el estado, guardan y vuelven a dibujar
formulario.addEventListener("submit", (evento) => {
  evento.preventDefault();
  const texto = formulario.elements.texto.value.trim();
  if (texto === "") return;
  tareas.push({ id: Date.now(), texto: texto, hecha: false });
  guardar(tareas);
  render();
  formulario.reset();
});

// 5. Arranque: dibujar lo que había guardado
render();

Cada tarea lleva un id para poder encontrarla después (para borrarla o marcarla). Date.now() devuelve los milisegundos transcurridos desde el 1 de enero de 1970, un número distinto cada vez que lo llamas con al menos un milisegundo de diferencia; para una lista personal es suficiente. En el render se guarda ese id en el elemento con li.dataset.id = tarea.id, y así un escuchador delegado puede saber a qué tarea pertenece el botón pulsado.

¿No es un desperdicio volver a dibujar todo?

Para decenas o cientos de elementos, vaciar y reconstruir es rápido y te ahorra una enorme cantidad de errores. Tiene un coste que notarás en proyectos mayores: si reconstruyes un campo de texto mientras alguien escribe en él, se pierde el foco. Por eso los campos de entrada suelen quedarse fuera de lo que se redibuja. Las bibliotecas como React (Estación 32) usan exactamente esta idea, «la interfaz es una función del estado», pero calculan qué cambió y solo tocan esas partes.

Consejo de oficio

Separa la lógica (funciones que solo trabajan con datos: validar(datos), pendientes(tareas), ganador(jugada1, jugada2)) del código que toca el DOM. Las funciones de lógica no usan document, así que puedes probarlas en la consola, en Node.js o con pruebas automáticas, y reutilizarlas si mañana haces la misma aplicación para el teléfono.

Un proyecto web pequeño se organiza en tres archivos: index.html (estructura), estilos.css (aspecto) y app.js (comportamiento), enlazados desde el HTML con <link> y <script defer>. El tiempo también produce eventos: temporizadores

No todo lo que ocurre en una página lo provoca una persona. Un aviso que desaparece a los tres segundos, una cuenta atrás, un enemigo que dispara cada segundo: son cosas que dependen del reloj. Para ellas existen los temporizadores:

FunciónQué haceCómo se cancela
setTimeout(funcion, ms)Ejecuta la función una vez, pasados al menos ms milisegundos.clearTimeout(id)
setInterval(funcion, ms)Ejecuta la función una y otra vez, cada ms milisegundos aproximadamente.clearInterval(id)

Las dos devuelven un número, el identificador del temporizador, que hay que guardar si quieres cancelarlo después. Igual que con addEventListener, les pasas la función, no la llamas.

const aviso = document.querySelector("#aviso");
aviso.textContent = "Guardado";
setTimeout(() => {
  aviso.textContent = "";      // el aviso se borra 3 segundos después
}, 3000);

Los milisegundos son un mínimo

El tiempo que indicas es lo mínimo que esperará el navegador, no una cita exacta: si está ocupado, la función se retrasa. Además, cuando una pestaña está en segundo plano, los navegadores frenan sus temporizadores para ahorrar batería (a una vez por segundo o incluso menos). Si necesitas medir tiempo con precisión, por ejemplo en un cronómetro, no cuentes cuántas veces se ejecutó el intervalo: guarda el momento de inicio con Date.now() y calcula la diferencia.

Animaciones fluidas: requestAnimationFrame

Para mover algo por la pantalla con suavidad, como un personaje o una bola, setInterval no es la mejor herramienta: no sabe cuándo va a dibujar la pantalla el navegador, y el movimiento sale a saltos. Para eso existe requestAnimationFrame («pide un fotograma de animación»): le pasas una función y el navegador la ejecuta justo antes de dibujar el siguiente fotograma (cada una de las imágenes que forman el movimiento).

  • Se llama tantas veces por segundo como se refresque la pantalla: normalmente 60, pero 120 o 144 en muchas pantallas modernas.
  • Pide un solo fotograma. Para animar de forma continua, tu función tiene que volver a llamar a requestAnimationFrame al final.
  • Tu función recibe un número: el momento actual en milisegundos. Con la diferencia entre dos fotogramas calculas cuánto mover, para que la velocidad sea la misma en una pantalla de 60 y en una de 144. Si movieras «3 píxeles por fotograma», en la pantalla rápida todo iría más del doble de rápido.
  • El navegador la pausa cuando la pestaña no está visible, lo que ahorra batería.

Cuándo no hace falta JavaScript

Si la animación es un cambio de un estado a otro (un menú que se despliega, un botón que cambia de color), las transiciones y animaciones de CSS que viste en la Estación 14 son más sencillas y eficientes: JavaScript solo pone o quita una clase. requestAnimationFrame brilla cuando el movimiento depende de datos que cambian cada fotograma, como en un juego. En la Estación 34 lo convertirás en el corazón de un juego: el bucle de juego, que en cada fotograma lee la entrada, actualiza el estado y dibuja.

Resumen

  • El navegador convierte el HTML en el DOM, un árbol de objetos en memoria, y dibuja la pantalla a partir de él. JavaScript cambia el DOM, no el archivo; al recargar, todo se reconstruye desde el HTML.
  • Carga tu código con <script src="app.js" defer> en el <head>: se ejecuta cuando el HTML ya está leído. Si querySelector devuelve null, revisa el selector (#, ., mayúsculas) y el momento en que corre el script.
  • querySelector devuelve el primer elemento que cumple un selector de CSS; querySelectorAll, una NodeList con todos, que se recorre con forEach; getElementById busca por id, sin #.
  • Cambia el texto con textContent. Usa innerHTML solo con HTML que escribes tú: con datos de personas abre la puerta al XSS. Cambia el aspecto con classList y deja style para valores calculados.
  • Para crear elementos: createElement, configurar y después append (o prepend, before, after). Para quitar, remove(); para vaciar, replaceChildren().
  • addEventListener(tipo, funcion) registra una función que el navegador llamará cada vez que ocurra el evento, pasándole un objeto evento. Se pasa la función, sin paréntesis.
  • input salta con cada cambio; change, al confirmar. En el teclado, key es el carácter y code, la posición física de la tecla.
  • Los eventos suben por el árbol (propagación). Por eso un solo escuchador en un contenedor puede atender a todos sus hijos, incluso los futuros: es la delegación, con evento.target.closest(...).
  • En formularios, escucha submit en el <form> y llama a preventDefault(). Los valores llegan como texto. Valida primero con HTML y después con JavaScript, y recuerda que el servidor debe volver a validar.
  • localStorage guarda textos por clave en ese navegador; para objetos y arrays, JSON.stringify al guardar y JSON.parse al cargar. Organiza la aplicación como estado → vista: los eventos cambian el estado, se guarda y render() redibuja. Para el tiempo, setTimeout, setInterval y requestAnimationFrame.

  document.body.classList.toggle("oscuro", oscuro);
  boton.textContent = oscuro ? "Activar modo claro" : "Activar modo oscuro";
}

let tema = localStorage.getItem(CLAVE) ?? "claro";
aplicar(tema);

Es el patrón estado → vista en miniatura: la variable tema es el estado, aplicar es el render y localStorage lo conserva entre visitas. En una web de verdad, añade también <meta name="color-scheme" content="light dark"> y respeta la preferencia del sistema con matchMedia("(prefers-color-scheme: dark)") cuando no haya nada guardado.

Proyecto: dos aplicaciones de verdad

El proyecto de esta estación tiene dos partes. La primera es una lista de tareas que recuerda: el «hola mundo» de las aplicaciones web, porque obliga a usar todo lo de esta estación a la vez. La segunda es un juego pequeño, piedra, papel o tijera, con botones, teclado y marcador. Las dos siguen el patrón estado → vista. Cuando las termines, cópialas a tu computadora en tres archivos (index.html, estilos.css y app.js, sin el ayudante de los talleres) y ábrelas con un servidor local: tendrás tus dos primeras aplicaciones web.

Parte 1: lista de tareas que recuerda

El HTML y el CSS ya están hechos. El JavaScript trae el esqueleto con los bloques del patrón estado → vista; tu trabajo es rellenarlo.

  1. Guardar y cargar. Completa guardar() para que escriba el array tareas en localStorage como JSON, en la clave tareas-v1, y cargar() para que lo lea y devuelva un array vacío si no hay nada o si está dañado.

  2. Render. Completa render(): vacía la lista y crea un li por tarea con una casilla <input type="checkbox" class="marcar"> (marcada si la tarea está hecha), un <span class="texto"> con el texto y un <button type="button" class="borrar">. Guarda el id en li.dataset.id y añade la clase hecha a las tareas hechas. Al final, escribe en el contador cuántas quedan pendientes, por ejemplo 2 pendientes.

  3. Añadir. Escucha el submit del formulario: evita la recarga, recorta el texto con trim(), ignóralo si queda vacío y, si no, añade al estado { id: Date.now(), texto, hecha: false }. Después guarda, llama a render() y vacía el campo.

  4. Marcar. Con un escuchador de change en la lista (delegación), cuando cambie una casilla .marcar, busca la tarea por su id (tareas.find), actualiza su propiedad hecha, guarda y dibuja.

  5. Borrar. Con un escuchador de click en la lista, cuando se pulse un botón .borrar, quita la tarea del estado con filter, guarda y dibuja. Haz lo mismo con el botón «Borrar hechas», que elimina todas las tareas hechas.

  6. Prueba que recuerda. Añade tres tareas, marca una y pulsa «Ejecutar» otra vez: deben seguir ahí, con la marca. Abre también la solución y compárala con la tuya.

function crearElemento(tarea) {
  const li = document.createElement("li");
  li.dataset.id = tarea.id;
  li.classList.toggle("hecha", tarea.hecha);

  const casilla = document.createElement("input");
  casilla.type = "checkbox";
  casilla.classList.add("marcar");
  casilla.checked = tarea.hecha;
  casilla.setAttribute("aria-label", "Hecha: " + tarea.texto);

  const texto = document.createElement("span");
  texto.classList.add("texto");
  texto.textContent = tarea.texto;

  const borrar = document.createElement("button");
  borrar.type = "button";
  borrar.classList.add("borrar");
  borrar.textContent = "Borrar";

  li.append(casilla, texto, borrar);
  return li;
}

function render() {
  lista.replaceChildren();
  for (const tarea of tareas) {
    lista.append(crearElemento(tarea));
  }
  const pendientes = tareas.filter((t) => !t.hecha).length;
  contador.textContent = `${pendientes} pendientes`;
  botonLimpiar.disabled = tareas.every((t) => !t.hecha);

  return Number(elemento.closest("li").dataset.id);
}

  evento.preventDefault();
  const texto = formulario.elements.texto.value.trim();
  if (texto === "") return;
  tareas.push({ id: Date.now(), texto: texto, hecha: false });
  guardar();
  render();
  formulario.reset();
});

  if (!evento.target.classList.contains("marcar")) return;

  tarea.hecha = evento.target.checked;
  guardar();
  render();
});

  guardar();
  render();

const opciones = ["piedra", "papel", "tijera"];
const vence = { piedra: "tijera", tijera: "papel", papel: "piedra" };
const MENSAJES = { ganas: "¡Ganas!", pierdes: "Pierdes.", empate: "Empate." };

// 1. Lógica (sin DOM)
function resultado(jugador, rival) {
  if (jugador === rival) return "empate";
  return vence[jugador] === rival ? "ganas" : "pierdes";
}

function jugadaAlAzar() {
  return opciones[Math.floor(Math.random() * opciones.length)];
}

// 2. Estado
let puntos = { jugador: 0, rival: 0 };
let ultima = null;   // texto de la última partida

// 3. Render
const textoResultado = document.querySelector("#resultado");
const marcador = document.querySelector("#marcador");

function render() {
  textoResultado.textContent = ultima ?? "Elige una jugada.";
  marcador.textContent = `Tú ${puntos.jugador} · Rival ${puntos.rival}`;
}

// 4. Jugar: cambia el estado y redibuja
function jugar(jugador) {
  const rival = jugadaAlAzar();
  const r = resultado(jugador, rival);
  if (r === "ganas") puntos.jugador++;
  if (r === "pierdes") puntos.rival++;
  ultima = `Tú: ${jugador}. Rival: ${rival}. ${MENSAJES[r]}`;
  render();
}

// 5. Eventos
document.querySelector("#jugadas").addEventListener("click", (evento) => {
  const boton = evento.target.closest("button[data-jugada]");
  if (!boton) return;
  jugar(boton.dataset.jugada);
});

document.addEventListener("keydown", (evento) => {
  const posicion = ["1", "2", "3"].indexOf(evento.key);
  if (posicion === -1) return;
  jugar(opciones[posicion]);
});

document.querySelector("#reiniciar").addEventListener("click", () => {
  puntos = { jugador: 0, rival: 0 };
  ultima = null;
  render();
});

Autoevaluación

Responde sin mirar arriba. Si fallas alguna, lee la explicación de cada opción: los errores de estas preguntas son los que más se cometen al empezar con el DOM.

¿Qué es el DOM?

  1. El archivo HTML tal como está guardado en el disco.

    No. El archivo es el plano; el DOM se construye a partir de él, y JavaScript puede cambiar el DOM sin que el archivo cambie.

  2. Una parte del lenguaje JavaScript, como let o las funciones.

    No. Es una API que el navegador ofrece a JavaScript. Por eso en Node.js no existe document.

  3. La representación de la página en la memoria del navegador, un árbol de objetos que JavaScript puede leer y cambiar.

    Correcto. La pantalla se dibuja a partir de ese árbol, y cada cambio en él se refleja en lo que ves.

  4. Una biblioteca que hay que instalar para manipular páginas.

    No hace falta instalar nada: todos los navegadores construyen el DOM y ofrecen sus herramientas.

Tu <script src="app.js"> está en el <head>, sin defer, y document.querySelector("#lista") devuelve null, aunque la lista existe en el <body>. ¿Por qué?

  1. El script se ejecutó antes de que el navegador leyera el <body>.

    Correcto. Un script normal se ejecuta en cuanto aparece. Con defer esperaría a que el HTML estuviera completo.

  2. querySelector no funciona con ids; hay que usar getElementById.

    No. querySelector acepta cualquier selector de CSS, incluido #lista.

  3. Hay que escribir el selector sin almohadilla: "lista".

    Al revés: sin # buscaría una etiqueta <lista>. La almohadilla solo sobra en getElementById.

  4. Las listas ul no se pueden seleccionar con JavaScript.

    Cualquier elemento se puede seleccionar. El problema es el momento en que se ejecuta el script.

document.querySelectorAll(".boton").addEventListener("click", avisar) da un error. ¿Por qué?

  1. Porque el evento se llama "onclick", no "click".

    En addEventListener el tipo se escribe sin «on»: "click" es correcto.

  2. Porque la clase debe escribirse sin punto.

    No. querySelectorAll usa selectores de CSS, y las clases llevan punto.

  3. Porque avisar debe escribirse con paréntesis: avisar().

    Eso ejecutaría la función en ese momento. Hay que pasarla sin paréntesis.

  4. Porque querySelectorAll devuelve una lista, y la lista no tiene addEventListener: hay que recorrerla con forEach o usar delegación.

    Correcto. Cada elemento de la lista tiene su addEventListener; la lista en sí, no.

Una persona escribe su nombre en un formulario y quieres mostrarlo en el párrafo saludo. ¿Qué línea es la adecuada?

  1. saludo.innerHTML = "Hola, " + nombre;

    Si el nombre contiene HTML con un atributo como onerror, ese código se ejecutará: es la puerta del XSS.

  2. saludo.textContent = "Hola, " + nombre;

    Correcto. textContent muestra el texto tal cual, aunque parezca HTML, y no ejecuta nada.

  3. saludo.innerHTML = `<b>Hola</b>, ${nombre}`;

    La negrita es tuya, pero el nombre se sigue insertando como HTML: mismo riesgo. Crea el <b> con createElement y el nombre con texto.

  4. saludo.value = "Hola, " + nombre;

    value es el contenido de los campos de formulario; un párrafo no lo muestra.

¿Qué ocurre con boton.addEventListener("click", saludar());?

  1. Saluda cada vez que se hace clic.

    Eso haría addEventListener("click", saludar), sin paréntesis.

  2. Da un error de sintaxis.

    La sintaxis es válida, y por eso el error es difícil de ver: no hay mensaje en rojo.

  3. saludar se ejecuta una vez al cargar la página y los clics no hacen nada.

    Correcto. Los paréntesis ejecutan la función ya, y se registra como escuchador lo que devuelve (normalmente undefined), que el navegador ignora.

  4. Saluda dos veces en cada clic.

    No. La función no queda registrada como escuchador.

Hay un escuchador de clics en una ul, y haces clic en un botón que está dentro de uno de sus li. Dentro de la función, ¿qué valen evento.target y evento.currentTarget?

  1. target es el botón y currentTarget es la ul.

    Correcto. target es donde empezó el evento; currentTarget, quien escucha.

  2. target es la ul y currentTarget es el botón.

    Es justo al revés.

  3. Los dos son el botón.

    currentTarget es el elemento del escuchador que se está ejecutando: la ul.

  4. Los dos son la ul.

    target no cambia durante la propagación: sigue siendo el botón donde se hizo clic.

¿Cuál es la principal ventaja de la delegación de eventos?

  1. Los eventos viajan más rápido por el árbol.

    La velocidad del evento no cambia; lo que cambia es cuántos escuchadores necesitas.

  2. Impide que el evento llegue a document.

    Eso lo haría stopPropagation(). La delegación, al contrario, se basa en que el evento sube.

  3. Permite usar innerHTML sin riesgo de XSS.

    No tiene relación con la seguridad del contenido.

  4. Un solo escuchador en un contenedor atiende a todos sus hijos, incluidos los que se creen más tarde.

    Correcto. Por eso es el patrón habitual en listas que cambian.

Al enviar tu formulario, la página «parpadea» y la lista que habías construido desaparece. ¿Qué falta?

  1. Escuchar el click del botón en lugar del submit del formulario.

    Con eso no se evita el envío, y además dejarías de atender el envío con Enter.

  2. Llamar a evento.preventDefault() en el escuchador de submit.

    Correcto. Sin eso, el navegador sigue con el envío, la página se recarga y el DOM se reconstruye desde el HTML.

  3. Llamar a evento.stopPropagation().

    Eso detiene la subida del evento, pero no cancela la acción del navegador.

  4. Guardar la lista en una variable con const.

    Las variables también se pierden al recargar. El problema es que la página se recarga.

Ejecutas localStorage.setItem("jugador", { nombre: "Ana" }) y, al leerlo, obtienes "[object Object]". ¿Qué debiste hacer?

  1. Usar sessionStorage.

    Tiene los mismos métodos y la misma limitación: solo guarda textos.

  2. Leerlo con Number(localStorage.getItem("jugador")).

    No es un número; y el texto guardado ya perdió los datos.

  3. Guardar JSON.stringify(jugador) y leerlo con JSON.parse(...).

    Correcto. JSON convierte el objeto en un texto que conserva todos los datos, y JSON.parse lo reconstruye.

  4. Escribir la clave sin comillas: setItem(jugador, ...).

    La clave debe ser un texto. El problema está en el valor, que no es texto.

Pulsas tres veces «Empezar» y la cuenta atrás va tres veces más rápido; además, «Pausar» ya no la detiene. ¿Por qué?

  1. Cada clic creó un setInterval nuevo; los tres restan a la vez y la variable solo guarda el id del último.

    Correcto. Antes de crear un intervalo, comprueba si ya hay uno en marcha.

  2. setInterval se acelera cuando la pestaña está visible.

    No existe esa aceleración. Lo que sí ocurre es que los navegadores frenan los temporizadores de las pestañas en segundo plano.

  3. El navegador duplica los temporizadores para compensar retrasos.

    El navegador nunca duplica temporizadores por su cuenta.

  4. Porque setInterval se ejecuta una vez por fotograma de la pantalla.

    Eso describe a requestAnimationFrame, y aun así no explicaría la aceleración.

¿Por qué, dentro de requestAnimationFrame, se mueve un personaje según el tiempo transcurrido y no una cantidad fija por fotograma?

  1. Para que la animación use menos memoria.

    La memoria no tiene que ver: se trata de la velocidad.

  2. Porque la función se llama tantas veces por segundo como se refresca la pantalla (60, 120, 144…), y así la velocidad es igual en todas.

    Correcto. Con una cantidad fija por fotograma, en una pantalla de 144 Hz todo iría más del doble de rápido que en una de 60 Hz.

  3. Porque requestAnimationFrame se llama exactamente cada 16 milisegundos en todos los dispositivos.

    Justo lo contrario: depende de la pantalla, y por eso hay que medir el tiempo.

  4. Porque si no, la animación no se pausa cuando la pestaña está en segundo plano.

    El navegador la pausa en cualquier caso; no depende de cómo calcules el movimiento.

En el patrón estado → vista, ¿qué debería hacer el escuchador del botón «Borrar» de una tarea?

  1. Quitar el li de la pantalla y dejar el array como está.

    La vista y el estado dejarían de coincidir: al redibujar o recargar, la tarea «resucitaría».

  2. Contar los li que quedan en la página para actualizar el contador.

    Leer datos de la pantalla es frágil. El contador debe salir del estado.

  3. Borrar todo localStorage y recargar la página.

    Perderías todas las tareas, no solo esa.

  4. Quitar la tarea del array de estado, guardar y llamar a render().

    Correcto. El estado cambia, se guarda, y la vista se reconstruye a partir de él.

Glosario

DOM
Siglas de Document Object Model. Representación de una página en la memoria del navegador, en forma de árbol de objetos que JavaScript puede leer y cambiar.
Nodo
Cada pieza del árbol del DOM: un elemento, un trozo de texto, un comentario. Tiene un padre y puede tener hijos y hermanos.
Elemento
Nodo del DOM que corresponde a una etiqueta de HTML, como un h1 o un button.
document
Objeto que representa la página entera y es la raíz del DOM. Desde él se buscan y crean los elementos.
API web
Conjunto de objetos y funciones que el navegador ofrece a JavaScript, como el DOM, localStorage o los temporizadores. No forman parte del lenguaje.
querySelector
Método que devuelve el primer elemento que cumple un selector de CSS, o null si no hay ninguno. querySelectorAll devuelve todos.
NodeList
Lista de nodos que devuelve querySelectorAll. Tiene length y forEach, pero no es un array.
textContent
Propiedad con el texto de un elemento. Al asignarla, el texto se muestra tal cual, sin interpretar etiquetas.
innerHTML
Propiedad con el contenido de un elemento como HTML. Al asignarla, el navegador interpreta las etiquetas; con datos de personas es peligrosa.
XSS
Siglas de cross-site scripting. Ataque que cuela código en una página para que se ejecute en el navegador de otras personas, por ejemplo mediante innerHTML.
dataset
Propiedad para leer y escribir los atributos data-* de un elemento. Sus valores son textos.
classList
Propiedad para añadir, quitar, alternar y consultar las clases de un elemento (add, remove, toggle, contains).
defer
Atributo de <script> que descarga el archivo en paralelo y lo ejecuta cuando el HTML ya está completo.
Evento
Aviso que da el navegador cuando ocurre algo: un clic, una tecla, un envío de formulario, un cambio en un campo.
Escuchador de eventos
Función que se registra con addEventListener para que el navegador la ejecute cada vez que ocurre un evento. En inglés, event listener.
Objeto evento
Objeto con los detalles de un evento (type, target, currentTarget, key…) que el navegador pasa al escuchador.
preventDefault
Método del objeto evento que cancela la acción que el navegador haría por su cuenta, como enviar un formulario o seguir un enlace.
Propagación
Viaje de un evento por el árbol del DOM. En la fase de burbuja sube desde el elemento donde ocurrió hasta document.
Delegación de eventos
Técnica que pone un solo escuchador en un contenedor y usa evento.target para saber qué hijo se activó. Funciona también con elementos creados después.
localStorage
Almacén de textos por clave que el navegador conserva para cada origen, incluso después de cerrar el navegador.
Serializar
Convertir un objeto o un array en texto para guardarlo o enviarlo, por ejemplo con JSON.stringify.
Estado
Datos que describen cómo está una aplicación en un momento dado. En el patrón estado → vista es la única fuente de verdad.
Renderizar
Generar la vista (lo que se ve en pantalla) a partir de los datos. Suele hacerlo una función llamada render.
Temporizador
Mecanismo para ejecutar una función más tarde (setTimeout) o repetidamente (setInterval).
requestAnimationFrame
Función del navegador que ejecuta tu código justo antes de dibujar el siguiente fotograma. Es la base de las animaciones fluidas y de los bucles de juego.
