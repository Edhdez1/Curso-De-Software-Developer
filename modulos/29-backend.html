Dos formas de trabajar en esta estación

Un servidor de verdad necesita abrir un puerto en tu computadora, y una página web no puede hacer eso. Por eso vas a trabajar de dos maneras. En esta página, los talleres simulan las peticiones: escribirás la lógica del servidor como funciones que reciben una petición y devuelven una respuesta, y verás el resultado al instante. Qué es el backend y para qué sirve

Imagina que hiciste un juego de navegador tipo Snake. Guardas la mejor puntuación con localStorage (lo viste en la Estación 15) y funciona. Ahora quieres un ranking mundial: que tu amiga en Lima vea que le ganaste desde Madrid. Ahí aparecen dos problemas:

  • No hay un lugar común. Cada navegador tiene su propio localStorage. Las puntuaciones de tu amiga están en su computadora y las tuyas en la tuya.
  • No hay reglas que se cumplan. Todo lo que corre en el navegador lo controla la persona que juega. Con las herramientas de desarrollo puede cambiar su puntuación a 999 999 en dos segundos.

La solución es un programa que corre en una computadora que controlas tú, siempre encendida y conectada, al que todos los jugadores le envían sus puntuaciones y le piden el ranking. Ese programa es el backend.

El frontend es la parte de una aplicación que corre en el dispositivo de quien la usa: la página web, la app del móvil o el juego. Es lo que se ve y se toca. El backend es la parte que corre en un servidor: recibe peticiones, aplica las reglas, guarda los datos y responde. Nadie lo ve, pero sin él no hay ranking, ni cuentas de usuario, ni un carrito de compras que aparezca igual en tu móvil y en tu computadora.

«Servidor» tiene dos significados

A veces «servidor» es una computadora (física o alquilada en la nube) y a veces es el programa que atiende peticiones dentro de ella. En esta estación casi siempre hablamos del programa. Mientras desarrollas, ese programa corre en tu propia computadora; publicarlo en internet es tarea de la Estación 35.

Estas son las tareas típicas de un backend, y la razón por la que no se pueden dejar en el frontend:

Hacer cumplir las reglasUna puntuación no puede ser negativa; solo tú borras tu partidaEl código del navegador se puede leer y modificar. El del servidor, no.

Nunca confíes en el cliente

Llamamos cliente a quien envía la petición: tu frontend, una app o cualquier programa. Todo lo que llega a tu servidor puede venir de alguien que ni siquiera usa tu app: con una sola línea en la terminal cualquiera puede enviar {"puntos": 999999}. Por eso el servidor comprueba todo lo que recibe, aunque el frontend ya lo haya comprobado. Lo harás en la sección Validar los datos, y la Estación 31 lo lleva mucho más lejos.

Cómo se ve un servidor por dentro

Tus programas anteriores empezaban, hacían su trabajo y terminaban. Un servidor no termina: se queda encendido esperando. Abre un puerto, el número que identifica a un programa dentro de una computadora (lo viste en la Estación 3), y escucha. Cada vez que llega una petición HTTP, la procesa, responde y vuelve a esperar la siguiente.

Mientras desarrollas, el cliente y el servidor están en la misma computadora. Para eso existe el nombre especial localhost, que significa «esta misma computadora» (su dirección IP es 127.0.0.1). Si tu servidor escucha en el puerto 3000, lo visitas en http://localhost:3000. Nadie más en internet puede verlo: solo tú.

Node.js: JavaScript fuera del navegador

JavaScript nació en 1995 para vivir dentro del navegador. En 2009, Ryan Dahl tomó el motor de JavaScript de Chrome, V8, y lo envolvió en un programa que se podía ejecutar en cualquier computadora, sin navegador. Lo llamó Node.js. Desde entonces puedes usar JavaScript para escribir servidores, herramientas de terminal y hasta apps de escritorio.

Node.js es un entorno de ejecución (en inglés, runtime): un programa que ejecuta tu código JavaScript y le da herramientas para hablar con el sistema. Tiene dos partes: el motor V8, que traduce tu código a instrucciones de la máquina (lo viste en la Estación 22), y una biblioteca de módulos para leer archivos, abrir conexiones de red o conocer el entorno donde corre. Lo instalaste en la Estación 5.

El lenguaje es el mismo, pero cada entorno trae herramientas distintas:

Solo existe aquídocument, window, localStorage, alertprocess (con process.env), módulos como node:fs (archivos) y node:http (servidores)
Existe en los dosconsole, setTimeout, Promise, JSON, fetch, URL, structuredClone, performance

document is not defined

Si copias código de una página web a un archivo que ejecutas con node, puedes ver ReferenceError: document is not defined o window is not defined. No es un fallo de instalación: en Node no hay página, así que no hay DOM. Al revés pasa lo mismo: process no existe en el navegador.

Qué versión usar

Node.js publica una versión principal cada seis meses. Las versiones pares se convierten en LTS (del inglés Long Term Support, soporte a largo plazo): reciben correcciones de errores y de seguridad durante unos tres años, así que son las que se usan para servidores. En septiembre de 2026 la LTS activa es Node.js 24, y Node.js 26 pasa a LTS el 28 de octubre de 2026. Usa siempre la LTS más reciente. Compruébalo así:

$ node --version
v24.21.0
$ npm --version
11.19.0

Tus números pueden ser mayores. Lo importante es que Node empiece por 24 o más, porque en esta estación usarás funciones que se declararon estables en esa versión, como --env-file. Si tu número es menor, instala la LTS desde nodejs.org como en la Estación 5.

Un solo hilo que nunca se queda esperando

Un servidor popular recibe cientos de peticiones por segundo, y muchas necesitan algo lento: leer de la base de datos, leer un archivo, preguntarle a otra API. Si el servidor se quedara quieto esperando cada respuesta, atendería a una persona por vez y el resto haría cola.

Node.js resuelve esto con el mismo modelo que viste en la Estación 16: el bucle de eventos (en inglés, event loop). Un solo hilo (la secuencia de instrucciones que el procesador sigue de una en una) ejecuta tu JavaScript, una cosa a la vez. Las esperas lentas, como la red, el disco o la base de datos, se las encarga al sistema operativo. Cuando una termina, su continuación va a una cola, y el bucle de eventos la ejecuta en cuanto el hilo queda libre. Mientras la base de datos busca lo que pidió la petición A, Node atiende a B, a C y a D.

Para entenderlo

Piensa en un restaurante con un solo camarero muy rápido. Toma el pedido de la mesa 1, lo pasa a la cocina y no se queda mirando la olla: va a la mesa 2, luego a la 3. Cuando la cocina toca la campana, lleva el plato. Un camarero atiende muchas mesas porque casi todo su tiempo se va en esperar a la cocina, y esa espera la hace otro. El límite de la analogía: si el propio camarero se pone a cocinar algo largo, todas las mesas esperan. En Node, «cocinar» es hacer un cálculo pesado en JavaScript.

Compruébalo con un servidor de mentira. La función esperar imita una consulta a la base de datos: devuelve una promesa que se cumple después de unos milisegundos. Antes de ejecutar, predice en qué orden aparecerán las líneas y en qué milisegundo responderá cada petición:

Con false, B responde en el milisegundo 0, C hacia el 100 y A hacia el 300. El total es lo que tarda la espera más larga. Ahora cambia la primera línea a true: el cálculo pesado bloquea el hilo un segundo entero. C y A ya tenían sus datos a los 100 y 300 ms, pero no pueden responder hasta que el bucle termina, cerca del milisegundo 1000. Así se congela un servidor de verdad.

No bloquees el hilo

En un servidor, evita los cálculos largos dentro de una ruta y las funciones síncronas de Node que terminan en Sync, como fs.readFileSync, mientras atiendes peticiones. Leer un archivo de configuración con readFileSync al arrancar está bien; hacerlo en cada petición, no. Si de verdad necesitas calcular algo pesado (redimensionar imágenes, generar un mapa de juego), se hace en otro hilo con worker_threads o en otro servicio. El funcionamiento detallado del bucle de eventos, con sus microtareas y su orden exacto, está en la Estación 22.

npm: paquetes, package.json y versiones

Con lo que trae Node ya podrías escribir un servidor completo, y lo harás en la siguiente sección para ver cómo es por dentro. Pero para una API real tendrías que reescribir código que miles de personas ya escribieron y probaron: separar las rutas, leer el cuerpo de las peticiones, convertir JSON, validar datos. En vez de eso se usan paquetes: carpetas de código que alguien publicó para que otros lo instalen en sus proyectos.

npm (Node Package Manager, gestor de paquetes de Node) es dos cosas a la vez: el registro público npmjs.com, con millones de paquetes, y el comando npm, que se instala junto con Node y los descarga por ti. Ya lo usaste en la Estación 23 para instalar TypeScript. Ahora vas a entender cada pieza.

Pediste uno y llegaron 68. Express no hace todo solo: usa 28 paquetes más pequeños, cada uno con una tarea concreta, y varios de esos usan otros. npm los descarga todos. A los paquetes que instalas tú se les llama dependencias directas; a los que llegan con ellas, dependencias transitivas.

Scripts: atajos para tus comandos

Con los scripts de arriba, en vez de escribir el comando completo escribes:

$ npm run dev

npm run dev ejecuta node --watch src/servidor.js. La opción --watch vigila tus archivos y reinicia Node cada vez que guardas un cambio, así no tienes que parar y arrancar el servidor a mano. El script start es el que usan las plataformas donde publicarás tu API; es tan común que se puede escribir sin run: npm start. Lo mismo pasa con npm test. Para detener cualquiera de ellos, pulsa Ctrl + C en la terminal.

Consejo de oficio

Los scripts son la documentación viva de un proyecto. Cuando llegues a un proyecto ajeno, abre su package.json y mira la sección scripts: ahí está cómo se arranca, cómo se prueba y cómo se prepara para publicar. Node también puede ejecutarlos sin npm con node --run dev, un poco más rápido pero con menos funciones.

Versiones semánticas: qué significa ^5.2.1

Casi todos los paquetes numeran sus versiones con tres números, MAYOR.MENOR.PARCHE. Esta convención se llama versionado semántico (en inglés, semantic versioning o semver), y cada número promete algo:

  • PARCHE (de 5.2.1 a 5.2.2): arregla errores. Tu código sigue funcionando igual.
  • MENOR (de 5.2 a 5.3): añade funciones nuevas sin romper las que ya existían.
  • MAYOR (de 5 a 6): cambios que pueden romper tu código. Pasó de Express 4 a Express 5, y por eso hay una guía de migración.

En package.json no se guarda una versión exacta, sino un rango: qué versiones aceptas. El símbolo delante del número decide cuáles:

RangoAceptaEn palabras
^5.2.1desde 5.2.1 hasta antes de 6.0.0Cualquier mejora o arreglo, pero no un cambio mayor. Es lo que escribe npm install por defecto.
~5.2.1desde 5.2.1 hasta antes de 5.3.0Solo arreglos.
5.2.1solo 5.2.1Exactamente esa.
^0.4.2desde 0.4.2 hasta antes de 0.5.0Con versiones 0.x el paquete todavía no es estable, y el número del medio se trata como si fuera el mayor.
* o latestcualquier versiónNo lo uses: un cambio mayor puede romper tu proyecto sin avisar.

Semver es una promesa, no una garantía

Quien publica un paquete puede equivocarse y romper algo en una versión «menor». Por eso existe el archivo de la siguiente sección, y por eso conviene leer las notas de la versión (en inglés, changelog) antes de actualizar una dependencia importante. Para ver qué versiones nuevas hay de tus paquetes, usa npm outdated. Para saber cuál es la última versión publicada de un paquete, npm view express version.

package-lock.json y npm ci

package.json dice «cualquier Express 5 desde la 5.2.1». Si tu compañera clona el proyecto dentro de tres meses, podría recibir una versión distinta de la tuya, y lo mismo con cada una de las 68 dependencias. El archivo package-lock.json evita eso: anota la versión exacta y una huella de seguridad (integrity) de cada paquete que se instaló. Cuando alguien ejecuta npm install, npm respeta esas versiones exactas.

Existe además npm ci (de clean install, instalación limpia): borra node_modules e instala exactamente lo que dice el lock. Si package.json y package-lock.json no coinciden, falla en lugar de adivinar. Se usa en los servidores y en la integración continua (Estación 35), donde quieres el mismo resultado siempre.

Idea clave

Sube a Git package.json y package-lock.json. Nunca subas node_modules: pesa mucho y cualquiera lo recrea con npm install (lo configuraste en .gitignore en la Estación 24). Y nunca edites a mano node_modules ni el lock: npm los sobrescribe.

Importar paquetes y tus propios archivos

Con "type": "module", cada archivo es un módulo: tiene sus propias variables y comparte con otros solo lo que exporta. Las tres formas de importar que verás en un backend son estas (los módulos a fondo están en la Estación 22):

import express from "express";                // un paquete instalado en node_modules
import { readFile } from "node:fs/promises";  // un módulo que trae Node: prefijo node:
import { app } from "./app.js";               // un archivo tuyo: ruta relativa con ./ y extensión .js

export function sumar(a, b) {                 // lo que otros archivos pueden importar
  return a + b;
}

En tutoriales antiguos verás const express = require("express");. Es el sistema anterior, llamado CommonJS; funciona en proyectos con "type": "commonjs". La idea es la misma: traer código de otro archivo.

ERR_MODULE_NOT_FOUND

Con módulos modernos, las rutas a tus archivos necesitan el ./ del principio y la extensión. Si escribes import { app } from "./app", Node responde Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/…/src/app' imported from /…/src/servidor.js. La solución es escribir "./app.js". Y si el que falta es un paquete, como express, casi siempre es que olvidaste npm install o que estás en otra carpeta.

Impacto

Cada paquete que instalas es código de desconocidos que se ejecuta en tu computadora y en tu servidor. El 8 de septiembre de 2025, alguien engañó con un correo falso a la persona que mantenía paquetes muy usados, como chalk y debug, y publicó versiones con código malicioso que desviaba pagos con criptomonedas hechos desde el navegador. Estuvieron disponibles unas horas; esos paquetes se descargan miles de millones de veces por semana, y Express usa debug por dentro. Antes de instalar algo, comprueba que el nombre es exacto (hay paquetes trampa como expres), que se usa y se mantiene, y deja que package-lock.json fije versiones. Cómo auditar dependencias con npm audit lo verás en la Estación 31.

Tu primer servidor con node:http

Antes de usar Express, mira cómo es un servidor sin ayuda. Node trae el módulo node:http, que sabe abrir un puerto, recibir peticiones HTTP y enviar respuestas. Con él entenderás qué hace Express por ti. Crea el archivo src/hola-http.js dentro de tu carpeta api-tareas:

import { createServer } from "node:http";

const servidor = createServer((req, res) => {
  console.log(req.method, req.url);
  if (req.method === "GET" && req.url === "/") {
    res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
    res.end("¡Hola desde mi servidor!");
  } else if (req.method === "GET" && req.url === "/api/saludo") {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify({ mensaje: "Hola", hora: new Date().toISOString() }));
  } else {
    res.writeHead(404, { "Content-Type": "application/json" });
    res.end(JSON.stringify({ error: "No existe esa ruta" }));
  }
});

servidor.listen(3000, () => {
  console.log("Servidor escuchando en http://localhost:3000");
});

Pieza por pieza:

  • createServer(función) crea el servidor. La función que le pasas es un callback (Estación 10) que Node llamará una vez por cada petición que llegue. A esa función se le llama manejador (en inglés, handler).
  • req es la petición: req.method es el método ("GET", "POST"…), req.url es la ruta con su consulta ("/api/saludo?x=1") y req.headers, las cabeceras.
  • res es la respuesta que vas armando. res.writeHead(código, cabeceras) pone el código de estado y las cabeceras; res.end(texto) envía el cuerpo y cierra la respuesta.
  • La cabecera Content-Type le dice al cliente qué le envías: texto, HTML o JSON (la viste en la Estación 3). JSON.stringify convierte el objeto en el texto JSON que viaja por la red.
  • servidor.listen(3000, función) abre el puerto 3000 y empieza a escuchar. La función se ejecuta una vez, cuando el puerto ya está abierto.

El corazón de un servidor es una función

Mira otra vez el callback de createServer: recibe una petición y produce una respuesta. Si quitas todo lo que tiene que ver con la red (abrir el puerto, leer bytes, escribir cabeceras), lo que queda es una función que decide: «para esta petición, esta respuesta». Esa decisión es lo que programa un backend.

En los talleres de esta página vas a escribir esa decisión así: una función manejar que recibe un objeto { metodo, ruta, cuerpo } y devuelve otro { estado, cuerpo }. No toca la red, así que es una función pura (Estación 21): con la misma petición devuelve siempre la misma respuesta, y se puede probar sin encender nada. Sigue cómo decide:

function manejar(peticion) {
  if (peticion.metodo === "GET" && peticion.ruta === "/") {
    return { estado: 200, cuerpo: "¡Hola desde mi servidor!" };
  }
  if (peticion.metodo === "GET" && peticion.ruta === "/api/saludo") {
    return { estado: 200, cuerpo: { mensaje: "Hola" } };
  }
  return { estado: 404, cuerpo: { error: "No existe esa ruta" } };
}

const respuesta = manejar({ metodo: "GET", ruta: "/api/saludo" });
console.log(respuesta.estado, respuesta.cuerpo.mensaje);

Ahora la misma función con varias peticiones. La función probar hace el papel de curl: arma una petición simulada, se la pasa a manejar e imprime la respuesta en una línea. Predice las cinco líneas antes de ejecutar. Después, modifica manejar para que GET /api/version responda 200 con { "version": "1.0.0" }.

Tres detalles que merecen una segunda mirada. POST /api/saludo da 404 aunque la ruta existe, porque el manejador solo acepta GET en ella (un servidor más cuidadoso respondería 405, Method Not Allowed). /api/Saludo da 404 porque las rutas distinguen mayúsculas, como ya viste en la Estación 3. Y el texto de la primera línea sale entre comillas porque JSON.stringify de un texto produce un texto JSON, con sus comillas.

¿Y el cuerpo de un POST?

Hasta aquí todo es manejable. Pero mira lo que hace falta con node:http para recibir una tarea nueva en JSON: el cuerpo llega por la red en trozos, hay que juntarlos, convertirlos y defenderse de un JSON mal escrito.

const servidor = createServer(async (req, res) => {
  if (req.method === "POST" && req.url === "/api/tareas") {
    let texto = "";
    for await (const trozo of req) texto += trozo;   // el cuerpo llega en trozos
    let datos;
    try {
      datos = JSON.parse(texto);
    } catch {
      res.writeHead(400, { "Content-Type": "application/json" });
      return res.end(JSON.stringify({ error: "El cuerpo no es JSON válido" }));
    }
    // … comprobar los datos, guardar la tarea, responder 201 …
  }
  // … y un if más por cada ruta y cada método …
});

Y aún faltaría separar /api/tareas/7 para sacar el 7, leer consultas como ?hecha=true, poner siempre la cabecera correcta y responder 404 a lo desconocido. Funciona, pero es mucho código repetido y fácil de equivocar. Para eso existen los frameworks.

Express: rutas, parámetros y respuestas

Un framework es un conjunto de código ya hecho que resuelve lo repetitivo de un tipo de programa y te deja escribir solo lo que es propio de tu proyecto. Express es el framework de servidores más usado de Node.js: pequeño, estable desde 2010 y con miles de complementos. Se encarga de leer el método y la ruta, elegir qué función ejecutar, convertir JSON y poner las cabeceras. Tú escribes las rutas.

La versión actual es Express 5. La 5.0 salió en septiembre de 2024, después de años en preparación, y en septiembre de 2026 la última publicada es la 5.2.1. Necesita Node.js 18 o posterior. Para comprobar la última versión en cualquier momento: npm view express version.

Muchos tutoriales usan Express 4

Gran parte de los videos y artículos de internet se escribieron con Express 4. Casi todo sigue igual, pero estas diferencias te pueden confundir:

  • Si no preparas el cuerpo con express.json(), req.body vale undefined (en Express 4 valía {}).
  • Si una ruta async lanza un error, Express 5 lo lleva solo a tu manejador de errores. En Express 4, si no lo capturabas tú, la petición se quedaba colgada o se caía el servidor entero.
  • Las rutas comodín necesitan nombre: "/*splat" en vez de "/*", y las partes opcionales se escriben entre llaves: "/archivo{.:ext}".
  • Para poner el código de estado se usa res.status(201).json(datos); formas antiguas como res.json(datos, 201) o res.send(404) ya no existen (la segunda se escribe res.sendStatus(404)).

Este es el mismo «hola» de antes, ahora con Express. Guárdalo como src/servidor.js:

import express from "express";

const app = express();

app.get("/", (req, res) => {
  res.send("¡Hola desde Express!");
});

app.get("/api/saludo", (req, res) => {
  res.json({ mensaje: "Hola", hora: new Date().toISOString() });
});

app.listen(3000, (error) => {
  if (error) throw error;
  console.log("API lista en http://localhost:3000");
});

express() crea tu aplicación, a la que por costumbre se llama app. Cada app.get(...) declara una ruta: «cuando llegue un GET a esta dirección, ejecuta esta función». Ya no hay un if por ruta: Express elige por ti. Y si llega algo que no coincide con ninguna ruta, Express responde solo con un 404. En Express 5, la función de app.listen recibe un error si el puerto no se pudo abrir, por ejemplo por un EADDRINUSE; con throw error lo verás en la terminal.

Responder

El objeto res trae métodos para cada tipo de respuesta. Varios se pueden encadenar, porque devuelven el mismo res:

res.status(201).json(datos)Lo mismo, con otro código de estado.

Una respuesta, y solo una

Cada petición debe recibir exactamente una respuesta. Si una ruta no responde, el cliente se queda esperando hasta rendirse. Si responde dos veces, Node se queja con Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client y el cliente recibe un 500. La causa más común es olvidar el return:

Responde dos veces

app.get("/api/tareas/:id", (req, res) => {
  const tarea = buscar(req.params.id);
  if (!tarea) {
    res.status(404).json({ error: "No existe" });
  }
  res.json(tarea); // también se ejecuta
});

return corta la función

app.get("/api/tareas/:id", (req, res) => {
  const tarea = buscar(req.params.id);
  if (!tarea) {
    return res.status(404).json({ error: "No existe" });
  }
  res.json(tarea);
});

Parámetros de ruta: req.params

Una API no tiene una ruta por tarea: tiene una ruta con un hueco. En "/api/tareas/:id", los dos puntos marcan un parámetro de ruta: esa parte de la dirección puede ser cualquier cosa, y Express la guarda en req.params con el nombre que pusiste. Para GET /api/tareas/7, req.params.id vale "7".

app.get("/api/tareas/:id", (req, res) => {
  const id = Number(req.params.id);          // "7" → 7
  const tarea = tareas.find((t) => t.id === id);
  if (!tarea) {
    return res.status(404).json({ error: `No existe la tarea ${req.params.id}` });
  }
  res.json(tarea);
});

// Puede haber varios: /api/juegos/snake/puntuaciones/3
app.get("/api/juegos/:juego/puntuaciones/:id", (req, res) => {
  res.json(req.params); // { "juego": "snake", "id": "3" }
});

Los parámetros siempre son texto

Todo lo que viene en la URL es texto. Si comparas t.id === req.params.id, estás comparando el número 7 con el texto "7", y === dice que no son iguales (Estación 8). Tu API respondería 404 a todas las tareas que sí existen. Convierte primero con Number(), como en la Estación 7.

Parámetros de consulta: req.query

Lo que va después del ? en una URL son los parámetros de consulta (en inglés, query parameters), que conociste en la Estación 16. Express los separa por ti en req.query. Para GET /api/tareas?hecha=true&limite=5:

app.get("/api/tareas", (req, res) => {
  console.log(req.query);            // { hecha: 'true', limite: '5' }
  let lista = tareas;
  if (req.query.hecha !== undefined) {
    const quiero = req.query.hecha === "true";
    lista = lista.filter((t) => t.hecha === quiero);
  }
  res.json(lista);
});

Igual que los parámetros de ruta, los de consulta son texto: "true" no es true y "5" no es 5. Si un parámetro no viene, vale undefined. ¿Cuándo usar cada uno? Una regla que casi nunca falla: la ruta identifica el recurso (/api/tareas/7 es la tarea 7) y la consulta ajusta una lista: filtrar, ordenar, limitar o buscar (/api/tareas?hecha=false&limite=10).

Recibir JSON en el cuerpo: req.body

Para crear una tarea, el cliente envía sus datos en el cuerpo de un POST. Express no lee el cuerpo si no se lo pides: la línea app.use(express.json()) prepara, para todas las rutas, un paso previo que lee el cuerpo, lo convierte de JSON a objeto y lo deja en req.body. (Ese «paso previo» se llama middleware y tiene su propia sección más abajo.)

app.use(express.json());

app.post("/api/tareas", (req, res) => {
  const nueva = { id: siguienteId++, titulo: req.body.titulo, hecha: false };
  tareas.push(nueva);
  res.status(201).location(`/api/tareas/${nueva.id}`).json(nueva);
});

Comillas en Windows

Las comillas simples de '{"titulo": …}' funcionan en macOS, Linux y Git Bash, pero en PowerShell y en cmd las comillas se interpretan de otra manera y el JSON llega roto. La forma que funciona en todas partes es guardar el JSON en un archivo, por ejemplo tarea.json, y enviarlo con @: curl.exe -i --json "@tarea.json" http://localhost:3000/api/tareas.

Cannot read properties of undefined (reading 'titulo')

Es el error más frecuente al empezar con Express 5, y el servidor responde 500. Significa que req.body es undefined. Tiene dos causas: olvidaste app.use(express.json()), o el cliente no envió la cabecera Content-Type: application/json (por ejemplo, usaste -d sin -H). express.json() solo lee cuerpos que dicen ser JSON. En la sección Validar harás que tu API responda un 400 claro en vez de romperse.

El orden de las rutas importa

Express prueba las rutas en el orden en que las declaraste y usa la primera que coincide. Mira este problema:

app.get("/api/tareas/:id", verTarea);          // coincide con /api/tareas/CUALQUIER-COSA
app.get("/api/tareas/pendientes", verPendientes); // nunca se alcanza

Una petición a /api/tareas/pendientes entra en la primera ruta con req.params.id igual a "pendientes", y responde 404 porque no existe una tarea con ese id. La solución es declarar primero las rutas fijas y después las que tienen parámetros. (O mejor: usar una consulta, /api/tareas?hecha=false, como verás en la sección de diseño.)

Diseñar una API REST

En la Estación 16 usaste APIs REST desde fuera: recursos con URL propia, métodos HTTP como verbos y respuestas en JSON. Ahora te toca decidir cómo será la tuya. Una API bien diseñada se puede usar casi sin leer su documentación, porque se parece a todas las demás. Una mal diseñada obliga a adivinar, y cada petición es una sorpresa para quien la usa, que muchas veces serás tú dentro de tres meses.

Las URL nombran cosas; los métodos dicen qué hacer

En REST, la URL es un sustantivo: nombra un recurso, que es cualquier cosa de la que tu API guarda datos (tareas, jugadores, puntuaciones). El método HTTP es el verbo. Por eso la acción no va en la URL:

Verbos en la URL

POST /api/crearTarea
GET  /api/obtenerTareas
POST /api/borrarTarea?id=7
GET  /api/tareas/7/completar

Recursos y métodos

POST   /api/tareas
GET    /api/tareas
DELETE /api/tareas/7
PATCH  /api/tareas/7   {"hecha": true}

Las convenciones más extendidas:

  • Nombres en plural para las colecciones: /api/tareas es la lista y /api/tareas/7 es un elemento de ella.
  • Minúsculas y guiones si hay varias palabras: /api/partidas-guardadas.
  • Anidar cuando un recurso pertenece a otro, sin pasar de dos niveles: /api/juegos/snake/puntuaciones.
  • Un prefijo común, como /api, para separar la API de las páginas. Algunas APIs añaden la versión, /api/v1/tareas, para poder cambiar el diseño sin romper las apps que ya la usan.

Antes de escribir código, escribe esta tabla. Es el contrato entre tu backend y quien lo use. Para las tareas queda así:

Una lista vacía no es un 404

Si alguien pide GET /api/tareas?hecha=true y no hay tareas hechas, la respuesta correcta es 200 con []. La lista existe; solo está vacía. El 404 es para cuando el recurso que pides no existe, como /api/tareas/999. Algunas APIs públicas lo hacen al revés, como la de Rick and Morty que viste en la Estación 16, y obligan a quien las usa a tratar ese caso aparte.

Respuestas coherentes

Quien use tu API escribirá código que depende de la forma de tus respuestas. Mantenla siempre igual:

  • Los errores tienen siempre la misma forma, por ejemplo { "error": "mensaje para personas", "detalles": { … } }. Así el frontend puede mostrar respuesta.error sin preguntarse de qué ruta vino.
  • Las listas son arrays, aunque tengan cero o un elemento.
  • Las fechas van en formato ISO 8601, el que produce new Date().toISOString(): "2026-09-30T08:48:31.743Z". Lo entiende cualquier lenguaje y no depende del país.
  • Los nombres de campo siguen un único estilo. En APIs escritas en JavaScript suele ser camelCase (siguientePagina), como en la Estación 7.

Métodos seguros e idempotentes

Las redes fallan. Una app que no recibe respuesta suele reintentar, y hay personas que pulsan dos veces el mismo botón. Por eso cada método HTTP promete algo sobre qué pasa si se repite:

MétodoSeguro (no cambia nada)Idempotente (repetirlo deja todo igual que hacerlo una vez)
GETSíSí
PUTNoSí: reemplazar dos veces por lo mismo da lo mismo
DELETENoSí: después del primero ya no existe; el segundo responde 404, pero el estado final es igual
PATCHNoDepende de lo que haga: {"hecha": true} sí lo es; «suma 10 puntos», no
POSTNoNo: dos POST crean dos tareas

Consecuencia práctica: un GET jamás debe cambiar datos (los navegadores y buscadores hacen GET por su cuenta, por ejemplo al precargar enlaces), y las operaciones que no se deben duplicar, como un pago, necesitan protección extra contra los reintentos.

function express() {

    }
    next();

  }
  app.use = (a, b) => capas.push(b ? { ruta: a, f: b } : { ruta: "", f: a });
  app.probar = (metodo, url, cuerpo) => {

    const req = { method: metodo, path: u.pathname, originalUrl: url, params: {},
      query: Object.fromEntries(u.searchParams),
      crudo: cuerpo === undefined ? undefined : typeof cuerpo === "string" ? cuerpo : JSON.stringify(cuerpo) };
    const res = { statusCode: 200, cuerpo: "", enviada: false, extra: "",
      status(n) { this.statusCode = n; return this; },
      location(l) { this.extra = " (Location: " + l + ")"; return this; },
      json(d) { return this.send(JSON.stringify(d)); },
      send(d) { this.cuerpo = typeof d === "object" ? JSON.stringify(d) : String(d); this.enviada = true; return this; },
      sendStatus(n) { return this.status(n).send(""); },
      end() { this.enviada = true; return this; } };
    let i = 0;
    const siguiente = (err) => {
      while (i < capas.length) {
        const c = capas[i++];
        if (c.f.length === 4 ? !err : err) continue;
        const params = coincide(c, req.method, req.path);
        if (!params) continue;
        req.params = params;
        try { if (err) c.f(err, req, res, siguiente); else c.f(req, res, siguiente); } catch (e) { siguiente(e); }
        return;
      }
      if (err) res.status(err.status || 500).send(err.name + ": " + err.message);
      else res.status(404).send("Cannot " + metodo + " " + u.pathname);
    };
    siguiente();
    console.log(metodo + " " + url + " → " + (res.enviada ? res.statusCode + res.extra + (res.cuerpo ? " " + res.cuerpo : "") : "(sin respuesta: el cliente se queda esperando)"));
  };
  function coincide(capa, metodo, ruta) {
    if (capa.metodo && capa.metodo !== metodo) return null;
    const a = capa.ruta.split("/").filter(Boolean), b = ruta.split("/").filter(Boolean);
    if (capa.metodo ? a.length !== b.length : a.length > b.length) return null;
    const params = {};
    for (let k = 0; k < a.length; k++) {
      if (a[k][0] === ":") params[a[k].slice(1)] = decodeURIComponent(b[k]);
      else if (a[k] !== b[k]) return null;
    }
    return params;
  }
  return app;
}

Middleware, errores y registros

Hay tareas que se repiten en todas las peticiones: anotar cuál llegó y cuánto tardó, convertir el cuerpo JSON, rechazar a quien no tiene permiso, cerrar la API por mantenimiento. Escribirlas dentro de cada ruta sería copiar lo mismo veinte veces, y el día que olvides una, tendrás un agujero.

Un middleware (literalmente, «software del medio») es una función que Express ejecuta en cada petición, en el orden en que la registraste, antes de llegar a las rutas o en lugar de ellas. Recibe tres cosas: req, res y next, una función que significa «ya terminé, que pase el siguiente». Un middleware puede hacer tres cosas:

  • Leer o modificar req y res. Por ejemplo, express.json() rellena req.body.
  • Responder él mismo y cortar la cadena. Por ejemplo, un 503 si la API está en mantenimiento.
  • Llamar a next() para pasar la petición al siguiente middleware o ruta.
function miMiddleware(req, res, next) {
  // … hacer algo con la petición …
  next(); // o bien responder con res.status(…).json(…), pero no las dos cosas
}

app.use(miMiddleware); // se ejecuta en TODAS las peticiones, en este punto de la fila

Para entenderlo

Piensa en los controles de un aeropuerto: primero revisan tu documento, luego pasa tu equipaje por el escáner y al final llegas a la puerta de embarque. Cada control puede dejarte pasar (next()) o detenerte ahí mismo (responder). Y el orden importa: no te revisan el equipaje después de embarcar. El límite de la analogía: en Express, un middleware también puede actuar cuando la respuesta ya va de vuelta, como verás en el paso 5.

Este es el middleware registro de la cápsula, tal como lo usarás en el proyecto. res.on("finish", función) deja preparada una función que Node ejecutará cuando la respuesta termine de enviarse; así el registro puede anotar el código final y el tiempo total. performance.now() mide el tiempo en milisegundos, como en la Estación 20.

// src/middleware/registro.js
export function registro(req, res, next) {
  const inicio = performance.now();
  res.on("finish", () => {
    const ms = (performance.now() - inicio).toFixed(1);
    console.log(`${req.method} ${req.originalUrl} → ${res.statusCode} (${ms} ms)`);
  });
  next();
}

El orden es el del código

app.use(registro) tiene que ir antes de las rutas: un middleware que declaras después de una ruta que ya respondió no llega a ejecutarse para esa petición. Y un middleware que no responde ni llama a next() deja la petición colgada: el cliente espera hasta rendirse, sin ningún error en la consola que te dé una pista.

En este taller hay dos middleware propios, dos rutas, un 404 a medida y un manejador de errores. Predice qué imprime cada petición, incluidas las líneas del registro. Después prueba tres cambios, de uno en uno: pon enMantenimiento en true; quita el next(); del registro; y mueve el bloque del 404 al principio, justo después de const app.

Con los valores iniciales verás cada petición precedida de su línea de registro. /api/nada no coincide con ninguna ruta y cae en tu 404, que ahora responde JSON en vez de la página HTML de Express. /api/explota lanza un error: Express lo captura y lo entrega al manejador de errores, que lo anota y responde 500 sin contar detalles. El POST con JSON roto nunca llega a ninguna ruta: express.json() falla y el error salta directo al final. Con enMantenimiento = true, todo responde 503 después de registrarse. Sin next() en el registro, nadie responde nunca. Y con el 404 al principio, todas las peticiones reciben 404, porque ese middleware responde sin mirar la ruta.

Manejar los errores en un solo lugar

Un manejador de errores es un middleware con cuatro parámetros: (err, req, res, next). Express lo reconoce por ese cuarto parámetro y solo lo llama cuando algo falla: cuando una ruta lanza un error con throw, cuando una función async rechaza su promesa, o cuando alguien llama a next(error). Se declara al final de todo, después de las rutas y del 404. Así queda el del proyecto:

// src/middleware/errores.js
export function rutaNoEncontrada(req, res) {
  res.status(404).json({ error: `No existe ${req.method} ${req.originalUrl}` });
}

export function manejarErrores(err, req, res, next) {
  if (err.type === "entity.parse.failed") {       // el JSON que envió el cliente está roto
    return res.status(400).json({ error: "El cuerpo no es JSON válido" });
  }
  const estado = err.status ?? 500;
  if (estado >= 500) console.error(err);        // el detalle completo, solo en tu terminal
  res.status(estado).json({
    error: estado >= 500 ? "Error interno del servidor" : err.message,
  });
}

Los errores que produce express.json() traen dos propiedades útiles: status (400) y type, que vale "entity.parse.failed" cuando el JSON no se puede leer. Los demás errores usan su status si lo tienen, y 500 si no. Con esto, tus rutas pueden lanzar errores sin preocuparse de cómo se responden. En Express 5 funciona también dentro de funciones async, que es lo que usarás cuando tus datos vivan en una base de datos (Estación 30). Crear un error con un código de estado es añadirle una propiedad:

app.get("/api/tareas/:id", async (req, res) => {
  const tarea = await buscarTarea(Number(req.params.id)); // imagina que consulta una base de datos
  if (!tarea) {
    const error = new Error("No existe esa tarea");
    error.status = 404;
    throw error;               // Express 5 lo lleva a manejarErrores
  }
  res.json(tarea);
});

Si prefieres algo más ordenado, crea una clase de error propia con class ErrorHttp extends Error, como aprendiste con la herencia en la Estación 21, y dale un status en el constructor.

No le cuentes tus secretos al cliente

Si no escribes tu propio manejador, Express usa uno de serie. Mientras la variable de entorno NODE_ENV no valga "production", responde con una página que incluye la traza completa del error: <pre>Error: Algo se rompió<br> at file:///home/tu/api-tareas/src/servidor.js:48:9 …. Eso revela rutas de tu computadora, nombres de archivos y librerías: pistas valiosas para un atacante. Tu manejador debe responder un mensaje genérico en los 5xx y guardar el detalle en el registro del servidor, con console.error. En los 4xx, en cambio, el mensaje sí debe explicar qué corregir.

Registros: qué anotar y qué no

Los registros (en inglés, logs) son las líneas que tu servidor escribe mientras trabaja. Cuando algo falle en producción, a las tres de la madrugada y en una computadora que no es la tuya, serán lo único que tengas para entender qué pasó.

  • Anota cada petición (método, ruta, código, duración), los errores con su traza completa y los eventos importantes: el servidor arrancó, se conectó a la base de datos, se creó una cuenta.
  • Nunca anotes contraseñas, claves, tokens de sesión ni datos personales como correos o direcciones completas. Los registros se leen, se copian y se guardan durante meses, y los ve más gente que tu base de datos.
  • console.log escribe en la salida estándar y console.error en la salida de errores. Las plataformas de publicación las recogen por separado, así que usa cada una para lo suyo.

Para empezar, tu middleware registro es suficiente. En proyectos reales se usan librerías. morgan, del propio equipo de Express, escribe una línea por petición con app.use(morgan("dev")), algo como GET /api/tareas 200 2.765 ms - 47 (el último número son los bytes de la respuesta). pino escribe cada registro como una línea de JSON, con nivel (info, warn, error) y hora, para que otras herramientas puedan buscar y filtrar. Qué pasa con esos registros cuando la API está publicada lo verás en la Estación 35.

CORS, en pocas palabras

Cuando el frontend de tu juego corra en http://localhost:5173 (el puerto típico de Vite, que usarás en la Estación 32) y le haga fetch a tu API en http://localhost:3000, el navegador puede bloquear la respuesta con un error de CORS (Cross-Origin Resource Sharing). Otro puerto cuenta como otro «origen», y por seguridad el navegador solo deja que una página lea respuestas de otro origen si el servidor lo autoriza con la cabecera Access-Control-Allow-Origin. El paquete cors la añade:

import cors from "cors";   // npm install cors

app.use(cors({ origin: "http://localhost:5173" })); // solo tu frontend, no cualquiera

Dos cosas que ahorran horas de confusión: CORS lo aplica el navegador, así que curl, Bruno y otros servidores no lo sufren (por eso con curl todo funciona y desde tu página no). Y abrir la API a todos los orígenes sin pensar tiene consecuencias de seguridad. Por qué existe CORS y cómo configurarlo bien está en la Estación 31.

Validar los datos que llegan

Tu ruta POST /api/puntuaciones espera algo como {"jugador": "Ana", "juego": "snake", "puntos": 420}. Pero por la red puede llegar cualquier cosa: {"puntos": "mil"}, {"puntos": -50}, {"jugador": ""}, un nombre de cinco millones de letras o {"puntos": 420, "esAdmin": true}. Si lo guardas sin mirar, el ranking se rompe en el mejor de los casos. Validar es comprobar que los datos tienen la forma y los valores que esperas antes de usarlos, y si no, responder 400 explicando qué está mal.

Validar en el frontend no basta

Las validaciones de un formulario HTML (required, pattern, que viste en la Estación 13) son para la comodidad de la persona: le avisan al momento. Las del servidor son para la seguridad: cualquiera puede saltarse tu formulario enviando la petición con curl. Necesitas las dos, y la del servidor es obligatoria.

Validar a mano

Una validación es una función que recibe los datos y devuelve la lista de problemas. Si la lista está vacía, los datos sirven. Number.isInteger(valor) responde si un valor es un número entero; para un texto como "mil" o un decimal como 12.5 responde false. Sigue la función con datos malos:

function validarPuntuacion(datos) {
  const errores = [];
  if (typeof datos.jugador !== "string" || datos.jugador.trim() === "") {
    errores.push("jugador: escribe un nombre");
  }
  if (!Number.isInteger(datos.puntos) || datos.puntos < 0) {
    errores.push("puntos: debe ser un entero de 0 o más");
  }
  return errores;
}

const problemas = validarPuntuacion({ jugador: "  ", puntos: "mil" });
console.log(problemas.length, problemas[0]);

Ahora una versión con una regla más (el nombre no puede pasar de 20 caracteres). Predice qué lista imprime cada línea. Presta atención a la tercera, la cuarta y la última.

"510" falla porque es texto, aunque parezca un número: en JSON, "puntos": "510" y "puntos": 510 son cosas distintas. 12.5 falla porque no es entero. Y la última pasa... con un campo de regalo, esAdmin. Si después guardaras { ...req.body }, ese campo acabaría en tu base de datos. A ese ataque se le llama asignación masiva (mass assignment): colar campos que el servidor no esperaba. La defensa es construir el objeto a guardar solo con los campos que validaste.

Validar a mano funciona, pero crece rápido: cada campo, cada tipo, longitudes, valores por defecto, quitar espacios, mensajes claros, campos que sobran. Por eso se usan librerías.

Zod: describe la forma y deja que compruebe

Zod es una librería de validación muy usada en JavaScript y TypeScript. En vez de escribir if tras if, describes la forma que deben tener los datos, un esquema, y Zod comprueba cualquier valor contra él. La versión actual es la 4. Se instala como cualquier paquete:

$ npm install zod

import * as z from "zod";

z.config(z.locales.es()); // mensajes de error en español

const EsquemaPuntuacion = z.object({
  jugador: z.string().trim().min(1, "Escribe un nombre").max(20, "Máximo 20 caracteres"),
  juego: z.string().trim().min(1, "Indica el juego"),
  puntos: z.number({ error: "Los puntos deben ser un número" })
    .int("Los puntos deben ser un número entero")
    .nonnegative("Los puntos no pueden ser negativos"),
});

Se lee casi como una frase: un objeto con un jugador que es un texto, sin espacios en los extremos, de 1 a 20 caracteres; un juego que es un texto no vacío; y unos puntos que son un número entero no negativo. El segundo argumento de cada regla es el mensaje de error; si no lo pones, Zod usa uno genérico, que z.config(z.locales.es()) traduce al español.

Para comprobar datos se usa safeParse, que nunca lanza errores: devuelve un objeto con success y, según el caso, data (los datos ya limpios) o error (los problemas). Así se ve con datos buenos:

const bien = EsquemaPuntuacion.safeParse({ jugador: "  Sofía ", juego: "snake", puntos: 777, esAdmin: true });
console.log(bien);
// { success: true, data: { jugador: 'Sofía', juego: 'snake', puntos: 777 } }

Mira dos regalos: trim() quitó los espacios de " Sofía ", y esAdmin desapareció. z.object descarta los campos que no están en el esquema, así que la asignación masiva queda bloqueada. (Si prefieres rechazar la petición cuando sobran campos, usa z.strictObject.) Y con datos malos:

const mal = EsquemaPuntuacion.safeParse({ jugador: "", puntos: 12.5 });
console.log(mal.success);                // false
console.log(z.flattenError(mal.error));
// {
//   formErrors: [],
//   fieldErrors: {
//     jugador: [ 'Escribe un nombre' ],
//     juego: [ 'Entrada inválida: se esperaba texto, recibido indefinido' ],
//     puntos: [ 'Los puntos deben ser un número entero' ]
//   }
// }

z.flattenError ordena los problemas por campo en fieldErrors, justo lo que necesita un frontend para pintar cada mensaje junto a su casilla. En formErrors van los problemas del conjunto: por ejemplo, si no llegó ningún cuerpo, aparece 'Entrada inválida: se esperaba objeto, recibido indefinido'. En una ruta queda así:

app.post("/api/puntuaciones", (req, res) => {
  const resultado = EsquemaPuntuacion.safeParse(req.body);
  if (!resultado.success) {
    return res.status(400).json({ error: "Datos no válidos", detalles: z.flattenError(resultado.error) });
  }
  const nueva = { id: siguienteId++, ...resultado.data };   // resultado.data, no req.body
  puntuaciones.push(nueva);
  res.status(201).location(`/api/puntuaciones/${nueva.id}`).json(nueva);
});

Después de validar, usa los datos validados

Una vez que Zod aprobó los datos, trabaja con resultado.data y olvídate de req.body. resultado.data tiene los textos recortados, los valores por defecto aplicados y solo los campos permitidos. Si vuelves a usar req.body, pierdes todo eso.

Validar también la consulta

Los parámetros de consulta llegan como texto, así que z.number() rechazaría "5". Para ellos existe z.coerce.number(), que primero convierte con Number() y después valida. Con .default() das un valor cuando el parámetro no viene, y con .optional() permites que falte:

const EsquemaConsulta = z.object({
  juego: z.string().optional(),
  limite: z.coerce.number().int().min(1).max(100).default(10),
});

EsquemaConsulta.safeParse({ limite: "5" });     // { success: true, data: { limite: 5 } }
EsquemaConsulta.safeParse({});                  // { success: true, data: { limite: 10 } }
EsquemaConsulta.safeParse({ limite: "mucho" }); // success: false → "se esperaba número, recibido NaN"
EsquemaConsulta.safeParse({ limite: "500" });   // success: false → "se esperaba que número fuera <=100"

Limitar limite no es un capricho: sin un máximo, alguien podría pedir un millón de puntuaciones en una sola petición y dejar tu servidor ocupado.

Zod y TypeScript

Si escribes tu API en TypeScript (Estación 23), Zod te da además el tipo a partir del esquema: type Puntuacion = z.infer<typeof EsquemaPuntuacion>. Así el esquema es la única fuente de verdad, para la comprobación mientras el programa corre y para los tipos mientras programas. Hay alternativas con la misma idea, como Valibot, Joi o express-validator.

Validar no es toda la seguridad

Validar la forma de los datos es la primera defensa, pero no la única. Un texto válido todavía puede ser un ataque si lo metes en una consulta SQL sin cuidado (Estación 30) o en una página con innerHTML (Estación 15), y validar no dice si esa persona tiene permiso para hacer lo que pide (Estación 31). Un detalle útil: express.json() rechaza por defecto cuerpos de más de 100 KB, así que nadie puede colarte un JSON gigante.

Si los escribes en el código, acaban en Git, y lo que entra en el historial de Git se queda ahí para siempre (Estación 24). La configuración tiene que vivir fuera del código.

Variables de entorno

Una variable de entorno es un valor con nombre que el sistema operativo le entrega a un programa al arrancarlo. Cada programa recibe las suyas, y en Node están en el objeto process.env:

const puerto = Number(process.env.PORT) || 3000;

app.listen(puerto, (error) => {
  if (error) throw error;
  console.log(`API lista en http://localhost:${puerto}`);
});

Los valores de process.env son siempre texto, o undefined si la variable no existe. Por eso se convierte con Number() y se da un valor por defecto con ||. Para darle un valor al arrancar, en la terminal:

$ PORT=4000 node src/servidor.js
API lista en http://localhost:4000

Así se hace en macOS, Linux y Git Bash. En PowerShell es $env:PORT=4000; node src/servidor.js, y la variable queda puesta hasta que cierres esa terminal.

El archivo .env y --env-file

Escribir todas las variables en cada arranque es incómodo. La costumbre es guardarlas en un archivo llamado .env en la raíz del proyecto, una por línea, con la forma NOMBRE=valor:

# Configuración de MI computadora. Este archivo NO se sube a Git.
PORT=3000
NODE_ENV=development
CLAVE_API_CORREO=pon-aqui-tu-clave

Node lo lee con la opción --env-file: todas esas variables aparecen en process.env antes de que empiece tu código. Existe desde Node 20.6 y es estable desde Node 24.10:

$ node --env-file=.env src/servidor.js
API lista en http://localhost:3000

Si el archivo no existe, Node se niega a arrancar con node: .env: not found. Cuando el archivo es opcional, usa --env-file-if-exists=.env. Y si una variable está a la vez en el entorno real y en el archivo, gana la del entorno. En tutoriales anteriores verás el paquete dotenv (import "dotenv/config"), que hacía lo mismo cuando Node todavía no sabía hacerlo; hoy no lo necesitas. Con esto, los scripts de package.json quedan así:

"scripts": {
  "dev": "node --watch --env-file=.env src/servidor.js",
  "start": "node src/servidor.js"
}

¿Por qué start no lee .env? Porque start es lo que ejecuta la plataforma de publicación, y allí no hay archivo .env: las variables se escriben en el panel de la plataforma, que se las entrega a tu programa como variables de entorno reales (Estación 35).

.env nunca va a Git

Añade .env a .gitignore antes del primer commit. Para que tu equipo sepa qué variables hacen falta, sube en su lugar un .env.example con los mismos nombres y valores de mentira: CLAVE_API_CORREO=cambia-esto. Si alguna vez subes un secreto por error, dalo por robado: hay programas que recorren GitHub buscando claves. Borrarlo del historial no basta; hay que cambiar la clave en el servicio (en inglés, rotarla). La Estación 31 trata la gestión de secretos a fondo.

Dos costumbres más. La primera: comprueba la configuración al arrancar. Si falta algo imprescindible, es mejor que el servidor se niegue a encender con un mensaje claro que descubrirlo a medianoche cuando falle el primer correo:

const claveCorreo = process.env.CLAVE_API_CORREO;
if (!claveCorreo) {
  throw new Error("Falta la variable de entorno CLAVE_API_CORREO. Revisa tu archivo .env");
}

La segunda: la variable NODE_ENV. Por convención vale "production" en el servidor publicado, y muchas librerías cambian su comportamiento con ella. Express, por ejemplo, deja de mostrar la traza de los errores en su manejador de serie. La pondrás en la plataforma de publicación, no en tu computadora.

Estructura de carpetas

Un solo archivo sirve para aprender, pero con diez rutas se vuelve un laberinto. No hay una estructura obligatoria en Express; esta es una forma sencilla y muy común, la que usarás en el proyecto:

Dos decisiones de esta estructura merecen explicación:

  • app.js y servidor.js están separados. app.js crea y configura la aplicación y la exporta; servidor.js la importa y abre el puerto. Parece un archivo de más, pero permite que las pruebas automáticas importen app y le envíen peticiones sin encender un servidor de verdad (Estación 26).
  • Las rutas de cada recurso van en su propio archivo, agrupadas con un Router: una mini aplicación de Express que solo tiene rutas. Se «monta» en una ruta base, y dentro de él las rutas se escriben sin esa base.
// src/rutas/puntuaciones.js
import { Router } from "express";

export const rutasPuntuaciones = Router();

rutasPuntuaciones.get("/", (req, res) => { /* … */ });     // GET  /api/puntuaciones
rutasPuntuaciones.get("/:id", (req, res) => { /* … */ });  // GET  /api/puntuaciones/7
rutasPuntuaciones.post("/", (req, res) => { /* … */ });    // POST /api/puntuaciones

// src/app.js
app.use("/api/puntuaciones", rutasPuntuaciones);           // monta el Router en su ruta base

Cuando el proyecto crece

En proyectos grandes se separa además la lógica en capas: las rutas solo hablan HTTP (leen req, responden con res), los servicios aplican las reglas del negocio y los repositorios hablan con la base de datos. Es la arquitectura en capas de la Estación 28. Otra opción popular es agrupar por funcionalidad (src/puntuaciones/rutas.js, src/puntuaciones/esquemas.js…). Empieza simple y divide un archivo cuando cueste encontrar cosas en él.

Practica la estructura en esta terminal. La carpeta api-puntuaciones ya tiene su package.json y sus dependencias instaladas; te falta el resto. Recuerda: los archivos que empiezan por punto no aparecen con ls; para verlos, ls -a.

  1. Entra en el proyecto: cd api-puntuaciones.
  2. Crea las carpetas de una vez: mkdir -p src/rutas src/middleware.
  3. Crea los archivos vacíos: touch src/servidor.js src/app.js src/rutas/puntuaciones.js src/middleware/registro.js src/middleware/errores.js.
  4. Crea la configuración: echo "PORT=3000" > .env y lo mismo para .env.example.
  5. Crea .gitignore con dos líneas: echo "node_modules/" > .gitignore y echo ".env" >> .gitignore (dos signos: añadir sin borrar).
  6. Comprueba con ls -a y cat .gitignore.

Y ahora el orden dentro de app.js, que es donde más se nota que el orden importa. Las importaciones pueden ir en cualquier orden entre sí; el resto, no. El registro va primero para que anote incluso las peticiones que fallen al leer el cuerpo.

  1. import express from "express";
  2. import { registro } from "./middleware/registro.js";
  3. import { rutaNoEncontrada, manejarErrores } from "./middleware/errores.js";
  4. import { rutasPuntuaciones } from "./rutas/puntuaciones.js";
  5. export const app = express();
  6. app.use(registro);
  7. app.use(express.json());
  8. app.use("/api/puntuaciones", rutasPuntuaciones);
  9. app.use(rutaNoEncontrada);
  10. app.use(manejarErrores);

¿Y si quiero escribirla en TypeScript?

Todo lo de esta estación funciona igual en TypeScript. Parte del proyecto y del tsconfig.json de la Estación 23 y haz cuatro cambios. Instala los tipos de Node y de Express como dependencias de desarrollo: npm install -D typescript @types/node @types/express (Zod ya trae los suyos). En tsconfig.json, cambia "types": [] por "types": ["node"], para que TypeScript conozca process y los módulos de Node, y añade "rewriteRelativeImportExtensions": true. Nombra tus archivos .ts e impórtalos con su extensión real: import { app } from "./app.ts". Para desarrollar, node --watch --env-file=.env src/servidor.ts ejecuta el código directamente gracias al borrado de tipos de Node 24, y en otra terminal npx tsc --noEmit --watch revisa los tipos. Para publicar, npx tsc escribe la versión JavaScript en dist/ (cambiando esas extensiones a .js) y el script start pasa a ser node dist/servidor.js.

Resumen

  • El backend corre en un servidor que controlas tú: guarda los datos compartidos, aplica las reglas y guarda los secretos. Nunca confíes en lo que envía el cliente.
  • Node.js ejecuta JavaScript fuera del navegador (sin DOM, con process, archivos y red). Con un solo hilo y el bucle de eventos atiende muchas peticiones, siempre que no lo bloquees con cálculos largos. Usa la LTS más reciente.
  • npm instala paquetes. package.json es la ficha del proyecto (dependencias, scripts, "type": "module"); package-lock.json fija las versiones exactas. Los dos van a Git; node_modules, no.
  • Semver: MAYOR.MENOR.PARCHE. ^5.2.1 acepta cualquier 5.x desde la 5.2.1; ~5.2.1, solo arreglos. npm ci instala exactamente lo del lock.
  • Un servidor es, en el fondo, una función: petición → respuesta. node:http lo muestra al desnudo; Express 5 añade rutas, req.params, req.query, req.body (con express.json()) y res.status().json(). Los parámetros siempre llegan como texto.
  • Una API REST usa sustantivos en las URL y métodos como verbos, con códigos precisos: 200, 201 con Location, 204, 400, 404, 409 y, solo cuando falla tu código, 500. Las listas vacías son 200 con [].
  • El middleware (req, res, next) se ejecuta en el orden del código. El 404 va casi al final y el manejador de errores, con cuatro parámetros, al final de todo. En Express 5 también captura los errores de las rutas async. Nunca envíes trazas al cliente.
  • Valida todo lo que llega, mejor con un esquema de Zod: safeParse, 400 con z.flattenError y, después, usa resultado.data.
  • La configuración va en variables de entorno (process.env), en desarrollo desde un .env con node --env-file=.env. .env nunca va a Git; .env.example, sí.
  • Separa app.js (configura) de servidor.js (escucha), agrupa rutas con Router, y prueba con curl, un cliente gráfico o un archivo .http.

Práctica

Estos ejercicios usan el modelo de los talleres: tu servidor es una función manejar(peticion) que recibe { metodo, ruta, cuerpo } y devuelve { estado, cuerpo }. Al final de cada uno hay unas líneas de prueba con probar, que hacen de curl: no las cambies. Intenta cada ejercicio unos minutos antes de abrir las pistas.

Tu primera ruta: /api/salud

Guiado

Casi todas las APIs tienen una ruta que solo responde «estoy vivo», para que las plataformas comprueben que el servidor funciona. Completa manejar para que GET /api/salud responda 200 con { "estado": "ok" } y cualquier otra petición responda 404 con { "error": "No encontrado" }. La salida debe ser:

GET /api/salud → 200 {"estado":"ok"}
POST /api/salud → 404 {"error":"No encontrado"}
GET /api/nada → 404 {"error":"No encontrado"}
Pista 1

Necesitas un if que compruebe dos cosas a la vez con &&: el método y la ruta. Dentro, un return con el objeto de la respuesta.

Pista 2

El último return de la función, el que se ejecuta si ningún if coincidió, es el del 404. Cambia el 501 de ejemplo por lo que pide el enunciado.

Ver una solución 
function manejar(peticion) {
  if (peticion.metodo === "GET" && peticion.ruta === "/api/salud") {
    return { estado: 200, cuerpo: { estado: "ok" } };
  }
  return { estado: 404, cuerpo: { error: "No encontrado" } };
}

// ── Pruebas: no cambies estas líneas ──
probar("GET", "/api/salud");
probar("POST", "/api/salud");
probar("GET", "/api/nada");

function probar(metodo, ruta, cuerpo) {
  const r = manejar({ metodo, ruta, cuerpo });
  const texto = r.cuerpo === undefined ? "" : " " + JSON.stringify(r.cuerpo);
  console.log(`${metodo} ${ruta} → ${r.estado}${texto}`);
}

En Express sería app.get("/api/salud", (req, res) => res.json({ estado: "ok" })), y el 404 lo pondría Express solo. Un servidor más estricto respondería 405 al POST, porque la ruta existe pero no admite ese método.

Arregla los códigos de estado

Guiado

Este manejador funciona, pero cuatro de sus respuestas usan un código de estado equivocado, y una de ellas además envía un cuerpo que sobra. Ejecútalo, compara con la salida correcta y corrige solo lo necesario:

GET /api/tareas/1 → 200 {"id":1,"titulo":"Comprar pan"}
GET /api/tareas/7 → 404 {"error":"No existe esa tarea"}
POST /api/tareas → 400 {"error":"Falta el título"}
POST /api/tareas → 201 {"id":2,"titulo":"Leer"}
DELETE /api/tareas/1 → 204
Pista 1

Pregúntate en cada return: ¿es culpa del cliente (4xx), del servidor (5xx) o salió bien (2xx)? Un título que falta es culpa de quien envió la petición.

Pista 2

Crear algo se responde con 201. Borrar, con 204, que significa «sin contenido»: devuelve { estado: 204 }, sin la propiedad cuerpo.

Ver una solución 
const tareas = [{ id: 1, titulo: "Comprar pan" }];

function manejar(peticion) {
  const { metodo, ruta, cuerpo } = peticion;

  if (metodo === "GET" && ruta === "/api/tareas/1") {
    return { estado: 200, cuerpo: tareas[0] };
  }
  if (metodo === "GET") {
    return { estado: 404, cuerpo: { error: "No existe esa tarea" } };
  }
  if (metodo === "POST" && ruta === "/api/tareas") {
    if (!cuerpo || !cuerpo.titulo) {
      return { estado: 400, cuerpo: { error: "Falta el título" } };
    }
    const nueva = { id: tareas.length + 1, titulo: cuerpo.titulo };
    tareas.push(nueva);
    return { estado: 201, cuerpo: nueva };
  }
  if (metodo === "DELETE" && ruta === "/api/tareas/1") {
    tareas.splice(0, 1);
    return { estado: 204 };
  }
  return { estado: 404, cuerpo: { error: "No encontrado" } };
}

// ── Pruebas: no cambies estas líneas ──
probar("GET", "/api/tareas/1");
probar("GET", "/api/tareas/7");
probar("POST", "/api/tareas", {});
probar("POST", "/api/tareas", { titulo: "Leer" });
probar("DELETE", "/api/tareas/1");

function probar(metodo, ruta, cuerpo) {
  const r = manejar({ metodo, ruta, cuerpo });
  const texto = r.cuerpo === undefined ? "" : " " + JSON.stringify(r.cuerpo);
  console.log(`${metodo} ${ruta} → ${r.estado}${texto}`);
}

El primer error era el más peligroso: un 200 con un mensaje de error dentro engaña al cliente, que cree que todo salió bien (con fetch, response.ok sería true). Fíjate también en que tareas.length + 1 para el id falla en cuanto borras algo: dos tareas podrían acabar con el mismo id. Por eso en los talleres se usa un contador aparte, siguienteId.

Una tarea por su id

Semiguiado

Sin Express, sacar el id de /api/tareas/2 es trabajo tuyo. ruta.split("/") convierte "/api/tareas/2" en ["", "api", "tareas", "2"]. Completa GET /api/tareas/:id: si el id no es un número entero, responde 400; si no existe, 404; si existe, 200 con la tarea. Una ruta con partes de más, como /api/tareas/1/extra, no debe coincidir.

GET /api/tareas → 200 [{"id":1,"titulo":"Comprar pan","hecha":false},{"id":2,"titulo":"Estudiar Express","hecha":true}]
GET /api/tareas/2 → 200 {"id":2,"titulo":"Estudiar Express","hecha":true}
GET /api/tareas/9 → 404 {"error":"No existe la tarea 9"}
GET /api/tareas/abc → 400 {"error":"El id debe ser un número entero"}
GET /api/tareas/1/extra → 404 {"error":"Ruta desconocida"}
Pista 1

La ruta que buscas tiene exactamente cuatro partes, y las partes 1 y 2 son "api" y "tareas". El id es partes[3], que es texto.

Pista 2

const id = Number(partes[3]); Después, Number.isInteger(id) te dice si sirve. Para buscar, tareas.find((t) => t.id === id).

Ver una solución 
const tareas = [
  { id: 1, titulo: "Comprar pan", hecha: false },
  { id: 2, titulo: "Estudiar Express", hecha: true },
];

function manejar(peticion) {
  const partes = peticion.ruta.split("/"); // "/api/tareas/2" → ["", "api", "tareas", "2"]
  if (peticion.metodo === "GET" && peticion.ruta === "/api/tareas") {
    return { estado: 200, cuerpo: tareas };
  }
  if (peticion.metodo === "GET" && partes.length === 4 && partes[1] === "api" && partes[2] === "tareas") {
    const id = Number(partes[3]);
    if (!Number.isInteger(id)) {
      return { estado: 400, cuerpo: { error: "El id debe ser un número entero" } };
    }
    const tarea = tareas.find((t) => t.id === id);
    if (!tarea) {
      return { estado: 404, cuerpo: { error: "No existe la tarea " + partes[3] } };
    }
    return { estado: 200, cuerpo: tarea };
  }
  return { estado: 404, cuerpo: { error: "Ruta desconocida" } };
}

probar("GET", "/api/tareas");
probar("GET", "/api/tareas/2");
probar("GET", "/api/tareas/9");
probar("GET", "/api/tareas/abc");
probar("GET", "/api/tareas/1/extra");

Esto es lo que hace Express por ti con "/api/tareas/:id": comprobar que la forma de la ruta coincide y dejarte el trozo variable en req.params.id. La conversión y la comprobación del número siguen siendo trabajo tuyo, o de Zod.

El top de puntuaciones

Semiguiado

Completa GET /api/puntuaciones para que respete la consulta: juego filtra por juego si viene; limite dice cuántas devolver (10 si no viene) y tiene que ser un entero entre 1 y 100, o se responde 400 con { "error": "limite debe ser un entero entre 1 y 100" }. La lista va siempre de mayor a menor puntuación. new URL(ruta, "http://localhost") separa la consulta por ti, como en la Estación 3.

GET /api/puntuaciones?limite=2 → 200 [{"jugador":"Ana","juego":"tetris","puntos":9800},{"jugador":"Sofía","juego":"snake","puntos":777}]
GET /api/puntuaciones?juego=snake → 200 [{"jugador":"Sofía","juego":"snake","puntos":777},{"jugador":"Leo","juego":"snake","puntos":510},{"jugador":"Ana","juego":"snake","puntos":420}]
GET /api/puntuaciones?juego=pong → 200 []
GET /api/puntuaciones?limite=0 → 400 {"error":"limite debe ser un entero entre 1 y 100"}
GET /api/puntuaciones?juego=snake&limite=1 → 200 [{"jugador":"Sofía","juego":"snake","puntos":777}]
Pista 1

const limite = limiteTexto === null ? 10 : Number(limiteTexto); Luego comprueba Number.isInteger(limite) y el rango con < y >.

Pista 2

Encadena filter, toSorted((a, b) => b.puntos - a.puntos) y slice(0, limite) (Estación 11). Usa toSorted y no sort: sort desordenaría el array original, y el resto de peticiones lo verían cambiado.

Ver una solución 
const puntuaciones = [
  { jugador: "Ana", juego: "snake", puntos: 420 },
  { jugador: "Leo", juego: "snake", puntos: 510 },
  { jugador: "Ana", juego: "tetris", puntos: 9800 },
  { jugador: "Sofía", juego: "snake", puntos: 777 },
];

function manejar(peticion) {
  const url = new URL(peticion.ruta, "http://localhost");
  if (peticion.metodo !== "GET" || url.pathname !== "/api/puntuaciones") {
    return { estado: 404, cuerpo: { error: "No encontrado" } };
  }
  const juego = url.searchParams.get("juego");        // null si no viene
  const limiteTexto = url.searchParams.get("limite"); // null si no viene
  const limite = limiteTexto === null ? 10 : Number(limiteTexto);
  if (!Number.isInteger(limite) || limite < 1 || limite > 100) {
    return { estado: 400, cuerpo: { error: "limite debe ser un entero entre 1 y 100" } };
  }
  const lista = puntuaciones
    .filter((p) => juego === null || p.juego === juego)
    .toSorted((a, b) => b.puntos - a.puntos)
    .slice(0, limite);
  return { estado: 200, cuerpo: lista };
}

// ── Pruebas: no cambies estas líneas ──
probar("GET", "/api/puntuaciones?limite=2");
probar("GET", "/api/puntuaciones?juego=snake");
probar("GET", "/api/puntuaciones?juego=pong");
probar("GET", "/api/puntuaciones?limite=0");
probar("GET", "/api/puntuaciones?juego=snake&limite=1");

function probar(metodo, ruta, cuerpo) {
  const r = manejar({ metodo, ruta, cuerpo });
  const texto = r.cuerpo === undefined ? "" : " " + JSON.stringify(r.cuerpo);
  console.log(`${metodo} ${ruta} → ${r.estado}${texto}`);
}

En Express, url.searchParams.get("juego") sería req.query.juego (que vale undefined, no null, cuando falta), y la comprobación del límite la haría Zod con z.coerce.number().int().min(1).max(100).default(10).

Valida antes de guardar

Semiguiado

La ruta POST /api/puntuaciones ya está escrita, pero validarPuntuacion está vacía y deja pasar cualquier cosa. Complétala con tres reglas, en este orden: jugador es un texto de 1 a 20 caracteres después de quitar los espacios (si no, "jugador: de 1 a 20 caracteres"); juego es un texto no vacío (si no, "juego: obligatorio"); puntos es un entero de 0 o más (si no, "puntos: entero de 0 o más"). Al principio, la última prueba rompe el programa con un TypeError: es justo lo que evita validar.

POST /api/puntuaciones → 201 {"id":1,"jugador":"Ana","juego":"snake","puntos":420}
POST /api/puntuaciones → 400 {"error":"Datos no válidos","detalles":["jugador: de 1 a 20 caracteres"]}
POST /api/puntuaciones → 400 {"error":"Datos no válidos","detalles":["juego: obligatorio","puntos: entero de 0 o más"]}
POST /api/puntuaciones → 400 {"error":"Datos no válidos","detalles":["jugador: de 1 a 20 caracteres","puntos: entero de 0 o más"]}
POST /api/puntuaciones → 201 {"id":2,"jugador":"Sofía","juego":"tetris","puntos":9800}
POST /api/puntuaciones → 400 {"error":"Datos no válidos","detalles":["jugador: de 1 a 20 caracteres","juego: obligatorio","puntos: entero de 0 o más"]}
Pista 1

Para jugador, primero comprueba typeof datos.jugador !== "string"; solo si es texto puedes usar .trim(). Con || la segunda parte no se evalúa si la primera ya es verdadera.

Pista 2

La regla de puntos es la misma de la traza de la sección Validar: !Number.isInteger(datos.puntos) || datos.puntos < 0.

Ver una solución 
const puntuaciones = [];
let siguienteId = 1;

function validarPuntuacion(datos) {
  const errores = [];
  if (typeof datos.jugador !== "string" || datos.jugador.trim() === "" || datos.jugador.trim().length > 20) {
    errores.push("jugador: de 1 a 20 caracteres");
  }
  if (typeof datos.juego !== "string" || datos.juego.trim() === "") {
    errores.push("juego: obligatorio");
  }
  if (!Number.isInteger(datos.puntos) || datos.puntos < 0) {
    errores.push("puntos: entero de 0 o más");
  }
  return errores;
}

function manejar(peticion) {
  if (peticion.metodo === "POST" && peticion.ruta === "/api/puntuaciones") {
    const datos = peticion.cuerpo ?? {};
    const errores = validarPuntuacion(datos);
    if (errores.length > 0) {
      return { estado: 400, cuerpo: { error: "Datos no válidos", detalles: errores } };
    }
    const nueva = { id: siguienteId++, jugador: datos.jugador.trim(), juego: datos.juego, puntos: datos.puntos };
    puntuaciones.push(nueva);
    return { estado: 201, cuerpo: nueva };
  }
  return { estado: 404, cuerpo: { error: "No encontrado" } };

Construye tu propia cadena de middleware

Reto

¿Cómo sabe Express a quién llamar cuando haces next()? Escríbelo tú. Completa ejecutar(cadena, req): debe llamar a la primera función de la lista con (req, res, next), y cada vez que una función llame a next(), debe ejecutarse la siguiente. Si una función no llama a next(), la cadena se detiene. La salida esperada es:

registro → clave → ruta | 200 {"datos":"ranking secreto"}
registro → clave | 401 {"error":"Falta la clave"}
registro | null null
Pista 1

Necesitas recordar por dónde vas: una variable i que empieza en 0. next es una función que toma cadena[i], suma 1 a i y, si esa función existe, la llama.

Pista 2

Declara next dentro de ejecutar, para que vea i, req y res (es un closure, Estación 10). Al llamar a la siguiente función, pásale el propio next como tercer argumento. Para arrancar, llama a next() una vez.

Ver una solución 
// Tres middleware con la misma forma que en Express: (req, res, next)
function registro(req, res, next) {
  res.log.push("registro");
  next();
}
function exigirClave(req, res, next) {
  res.log.push("clave");
  if (req.clave !== "secreta") {
    res.estado = 401;
    res.cuerpo = { error: "Falta la clave" };
    return; // responde y NO llama a next: la cadena se corta
  }
  next();
}
function responder(req, res, next) {
  res.log.push("ruta");
  res.estado = 200;
  res.cuerpo = { datos: "ranking secreto" };
}

function ejecutar(cadena, req) {
  const res = { estado: null, cuerpo: null, log: [] };
  let i = 0;
  function next() {
    const siguiente = cadena[i];
    i++;
    if (siguiente) siguiente(req, res, next);
  }
  next();
  return res;
}

Esta es, en esencia, la idea que usa Express. El tercer caso muestra el problema de una cadena sin respuesta: nadie puso estado, y en un servidor real el cliente se quedaría esperando. ¿Qué versión instalará npm?

Reto

Completa aceptaCaret(rango, version), que responde si un rango con ^ acepta una versión. Reglas: la versión tiene que ser igual o posterior a la del rango; y además, si el MAYOR del rango es mayor que 0, la versión debe tener el mismo MAYOR; si el MAYOR es 0, debe tener el mismo MAYOR y el mismo MENOR. Compara los números como números, no como texto. Salida esperada:

^5.2.1 5.2.1 → sí
^5.2.1 5.9.0 → sí
^5.2.1 5.2.0 → no
^5.2.1 6.0.0 → no
^0.4.2 0.4.9 → sí
^0.4.2 0.5.0 → no
^1.0.0 1.10.3 → sí
Pista 1

Divide el problema en dos preguntas. Primera: ¿la versión es igual o posterior? Compara el mayor; si empatan, el menor; si también empatan, el parche. Segunda: ¿sigue dentro del mismo «mayor»?

Pista 2

Para la primera pregunta, un operador ternario encadenado queda compacto: vMa !== ma ? vMa > ma : vMe !== me ? vMe > me : vPa >= pa. Si da false, devuelve false y ya no hace falta mirar más.

Ver una solución 
function aceptaCaret(rango, version) {
  const [ma, me, pa] = rango.slice(1).split(".").map(Number);   // "^5.2.1" → 5, 2, 1
  const [vMa, vMe, vPa] = version.split(".").map(Number);       // "5.9.0"  → 5, 9, 0
  const igualOPosterior = vMa !== ma ? vMa > ma : vMe !== me ? vMe > me : vPa >= pa;
  if (!igualOPosterior) return false;
  if (ma > 0) return vMa === ma;
  return vMa === 0 && vMe === me;
}

// ── Pruebas: no cambies estas líneas ──

  ["^0.4.2", "0.4.9"], ["^0.4.2", "0.5.0"], ["^1.0.0", "1.10.3"],
];

  console.log(`${rango} ${version} → ${aceptaCaret(rango, version) ? "sí" : "no"}`);

function manejar(peticion) {
  const { metodo, ruta, cuerpo } = peticion;
  if (metodo === "GET" && ruta === "/api/tareas") {
    return { estado: 200, cuerpo: tareas };
  }
  const partes = ruta.split("/");
  if (partes.length === 4 && partes[1] === "api" && partes[2] === "tareas") {
    const i = tareas.findIndex((t) => t.id === Number(partes[3]));
    const noExiste = { estado: 404, cuerpo: { error: "No existe la tarea " + partes[3] } };
    if (metodo === "PATCH") {
      if (i === -1) return noExiste;
      const datos = cuerpo ?? {};
      if (datos.titulo === undefined && datos.hecha === undefined) {
        return { estado: 400, cuerpo: { error: "Nada que cambiar" } };
      }
      const tituloMal = datos.titulo !== undefined && (typeof datos.titulo !== "string" || datos.titulo.trim() === "");
      const hechaMal = datos.hecha !== undefined && typeof datos.hecha !== "boolean";
      if (tituloMal || hechaMal) {
        return { estado: 400, cuerpo: { error: "Datos no válidos" } };
      }
      if (datos.titulo !== undefined) tareas[i].titulo = datos.titulo.trim();
      if (datos.hecha !== undefined) tareas[i].hecha = datos.hecha;
      return { estado: 200, cuerpo: tareas[i] };
    }
    if (metodo === "DELETE") {
      if (i === -1) return noExiste;
      tareas.splice(i, 1);
      return { estado: 204 };
    }
  }
  return { estado: 404, cuerpo: { error: "Ruta desconocida" } };
}

function express() {
  express.json = () => function json(req, res, next) {
    if (req.crudo !== undefined) {
      try { req.body = JSON.parse(req.crudo); } catch (e) { e.status = 400; e.type = "entity.parse.failed"; throw e; }
    }
    next();
  };
  const capas = [];
  const app = { listen: (puerto, listo) => listo && listo() };
  for (const m of ["get", "post", "put", "patch", "delete"]) {
    app[m] = (ruta, f) => capas.push({ metodo: m.toUpperCase(), ruta, f });
  }
  app.use = (a, b) => capas.push(b ? { ruta: a, f: b } : { ruta: "", f: a });
  app.probar = (metodo, url, cuerpo) => {
    const u = new URL(url, "http://localhost");
    const req = { method: metodo, path: u.pathname, originalUrl: url, params: {},
      query: Object.fromEntries(u.searchParams),
      crudo: cuerpo === undefined ? undefined : typeof cuerpo === "string" ? cuerpo : JSON.stringify(cuerpo) };
    const res = { statusCode: 200, cuerpo: "", enviada: false, extra: "",
      status(n) { this.statusCode = n; return this; },
      location(l) { this.extra = " (Location: " + l + ")"; return this; },
      json(d) { return this.send(JSON.stringify(d)); },
      send(d) { this.cuerpo = typeof d === "object" ? JSON.stringify(d) : String(d); this.enviada = true; return this; },
      sendStatus(n) { return this.status(n).send(""); },
      end() { this.enviada = true; return this; } };
    let i = 0;
    const siguiente = (err) => {
      while (i < capas.length) {
        const c = capas[i++];
        if (c.f.length === 4 ? !err : err) continue;
        const params = coincide(c, req.method, req.path);
        if (!params) continue;
        req.params = params;
        try { if (err) c.f(err, req, res, siguiente); else c.f(req, res, siguiente); } catch (e) { siguiente(e); }
        return;
      }
      if (err) res.status(err.status || 500).send(err.name + ": " + err.message);
      else res.status(404).send("Cannot " + metodo + " " + u.pathname);
    };
    siguiente();
    console.log(metodo + " " + url + " → " + (res.enviada ? res.statusCode + res.extra + (res.cuerpo ? " " + res.cuerpo : "") : "(sin respuesta: el cliente se queda esperando)"));
  };
  function coincide(capa, metodo, ruta) {
    if (capa.metodo && capa.metodo !== metodo) return null;
    const a = capa.ruta.split("/").filter(Boolean), b = ruta.split("/").filter(Boolean);
    if (capa.metodo ? a.length !== b.length : a.length > b.length) return null;
    const params = {};
    for (let k = 0; k < a.length; k++) {
      if (a[k][0] === ":") params[a[k].slice(1)] = decodeURIComponent(b[k]);
      else if (a[k] !== b[k]) return null;
    }
    return params;
  }
  return app;
}

Tus datos viven en la memoria

Las puntuaciones están en un array dentro del programa. Cada vez que el servidor se reinicia (y con --watch se reinicia cada vez que guardas un archivo), vuelven a ser las tres del principio. Para que duren hace falta una base de datos, y eso es justo lo que harás en la Estación 30: las rutas quedarán casi iguales y solo cambiará de dónde salen los datos.

export function manejarErrores(err, req, res, next) {
  if (err.type === "entity.parse.failed") {
    return res.status(400).json({ error: "El cuerpo no es JSON válido" });
  }
  const estado = err.status ?? 500;
  if (estado >= 500) console.error(err);
  res.status(estado).json({
    error: estado >= 500 ? "Error interno del servidor" : err.message,
  });
}

src/rutas/puntuaciones.js:

import { Router } from "express";
import * as z from "zod";

z.config(z.locales.es());

const EsquemaPuntuacion = z.object({
  jugador: z.string().trim().min(1, "Escribe un nombre").max(20, "Máximo 20 caracteres"),
  juego: z.string().trim().min(1, "Indica el juego"),
  puntos: z.number({ error: "Los puntos deben ser un número" })
    .int("Los puntos deben ser un número entero")
    .nonnegative("Los puntos no pueden ser negativos"),
});

const EsquemaConsulta = z.object({
  juego: z.string().optional(),
  limite: z.coerce.number().int().min(1).max(100).default(10),
});

// Datos en memoria: se pierden al reiniciar (en la Estación 30 irán a una base de datos)
const puntuaciones = [
  { id: 1, jugador: "Ana", juego: "snake", puntos: 420 },
  { id: 2, jugador: "Leo", juego: "snake", puntos: 510 },
  { id: 3, jugador: "Ana", juego: "tetris", puntos: 9800 },
];
let siguienteId = 4;

export const rutasPuntuaciones = Router();

rutasPuntuaciones.get("/", (req, res) => {
  const consulta = EsquemaConsulta.safeParse(req.query);
  if (!consulta.success) {
    return res.status(400).json({ error: "Consulta no válida", detalles: z.flattenError(consulta.error) });
  }
  const { juego, limite } = consulta.data;
  const lista = puntuaciones
    .filter((p) => juego === undefined || p.juego === juego)
    .toSorted((a, b) => b.puntos - a.puntos)
    .slice(0, limite);
  res.json(lista);
});

rutasPuntuaciones.get("/:id", (req, res) => {
  const p = puntuaciones.find((p) => p.id === Number(req.params.id));
  if (!p) return res.status(404).json({ error: "No existe esa puntuación" });
  res.json(p);
});

rutasPuntuaciones.post("/", (req, res) => {
  const resultado = EsquemaPuntuacion.safeParse(req.body);
  if (!resultado.success) {
    return res.status(400).json({ error: "Datos no válidos", detalles: z.flattenError(resultado.error) });
  }
  const nueva = { id: siguienteId++, ...resultado.data };
  puntuaciones.push(nueva);
  res.status(201).location(`/api/puntuaciones/${nueva.id}`).json(nueva);
});

rutasPuntuaciones.delete("/:id", (req, res) => {
  const i = puntuaciones.findIndex((p) => p.id === Number(req.params.id));
  if (i === -1) return res.status(404).json({ error: "No existe esa puntuación" });
  puntuaciones.splice(i, 1);
  res.status(204).end();
});
