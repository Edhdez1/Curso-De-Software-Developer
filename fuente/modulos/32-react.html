Por qué existe React

Empieza por el problema. Imagina una tienda en línea. El número de productos del carrito aparece en cuatro sitios a la vez: en el icono de la cabecera, en la lista del carrito, en el total a pagar y en el botón «Pagar», que debe desactivarse si el carrito está vacío. Con lo que aprendiste en la Estación 15, cada vez que alguien añade un producto tu código tiene que recordar los cuatro sitios y cambiarlos uno por uno.

Imperativo: das cada orden

let cantidad = 0;

botonAnadir.addEventListener("click", () => {
  cantidad = cantidad + 1;
  insignia.textContent = cantidad;
  resumen.textContent = `Productos: ${cantidad}`;
  if (cantidad === 1) avisoVacio.remove();
  botonPagar.disabled = false;
  // ...y no olvides ningún otro sitio
});

Declarativo: describes el resultado

function Carrito() {
  const [cantidad, setCantidad] = useState(0);
  return (
    <>
      <span className="insignia">{cantidad}</span>
      <p>Productos: {cantidad}</p>
      {cantidad === 0 && <p>Tu carrito está vacío</p>}
      <button disabled={cantidad === 0}>Pagar</button>
      <button onClick={() => setCantidad(cantidad + 1)}>Añadir</button>
    </>
  );
}

El código de la izquierda es imperativo: le das a la computadora cada orden, paso a paso («cambia este texto», «quita ese aviso»). El de la derecha es declarativo: describes cómo debe verse la pantalla para cualquier valor de cantidad, y otra pieza de software se encarga de los pasos. No te preocupes por entender todavía cada símbolo de la derecha: al terminar esta estación lo leerás sin esfuerzo. Fíjate solo en una cosa: en ningún sitio dice «cambia el texto». Dice qué texto hay.

Es la diferencia entre darle a un taxista cada giro («a la derecha, dos cuadras, ahora a la izquierda») y darle la dirección de destino. Con la dirección, el taxista decide el camino. La analogía tiene un límite: el taxista puede elegir una ruta mala, mientras que React sigue siempre el mismo método, que puedes estudiar y predecir. Lo verás en la animación de más abajo.

La interfaz es una función del estado

En la Estación 15 ya separaste el estado (los datos que describen cómo está la app ahora mismo) de la vista (lo que se ve), con una función render() que dibujaba la pantalla entera a partir del estado. React lleva esa idea hasta el final. Se resume en una fórmula que vas a oír mucho:

interfaz = f(estado)

Se lee «la interfaz es una función del estado». Igual que una función matemática, para un mismo estado siempre produce la misma interfaz. Si quieres que la pantalla cambie, no tocas la pantalla: cambias el estado, y React vuelve a calcular la interfaz.

En React nunca modificas la página directamente. Cambias datos. La página es la consecuencia. Si alguna vez te descubres escribiendo document.querySelector dentro de un componente para cambiar un texto, detente: casi siempre hay una forma de hacerlo cambiando el estado.

Componentes: piezas de interfaz

La segunda idea de React es el componente: una pieza de interfaz con nombre propio, que junta estructura, aspecto y comportamiento. Una tienda se arma con componentes como Cabecera, Buscador, TarjetaProducto y Carrito. Cada uno se escribe una vez y se usa todas las veces que haga falta, igual que una función (Estación 10). En React, de hecho, un componente es una función.

Qué es React exactamente, y en qué versión está

React es una biblioteca (en inglés, library): un conjunto de código que tu programa llama cuando lo necesita. Su propia web lo define como «la biblioteca para interfaces de usuario web y nativas». Solo se ocupa de la interfaz: no trae de serie navegación entre páginas, ni forma de pedir datos, ni estilos. Para eso se combina con otras herramientas, o se usa dentro de un framework (en español, «marco de trabajo»): un sistema más grande que decide la estructura del proyecto y llama a tu código, como Next.js. La diferencia práctica: tú llamas a una biblioteca; un framework te llama a ti.

Crear un proyecto con Vite

Los talleres de esta página traducen tu código en el navegador cada vez que pulsas «Ejecutar». Para una app de verdad eso no sirve: sería lento para cada visitante y no podrías repartir el código en muchos archivos ni instalar paquetes de npm con comodidad. Hace falta una herramienta de construcción (en inglés, build tool): un programa que, en tu computadora, hace tres trabajos.

  • En desarrollo, levanta un servidor local que traduce el JSX al vuelo y recarga la página en cuanto guardas un archivo.
  • Resuelve los import: tanto los de tus archivos como los de los paquetes que instalaste con npm.
  • Para publicar, genera una versión optimizada: pocos archivos, pequeños, sin espacios ni comentarios, listos para subir a internet.

La herramienta que se usa hoy para empezar con React es Vite (se pronuncia «vit», que en francés significa «rápido»). La creó en 2020 Evan You, el autor de Vue, y hoy sirve para casi cualquier biblioteca de interfaces. Ya la mencionaron la Estación 22 y la Estación 26. A septiembre de 2026 la versión actual es Vite 8, que empaqueta el código con un motor nuevo llamado Rolldown.

En muchos cursos y videos verás el comando npx create-react-app. El equipo de React lo declaró obsoleto en febrero de 2025 y ya no recibe mantenimiento. Si un tutorial empieza así, es anterior a 2025: sus ideas de React siguen valiendo, pero crea el proyecto con Vite.

JSX, componentes y props

Ya escribiste JSX sin saber su nombre. JSX es una extensión de la sintaxis de JavaScript que permite escribir etiquetas parecidas a HTML dentro del código. El navegador no la entiende: antes de ejecutarse, una herramienta (Babel en los talleres, Vite en tu proyecto) la convierte en JavaScript normal. Ver esa conversión quita mucho misterio:

// Lo que escribes
const titulo = <h1 className="grande">Hola</h1>;

// Lo que se ejecuta (en los talleres, con Babel)
const titulo = React.createElement("h1", { className: "grande" }, "Hola");

// Lo que devuelve: un objeto normal de JavaScript, más o menos así
// { type: "h1", props: { className: "grande", children: "Hola" } }

Una etiqueta JSX es, por tanto, una expresión: un trozo de código que produce un valor. Puedes guardarla en una variable, devolverla con return o meterla en un array. Ese objeto no es un elemento del DOM: es la descripción que React usa para crearlo o actualizarlo. En los proyectos con Vite la conversión usa otra función (jsx(), del paquete react/jsx-runtime) y por eso no hace falta importar React en cada archivo, pero la idea es la misma.

Las reglas de JSX

JSX se parece tanto a HTML que es fácil olvidar que no lo es. Estas son las diferencias que más errores causan:

  1. Un solo elemento raíz. Un componente devuelve un único elemento. Si quieres devolver varios hermanos sin añadir un <div> de más, envuélvelos en un fragmento: <> … </>, que agrupa sin crear nada en el DOM.
  2. Todas las etiquetas se cierran. <img>, <input> y <br> se escriben <img />, <input /> y <br />.
  3. Atributos en camelCase. Como JSX es JavaScript, los atributos siguen sus nombres de propiedades: class pasa a ser className (porque class es una palabra reservada), for pasa a ser htmlFor, onclick pasa a ser onClick y tabindex, tabIndex. Los atributos aria-* y data-* se escriben igual que en HTML.
  4. Llaves para JavaScript. Entre { } va cualquier expresión: variables, cuentas, llamadas a funciones, un operador ternario. No van instrucciones como if, for o let.
  5. style recibe un objeto. style="color: red" se escribe style={{ color: "red", fontSize: 20 }}: las llaves de fuera abren JavaScript y las de dentro son el objeto. Las propiedades van en camelCase y los números sin unidad se entienden como píxeles.
  6. Comentarios con llaves. Dentro del JSX se escriben {/* así */}; <!-- --> no funciona.

HTML pegado tal cual

return (
  <label for="correo">Correo</label>
  <input id="correo" class="campo">
);

JSX correcto

return (
  <>
    <label htmlFor="correo">Correo</label>
    <input id="correo" className="campo" />
  </>
);

El error más común al empezar es escribir class en vez de className. React lo acepta y lo arregla, pero muestra en la consola un aviso en rojo: Invalid DOM property `class`. Did you mean `className`? Los avisos de React en desarrollo llevan marcas como %s en los talleres; léelos igual, porque casi siempre te dicen exactamente qué cambiar.

Componentes: funciones que devuelven JSX

Un componente de React es una función que devuelve JSX. Dos reglas lo distinguen de una función cualquiera:

  • Su nombre empieza con mayúscula: TarjetaProducto, no tarjetaProducto. En JSX, una etiqueta en minúscula (<button>) es un elemento HTML; una con mayúscula (<TarjetaProducto />) es un componente tuyo. A este estilo de nombres, con mayúscula al inicio de cada palabra, se le llama PascalCase.
  • Se usa como una etiqueta, no se llama con paréntesis. Escribes <TarjetaProducto /> y React decide cuándo llamar a la función.

Para pasarle datos a un componente se usan props (de properties, «propiedades»). Se escriben como atributos al usar el componente, y la función los recibe todos juntos en un objeto, su primer parámetro. Lo habitual es desestructurarlo en la misma línea (Estación 11):

function TarjetaProducto({ nombre, precio, oferta = false }) {
  return (
    <article className="tarjeta">
      <h3>{nombre}</h3>
      <p>${precio.toFixed(2)}</p>
      {oferta && <span className="etiqueta">Oferta</span>}
    </article>
  );
}

// Usarlo tres veces con datos distintos
<TarjetaProducto nombre="Café de Colombia" precio={12.5} oferta />
<TarjetaProducto nombre="Taza de cerámica" precio={8} />
<TarjetaProducto nombre="Molinillo" precio={34.9} />
  • Los textos van entre comillas (nombre="Café"); cualquier otro valor va entre llaves (precio={12.5}, activo={true}, lista={productos}).
  • Un atributo sin valor, como oferta, equivale a oferta={true}.
  • oferta = false es un valor por defecto: si no pasas esa prop, vale false.
  • El $ de ${precio.toFixed(2)} es el signo de pesos que se ve en pantalla: está fuera de las llaves, así que es texto normal, no una plantilla literal.

Las props son de solo lectura. Un componente nunca debe cambiar sus props (precio = precio * 2 dentro de TarjetaProducto está prohibido). Si un dato tiene que cambiar, es estado, y lo verás en la próxima sección. Además, un componente debe ser una función pura (Estación 21): con las mismas props devuelve siempre el mismo JSX y, mientras se ejecuta, no modifica nada de fuera. React puede llamar a tus componentes cuando quiera y las veces que quiera, así que no deben tener sorpresas.

Estado y eventos

Hasta ahora tus componentes muestran siempre lo mismo. Una interfaz de verdad cambia: un contador sube, un carrito se llena, un menú se abre. Lo primero que se le ocurre a cualquiera es usar una variable normal. Investiga por qué no funciona: pulsa varias veces cada botón y compara la pantalla con la consola.

El botón de la variable normal se queda en 0 aunque la consola diga que la variable sube. Hay dos motivos:

  1. Cambiar una variable no avisa a React. React solo vuelve a llamar al componente cuando algo le dice que los datos cambiaron. Nadie se lo dijo.
  2. Las variables locales no sobreviven. Aunque React volviera a llamar a ContadorRoto, la primera línea haría let cuenta = 0 otra vez. Cada llamada a una función empieza de cero (Estación 10).

El estado de un componente resuelve las dos cosas: es memoria que React guarda por ti entre una llamada y la siguiente, y cambiarla hace que React vuelva a renderizar. Fíjate también en los dos botones «Con useState»: son dos usos del mismo componente y cada uno lleva su propia cuenta. El estado pertenece a cada copia del componente en la pantalla, no a la función.

useState

import { useState } from "react";       // en los talleres: const { useState } = React;

function Contador() {
  const [cuenta, setCuenta] = useState(0);
  // cuenta: el valor actual. setCuenta: la función que lo cambia. 0: el valor inicial.
  return <button onClick={() => setCuenta(cuenta + 1)}>{cuenta}</button>;
}
  • useState(0) crea una variable de estado cuyo valor inicial es 0. Devuelve un array con dos cosas, que se desestructuran en la misma línea: el valor actual y una función para cambiarlo.
  • El nombre es libre, pero la costumbre es [algo, setAlgo]: [cuenta, setCuenta], [abierto, setAbierto], [productos, setProductos].
  • Llamar a setCuenta(5) no cambia cuenta en ese momento: le pide a React que vuelva a renderizar el componente, y en ese nuevo render useState devolverá 5.

useState es un hook («gancho»): una función especial de React, cuyo nombre empieza por use, que permite a un componente «engancharse» a una capacidad de React, como guardar estado. Verás varios: useState, useEffect, useContext, useRef… y aprenderás a crear los tuyos.

React reconoce cada hook por el orden en que lo llamas: el primer useState del componente, el segundo, el tercero. Por eso hay dos reglas estrictas: (1) llama a los hooks solo en el nivel superior del componente, nunca dentro de un if, de un bucle o de una función interna; y (2) llámalos solo desde componentes o desde tus propios hooks, no desde funciones normales. Si un if se saltara un hook en un render, todos los siguientes se desordenarían. El linter de tu proyecto de Vite detecta estas faltas.

Eventos

Los eventos funcionan como en la Estación 15, pero se escriben como props en camelCase: onClick, onChange, onSubmit, onKeyDown, onMouseEnter, onFocus. Se les pasa una función; React la llama con un objeto evento que tiene las propiedades de siempre (target, key, preventDefault()…).

function Tienda() {
  const [mensaje, setMensaje] = useState("");

  function manejarCompra(evento) {
    console.log("Clic en", evento.target.textContent);
    setMensaje("¡Añadido al carrito!");
  }

  return (
    <>
      <button onClick={manejarCompra}>Comprar</button>           {/* pasa la función */}
      <button onClick={() => setMensaje("")}>Limpiar</button>  {/* o una flecha */}
      <p>{mensaje}</p>
    </>
  );
}

onClick={manejarCompra()}, con paréntesis, es el mismo error que addEventListener("click", sumar()): ejecuta la función mientras se renderiza y pasa su resultado. Si esa función cambia el estado, provoca un nuevo render, que la vuelve a ejecutar, que provoca otro render… React lo corta con el error Too many re-renders. React limits the number of renders to prevent an infinite loop («demasiados renders»). Si necesitas pasar un argumento, envuelve la llamada en una flecha: onClick={() => comprar(producto)}.

Por costumbre, las funciones que manejan eventos se llaman manejarAlgo (en inglés, handleSomething), y las props que reciben esas funciones, onAlgo: onComprar, onCerrar.

El estado es una foto

Esta es la idea de React que más confunde al principio. Dentro de un render, el valor del estado no cambia, aunque llames a su función set. Cada render recibe una foto del estado de ese momento, y todo el código de ese render (incluidos los manejadores de eventos creados en él) ve esa foto. Sigue este botón, que intenta sumar tres de golpe:

function Contador() {
  const [cuenta, setCuenta] = useState(0);

  function sumarTres() {
    setCuenta(cuenta + 1);
    setCuenta(cuenta + 1);
    setCuenta(cuenta + 1);
  }

  return <button onClick={sumarTres}>+3 (ahora: {cuenta})</button>;
}

La solución es pasarle a set una función de actualización en vez de un valor: setCuenta(c => c + 1). React guarda la función en la cola y, al procesarla, le pasa el valor pendiente: la primera recibe 0 y devuelve 1, la segunda recibe 1 y devuelve 2, la tercera recibe 2 y devuelve 3. Arrays y objetos en el estado: siempre copias nuevas

El estado puede guardar cualquier valor: números, textos, booleanos, arrays y objetos. Con los dos últimos hay una trampa. Mira este código:

Muta el array: la pantalla no cambia

function agregar(producto) {
  carrito.push(producto);
  setCarrito(carrito);
}

Crea un array nuevo

function agregar(producto) {
  setCarrito([...carrito, producto]);
}

Para decidir si hace falta renderizar, React compara el valor nuevo con el anterior usando Object.is, que para arrays y objetos compara referencias, no contenidos (Estación 11). Con push el array es el mismo objeto, con un elemento más: para React «no cambió nada» y no renderiza. Condiciones, listas y formularios

Casi todas las pantallas de una app combinan tres cosas: partes que aparecen solo a veces, listas que salen de un array y formularios. Con JSX no hay instrucciones especiales para ninguna de las tres: se resuelven con el JavaScript que ya conoces.

Mostrar algo solo a veces

Como dentro de las llaves no cabe un if, se usan tres técnicas, según el caso:

function Pedido({ productos, cargando, usuario }) {
  // 1. if con return temprano: para casos que cambian toda la vista
  if (cargando) {
    return <p>Cargando tu pedido…</p>;
  }

  return (
    <section>
      {/* 2. Ternario: elegir entre dos cosas */}
      {usuario ? <p>Hola, {usuario.nombre}</p> : <button>Iniciar sesión</button>}

      {/* 3. &&: mostrar algo o nada */}
      {productos.length === 0 && <p>Tu carrito está vacío.</p>}
    </section>
  );
}

El truco del && sale de la Estación 8: si la izquierda es falsa, la expresión vale lo de la izquierda (que React no dibuja); si es verdadera, vale lo de la derecha. Y cuando un componente no debe mostrar nada, puede devolver null.

{productos.length && <p>Tienes productos</p>} muestra un 0 en pantalla cuando la lista está vacía. 0 es falsy, así que la expresión vale 0… y React sí dibuja los números. Pon siempre una comparación a la izquierda: {productos.length > 0 && …}.

Listas con map y key

Para convertir un array de datos en elementos, usa map (Estación 11): cada dato se transforma en un trozo de JSX, y React dibuja el array resultante.

const juegos = [
  { id: "a1", titulo: "Hollow Knight", precio: 15 },
  { id: "b7", titulo: "Celeste", precio: 20 },
  { id: "c3", titulo: "Stardew Valley", precio: 15 },

Cada elemento de la lista lleva una prop especial, key («clave»): un identificador que lo distingue de sus hermanos. React la usa para saber qué elemento es cuál entre un render y el siguiente. Sin ella, si insertas, borras o reordenas, React solo puede emparejar los elementos por su posición, y se equivoca. Si olvidas la key, la consola muestra el aviso Each child in a list should have a unique "key" prop.

Investiga qué significa «se equivoca». Las dos listas son idénticas salvo la key: la de la izquierda usa la posición en el array (el índice) y la de la derecha, el id de cada tarea. Escribe «urgente» en la nota de «Comprar pan» en las dos listas y después pulsa «Añadir arriba» en cada una.

En la lista de la izquierda, «urgente» se queda en la primera fila, que ahora es «Tarea nueva». Antes del clic, la key 0 era «Comprar pan»; después, la key 0 es la tarea nueva. React ve la misma key, reutiliza el mismo <li> (con su campo y lo que escribiste dentro) y solo cambia el texto. En la derecha, la key 1 sigue siendo «Comprar pan», así que su nota viaja con ella. En una app real este fallo mezcla datos: el comentario de un cliente aparece en el pedido de otro.

  • La key debe ser única entre hermanos (puede repetirse en otra lista) y estable: el mismo dato, la misma key, en todos los renders.
  • Lo ideal es el id que ya traen los datos (de la base de datos o de la API). Si los creas tú, genera el id al crear el dato, no al dibujarlo.
  • El índice solo vale si la lista nunca se reordena, ni se filtra, ni recibe elementos en medio.
  • key={Math.random()} es el peor caso: una key distinta en cada render obliga a React a destruir y crear de nuevo todos los elementos, y se pierde todo lo que tenían dentro.
  • La key va en el elemento de más afuera que devuelve el map. Si ese elemento es un componente, la pones en él: <TarjetaProducto key={p.id} {...p} />. El componente no la recibe como prop: es solo para React.

Ese {...p} es otro atajo que verás mucho: pasa todas las propiedades del objeto p como props, igual que escribir nombre={p.nombre} precio={p.precio}.

Para mostrar solo una parte de la lista, encadena filter y map. Para ordenarla, no ordenes el estado: ordena una copia justo antes de dibujar.

En la Estación 15 leías el valor de un campo cuando hacía falta, con campo.value. En React lo habitual es otra cosa: guardar el contenido del campo en el estado y hacer que el campo muestre siempre ese estado. Es un campo controlado: React controla lo que muestra.

const [texto, setTexto] = useState("");

<input value={texto} onChange={e => setTexto(e.target.value)} />

Compartir estado entre componentes

Hasta ahora cada estado vivía en un solo componente. En una app real, varios componentes necesitan el mismo dato. En la tienda, la lista de productos cambia el carrito (al pulsar «Añadir») y el resumen de la cabecera lo muestra. Son componentes hermanos, y en React la información solo viaja de padres a hijos, a través de las props. ¿Dónde se pone entonces el carrito?

A este recorrido (los datos bajan por props, los cambios suben llamando a funciones que también llegaron por props) se le llama flujo de datos en un solo sentido (en inglés, one-way data flow). Al principio parece mucho cableado. A cambio, cuando algo se ve mal, sabes dónde buscar: el dato tiene un único dueño, y solo el dueño lo cambia. En código:

Una sola fuente de verdad: no dupliques el estado

El total del carrito se calcula en cada render a partir del carrito; no es estado. Es tentador guardarlo aparte, «para tenerlo a mano»:

Dos estados que deben coincidir

// ¿Y al quitar? ¿Y al vaciar? ¿Y si cambia un precio?

const total = carrito.reduce(
  (suma, p) => suma + p.precio, 0

Guarda en el estado lo mínimo imprescindible y calcula todo lo demás al renderizar. Si un dato se puede calcular a partir de props o de otro estado, no debe ser estado. Así es imposible que dos datos se contradigan, el mismo problema que la Estación 15 resolvía con render().

Contexto: datos para todo un árbol

Levantar el estado funciona muy bien entre padres e hijos cercanos. Pero hay datos que necesita media aplicación: la persona que inició sesión, el tema claro u oscuro, el idioma. Si viven en App, tendrías que pasarlos por props a través de cinco o seis niveles de componentes que no los usan, solo para que lleguen abajo. A eso se le llama perforación de props (en inglés, prop drilling), y es incómodo de mantener.

El contexto (context) resuelve ese caso: un componente de arriba ofrece un valor, y cualquier componente de debajo, a cualquier profundidad, puede leerlo directamente. Tiene tres pasos:

import { createContext, useContext, useState } from "react";

// 1. Crear el contexto (fuera de los componentes), con un valor por defecto
const TemaContext = createContext("claro");

// 2. Ofrecer un valor a todo lo que hay dentro
function App() {
  const [tema, setTema] = useState("claro");
  return (
    <TemaContext value={tema}>          {/* React 18: <TemaContext.Provider value={tema}> */}
      <Pagina />
      <button onClick={() => setTema(tema === "claro" ? "oscuro" : "claro")}>
        Cambiar tema
      </button>
    </TemaContext>
  );
}

// 3. Leerlo donde haga falta, sin recibirlo por props
function Boton({ children }) {
  const tema = useContext(TemaContext);
  return <button className={"boton-" + tema}>{children}</button>;
}

En React 19 el propio contexto sirve de proveedor, <TemaContext value={…}>; en React 18, y en código anterior a 2025, verás <TemaContext.Provider value={…}>, que sigue funcionando. Efectos, datos y hooks propios

Un componente debe ser puro: recibe props y estado, devuelve JSX, y no toca nada de fuera mientras se renderiza. Pero una app necesita hablar con el mundo exterior: pedir datos a un servidor, poner un temporizador, guardar en localStorage, escuchar el tamaño de la ventana, conectarse a un chat. Nada de eso es «calcular JSX». Para eso existen los efectos: código que React ejecuta después de actualizar la pantalla, para sincronizar el componente con un sistema externo a React.

import { useEffect, useState } from "react";

function Reloj({ velocidad }) {
  const [ticks, setTicks] = useState(0);

  useEffect(() => {
    const id = setInterval(() => setTicks(t => t + 1), velocidad);   // 1. el efecto
    return () => clearInterval(id);                                   // 2. la limpieza
  }, [velocidad]);                                                    // 3. las dependencias

  return <p>Ticks: {ticks}</p>;
}
  1. El efecto es la función que le pasas a useEffect. React la ejecuta después de pintar.
  2. La limpieza es la función que el efecto devuelve (opcional). React la ejecuta antes de repetir el efecto y cuando el componente desaparece. Deshace lo que hizo el efecto: para el intervalo, cierra la conexión, quita el escuchador.
  3. Las dependencias son un array con los valores de props y estado que usa el efecto. React repite el efecto solo si alguno cambió desde el render anterior.

useEffect(fn, [])Una vez, al aparecer el componente en pantalla (al montarse). La limpieza, al desaparecer (al desmontarse).
useEffect(fn, [a, b])Al montarse y cada vez que a o b cambien.
useEffect(fn)Después de cada render. Casi nunca es lo que quieres.

Este taller tiene exactamente ese reloj, dentro de React.StrictMode y con mensajes en la consola. Investiga: ejecútalo y lee la consola (verás el ensayo de StrictMode: efecto, limpieza, efecto). Después cambia la velocidad y quita y pon el reloj, y relaciona cada mensaje con un paso de la animación.

Modifica: borra las cuatro líneas del return de limpieza y ejecuta. Los ticks suben de dos en dos: el ensayo de StrictMode dejó dos intervalos vivos, porque nadie paró el primero. Eso mismo pasaría en producción al quitar y poner el reloj. Vuelve a poner la limpieza y comprueba que todo se arregla.

Todo valor de props o estado que uses dentro del efecto debe estar en el array de dependencias. Si usas velocidad y no la pones, el efecto se queda con la foto del primer render y nunca verá el valor nuevo. El linter de React (la regla react-hooks/exhaustive-deps) te avisa cuando falta alguna. Si una dependencia te molesta, la solución no es quitarla del array, sino cambiar el código para no necesitarla (por ejemplo, con la función de actualización t => t + 1, que no necesita leer ticks).

Cuándo NO usar useEffect

Los efectos son la herramienta de React que más se usa mal. La documentación oficial tiene una página entera titulada «Quizás no necesites un efecto». La pregunta clave es: ¿estoy sincronizando con algo externo a React? Si la respuesta es no, probablemente sobra.

Efecto para calcular datos

const [busqueda, setBusqueda] = useState("");
const [filtrados, setFiltrados] = useState(juegos);

useEffect(() => {
  setFiltrados(
    juegos.filter(j => j.titulo.includes(busqueda))
  );
}, [busqueda]);

Calcular al renderizar

const [busqueda, setBusqueda] = useState("");

const filtrados = juegos.filter(j =>
  j.titulo.includes(busqueda)
);

La versión de la izquierda renderiza dos veces por cada tecla (una con la lista vieja, otra con la nueva), tiene un estado duplicado que puede desincronizarse y es más larga. La de la derecha es un valor derivado. Estos son los casos típicos en los que sobra un efecto:

  • Transformar datos para mostrarlos (filtrar, ordenar, sumar): calcúlalos directamente en el cuerpo del componente.
  • Reaccionar a lo que hace el usuario (enviar la compra al pulsar «Pagar», mostrar un aviso al añadir): hazlo en el manejador del evento, que sabe exactamente qué pasó. Un efecto no sabe por qué cambió el estado.
  • Reiniciar el estado cuando cambia una prop (vaciar el formulario de comentarios al cambiar de producto): dale al componente una key distinta, <Comentarios key={producto.id} />, y React lo creará de cero.
  • Encadenar efectos que cambian estados que disparan otros efectos: casi siempre se reemplazan por un solo manejador de eventos que calcula todo a la vez.

Un efecto sin array de dependencias que cambia estado crea un bucle infinito: el efecto cambia el estado, el cambio provoca un render, el render ejecuta el efecto… La pestaña se congela o la consola se llena de Maximum update depth exceeded. Lo mismo pasa si pones en las dependencias un objeto o un array que se crea nuevo en cada render: para Object.is, siempre es «distinto».

Pedir datos a un servidor

El caso de uso clásico de un efecto es cargar datos cuando aparece un componente o cuando cambia lo que se busca. Junta lo que aprendiste en la Estación 16 (fetch, async/await) y los estados de la sección Carga, error y vacío:

function Productos({ categoria }) {
  const [productos, setProductos] = useState([]);
  const [cargando, setCargando] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let ignorar = false;              // ¿esta respuesta ya no interesa?

    async function cargar() {
      setCargando(true);
      setError(null);
      try {
        const respuesta = await fetch(`https://api.ejemplo.com/productos?categoria=${categoria}`);
        if (!respuesta.ok) throw new Error(`Error ${respuesta.status}`);
        const datos = await respuesta.json();
        if (!ignorar) setProductos(datos);
      } catch (e) {
        if (!ignorar) setError(e.message);
      } finally {
        if (!ignorar) setCargando(false);
      }
    }

    cargar();
    return () => { ignorar = true; };  // limpieza: descarta respuestas viejas
  }, [categoria]);

  if (cargando) return <p>Cargando…</p>;
  if (error) return <p role="alert">No se pudieron cargar los productos: {error}</p>;
  if (productos.length === 0) return <p>No hay productos en esta categoría.</p>;
  return <ul>{productos.map(p => <li key={p.id}>{p.nombre}</li>)}</ul>;
}
  • La función del efecto no puede ser async: debe devolver una función de limpieza o nada, y una función async devuelve una promesa. Por eso se declara una función async dentro y se llama enseguida.
  • La variable ignorar evita una condición de carrera: una situación en la que el resultado depende de qué respuesta llega primero. Si eliges «Cafés» y enseguida «Tazas», hay dos peticiones en vuelo. Si la de cafés llega la última, pisaría la lista de tazas. Con la limpieza, el efecto de cafés queda marcado como «ignorar» en cuanto la categoría cambia, y su respuesta se descarta. También puedes cancelar la petición de verdad con AbortController (Estación 16).

En el taller, el servidor está simulado (la vista previa no puede pedir datos a sitios externos): «Cafés» tarda 1,5 segundos, «Tazas» 0,3 y «Error» falla. Investiga: pulsa «Cafés» y, enseguida, «Tazas». Todo va bien. Ahora borra los tres if (!ignorar) (deja solo las llamadas set), ejecuta y repite: al cabo de un segundo y medio, el título dice «Tazas» y la lista muestra cafés.

Escribir a mano el efecto de carga está muy bien para entenderlo, pero en proyectos reales casi nadie lo hace. Se usa una biblioteca como TanStack Query o SWR, que añaden caché (no repetir peticiones que ya hiciste), reintentos, recarga al volver a la pestaña y protección contra carreras, todo con una línea: const { data, isPending, error } = useQuery(…). Los frameworks como Next.js o React Router cargan los datos antes de mostrar la página. Y React 19 añadió use(promesa), que junto con el componente <Suspense> permite «esperar» datos directamente en el render. Aprende primero el efecto a mano: es lo que esas herramientas hacen por dentro.

Refs: cuando necesitas el elemento del DOM

A veces sí necesitas un elemento real del DOM: poner el cursor en un campo, desplazarte hasta un mensaje, medir un tamaño. Para eso está useRef. Una ref es una caja con una propiedad current que React no vigila: cambiarla no provoca renders. Si se la pasas a un elemento con la prop ref, React guarda en current el elemento del DOM:

function Buscador() {
  const campo = useRef(null);
  return (
    <>
      <input ref={campo} placeholder="Buscar juego" />
      <button onClick={() => campo.current.focus()}>Buscar</button>
    </>
  );
}

Las refs también sirven para guardar valores que no se muestran, como el id de un setInterval. En React 19, además, tus propios componentes pueden recibir ref como una prop más; antes hacía falta envolverlos en forwardRef, que verás en código antiguo.

Tus propios hooks

Cuando la misma combinación de estado y efectos aparece en varios componentes, puedes extraerla a una función propia. Un hook personalizado (custom hook) es una función cuyo nombre empieza por use y que llama a otros hooks. Este guarda un valor en el estado y, además, lo copia en localStorage cada vez que cambia, para que sobreviva a una recarga (Estación 15):

function useLocalStorage(clave, valorInicial) {
  const [valor, setValor] = useState(() => {
    const guardado = localStorage.getItem(clave);
    return guardado !== null ? JSON.parse(guardado) : valorInicial;
  });

  useEffect(() => {
    localStorage.setItem(clave, JSON.stringify(valor));   // sincronizar con algo externo: ¡un buen efecto!
  }, [clave, valor]);

  return [valor, setValor];
}

// Se usa igual que useState
const [carrito, setCarrito] = useLocalStorage("carrito", []);
  • useState(() => …) recibe una función en vez de un valor: es un inicializador perezoso. React solo la ejecuta en el primer render, así no lees localStorage en cada render.
  • Un hook comparte lógica, no estado. Si dos componentes llaman a useLocalStorage, cada uno tiene su propio valor, como si hubieran escrito el useState y el useEffect ellos mismos.
  • El nombre debe empezar por use: así tú, el linter y React saben que dentro se aplican las reglas de los hooks.

Modifica: este taller es una lista de deseos que usa el hook. Añade un par de juegos y vuelve a pulsar «Ejecutar»: la lista sigue ahí (el localStorage del taller dura entre ejecuciones; «Reiniciar» lo borra). Después crea un segundo hook, useAlternar(inicial), que devuelva un booleano y una función que lo invierta, y úsalo para mostrar u ocultar la lista con un botón.

Rutas, estilos y herramientas

Con componentes, estado y efectos ya puedes construir cualquier pantalla. Para una app completa faltan tres piezas que React deja en manos de otras herramientas: navegar entre páginas, organizar los estilos e inspeccionar lo que pasa por dentro. Esta sección las presenta y cierra con las buenas prácticas que usan los equipos.

Varias páginas: React Router

Una app de React típica es una SPA (Single Page Application, «aplicación de una sola página»): el navegador carga un único index.html y, cuando navegas, JavaScript cambia el contenido sin pedir una página nueva al servidor. La dirección de la barra sí cambia, para que funcionen el botón «Atrás», los marcadores y los enlaces compartidos. La biblioteca más usada para esto es React Router, que relaciona cada dirección (ruta) con un componente. Su versión actual es la 8 (junio de 2026), y se instala así:

$ npm install react-router

Primero, envuelve la app en un BrowserRouter, que conecta React Router con la barra de direcciones:

// src/main.jsx
import { createRoot } from "react-dom/client";
import { BrowserRouter } from "react-router";
import App from "./App.jsx";

createRoot(document.getElementById("root")).render(
  <BrowserRouter>
    <App />
  </BrowserRouter>
);

Después, declara qué componente corresponde a cada ruta:

// src/App.jsx
import { Routes, Route, NavLink } from "react-router";
import Inicio from "./paginas/Inicio.jsx";
import DetalleProducto from "./paginas/DetalleProducto.jsx";
import Carrito from "./paginas/Carrito.jsx";
import NoEncontrada from "./paginas/NoEncontrada.jsx";

export default function App() {
  return (
    <>
      <nav>
        <NavLink to="/">Inicio</NavLink>
        <NavLink to="/carrito">Carrito</NavLink>
      </nav>
      <Routes>
        <Route path="/" element={<Inicio />} />
        <Route path="/producto/:id" element={<DetalleProducto />} />
        <Route path="/carrito" element={<Carrito />} />
        <Route path="*" element={<NoEncontrada />} />
      </Routes>
    </>
  );
}
  • <Routes> mira la dirección actual y muestra el element de la ruta que coincide. path="*" coincide con cualquier cosa: es la página «no encontrada».
  • :id es un segmento dinámico: /producto/7 y /producto/42 muestran el mismo componente con distinto dato.
  • <NavLink> y <Link> son enlaces que cambian de página sin recargar. NavLink añade además la clase active al enlace de la página actual, para resaltarlo con CSS.

Dentro de una página, dos hooks de React Router hacen el resto: useParams lee los segmentos dinámicos y useNavigate cambia de página desde el código (por ejemplo, después de pagar).

// src/paginas/DetalleProducto.jsx
import { useParams, useNavigate, Link } from "react-router";
import { CATALOGO } from "../datos.js";

export default function DetalleProducto() {
  const { id } = useParams();             // en /producto/7, id vale "7" (un texto)
  const navegar = useNavigate();
  const producto = CATALOGO.find(p => p.id === Number(id));

  if (!producto) return <p>Ese producto no existe. <Link to="/">Volver</Link></p>;
  return (
    <article>
      <h1>{producto.nombre}</h1>
      <button onClick={() => navegar("/carrito")}>Ir al carrito</button>
    </article>
  );
}
  1. <BrowserRouter>
  2. <Routes>
  3. <Route path="/" element={<Inicio />} />
  4. <Route path="/producto/:id" element={<DetalleProducto />} />
  5. <Route path="*" element={<NoEncontrada />} />
  6. </Routes>
  7. </BrowserRouter>

Dos fallos frecuentes. (1) Usar <a href="/carrito"> en vez de <Link to="/carrito">: el navegador recarga la página entera y se pierde todo el estado (el carrito queda vacío). (2) Copiar de tutoriales anteriores a 2026 import … from "react-router-dom": en la versión 8 ese paquete desapareció y todo se importa de "react-router". Las ideas (Routes, Route, Link, useParams) son las mismas desde la versión 6.

Si publicas la carpeta dist y alguien recarga la página en /carrito, el servidor buscará un archivo carrito que no existe y responderá 404. Hay que configurar el servidor para que devuelva index.html en cualquier ruta; React Router se encarga del resto. Cada servicio de publicación tiene su forma de hacerlo; lo verás en la Estación 35.

React Router tiene además un «modo framework», heredero de un proyecto llamado Remix, que añade carga de datos antes de mostrar cada página y renderizado en el servidor. Es una de las dos opciones que recomienda la documentación de React para proyectos grandes, junto con Next.js.

Buenas prácticas de oficio

  • Componentes pequeños y puros. Si un componente pasa de unas 150 líneas o hace dos cosas, divídelo.
  • Estado mínimo, lo más abajo posible. Guarda solo lo imprescindible, deriva el resto y ponlo en el componente más bajo que lo necesite. Súbelo solo cuando otro componente lo necesite también.
  • Nunca mutes estado ni props. Crea arrays y objetos nuevos.
  • Keys estables, sacadas de los datos.
  • Efectos solo para sincronizar con sistemas externos, siempre con su limpieza.
  • Deja que las herramientas te vigilen. Ejecuta el linter antes de cada commit (npm run lint) y, cuando el proyecto crezca, usa TypeScript (Estación 23): la plantilla react-ts de Vite ya viene preparada. Las props se describen con un tipo y el editor te avisa si olvidas una:

  • Prueba como lo haría una persona.   • Rendimiento: mide antes de optimizar. React es rápido por defecto. En código de otros verás memo, useMemo y useCallback, que evitan cálculos o renders repetidos.   • Accesibilidad desde el principio: HTML semántico, etiquetas en los campos, foco visible y navegación con teclado (Estación 17).

Next.js, Vue, Svelte y Angular

React no es la única forma de construir interfaces, ni siempre la mejor. Conviene conocer el panorama para saber qué estás eligiendo y para no asustarte cuando un equipo use otra cosa. La buena noticia: las ideas de esta estación (componentes, datos que entran, estado que cambia, efectos, rutas) existen en todas estas herramientas con otros nombres.

Un framework construido sobre React: Next.js

Una SPA como la que crea Vite tiene un punto débil: al abrirla, el navegador recibe un HTML casi vacío (<div id="root"></div>) y tiene que descargar y ejecutar todo el JavaScript antes de mostrar nada. En un teléfono modesto eso se nota, y los buscadores ven peor el contenido. La solución es el renderizado en el servidor (SSR, server-side rendering): el servidor ejecuta los componentes de React y envía el HTML ya hecho, y después el navegador lo «hidrata», es decir, le conecta los eventos para que sea interactivo.

Next.js, creado por la empresa Vercel, es el framework de React más usado. Su versión mayor actual es la 16 (octubre de 2025). Añade a React:

  • Rutas por carpetas: el archivo app/productos/[id]/page.jsx es la página /productos/7, sin configurar un router.
  • Renderizado en el servidor y generación de páginas estáticas al construir.
  • Server Components: componentes que se ejecutan solo en el servidor. Pueden leer una base de datos directamente y no envían su JavaScript al navegador. Los que necesitan estado o eventos se marcan con la línea "use client" al principio del archivo.
  • Rutas de API para escribir el backend en el mismo proyecto, optimización de imágenes y más.

Se crea con npx create-next-app@latest. Es la opción natural para tiendas, blogs, webs de empresa y cualquier cosa que deba aparecer bien en Google. A cambio, es más complejo: tienes que pensar qué parte corre en el servidor y cuál en el navegador. Aprende React «puro» primero; Next.js será mucho más fácil después.

Las alternativas a React

El mismo contador, escrito en cuatro herramientas. Fíjate en lo que cambia (la sintaxis) y en lo que no (un valor que cambia y una interfaz que lo refleja):

import { Component, signal } from "@angular/core";

@Component({
  selector: "app-contador",
  template: `<button (click)="sumar()">Clics: {{ cuenta() }}</button>`,
})
export class Contador {
  cuenta = signal(0);
  sumar() { this.cuenta.update(c => c + 1); }
}
  • Vue (creado por Evan You en 2014; versión 3.5) usa plantillas parecidas al HTML con atributos especiales (v-if, v-for, @click) y junta plantilla, lógica y estilos en un archivo .vue. Cuando cambias cuenta, Vue sabe exactamente qué partes dependen de ella, sin volver a ejecutar el componente entero. Su framework equivalente a Next.js es Nuxt.
  • Svelte (creado por Rich Harris en 2016; versión 5, de octubre de 2024) es un compilador: al construir, convierte tus componentes en JavaScript que actualiza el DOM directamente, sin una biblioteca que compare descripciones en el navegador. Resultado: muy poco código y archivos pequeños. $state es una de sus «runas», marcas que le dicen al compilador qué es reactivo. Su framework es SvelteKit.
  • Angular (de Google; la versión actual es la 22, de junio de 2026) es un framework completo: trae de serie router, formularios, cliente HTTP, pruebas y una estructura muy definida, y se escribe siempre en TypeScript. Usa señales (signal) para la reactividad. No confundir con AngularJS, su antecesor de 2010, que ya no tiene soporte.

Resumen

  • React es una biblioteca para construir interfaces de forma declarativa: describes qué debe verse para cada estado y React actualiza el DOM. La idea central es interfaz = f(estado). Al cambiar el estado, React vuelve a renderizar, compara la descripción nueva con la anterior y toca solo lo que cambió.
  • Los proyectos se crean con Vite (npm create vite@latest), se desarrollan con npm run dev y se construyen con npm run build. create-react-app está obsoleto. La versión actual es React 19 (19.3 en septiembre de 2026); los talleres usan 18.3.1, con las mismas bases.
  • JSX es JavaScript con etiquetas: un solo elemento raíz (o un fragmento <></>), etiquetas cerradas, className y htmlFor, y llaves para las expresiones. Lo que va entre llaves se muestra como texto, así que está protegido contra la inyección de HTML.
  • Un componente es una función con nombre en mayúscula que devuelve JSX. Recibe datos por props (de solo lectura) y lo que va entre sus etiquetas le llega en children. Debe ser puro.
  • useState guarda datos entre renders y, al cambiarlos, provoca un render. El estado es una foto: dentro de un render no cambia. Si el valor nuevo depende del anterior, usa la función de actualización: setCuenta(c => c + 1).
  • Nunca mutes arrays ni objetos del estado: crea copias con spread, map y filter. Guarda el estado mínimo y calcula lo demás (totales, filtros, validaciones) al renderizar.
  • Condiciones con if y return, ternario o && (cuidado con el 0). Listas con map y una key única y estable sacada de los datos, no del índice. Formularios controlados con value y onChange.
  • Los datos bajan por props y los eventos suben llamando a funciones recibidas por props. Si dos componentes necesitan el mismo estado, levántalo al ancestro común. Para datos que usa medio árbol, usa contexto.
  • useEffect sincroniza con sistemas externos (red, temporizadores, localStorage) después de pintar, con sus dependencias y su limpieza. Si no hay nada externo, casi seguro que no necesitas un efecto. Al pedir datos, muestra carga, error y vacío, y descarta respuestas viejas.
  • React Router da varias páginas a una SPA; CSS Modules y Tailwind organizan los estilos; React DevTools muestra el árbol, las props y el estado. Next.js añade servidor a React, y Vue, Svelte y Angular resuelven lo mismo con otra sintaxis.

Formulario de chat

Convierte el campo #mensaje en un campo controlado. Requisitos: el botón «Enviar» está desactivado mientras el mensaje esté vacío o tenga solo espacios; un párrafo con la clase contador muestra los caracteres escritos con el formato 4/80; el campo no admite más de 80 caracteres; al enviar, el mensaje (sin espacios en los extremos) se añade a la lista y el campo queda vacío.

Pista 1

El campo queda así: <input id="mensaje" value={texto} onChange={e => setTexto(e.target.value)} />. Para el límite, recorta dentro del onChange.

Pista 2

Calcula const vacio = texto.trim() === ""; y úsalo en disabled={vacio} y al principio de manejarEnvio. Cada mensaje nuevo necesita un id para su key: { id: Date.now(), texto: texto.trim() }.

Ver una solución 
const { useState } = React;

function Chat() {
  const [mensajes, setMensajes] = useState([]);
  const [texto, setTexto] = useState("");
  const vacio = texto.trim() === "";

  function manejarEnvio(e) {
    e.preventDefault();
    if (vacio) return;
    setMensajes([...mensajes, { id: Date.now(), texto: texto.trim() }]);
    setTexto("");
  }

  return (
    <>
      <form onSubmit={manejarEnvio}>
        <input
          id="mensaje"
          placeholder="Escribe un mensaje"
          value={texto}
          onChange={e => setTexto(e.target.value.slice(0, 80))}
        />{" "}
        <button disabled={vacio}>Enviar</button>
        <p className="contador">{texto.length}/80</p>
      </form>
      <ul className="mensajes">
        {mensajes.map(m => <li key={m.id}>{m.texto}</li>)}
      </ul>
    </>
  );
}

ReactDOM.createRoot(document.getElementById("root")).render(<Chat />);

Con un campo controlado, el límite de 80 caracteres y el contador son una línea cada uno. En HTML también existe el atributo maxLength, que hace lo mismo sin JavaScript; los dos enfoques son válidos.

Marcador en línea: pedir datos

Completa Marcador para que pida las puntuaciones al servidor simulado con pedirPuntuaciones(modo) dentro de un efecto. Mientras espera, muestra Cargando…. Pista 1

Necesitas tres estados: puntuaciones (empieza en []), cargando (empieza en true) y error (empieza en null). Después del efecto, tres if con return: cargando, error y, al final, la lista.

Pista 2

Copia la estructura del ejemplo de la sección Efectos y datos: una función async dentro del efecto con try, catch y finally, la variable ignorar y [modo] como dependencias.

Ver una solución 
const { useState, useEffect } = React;

const PUNTUACIONES = [
  { id: 1, nombre: "Lyra", puntos: 980 },
  { id: 2, nombre: "Bruno", puntos: 870 },
  { id: 3, nombre: "Ana", puntos: 640 },
];

function pedirPuntuaciones(modo) {
  return new Promise((resolver, rechazar) => {
    setTimeout(() => {
      if (modo === "caido") rechazar(new Error("servidor caído"));
      else resolver(PUNTUACIONES);
    }, 40);
  });
}

function Marcador({ modo }) {
  const [puntuaciones, setPuntuaciones] = useState([]);
  const [cargando, setCargando] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let ignorar = false;
    async function cargar() {
      setCargando(true);
      setError(null);
      try {
        const datos = await pedirPuntuaciones(modo);
        if (!ignorar) setPuntuaciones(datos);
      } catch (e) {
        if (!ignorar) setError(e.message);
      } finally {
        if (!ignorar) setCargando(false);
      }
    }
    cargar();
    return () => { ignorar = true; };
  }, [modo]);

  if (cargando) return <p>Cargando…</p>;
  if (error) return <p className="error">No se pudo cargar: {error}</p>;
  return (
    <ol className="puntuaciones">
      {puntuaciones.map(p => <li key={p.id}>{p.nombre}: {p.puntos}</li>)}
    </ol>
  );
}

function App() {
  return (
    <div className="dos">
      <section><h3>Servidor normal</h3><Marcador modo="normal" /></section>
      <section><h3>Servidor caído</h3><Marcador modo="caido" /></section>
    </div>
  );
}

ReactDOM.createRoot(document.getElementById("root")).render(<App />);

Cambia el 40 del servidor simulado por 2000 y ejecuta: verás el estado de carga durante dos segundos. Un mismo componente, con un modo distinto, recorre caminos diferentes: por eso conviene probar siempre el caso de error.

Tu propio hook: useContador

Vidas y Monedas repiten la misma lógica: un número que sube, baja sin pasar de 0 y vuelve a su valor inicial. Crea un hook useContador(inicial) que devuelva un objeto { valor, sumar, restar, reiniciar } y cambia los dos componentes para que lo usen. Al terminar, useState solo debe aparecer una vez en todo el código, dentro del hook.

Pista 1

El hook empieza así: function useContador(inicial) { const [valor, setValor] = useState(inicial); …. Dentro, crea las tres funciones con flechas y devuélvelas en un objeto junto con valor.

Pista 2

En Vidas: const vidas = useContador(3);, y después {vidas.valor} y onClick={vidas.restar}. Aquí no hacen falta flechas en los onClick: vidas.restar ya es una función sin argumentos.

Ver una solución 
const { useState } = React;

function useContador(inicial) {
  const [valor, setValor] = useState(inicial);
  const sumar = () => setValor(v => v + 1);
  const restar = () => setValor(v => Math.max(0, v - 1));
  const reiniciar = () => setValor(inicial);
  return { valor, sumar, restar, reiniciar };
}

function Vidas() {
  const vidas = useContador(3);
  return (
    <section className="panel" id="vidas">
      <p className="valor">Vidas: {vidas.valor}</p>
      <button onClick={vidas.sumar}>Curar</button>
      <button onClick={vidas.restar}>Perder vida</button>
      <button onClick={vidas.reiniciar}>Nueva partida</button>
    </section>
  );
}

function Monedas() {
  const monedas = useContador(0);
  return (
    <section className="panel" id="monedas">
      <p className="valor">Monedas: {monedas.valor}</p>
      <button onClick={monedas.sumar}>Ganar</button>
      <button onClick={monedas.restar}>Gastar</button>
      <button onClick={monedas.reiniciar}>Vaciar</button>
    </section>
  );
}

function App() {
  return (
    <div className="dos">
      <Vidas />
      <Monedas />
    </div>
  );
}

ReactDOM.createRoot(document.getElementById("root")).render(<App />);

{ valor, sumar, restar, reiniciar } es la forma abreviada de { valor: valor, sumar: sumar, … }. Devolver un objeto permite usar solo lo que necesites; useState devuelve un array porque así puedes elegir los nombres al desestructurar. Las dos opciones son habituales.

Vas a construir la tienda de «Café Terminal»: un catálogo con filtro por categoría, un carrito que suma cantidades, un total que se calcula solo, una insignia en la cabecera y un carrito que sobrevive a una recarga. Seguirás el método «Pensar en React»: el taller ya trae la versión estática (componentes y props, sin estado) y tú le das vida.

                <button onClick={() => onCambiar(l.id, -1)} aria-label={"Uno menos de " + l.nombre}>-</button>{" "}
                <button onClick={() => onQuitar(l.id)}>Quitar</button>
              </span>
            </li>
          ))}
        </ul>
      )}
      <p className="total">Total: {formatear(total)}</p>
    </aside>
  );
}

function App() {
  const [carrito, setCarrito] = useLocalStorage("carrito", []);
  const [categoria, setCategoria] = useState("todas");

  const visibles = categoria === "todas" ? CATALOGO : CATALOGO.filter(p => p.categoria === categoria);
  const unidades = carrito.reduce((suma, l) => suma + l.cantidad, 0);

  function agregar(producto) {
    setCarrito(c =>
      c.some(l => l.id === producto.id)
        ? c.map(l => (l.id === producto.id ? { ...l, cantidad: l.cantidad + 1 } : l))
        : [...c, { ...producto, cantidad: 1 }]
    );
  }

  function cambiarCantidad(id, cambio) {
    setCarrito(c =>
      c.map(l => (l.id === id ? { ...l, cantidad: l.cantidad + cambio } : l))
       .filter(l => l.cantidad > 0)
    );
  }

  function quitar(id) {
    setCarrito(c => c.filter(l => l.id !== id));
  }

  return (
    <>
      <Cabecera unidades={unidades} />
      <main className="tienda">
        <section>
          <label htmlFor="categoria">Categoría </label>
          <select id="categoria" value={categoria} onChange={e => setCategoria(e.target.value)}>
            <option value="todas">Todas</option>
            <option value="cafe">Café</option>
            <option value="accesorios">Accesorios</option>
          </select>
          <div className="catalogo">
            {visibles.map(p => <TarjetaProducto key={p.id} producto={p} onAgregar={agregar} />)}
          </div>
        </section>
        <Carrito lineas={carrito} onCambiar={cambiarCantidad} onQuitar={quitar} />
      </main>
    </>
  );
}

ReactDOM.createRoot(document.getElementById("root")).render(<App />);

Las tres funciones que cambian el carrito usan la forma con función (setCarrito(c => …)), así son correctas aunque se llamen varias veces seguidas. Los botones «+» y «-» llevan un aria-label porque, leídos en voz alta, un signo solo no dice de qué producto son. Y fíjate en qué no es estado: visibles, unidades y total.

Autoevaluación

Responde sin mirar arriba. Si fallas alguna, lee la explicación de cada opción: equivocarse aquí es la forma más barata de aprender.

¿Qué significa «la interfaz es una función del estado»?

  1. Que cada componente debe tener una función llamada estado.

    No. Es una forma de pensar, no un nombre obligatorio.

  2. Que para cambiar la pantalla escribes una función que modifica el DOM.

    Eso es el enfoque imperativo. En React no tocas el DOM: cambias el estado.

  3. Que para un mismo estado se ve siempre la misma interfaz, y para cambiar lo que se ve cambias el estado.

    Correcto. React vuelve a calcular la interfaz a partir del estado y actualiza el DOM por ti.

  4. Que React guarda el estado dentro de los elementos del DOM.

    Al revés: el estado vive en JavaScript y el DOM es la consecuencia.

Un componente tiene let cuenta = 0; y un botón con onClick={() => cuenta++}. ¿Por qué la pantalla sigue mostrando 0?

  1. Porque cambiar una variable normal no avisa a React, y además la variable vuelve a 0 en cada render.

    Correcto. Por eso existe useState: guarda el valor entre renders y, al cambiarlo, provoca un render.

  2. Porque habría que usar var en lugar de let.

    var tiene los mismos dos problemas. No es cuestión de cómo se declara.

  3. Porque falta un console.log después de sumar.

    console.log solo escribe en la consola; no cambia la pantalla.

  4. Porque los eventos de React no pueden cambiar variables.

    Sí pueden; la variable cambia (compruébalo en la consola). Lo que no ocurre es un nuevo render.

cuenta vale 0. Un clic ejecuta tres veces seguidas setCuenta(cuenta + 1). ¿Qué muestra la pantalla después?

  1. 3

    Es lo que parece, pero las tres llamadas usan la misma foto del estado: 0 + 1 las tres veces.

  2. 1

    Correcto. Dentro de un render el estado no cambia. Con setCuenta(c => c + 1) sí llegaría a 3.

  3. 0

    setCuenta sí cambia el estado, pero para el siguiente render.

  4. Un error por llamar tres veces a setCuenta.

    Se puede llamar las veces que quieras; React agrupa las actualizaciones.

¿Cuál de estos trozos de JSX es correcto?

  1. <label for="n" class="x">Nombre</label>

    En JSX se escribe htmlFor y className.

  2. return <h1>Hola</h1><p>Adiós</p>;

    Dos elementos hermanos sin envolver: hace falta un elemento raíz o un fragmento.

  3. <img src={foto}>

    En JSX todas las etiquetas se cierran: <img src={foto} />. Y le falta alt.

  4. <><h1 className="t">Hola</h1><img src={foto} alt="" /></>

    Correcto: fragmento como raíz, className y la imagen cerrada.

Este código no actualiza la pantalla: carrito.push(producto); setCarrito(carrito);. ¿Por qué?

  1. Porque push no funciona dentro de un componente.

    push funciona: el array sí tiene un elemento más. El problema es otro.

  2. Porque falta un useEffect que avise del cambio.

    Un efecto no arregla esto. Basta con pasar un array nuevo.

  3. Porque es el mismo array: React compara la referencia, ve que no cambió y no vuelve a renderizar.

    Correcto. Usa setCarrito([...carrito, producto]), que crea un array nuevo.

  4. Porque setCarrito solo acepta números y textos.

    El estado puede ser cualquier valor, incluidos arrays y objetos.

Una lista de tareas se puede reordenar y se pueden borrar tareas. ¿Qué key debe llevar cada <li>?

  1. key={indice}

    Al reordenar o borrar, las posiciones cambian de dueño y React mezcla los elementos (lo viste con las notas del taller).

  2. key={tarea.id}

    Correcto: un identificador único y estable que viaja con cada dato.

  3. key={Math.random()}

    Cambia en cada render: React destruye y crea todos los elementos cada vez, y se pierde lo que tenían dentro.

  4. Ninguna: React la deduce solo.

    Sin key, React empareja por posición (como con el índice) y muestra un aviso en la consola.

Con cero mensajes, ¿qué muestra {mensajes.length && <p>Tienes mensajes</p>}?

  1. Un 0 en la pantalla.

    Correcto. 0 && … vale 0, y React sí dibuja los números. Escribe mensajes.length > 0 && ….

  2. Nada.

    Sería así con false, null o undefined, pero no con el número 0.

  3. La palabra false.

    La expresión no vale false, vale 0. Y aunque valiera false, React no lo dibujaría.

  4. Un error.

    Es código válido; el fallo es que se ve un 0 inesperado.

Dos componentes hermanos necesitan el mismo dato, y uno de ellos lo cambia. ¿Qué haces?

  1. Creas el estado en los dos y los mantienes iguales con un useEffect.

    Dos copias del mismo dato acaban desincronizándose. Es justo lo que hay que evitar.

  2. Lo guardas en una variable global fuera de los componentes.

    Cambiar una variable global no provoca renders: la pantalla no se enteraría.

  3. El que lo necesita lee el DOM del otro con querySelector.

    En React no se lee la pantalla para obtener datos: se leen el estado y las props.

  4. Levantas el estado al ancestro común y lo pasas por props, junto con una función para cambiarlo.

    Correcto. Los datos bajan por props y los cambios suben llamando a la función.

¿En cuál de estos casos sí hace falta useEffect?

  1. Calcular el total del carrito.

    Es un valor derivado: se calcula al renderizar, sin efecto.

  2. Enviar el pedido cuando se pulsa «Pagar».

    Es la respuesta a un evento: va en el manejador del clic.

  3. Iniciar un setInterval cuando aparece un cronómetro y pararlo cuando desaparece.

    Correcto: es sincronizar con algo externo a React (un temporizador), con su limpieza.

  4. Filtrar una lista según lo que se escribe en un buscador.

    También es un valor derivado. Hacerlo con un efecto duplica el estado y renderiza dos veces.

¿Cuándo se ejecuta useEffect(cargar, [categoria])?

  1. Solo una vez, cuando el componente aparece.

    Eso sería con el array vacío, [].

  2. Cuando el componente aparece y cada vez que categoria cambia.

    Correcto. Antes de repetirlo, React ejecuta la limpieza del efecto anterior, si la hay.

  3. Después de cada render, cambie lo que cambie.

    Eso ocurre si no pasas array de dependencias.

  4. Antes de pintar el componente por primera vez.

    Los efectos se ejecutan después de que React actualiza la pantalla.

En un efecto que pide datos, ¿qué evita la limpieza return () => { ignorar = true; }?

  1. Que la respuesta de una petición vieja pise a la de la más reciente.

    Correcto. Es una condición de carrera: sin la limpieza, gana la respuesta que llega la última, no la última que pediste.

  2. Que la petición se haga dos veces.

    La petición se hace igual; lo que se descarta es su resultado. Para cancelarla de verdad existe AbortController.

  3. Que el servidor responda con un error.

    La limpieza no influye en el servidor. Los errores se manejan con try/catch.

  4. Que aparezca el mensaje «Cargando…».

    El estado de carga depende de cargando, no de la limpieza.

Glosario

React
Biblioteca de JavaScript para construir interfaces de usuario con componentes, de forma declarativa.
Declarativo
Estilo de programación en el que describes el resultado que quieres (qué debe verse) en lugar de cada paso para conseguirlo.
Componente
Pieza de interfaz con nombre propio. En React es una función, con nombre en mayúscula, que devuelve JSX.
JSX
Extensión de la sintaxis de JavaScript que permite escribir etiquetas parecidas a HTML. Se traduce a llamadas que crean objetos con la descripción de la interfaz.
Fragmento
Envoltorio <>…</> que agrupa varios elementos sin añadir nada al DOM.
Props
Datos que un componente recibe de su padre, escritos como atributos. Son de solo lectura.
children
Prop especial que contiene lo que se escribe entre la etiqueta de apertura y la de cierre de un componente.
Estado
Datos que un componente recuerda entre renders y que, al cambiar, hacen que React vuelva a renderizarlo.
Hook
Función especial de React cuyo nombre empieza por use (useState, useEffect…). Solo se llama en el nivel superior de un componente o de otro hook.
Renderizar
Llamar a un componente para calcular qué debe verse. Después, React aplica al DOM solo las diferencias.
Reconciliación
Proceso con el que React compara la descripción nueva de la interfaz con la anterior para decidir qué cambiar en el DOM.
Función de actualización
Función que se pasa a un set del estado (setCuenta(c => c + 1)) y que recibe el valor pendiente para calcular el siguiente.
Inmutabilidad
No modificar un valor existente, sino crear uno nuevo con los cambios. En React, obligatoria para arrays y objetos del estado.
Key
Prop especial, única y estable, que identifica cada elemento de una lista para que React sepa cuál es cuál entre renders.
Campo controlado
Campo de formulario cuyo valor sale del estado (value) y se actualiza con onChange.
Levantar el estado
Mover un estado al ancestro común de los componentes que lo necesitan, y pasarlo hacia abajo por props.
Valor derivado
Dato que se calcula al renderizar a partir de props o estado (un total, una lista filtrada), en lugar de guardarse como estado.
Contexto
Mecanismo para que un componente ofrezca un valor que cualquier componente de debajo puede leer con useContext, sin pasarlo por props.
Efecto
Código que React ejecuta después de actualizar la pantalla para sincronizar un componente con un sistema externo. Se declara con useEffect.
Dependencias
Array de valores que usa un efecto; React lo repite solo si alguno cambió.
Limpieza
Función que devuelve un efecto para deshacer lo que hizo (parar un intervalo, cerrar una conexión). Se ejecuta antes de repetir el efecto y al desmontar.
StrictMode
Envoltorio que, solo en desarrollo, hace comprobaciones extra, como ejecutar los efectos dos veces al montar para detectar limpiezas que faltan.
Hook personalizado
Función propia, con nombre que empieza por use, que reúne estado y efectos para reutilizar esa lógica en varios componentes.
SPA
Aplicación de una sola página (Single Page Application): carga un único HTML y cambia el contenido con JavaScript al navegar.
Vite
Herramienta de construcción que crea proyectos, sirve la app en desarrollo con recarga instantánea y genera la versión optimizada para publicar.
