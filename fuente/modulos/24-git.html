Git y GitHub: qué es cada cosa

Imagina que estás haciendo un juego de plataformas con dos amigas. Una dibuja los niveles, otra programa los enemigos y tú el salto del personaje. Si se pasan los archivos por correo o por una carpeta compartida, pronto aparecen las preguntas difíciles: ¿quién tiene la versión buena?, ¿quién borró la función del salto?, ¿cómo junto mis cambios con los tuyos sin perder nada?, ¿cómo vuelvo a como estaba el martes, cuando todo funcionaba?

Un sistema de control de versiones responde a esas preguntas. Ya sabes que Git guarda fotos de tu proyecto, los commits. Esa es solo la primera de sus cuatro capacidades:

  • Historial. Qué cambió, cuándo, quién lo hizo y, si el mensaje es bueno, por qué.
  • Volver atrás. Recuperar un archivo, deshacer un cambio o volver a una versión que funcionaba.
  • Experimentar sin miedo. Probar una idea en una línea paralela (una rama) sin tocar la versión que funciona.
  • Colaborar. Varias personas cambian los mismos archivos a la vez, y Git junta el trabajo.

Git no es GitHub

Mucha gente usa las dos palabras como si fueran lo mismo. No lo son:

  • Git es un programa que instalaste en tu computadora. Funciona sin internet. Guarda la historia en la carpeta oculta .git de cada proyecto.
  • GitHub es un servicio web (en github.com, propiedad de Microsoft desde 2018) que guarda copias de repositorios de Git en internet y les añade herramientas para colaborar: pull requests, revisión de código, issues, publicación de páginas web y automatización. Hay servicios parecidos, como GitLab, Codeberg o Bitbucket. Con todos se usa el mismo Git.

Fíjate en un detalle importante: en Git no hay una copia «principal» por diseño. Cada copia de un repositorio tiene la historia completa, por eso se dice que Git es un sistema de control de versiones distribuido. Si GitHub se cayera mañana, tu computadora seguiría teniendo todos los commits. Los equipos acuerdan usar la copia de GitHub como punto de encuentro, pero es un acuerdo, no una obligación técnica.

Git es como la cámara y el álbum de fotos de tu teléfono: funcionan sin conexión y el álbum es tuyo. GitHub es como un álbum compartido en internet donde tu familia sube sus fotos, las comenta y ordena. La analogía falla en algo: GitHub añade herramientas que Git no tiene (pull requests, issues, Pages), y Git junta el trabajo de varias personas de una forma que ningún álbum de fotos sabe hacer.

Qué hay dentro de un commit

En la Estación 5 dijimos que un commit es una foto del proyecto. Veamos qué guarda exactamente:

  • La foto de todos los archivos que Git sigue, tal como estaban al hacer el commit. No solo los que cambiaron: el proyecto entero. Por dentro, Git no duplica los archivos que no cambiaron y comprime todo, así que un repositorio con miles de commits ocupa poco.
  • El autor y la fecha. El nombre y el correo que configuraste con git config.
  • El mensaje que escribiste con -m.
  • El padre: el identificador del commit anterior. Así cada commit sabe de dónde viene y la historia forma una cadena. El primer commit no tiene padre, y un commit que junta dos ramas tiene dos.
  • Un identificador único, como a3f9c2e4b1d0..., de 40 dígitos hexadecimales. Se llama hash y se calcula a partir de todo lo anterior.

El hash funciona como una huella digital: si cambias un solo carácter del mensaje, de un archivo o del padre, sale un identificador completamente distinto. Por eso nadie puede alterar un commit antiguo sin que se note: cambiaría su hash y el de todos los que vienen detrás. Es la misma idea de las funciones hash que viste en la Estación 19, en su versión criptográfica, y los dígitos hexadecimales son los de la Estación 18. Casi siempre verás solo los 7 primeros dígitos, como a3f9c2e: bastan para distinguir un commit de los demás en un proyecto normal.

Hoy Git calcula los identificadores con un algoritmo llamado SHA-1. El proyecto Git ya anunció que la futura versión 3.0 usará SHA-256 en los repositorios nuevos, y también llamará main a la rama inicial. Cuando llegue, los identificadores serán más largos, pero todo lo que aprendas aquí seguirá valiendo igual.

Dos nombres más que vas a ver todo el tiempo. Una rama (en inglés, branch) es un nombre, como main, que señala un commit y avanza sola cada vez que haces un commit nuevo en ella. HEAD («cabeza») es la marca de «estás aquí»: normalmente apunta a la rama en la que trabajas. Lo verás en detalle en la sección de ramas.

El ciclo del commit, a fondo

Ya conoces el ciclo básico: cambias archivos, los preparas con git add y los guardas con git commit. Parece poca cosa, pero la diferencia entre un historial útil y uno inservible está en los detalles: qué entra en cada commit, qué se queda fuera y qué dice el mensaje. Un buen historial se lee como el diario de un proyecto; uno malo es una lista de «cambios», «más cambios» y «arreglo».

Los estados de un archivo

Para Git, cada archivo de tu carpeta está en uno de estos estados. git status te lo dice, y conviene leerlo con calma:

EstadoQué significaCómo aparece en git statusEn git status -s
Sin seguimientoGit lo ve, pero nunca lo ha guardadoUntracked files??
ModificadoCambió desde el último commit y no está preparadoChanges not staged for commit M (la M a la derecha)
PreparadoEstá en el área de preparación: entrará en el próximo commitChanges to be committedM o A (a la izquierda)
ConfirmadoEstá igual que en el último commitNo aparece: nothing to commit, working tree cleanNo aparece

La versión corta, git status -s (de short), usa dos columnas: la izquierda habla del área de preparación y la derecha de la carpeta de trabajo. Así, MM juego.js significa que preparaste una parte de los cambios de juego.js y después seguiste cambiándolo. Sí, eso es posible: el área de preparación guarda el archivo tal como estaba al hacer git add, no una referencia al archivo.

Un tropiezo clásico: haces git add juego.js, sigues editando juego.js, haces commit… y el commit no tiene tus últimos cambios. Es correcto: se guardó la versión que preparaste. Antes de cada commit, mira git status: si el archivo aparece a la vez en Changes to be committed y en Changes not staged, te falta otro git add.

Preparar con precisión

El área de preparación existe para que decidas qué entra en cada commit. Estas son las formas de usarla:

ComandoQué prepara
git add juego.jsEse archivo, tal como está ahora
git add sprites/Todo lo que hay dentro de la carpeta sprites
git add .Todo lo nuevo, modificado o borrado en la carpeta actual y sus subcarpetas
git add -p juego.jsTe enseña cada trozo de cambio y te pregunta si lo preparas (y sí, n no, q salir). Útil cuando un mismo archivo tiene dos cambios que no tienen nada que ver
git restore --staged juego.jsLo contrario: saca el archivo del área de preparación. Tus cambios siguen en el archivo; solo dejan de estar preparados

¿Por qué complicarse en vez de hacer siempre git add .? Porque un commit debería contener un solo cambio lógico: «añade el contador de puntos», no «añade el contador de puntos, cambia los colores y arregla un error del menú». Si mañana el contador de puntos resulta ser un problema, podrás deshacer ese commit sin perder los colores ni el arreglo. Y quien revise tu trabajo entenderá cada paso por separado.

Usar git add . está bien cuando sabes exactamente qué hay en la carpeta. Mira siempre git status antes: es la forma más barata de descubrir que ibas a guardar un archivo de contraseñas, una carpeta de 300 MB o un borrador que no querías compartir.

Ver exactamente qué cambió: git diff

git status te dice qué archivos cambiaron. git diff te dice qué líneas. Hay tres comparaciones posibles, según qué dos zonas quieras comparar:

Así se lee la salida de git diff. En este ejemplo cambiaste la velocidad de 5 a 8 y añadiste una línea:

$ git diff
diff --git a/juego.js b/juego.js
index 3b18e51..a1c2f0d 100644
--- a/juego.js
+++ b/juego.js
@@ -1,2 +1,3 @@
 let vidas = 3;
-let velocidad = 5;
+let velocidad = 8;
+let puntos = 0;
  • --- a/juego.js es la versión anterior y +++ b/juego.js la nueva.
  • @@ -1,2 +1,3 @@ dice dónde está el cambio: en la versión anterior, un trozo que empieza en la línea 1 y tiene 2 líneas; en la nueva, empieza en la línea 1 y tiene 3.
  • Las líneas que empiezan con un espacio no cambiaron: están ahí como contexto.
  • Las que empiezan con - se quitaron y las que empiezan con + se añadieron. Git no tiene la idea de «línea modificada»: un cambio en una línea aparece como la línea vieja quitada y la nueva añadida.

Si la salida es más larga que la pantalla, Git la muestra dentro de un visor: bájala con las flechas o con la barra espaciadora y sal con q. VS Code muestra lo mismo con colores si haces clic en un archivo del panel Control de código fuente.

Ahora practica. En esta misión vas a hacer lo que se hace a diario en un proyecto real: tienes dos cambios distintos en dos archivos y los guardas en dos commits separados, cada uno con su mensaje.

  1. Prepara el escenario: cd juego, git init, git add . y git commit -m "feat: primera versión del juego".
  2. Haz dos cambios: echo "let puntos = 0;" >> juego.js y echo "h1 { color: gold; }" >> estilos.css.
  3. Mira qué pasó con git status y qué líneas cambiaron con git diff.
  4. Guarda el cambio de juego.js solo, en un commit: git add juego.js y git commit -m "feat: añade el contador de puntos".
  5. Después guarda el de estilos.css en otro commit con el mensaje style: pinta el título de dorado, y termina con git log --oneline.

Tres commits, cada uno con una sola idea. Dentro de un mes, si el título dorado no gusta, podrás deshacer solo ese commit sin tocar el contador de puntos.

Lo que no debe entrar: .gitignore

Algunos archivos no deben guardarse nunca en el repositorio:

  • Dependencias descargadas, como la carpeta node_modules que crea npm. Pueden ser cientos de megas y cualquiera puede volver a descargarlas con un comando.
  • Secretos: contraseñas, claves de APIs, el archivo .env donde se suelen guardar. Lo que entra en un repositorio lo puede leer cualquiera que tenga acceso a él.
  • Archivos generados: versiones compiladas o empaquetadas (carpetas como dist o build) que se fabrican a partir del código.
  • Basura del sistema y de programas: .DS_Store de macOS, Thumbs.db de Windows, registros *.log, archivos temporales.

Para eso existe el archivo .gitignore: un archivo de texto en la raíz del repositorio con una regla por línea. Git no mostrará como «sin seguimiento» nada de lo que coincida, y git add . lo dejará fuera. El propio .gitignore sí se guarda en el repositorio, para que todo el equipo comparta las mismas reglas.

# Las líneas que empiezan con # son comentarios
node_modules/     # la carpeta node_modules, esté donde esté
.env              # un archivo llamado exactamente .env
*.log             # cualquier archivo que termine en .log
/dist             # dist solo en la raíz del proyecto
sprites/*.psd     # los .psd que estén directamente en sprites
!importante.log   # excepción: este sí se guarda
ReglaSignificado
*Cualquier cantidad de caracteres, excepto /. *.log son todos los archivos que terminan en .log
?Exactamente un carácter cualquiera
**Cualquier cantidad de carpetas: docs/**/*.pdf son los PDF dentro de docs, a cualquier profundidad
Termina en /Solo carpetas: build/ ignora una carpeta build, pero no un archivo llamado build
Empieza con / o tiene / en medioLa ruta se cuenta desde donde está el .gitignore. Sin barra, la regla vale en cualquier carpeta
Empieza con !Excepción: vuelve a incluir algo que una regla anterior ignoraba. Si ignoraste la carpeta entera, no puedes rescatar un archivo de dentro

Este taller imita cómo decide Git. Arriba están las reglas; abajo, los archivos de un proyecto. Predice cuáles se ignorarán antes de ejecutar.

Con las reglas iniciales se ignoran .env, los dos .log (el de la raíz y el de logs, porque *.log no tiene barra y vale en cualquier carpeta) y todo lo que está dentro de node_modules. Para completar el taller añade dist/ y *.psd.

.gitignore solo afecta a archivos que Git todavía no sigue. Si ya hiciste commit de node_modules o de .env, añadirlos a .gitignore no los saca del repositorio. Tienes que dejar de seguirlos con git rm --cached .env (quita el archivo del repositorio pero lo deja en tu disco) y hacer un commit. Aun así, la versión antigua sigue en el historial.

Si subes por error una clave o contraseña a un repositorio público, date por hecho que alguien la copió: hay programas que recorren GitHub buscando claves minutos después de cada push. Borrarla en un commit nuevo no basta, porque sigue en el historial. Lo correcto es anular la clave (cambiar la contraseña o revocar la clave en el servicio que la emitió) y crear una nueva. GitHub revisa los envíos a los repositorios públicos nuevos y bloquea muchos tipos de claves conocidas antes de que se publiquen (push protection), pero no las reconoce todas. Verás más sobre secretos en la Estación 31.

No hace falta escribir el .gitignore desde cero. Al crear un repositorio en GitHub puedes elegir una plantilla para tu lenguaje (por ejemplo, Node), y el repositorio público github/gitignore tiene plantillas para casi cualquier tecnología, incluidos motores de videojuegos como Unity y Godot.

Mensajes que cuentan una historia

El mensaje de un commit es para una persona que no está en tu cabeza: tu equipo, o tú dentro de seis meses. La propia documentación de Git recomienda empezar con una línea corta, de menos de unos 50 caracteres, que resuma el cambio; después una línea en blanco, y después, si hace falta, una explicación más larga. Estas reglas ayudan:

  • La primera línea dice qué hace el commit, con un verbo en presente: «Añade el contador de puntos», «Corrige el doble salto». Imagina que completa la frase «Si aplicas este commit, …».
  • El cuerpo explica por qué, si no es evidente: qué problema había, qué alternativa descartaste. El cómo ya está en el código.
  • Un commit, un cambio lógico. Si el mensaje necesita un «y», probablemente son dos commits.

Con -m puedes escribir los dos párrafos: el primer -m es el título y el segundo, el cuerpo.

$ git commit -m "fix: evita el doble salto en el aire" -m "El personaje podía saltar otra vez antes de tocar el suelo si se pulsaba la tecla muy rápido. Ahora solo salta si enSuelo es true."

Conventional Commits

Muchos equipos siguen una convención llamada Conventional Commits (en español, «commits convencionales»). El mensaje empieza con un tipo que dice qué clase de cambio es:

tipo(ámbito opcional): descripción

cuerpo opcional

notas al pie opcionales
TipoÚsalo cuando…Ejemplo
featAñades una funcionalidad nuevafeat: añade el modo multijugador
fixCorriges un errorfix(menu): el botón Salir no respondía

El ámbito entre paréntesis dice qué parte del proyecto toca: fix(menu):, feat(nivel-2):. Si un cambio rompe algo que funcionaba de otra forma (por ejemplo, las partidas guardadas antiguas dejan de cargarse), se marca con ! antes de los dos puntos, feat!: nuevo formato de partidas, o con una nota al pie que empieza por BREAKING CHANGE:.

¿Para qué tanta regla? Para que las personas y los programas entiendan el historial. Hay herramientas que leen estos mensajes y calculan solas el número de la siguiente versión con el sistema SemVer (versionado semántico, tres números MAYOR.MENOR.PARCHE, como 2.4.1): un fix sube el parche, un feat sube el menor y un cambio que rompe sube el mayor. Lo practicarás en un reto.

Los tipos (feat, fix…) se escriben siempre en inglés, porque las herramientas los buscan así. La descripción puede ir en el idioma del equipo. En proyectos de código abierto internacionales se escribe en inglés; en un equipo que habla español, en español. Lo importante es ser constante.

Cuando Git abre un editor (y es Vim)

Si escribes git commit sin -m, Git abre un editor para que escribas el mensaje con calma. En la Estación 5 configuraste VS Code para esto (core.editor "code --wait"): se abre una pestaña, escribes el mensaje en la primera línea, guardas y cierras la pestaña. Las líneas que empiezan con # son explicaciones de Git y no se guardan. Si cierras la pestaña sin escribir nada, Git cancela el commit: Aborting commit due to empty commit message.

Pero si no configuraste el editor, o estás en otra computadora, Git suele abrir Vim, un editor de terminal que no se usa como los demás: al abrirlo no puedes escribir, y ninguna tecla habitual lo cierra. No es tu culpa; es un rito de paso. Así se sale:

Corregir el último commit: --amend

Acabas de hacer un commit y ves que el mensaje tiene una falta, o que olvidaste un archivo. Si todavía no lo compartiste (no hiciste push, que verás más adelante), puedes rehacerlo:

$ git add sonido-salto.wav          # el archivo que olvidaste (opcional)
$ git commit --amend -m "feat: añade el sonido del salto"

--amend («enmendar») no edita el commit anterior: crea uno nuevo, con otro hash, que lo reemplaza. Por eso solo debe usarse con commits que nadie más tiene. La terminal de práctica de esta página no tiene --amend: pruébalo en tu computadora.

Leer y buscar en el historial

Un historial bien hecho vale poco si no sabes consultarlo. Imagina que el juego tiene 200 commits y alguien pregunta: «¿cuándo cambiamos la velocidad del personaje, y por qué?». Git responde en segundos, si sabes preguntarle.

Nombrar commits sin copiar hashes

Para señalar un commit puedes usar su hash corto (a3f9c2e) o una posición relativa a HEAD:

  • HEAD es el commit en el que estás.
  • HEAD~1 es su padre (un commit atrás); HEAD~2, el abuelo; HEAD~5, cinco commits atrás.
  • Verás también HEAD^, que en una historia sin fusiones es lo mismo que HEAD~1.

Con esos nombres puedes comparar versiones o mirar un commit concreto:

$ git show a3f9c2e             # el mensaje y el diff de ese commit
$ git diff HEAD~3 HEAD          # todo lo que cambió en los últimos 3 commits
$ git show HEAD~2:juego.js      # juego.js tal como era hace 2 commits

¿Quién escribió esta línea? git blame

git blame juego.js muestra el archivo con una anotación en cada línea: el commit, el autor y la fecha del último cambio de esa línea. El nombre (blame significa «culpar») es desafortunado: no sirve para buscar culpables, sino para encontrar el commit y su mensaje, que suelen explicar por qué la línea es como es. VS Code, GitHub y otras herramientas muestran la misma información con el nombre más amable de annotate.

Viajar al pasado

A veces quieres ver el proyecto entero como estaba hace una semana, por ejemplo para comprobar si un error ya existía. Puedes llevar tu carpeta a cualquier commit:

$ git switch --detach a3f9c2e
HEAD is now at a3f9c2e feat: añade el salto

Tus archivos pasan a estar como en ese commit. Git llama a esta situación HEAD separado (detached HEAD): estás en un commit, pero no en una rama. Con el comando antiguo, git checkout a3f9c2e, Git te lo advierte con un mensaje largo que empieza por You are in 'detached HEAD' state. No es un error: puedes mirar, ejecutar el programa y probar. Para volver al presente:

$ git switch main

Si haces commits en HEAD separado, no pertenecen a ninguna rama y es fácil perderlos al volver a main. Si quieres conservarlos, crea una rama ahí mismo antes de irte: git switch -c rescate.

Encontrar el commit culpable: git bisect

En la Estación 12 aprendiste a buscar un error partiendo el problema por la mitad. git bisect aplica esa bisección a la historia. Situación: el juego funcionaba hace 30 commits y hoy el personaje atraviesa el suelo. En vez de revisar 30 commits uno por uno, le das a Git un commit bueno y uno malo:

$ git bisect start
$ git bisect bad                  # la versión actual tiene el error
$ git bisect good 3f2a9c1         # esta versión antigua funcionaba
Bisecting: 15 revisions left to test after this (roughly 4 steps)
[7c2d9e1...] feat: añade enemigos voladores

Git te deja en un commit de la mitad. Pruebas el juego y le dices el resultado con git bisect good (aquí funciona) o git bisect bad (aquí falla). Git descarta la mitad y te lleva a otro punto medio. Con 30 commits bastan unos 5 pasos, porque cada respuesta parte el problema en dos (es la búsqueda binaria de la Estación 20). Al final:

4d5e6f7a... is the first bad commit
    refactor: unifica la detección de colisiones
$ git bisect reset                # vuelve a donde estabas

Ahora sabes exactamente qué commit rompió el juego y puedes leer su diff con git show 4d5e6f7. Esto funciona mucho mejor con commits pequeños: si el culpable es un commit de 800 líneas, el sospechoso sigue siendo enorme.

La terminal de práctica de esta página entiende git log y git log --oneline, pero no las demás opciones, ni show, blame o bisect. Pruébalos en tu computadora con cualquier proyecto que tenga unos cuantos commits.

Deshacer sin miedo

Para esto querías Git: para poder equivocarte. Borraste un archivo sin querer, preparaste algo que no debías, un commit rompió el juego… Cada situación tiene su comando. Lo importante es elegir el adecuado, porque algunos son seguros y otros borran trabajo sin preguntar.

Deshacer lo que no está en un commit: restore

git restore tiene dos usos, y ya los viste de pasada en la Estación 12. Sin opciones, devuelve un archivo de tu carpeta a su versión guardada: sirve para tirar un experimento o recuperar un archivo que borraste. Con --staged, saca el archivo del área de preparación sin tocar su contenido. Es la «tecla de retroceso» de git add.

En esta misión vas a vivir una tarde desastrosa y a arreglarla con esos dos comandos:

  1. Prepara el escenario: cd tienda, git init, git add productos.js estilos.css y git commit -m "feat: primera versión de la tienda". El archivo notas-privadas.txt se queda fuera a propósito.
  2. Primer accidente: vacías productos.js sin querer con echo "" > productos.js. Compruébalo con cat productos.js y git diff, y recupéralo con git restore productos.js.
  3. Haz un cambio bueno: echo "h1 { color: navy; }" >> estilos.css.
  4. Segundo accidente: preparas todo con git add ., y git status te muestra que también entraron las notas privadas. Sácalas con git restore --staged notas-privadas.txt.
  5. Guarda el cambio de estilos: git commit -m "style: título azul marino".

Al terminar, git status sigue mostrando notas-privadas.txt como archivo sin seguimiento. En un proyecto real lo añadirías al .gitignore para que deje de aparecer y nadie lo prepare por error.

Deshacer commits: revert o reset

Cuando el problema ya está en un commit hay dos caminos, y la diferencia es fundamental:

git revert («revertir») crea un commit nuevo que hace exactamente lo contrario del commit que le indicas: si aquel añadió tres líneas, este las quita. El historial queda completo y honesto: «añadimos esto, y después lo quitamos». Es la forma segura cuando el commit ya está en GitHub o lo tiene otra persona.

$ git revert HEAD --no-edit
[main 1a2b3c4] Revert "feat: añade música de fondo"
 1 file changed, 1 deletion(-)

Sin --no-edit, Git abre el editor para que ajustes el mensaje (que empieza por Revert). Puedes revertir cualquier commit, no solo el último: git revert a3f9c2e.

git reset («reiniciar») mueve la rama actual a otro commit, como si los posteriores no hubieran existido. Tiene tres modos, y conviene conocerlos todos antes de usar el tercero:

ComandoLa ramaLos cambios de los commits deshechos…
git reset --soft HEAD~1Retrocede un commit…quedan preparados, listos para otro commit. Útil para rehacer el último commit de otra manera
git reset HEAD~1Retrocede un commit…quedan en tus archivos, sin preparar (es el modo por defecto, --mixed)
git reset --hard HEAD~1Retrocede un commit…se borran de tus archivos, junto con cualquier cambio sin guardar

No reescribas historia que otras personas ya tienen. reset, commit --amend y rebase (que verás después) crean commits nuevos o hacen desaparecer otros. Si esos commits ya estaban en GitHub, tu historia y la del resto dejan de coincidir y el equipo tendrá que desenredarlo. Para deshacer algo compartido, usa revert.

--hard sobrescribe tu carpeta sin preguntar. Si tenías cambios sin commit, se pierden de verdad: no están en ningún commit, así que Git no puede devolvértelos. Antes de usarlo, haz git status y, si hay algo que quieras conservar, haz un commit o un git stash.

La red de seguridad: git reflog

Git anota en un registro privado cada vez que HEAD se mueve: commits, cambios de rama, resets. Ese registro es el reflog y te salva cuando un reset se llevó commits que sí querías:

$ git reflog
3f2a9c1 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2
8b1e0d4 HEAD@{1}: commit: fix: evita el doble salto en el aire
a3f9c2e HEAD@{2}: commit: feat: añade el salto
$ git reset --hard 8b1e0d4       # vuelve a donde estabas antes del reset

Los commits que ninguna rama señala no se borran enseguida: el reflog los conserva, por defecto, al menos 30 días. Lo que el reflog no puede salvar son los cambios que nunca estuvieron en un commit.

Apartar cambios a medias: git stash

Estás a mitad de algo y te piden arreglar un error urgente en otra rama. No quieres hacer un commit de trabajo a medias. git stash («guardar en un escondite») aparta tus cambios y deja la carpeta limpia; git stash pop los devuelve:

$ git stash
Saved working directory and index state WIP on main: 8b1e0d4 fix: evita el doble salto en el aire
$ git switch arreglo-urgente     # arreglas, haces commit…
$ git switch main
$ git stash pop                  # tus cambios a medias vuelven

git stash list muestra lo que tienes apartado. Úsalo para pausas cortas: un stash olvidado durante semanas es fácil de perder de vista.

La terminal de práctica tiene git restore y git restore --staged, pero no revert, reset, reflog ni stash. Para practicarlos sin riesgo, crea en tu computadora una carpeta de pruebas con git init, haz tres o cuatro commits de un archivo de texto y deshazlos de todas las formas que acabas de ver.

Ramas: líneas de trabajo paralelas

Tu juego funciona y quieres empezar el nivel 2. Va a llevarte una semana, y durante esa semana el código estará a medias. Mientras tanto, alguien encuentra un error en el nivel 1 que hay que arreglar ya. Si todo está en la misma línea de commits, el arreglo tendría que convivir con tu nivel 2 roto. Las ramas resuelven esto: cada línea de trabajo avanza por su lado y se juntan cuando están listas.

Una rama es una etiqueta

Mucha gente imagina que crear una rama copia el proyecto entero. No: una rama es solo un nombre que apunta a un commit. Crearla es instantáneo y no ocupa casi nada. Mira qué pasa:

Piensa en un libro de «elige tu propia aventura». Las páginas son los commits y cada una dice de qué página vienes. Una rama es un marcapáginas con nombre: puedes tener varios en distintos caminos del libro, y moverte de uno a otro. La analogía falla en que en Git tú escribes las páginas nuevas mientras lees, y el marcapáginas avanza solo cada vez que escribes una.

Los comandos de las ramas

ComandoQué hace
git branchLista las ramas; la actual lleva un *
git branch nivel-2Crea la rama, pero te deja donde estabas
git switch nivel-2Te cambia a esa rama (y cambia tus archivos)
git switch -c nivel-2Crea la rama y te cambia a ella (-c de create). Es lo más habitual
git branch -d nivel-2Borra la rama. Git se niega si tiene commits que no se han fusionado; -D la borra igual
git branch -m nombre-nuevoCambia el nombre de la rama actual

En tutoriales y respuestas antiguas verás git checkout nivel-2 y git checkout -b nivel-2. Hacen lo mismo que switch y switch -c. El comando checkout hacía demasiadas cosas distintas (cambiar de rama, recuperar archivos, viajar a commits), por eso Git lo dividió en switch y restore. Los tres seguirán existiendo; usa los nuevos, que son más claros.

Los nombres de rama no pueden tener espacios. Es costumbre usar minúsculas y guiones, a veces con un prefijo que indica el tipo de trabajo: nivel-2, feat/marcador, fix/doble-salto, docs/instalacion.

Sigue paso a paso qué pasa con las ramas y con tu carpeta en una sesión real:

git branch
git switch -c nivel-2
echo "const jefe = 'Dragón';" > nivel2.js
git add nivel2.js
git commit -m "feat: añade el jefe del nivel 2"
git switch main
ls
git branch

Si tienes cambios sin commit en un archivo que es distinto en la otra rama, Git no te deja cambiar: error: Your local changes to the following files would be overwritten by checkout. Te protege de perder trabajo. Haz un commit con esos cambios, apártalos con git stash, o descártalos con git restore si no los quieres. Si los cambios no chocan con la otra rama, Git te deja cambiar y se los lleva contigo: no se quedan «guardados» en la rama anterior, porque todavía no están en ningún commit.

Git por dentro, en 15 líneas

Este taller construye un repositorio de juguete con objetos de JavaScript, como los de la Estación 11. Cada commit guarda su mensaje y el identificador de su padre; las ramas son un objeto que asocia un nombre con un identificador. La función log hace lo mismo que git log: empieza en el commit de la rama y sigue a los padres hasta llegar al primero. Predice qué imprimirá cada log antes de ejecutar.

Fíjate en dos cosas. Los dos log comparten el final (desde 8b1e0d4 hacia atrás): esa es la historia común de las ramas. Y para «hacer un commit» basta con crear un objeto que apunte al commit actual y mover la etiqueta de la rama. Git real guarda además la foto de los archivos, el autor y la fecha, y calcula el identificador con un hash, pero la estructura es esta: un grafo de commits como los de la Estación 19, y unas etiquetas que lo señalan.

Ahora hazlo en la terminal. Esta vez tú decides cuándo mirar la carpeta:

  1. Prepara el escenario: cd juego, git init, git add . y git commit -m "feat: primera versión".
  2. Crea la rama nivel-2 y cámbiate a ella con un solo comando.
  3. Crea el archivo del nivel: echo "const jefe = 'Dragón';" > nivel2.js, prepáralo y haz commit con el mensaje feat: añade el jefe del nivel 2.
  4. Vuelve a main y comprueba con ls que nivel2.js no está. Termina con git branch para ver las dos ramas.

Si ahora escribes git switch nivel-2 y ls, verás que nivel2.js vuelve. Tu carpeta siempre muestra la foto de la rama en la que estás.

Fusionar ramas y resolver conflictos

El nivel 2 está terminado y probado. Ahora hay que llevar sus commits a main. Eso es fusionar (en inglés, merge). La regla para no confundirse: te pones en la rama que recibe los cambios y le pides que traiga la otra.

$ git switch main
$ git merge nivel-2

Lo que pasa a continuación depende de si main avanzó mientras tú trabajabas en nivel-2:

En el primer caso, llamado avance rápido (fast-forward), no hay nada que combinar: los commits de nivel-2 ya vienen detrás del último de main, así que Git solo mueve la etiqueta:

$ git merge nivel-2
Updating 8b1e0d4..9a8b7c6
Fast-forward
 nivel2.js | 12 ++++++++++++
 1 file changed, 12 insertions(+)
 create mode 100644 nivel2.js

En el segundo, Git mira qué cambió cada rama desde su antepasado común (el último commit que comparten, B en el dibujo) y aplica los dos grupos de cambios. Si tocaron archivos distintos, o partes distintas del mismo archivo, lo hace solo y crea el commit de fusión, con un mensaje propuesto como Merge branch 'nivel-2':

$ git merge nivel-2
Merge made by the 'ort' strategy.
 nivel2.js | 12 ++++++++++++
 1 file changed, 12 insertions(+)

ort es el nombre del algoritmo que Git usa para fusionar. Si Git abre el editor para confirmar el mensaje del commit de fusión, guárdalo tal cual y ciérralo (en Vim, Esc y :wq). Después, si ya no necesitas la rama, bórrala con git branch -d nivel-2: sus commits siguen en main, solo desaparece la etiqueta.

Cómo decide Git

Este taller hace, línea por línea, lo mismo que Git: compara cada línea de las dos ramas con la del antepasado común. Si una rama no tocó una línea, gana la versión de la otra. Predice el resultado y ejecuta.

Con las versiones iniciales, main cambió vidas y nivel-2 cambió velocidad: cada línea la cambió una sola rama, así que el resultado lleva los dos cambios. Si las dos ramas cambian la misma línea de forma distinta, la función no puede elegir y escribe las dos versiones entre marcas. Git hace lo mismo, con dos diferencias: trabaja con bloques de líneas que pueden crecer o encogerse (no exige que las versiones tengan las mismas líneas) y considera en conflicto también los cambios en líneas pegadas entre sí.

Conflictos: cuando Git necesita que decidas

Un conflicto aparece cuando las dos ramas cambiaron las mismas líneas de forma distinta, o cuando una borró un archivo que la otra modificó. No es un error ni significa que hiciste algo mal: Git no sabe qué versión quieres y te lo pregunta. Pasa a menudo en cualquier equipo.

Durante un conflicto, git status te dice exactamente en qué punto estás y qué hacer:

$ git merge titulo-nuevo
Auto-merging titulo.txt
CONFLICT (content): Merge conflict in titulo.txt
Automatic merge failed; fix conflicts and then commit the result.
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   titulo.txt

both modified significa «modificado por las dos ramas». Los pasos para resolverlo son siempre los mismos:

  1. Mira qué archivos tienen conflicto con git status (sección Unmerged paths).

  2. Abre cada archivo y busca las marcas <<<<<<<. Puede haber varios bloques en un mismo archivo. Decide el contenido final de cada bloque y borra las marcas. Si dudas qué quería la otra persona, pregúntale: resolver a ciegas es la forma más rápida de romper algo.

  3. Prueba que el programa sigue funcionando. Un archivo sin marcas no es lo mismo que un archivo correcto.

  4. Marca cada archivo como resuelto con git add archivo.

  5. Termina la fusión con git commit. Git propone un mensaje como Merge branch 'titulo-nuevo'; puedes dejarlo así.

Si te lías y prefieres empezar de nuevo, git merge --abort cancela la fusión y deja todo como estaba antes del git merge.

Cuando abres un archivo con conflicto, VS Code colorea los dos bloques y muestra encima unos botones: Accept Current Change (quedarte con tu versión), Accept Incoming Change (la de la otra rama), Accept Both Changes (las dos, una detrás de otra) y Compare Changes. También puedes pulsar Resolve in Merge Editor para ver las dos versiones lado a lado y el resultado debajo. Son atajos para editar el archivo: la decisión sigue siendo tuya.

El error más común es hacer git add y git commit con alguna marca todavía dentro del archivo. Git no lo comprueba: guarda lo que le das. El programa deja de funcionar con un error de sintaxis extraño en una línea que empieza por <<<<<<<. Antes del git add, busca en el archivo (Ctrl + F) los caracteres <<< y >>>.

Ahora provoca un conflicto tú y resuélvelo:

  1. Prepara el escenario: cd juego, git init, git add . y git commit -m "feat: primera versión".
  2. En una rama nueva, titulo-nuevo, cambia el título con echo "El bosque de cristal" > titulo.txt y haz commit.
  3. Vuelve a main, cambia el título con echo "El bosque perdido" > titulo.txt y haz commit.
  4. Fusiona: git merge titulo-nuevo. Mira el archivo con cat titulo.txt.
  5. Resuélvelo con un título que combine los dos, sin marcas: echo "El bosque de cristal perdido" > titulo.txt. Márcalo como resuelto con git add y termina con git commit -m "merge: une los dos títulos".

La terminal de práctica simplifica los conflictos: marca el archivo entero aunque solo cambie una línea, deja alguna línea en blanco de más entre las marcas, y su git status muestra el archivo como modified en vez de both modified. Los pasos para resolverlo son los mismos que en tu computadora.

Repasa el orden de los pasos:

  1. git switch main
  2. git merge titulo-nuevo
  3. git status
  4. # edita titulo.txt: deja el texto final y borra las marcas
  5. git add titulo.txt
  6. git commit -m "merge: une los dos títulos"

Menos conflictos

Los conflictos no se pueden evitar del todo, pero sí hacerlos pequeños y raros:

  • Ramas cortas. Una rama que vive dos días choca poco. Una que vive dos meses choca con todo.
  • Trae main a tu rama a menudo: estando en tu rama, git merge main. Resuelves los choques de uno en uno, cuando son pequeños, y no todos juntos al final.
  • No reformatees archivos enteros en la misma rama que un cambio de lógica. Cambiar la sangría de 400 líneas hace que todas choquen con el trabajo de los demás.
  • Habla con tu equipo antes de tocar a fondo un archivo que usa todo el mundo.

Rebase, solo para que lo reconozcas

Hay otra forma de juntar ramas: git rebase («cambiar la base»). En vez de crear un commit de fusión, toma tus commits de la rama y los vuelve a aplicar, uno por uno, encima del último commit de main, como si hubieras empezado a trabajar después. El historial queda en una línea recta, sin commits de fusión.

$ git switch nivel-2
$ git rebase main          # tus commits de nivel-2 se reescriben encima de main

El precio: los commits reaplicados son commits nuevos, con otros hashes. Es reescribir la historia, así que se aplica la regla de oro: nunca hagas rebase de commits que otras personas ya tienen. Muchos equipos lo usan para ordenar su rama antes de proponerla, y GitHub ofrece fusionar con rebase desde un botón, como verás. Hasta que te sientas cómodo con merge y con los conflictos, usa merge: es más fácil de entender y de deshacer.

Remotos: otras copias de tu repositorio

Un remoto es otra copia del mismo repositorio, en otro lugar, a la que le das un nombre corto. Por convención, el remoto principal se llama origin («origen»). Tu repositorio guarda su dirección y la usa cuando envías o recibes commits. git remote -v los lista:

$ git remote -v
origin  https://github.com/ana-perez/mi-juego.git (fetch)
origin  https://github.com/ana-perez/mi-juego.git (push)

Aparece dos veces porque podrías recibir de un sitio y enviar a otro; casi siempre es la misma dirección.

Subir un proyecto que ya tienes

  1. En GitHub, pulsa el botón + de arriba a la derecha y elige New repository. Escribe el nombre (el de tu carpeta, sin espacios: mi-juego), una descripción corta y elige Public (cualquiera puede verlo) o Private (solo tú y quien invites).

  2. Como el proyecto ya existe en tu computadora, deja el repositorio vacío: no añadas README, .gitignore ni licencia. Si GitHub crea un commit con esos archivos, su historia y la tuya empiezan distinto y el primer envío falla. Pulsa Create repository.

  3. GitHub te muestra una página con instrucciones. En la parte …or push an existing repository from the command line están los comandos, ya con tu dirección. Ejecútalos dentro de la carpeta del proyecto:

    $ git remote add origin https://github.com/ana-perez/mi-juego.git
$ git branch -M main
$ git push -u origin main

Qué hizo cada comando: git remote add origin URL registra el remoto con el nombre origin. git branch -M main se asegura de que tu rama se llame main (si ya se llamaba así, no hace nada). git push -u origin main envía la rama main al remoto origin; la opción -u (upstream) deja anotado que tu main se corresponde con el main de GitHub. HTTPS en Windows. Git para Windows incluye Git Credential Manager, un gestor de credenciales. En tu primer push se abre una ventana para iniciar sesión en GitHub desde el navegador. Autorizas, y el gestor recuerda la credencial. No tienes que hacer nada más.

HTTPS en macOS y Linux. Lo más cómodo es instalar la herramienta oficial de GitHub para la terminal, GitHub CLI (el comando gh, desde cli.github.com), y ejecutar una vez:

$ gh auth login

Te hará unas preguntas: elige GitHub.com, el protocolo HTTPS, responde Yes a autenticar Git con tus credenciales de GitHub y elige iniciar sesión con el navegador. Te muestra un código de un solo uso, lo pegas en la página que se abre, y listo: Git queda autenticado.

Con un token. Si Git te pide usuario y contraseña, en la contraseña no va tu contraseña: va un token de acceso personal (personal access token), una clave larga que creas en GitHub con permisos limitados y fecha de caducidad. Se crea en Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token. GitHub recomienda los fine-grained («de permisos finos») frente a los clásicos: elige una caducidad, solo los repositorios que necesites y, en los permisos, Contents: Read and write para poder hacer push. Copia el token en cuanto lo veas: GitHub no vuelve a mostrarlo.

Trata un token como una contraseña. No lo pegues en el código, ni en un chat, ni en un issue. Si se filtra, bórralo en la misma página de GitHub y crea otro. Que caduque es una ventaja: un token olvidado deja de ser peligroso solo.

SSH. Si prefieres claves SSH, estos son los pasos de la documentación de GitHub:

  1. Genera un par de claves con el algoritmo Ed25519. Pulsa Enter para aceptar la ubicación propuesta y escribe una frase de contraseña (passphrase) para proteger la clave privada:

    $ ssh-keygen -t ed25519 -C "123456+ana-perez@users.noreply.github.com"

  2. Añade la clave al agente SSH, un programa que la recuerda para no pedirte la frase en cada push. En Git Bash, macOS y Linux: eval "$(ssh-agent -s)" y después ssh-add ~/.ssh/id_ed25519. En macOS, la documentación recomienda ssh-add --apple-use-keychain ~/.ssh/id_ed25519 para guardarla en el llavero.

  3. Muestra la clave pública (termina en .pub) con cat ~/.ssh/id_ed25519.pub, cópiala y pégala en GitHub, en Settings → SSH and GPG keys → New SSH key. La clave privada, la que no termina en .pub, no se comparte nunca.

  4. Comprueba la conexión. La primera vez te preguntará si confías en el servidor: compara la huella que muestra con la que publica GitHub en su documentación (la de Ed25519 es SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU) y responde yes:

    $ ssh -T git@github.com
Hi ana-perez! You've successfully authenticated, but GitHub does not provide shell access.

    Ese mensaje significa que todo está bien. Desde ahora usa las direcciones que empiezan por git@github.com:.

Traer un repositorio: git clone

Para trabajar en un repositorio que ya está en GitHub (tuyo desde otra computadora, o de otra persona), lo clonas: descargas una copia completa, con toda su historia. En la página del repositorio, el botón verde Code te da la dirección:

$ cd ~/proyectos
$ git clone https://github.com/ana-perez/mi-juego.git
Cloning into 'mi-juego'...
remote: Enumerating objects: 9, done.
Receiving objects: 100% (9/9), done.
$ cd mi-juego

git clone crea la carpeta, descarga todos los commits, configura el remoto origin con esa dirección y te deja en la rama principal. No hace falta git init: el repositorio ya viene hecho.

Sincronizar: push, fetch y pull

Tu repositorio y el de GitHub no se sincronizan solos. Tú decides cuándo enviar y cuándo recibir. Para saber cómo estaba GitHub la última vez que hablaste con él, Git guarda unas etiquetas especiales, las ramas de seguimiento remoto, con nombres como origin/main. Son de solo lectura: se mueven cuando te comunicas con GitHub.

ComandoQué hace¿Cambia tus archivos?
git pushEnvía tus commits nuevos de la rama actual a GitHubNo
git fetchDescarga los commits nuevos de GitHub y actualiza origin/main y compañíaNo: es seguro en cualquier momento
git pullgit fetch y después junta origin/main con tu ramaSí, puede traer cambios y, a veces, conflictos
git push -u origin nombre-ramaSube una rama nueva por primera vez y la asocia con la de GitHubNo

Después de un git fetch, git status te dice en qué situación estás respecto a GitHub:

  • Your branch is up to date with 'origin/main': estás al día.
  • Your branch is ahead of 'origin/main' by 2 commits: tienes 2 commits que GitHub no tiene. Te toca git push.
  • Your branch is behind 'origin/main' by 3 commits, and can be fast-forwarded: GitHub tiene 3 commits que tú no. Te toca git pull.
  • Your branch and 'origin/main' have diverged: tú y GitHub tienen commits que el otro no tiene. Hay que juntarlos con git pull y, si hace falta, resolver conflictos.

Cuando push se niega

Si Leo subió commits a main después de tu último pull, tu push será rechazado:

$ git push
To https://github.com/ana-perez/mi-juego.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/ana-perez/mi-juego.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.

No es un fallo: Git impide que tu push borre los commits de Leo. La solución es la que propone el mensaje: git pull para traer y juntar su trabajo con el tuyo (resolviendo conflictos si los hay) y después git push.

La primera vez que las dos historias se hayan separado, puede que git pull se detenga con el mensaje You have divergent branches and need to specify how to reconcile them. Git quiere que elijas, una sola vez, cómo juntar las historias en un pull. Para empezar, elige fusionar (merge), que es lo que ya conoces:

$ git config --global pull.rebase false
$ git pull

Buscando cómo arreglar un push rechazado, encontrarás el consejo de usar git push --force. Fuerza a GitHub a aceptar tu versión borrando los commits que tú no tienes: el trabajo de Leo desaparecería de GitHub. En ramas compartidas no lo uses nunca. Si algún día necesitas forzar en una rama que solo usas tú (por ejemplo, después de un rebase), usa git push --force-with-lease, que se niega si alguien subió algo que no has visto.

Una rutina que evita la mayoría de los sustos: al empezar a trabajar, git pull; al terminar cada tarea, commit y git push. Cuanto más tiempo pasa entre un pull y un push, más probable es que alguien haya tocado lo mismo que tú.

La terminal de práctica no tiene conexión a internet, así que git remote, push, pull, fetch y clone no funcionan en ella. Practícalos en tu computadora con un repositorio de prueba en GitHub: el proyecto de esta estación te guía paso a paso.

Pull requests, revisiones e issues

Con ramas y un repositorio en GitHub ya tienes las piezas para trabajar en equipo. Falta el acuerdo: ¿quién puede meter cambios en main, cuándo y cómo? Si cada persona fusiona lo suyo cuando le parece, main se rompe cada dos por tres. La respuesta de GitHub es el pull request.

GitHub flow

El flujo de trabajo más extendido en equipos pequeños y medianos se llama GitHub flow. Tiene una regla central, main siempre funciona, y seis pasos:

  1. Crea una rama desde un main actualizado, con un nombre corto y descriptivo: git switch main, git pull, git switch -c feat/marcador.

  2. Haz commits en esa rama y súbela a GitHub: la primera vez con git push -u origin feat/marcador, después con git push. Subirla pronto sirve también de copia de seguridad.

  3. Abre un pull request para pedir que revisen tus cambios.

  4. Atiende la revisión: responde, haz commits con los ajustes y súbelos. El pull request se actualiza solo.

  5. Fusiona el pull request cuando esté aprobado. Tus cambios llegan a main.

  6. Borra la rama, que ya cumplió su función. En tu computadora: git switch main, git pull y git branch -d feat/marcador.

Hay más formas de organizarse. Git flow usa ramas fijas para desarrollo, versiones y arreglos urgentes; nació para programas con versiones que se publican cada cierto tiempo, y hoy muchos equipos lo consideran demasiado pesado. En el desarrollo basado en el tronco (trunk-based development) las ramas duran horas y se fusionan a main varias veces al día. GitHub flow es un buen punto de partida: sencillo y suficiente para casi cualquier proyecto personal o de equipo pequeño.

Qué es un pull request

Un pull request (PR, «solicitud de incorporación») es una propuesta en GitHub: «quiero fusionar la rama feat/marcador en main; aquí están los cambios, revísenlos». Es una página con tres partes: la conversación (descripción y comentarios), la lista de commits y los archivos cambiados, con su diff. En GitLab se llama merge request; es lo mismo.

Para crear uno, sube tu rama. GitHub mostrará un aviso amarillo en la página del repositorio con el botón Compare & pull request (también puedes ir a la pestaña Pull requests y pulsar New pull request). Comprueba arriba que la rama base (base) es main y la que comparas (compare) es la tuya, y escribe:

  • Un título que diga qué hace, igual que un buen mensaje de commit: feat: añade el marcador de puntos.
  • Una descripción que responda: qué cambia, por qué y cómo probarlo. Si hay algo visual, una captura.

GitHub escribe estos textos en Markdown, un formato de texto sencillo: ## al principio de una línea hace un título, - una lista, y el texto entre comillas invertidas se ve como código. Una buena descripción:

## Qué cambia
Añade un marcador de puntos en la esquina superior derecha.

## Por qué
Los jugadores no sabían cuántos puntos llevaban (lo pedían en el issue #12).

## Cómo probarlo
1. Abre index.html en el navegador.
2. Recoge tres monedas: el marcador debe mostrar 30.

Closes #12

La última línea tiene truco. Si la descripción incluye Closes #12 (o Fixes #12, Resolves #12 y sus variantes), cuando el PR se fusione en la rama principal, GitHub cerrará automáticamente el issue número 12. Verás qué es un issue enseguida.

Si todavía no has terminado pero quieres enseñar el trabajo o pedir opinión, abre el PR como borrador: en el botón de crear, elige Create draft pull request. Nadie podrá fusionarlo hasta que pulses Ready for review.

Revisar código en GitHub

La revisión de código (code review) es que otra persona lea tus cambios antes de que lleguen a main. Encuentra errores, pero sobre todo reparte el conocimiento: después de revisar, dos personas entienden ese código. Así se revisa en GitHub:

  1. En el PR, abre la pestaña Files changed («archivos cambiados»): verás el diff de cada archivo, en rojo lo quitado y en verde lo añadido.

  2. Pasa el ratón sobre una línea y pulsa el + azul para comentarla. Puedes arrastrar para seleccionar varias líneas. Elige Start a review para agrupar todos tus comentarios en una sola revisión.

  3. Si sabes exactamente cómo debería quedar una línea, propón el cambio con una sugerencia: el botón de sugerencia del comentario escribe un bloque así, que el autor puede aceptar con un clic.

    ```suggestion
if (enSuelo && teclaSaltoPulsada) {
```

  4. Termina con el botón de enviar la revisión (Submit review) y elige una de tres opciones: Comment (solo comentarios), Approve (aprobado, se puede fusionar) o Request changes (hay que cambiar algo antes de fusionar).

Quien hizo el PR responde a cada comentario, sube commits con los arreglos a la misma rama y marca las conversaciones como resueltas (Resolve conversation). No hace falta abrir otro PR: el mismo se actualiza con cada push.

Los PR pequeños se revisan bien; los enormes se aprueban sin leer. Apunta a menos de unas 300 líneas cambiadas por PR. Y comenta el código, no a la persona: «este bucle recorre la lista dos veces, ¿podríamos hacerlo en una?» funciona mejor que «esto está mal». Cómo dar y recibir comentarios de revisión, y cómo organizar un equipo, lo verás a fondo en la Estación 27.

Fusionar el pull request

Cuando el PR está aprobado, el botón verde de fusionar ofrece tres opciones:

OpciónQué haceHistorial resultante
Create a merge commitFusiona con un commit de fusión, como git mergeConserva todos los commits de la rama y deja ver dónde se juntó
Squash and mergeAplasta (squash) todos los commits de la rama en uno solo y lo añade a mainUn commit por PR: main queda muy limpio, pero se pierde el detalle de los commits intermedios
Rebase and mergeReaplica los commits de la rama encima de main, uno por unoLínea recta, sin commits de fusión

Cada equipo elige una y la usa siempre. Squash and merge es muy popular: permite hacer commits desordenados mientras trabajas en la rama y deja en main un solo commit con un buen mensaje. Después de fusionar, GitHub ofrece el botón Delete branch para borrar la rama en GitHub. Recuerda actualizar tu copia local: git switch main, git pull y git branch -d feat/marcador (si usaste squash, Git no reconoce la rama como fusionada y tendrás que usar -D).

Mientras no tengas un equipo, puedes practicar todo el flujo en tu computadora: la rama, los commits, y la fusión que haría GitHub al aprobar el PR.

  1. Prepara el escenario: cd juego, git init, git add . y git commit -m "feat: primera versión".
  2. Crea la rama feat/marcador y haz en ella dos commits con mensajes de Conventional Commits: el primero después de echo "let puntos = 0;" > marcador.js y el segundo después de echo "console.log('Puntos:', puntos);" >> marcador.js.
  3. Imagina que el PR está aprobado. Haz lo que haría el botón de fusionar: vuelve a main y fusiona la rama.
  4. Borra la rama, que ya no hace falta, y mira el historial con git log --oneline.

Fue un avance rápido: main no tenía commits nuevos, así que su etiqueta solo avanzó. En GitHub, con la opción Create a merge commit, se habría creado además un commit de fusión, porque GitHub la hace siempre así para que quede constancia del PR.

Ahora ordena el flujo completo, incluidos los pasos que se hacen en la web de GitHub:

  1. git switch main
  2. git pull
  3. git switch -c fix/doble-salto
  4. git commit -am "fix: evita el doble salto"
  5. git push -u origin fix/doble-salto
  6. # en GitHub: abre el pull request y pide revisión
  7. # en GitHub: tras la aprobación, pulsa Merge pull request

git commit -am es un atajo: prepara todos los archivos que Git ya seguía y que modificaste (no los nuevos) y hace el commit en un solo paso.

Contribuir a un proyecto ajeno: forks

En tu repositorio, o en uno donde te han dado permiso, puedes crear ramas directamente. Pero en un proyecto de otra persona (un juego de código abierto, una librería) no tienes permiso para escribir. Para eso existe el fork («bifurcación»): una copia del repositorio en tu cuenta de GitHub, donde sí puedes escribir, desde la que propones cambios al original con un pull request.

  1. En la página del repositorio original, pulsa Fork y después Create fork. Aparece una copia en tu cuenta.

  2. Clona tu fork (no el original) con git clone https://github.com/ana/juego.git.

  3. Crea una rama y trabaja en ella, con commits como siempre.

  4. Sube la rama a tu fork: git push -u origin mi-rama.

  5. En GitHub, abre el pull request desde tu fork hacia el original (GitHub te lo ofrece con el botón Compare & pull request o Contribute). Las personas que mantienen el proyecto lo revisarán.

Mientras trabajas, el original sigue avanzando. Para traer sus cambios, registra el original como un segundo remoto, al que por costumbre se llama upstream:

$ git remote add upstream https://github.com/equipo/juego.git
$ git fetch upstream
$ git switch main
$ git merge upstream/main
$ git push                     # actualiza también tu fork en GitHub

GitHub también tiene un botón Sync fork en la página de tu fork que actualiza la copia de GitHub; después haces git pull en tu computadora. Antes de contribuir a un proyecto, lee su archivo CONTRIBUTING.md si lo tiene: explica cómo quieren recibir los cambios. Tu primera contribución al código abierto la planificarás en la Estación 39.

Issues: la lista de tareas del proyecto

Un issue («asunto», «incidencia») es una ficha en la pestaña Issues del repositorio para anotar un error, pedir una funcionalidad o discutir una idea. Cada uno tiene un número (#12), una conversación, y puede tener etiquetas (labels, como bug, enhancement o good first issue, «buena primera tarea») y personas asignadas (assignees). Si escribes #12 en un commit, en un PR o en otro issue, GitHub crea un enlace automático.

Un buen issue de error permite reproducirlo sin preguntar nada:

Título: El personaje atraviesa el suelo en el nivel 2

Pasos para reproducirlo:
1. Empieza el nivel 2.
2. Salta sobre la plataforma que se mueve.
3. Espera a que baje.

Qué esperaba: que el personaje se quedara encima.
Qué pasa: cae a través de la plataforma y pierde una vida.
Navegador: Firefox 143 en Windows 11.

Con muchos issues, conviene verlos como un tablero. GitHub Projects (pestaña Projects) organiza issues y PR en columnas como «Por hacer», «En curso» y «Hecho», o en tablas y calendarios. Cómo planificar el trabajo con tableros, historias de usuario y prioridades es tema de la Estación 27.

Trabajar en equipo sin pisarse

Reglas que usan los equipos que trabajan a gusto con Git:

  • Nadie hace commits directamente en main. Todo entra por PR. En Settings → Rules (o Branches) puedes crear una regla que lo imponga: exigir PR, exigir una aprobación, bloquear el push --force.
  • Una tarea, una rama, un PR, y a poder ser, un issue asignado. Así todo el mundo sabe quién está con qué y nadie hace el mismo trabajo dos veces.
  • Ramas cortas y PR pequeños. Menos conflictos, revisiones mejores.
  • Pull antes de empezar y push al terminar. Y trae main a tu rama si pasan días.
  • No reescribas historia compartida: nada de reset, rebase ni push --force en ramas que usan otras personas.
  • Un .gitignore desde el primer commit, y nunca secretos en el repositorio.
  • Mensajes y descripciones que se entiendan sin estar en tu cabeza.

Publica tu web con GitHub Pages

Llevas desde la Estación 13 haciendo páginas que solo ves tú. GitHub Pages es un servicio de GitHub que publica en internet, gratis, los archivos HTML, CSS y JavaScript de un repositorio. Cada vez que haces push, la web se actualiza sola. Es ideal para tu portafolio, la página de un juego hecho en JavaScript o la documentación de un proyecto.

Tiene un límite importante: solo sirve webs estáticas, es decir, archivos que se envían tal cual al navegador. No ejecuta código en el servidor ni tiene base de datos. Un juego en JavaScript funciona perfectamente; una app con usuarios y contraseñas guardados en un servidor, no. Los servidores los construirás en la Estación 29.

Paso a paso

  1. Ten un repositorio en GitHub con un archivo index.html en la raíz: es la página que se abre al entrar en la web. El nombre tiene que ser exactamente ese, en minúsculas. En el plan gratuito, el repositorio tiene que ser público.

  2. En el repositorio, entra en Settings («configuración») y, en la barra lateral, en Pages.

  3. En Build and deployment, en Source, elige Deploy from a branch («publicar desde una rama»). En Branch, elige main y la carpeta / (root) (o /docs, si tu web está en esa carpeta). Pulsa Save.

  4. Espera. La primera publicación tarda uno o dos minutos, y GitHub avisa de que un cambio puede tardar hasta 10 minutos en verse. Recarga la página de ajustes: arriba aparecerá Your site is live at con la dirección.

  5. A partir de ahora, cada git push a main vuelve a publicar la web. En la pestaña Actions puedes ver cómo va cada publicación.

La dirección depende del nombre del repositorio:

RepositorioDirección de la webUso típico

ana-perez/ana-perez.github.iohttps://ana-perez.github.io/Tu web personal (user site). Solo hay una por cuenta y el repositorio tiene que llamarse exactamente así

La otra opción de Source, GitHub Actions, sirve para webs que hay que construir antes de publicar (por ejemplo, hechas con React). Las automatizaciones con GitHub Actions, otros servicios de publicación y los dominios propios (como anaperez.dev) los verás en la Estación 35.

Por qué funciona en tu computadora y no en GitHub Pages

El problema más habitual al publicar: la página se ve, pero sin estilos, sin imágenes o con enlaces que dan error 404 («no encontrado»). Casi siempre es por las rutas. Repasa las rutas relativas de la Estación 13 y estas causas:

Al publicar desde una rama, GitHub Pages procesa los archivos con Jekyll, un generador de webs que ignora las carpetas que empiezan por _. Si tu web tiene una carpeta como _recursos y no aparece, crea un archivo vacío llamado .nojekyll en la raíz del repositorio.

En este taller, la página de un portafolio tiene rutas que funcionan en la computadora de Ana y fallarían al publicarla. Los archivos del repositorio son index.html, proyectos.html, contacto.html e img/logo.png. Ejecuta, lee el diagnóstico de la consola y arregla las rutas en la pestaña HTML hasta que todas estén bien.

Las cuatro rutas buenas son relativas y con el nombre exacto: img/logo.png, index.html, proyectos.html y contacto.html. Funcionan igual al abrir el archivo en tu computadora y en https://ana-perez.github.io/portafolio/, porque se cuentan desde la página en la que están.

Todo lo que publicas con GitHub Pages es público, aunque la dirección no la conozca nadie: los buscadores pueden encontrarla. No pongas datos personales que no quieras compartir, como tu teléfono o tu dirección, y respeta los derechos de las imágenes, músicas y tipografías que uses en tus proyectos.

Resumen

  • Git es un programa que guarda la historia de tu proyecto en tu computadora; GitHub es un servicio web que guarda copias de repositorios y añade colaboración: pull requests, revisiones, issues y Pages.
  • Un commit es una foto completa del proyecto con autor, fecha, mensaje y un puntero a su padre. Su hash lo identifica y cambia si cambia cualquier cosa.
  • Prepara con precisión (git add archivo, git add -p), mira antes de guardar (git status, git diff, git diff --staged) y haz un commit por cada cambio lógico, con mensajes como feat: … o fix: … (Conventional Commits).
  • .gitignore deja fuera dependencias, archivos generados, basura y secretos. No afecta a lo que ya estaba en un commit, y un secreto publicado se anula, no se borra.
  • Para deshacer: restore para archivos, restore --staged para lo preparado, revert para commits compartidos y reset solo para commits que nadie más tiene (--hard borra). reflog es la red de seguridad.
  • Una rama es una etiqueta que apunta a un commit y avanza con cada commit; HEAD dice dónde estás. git switch -c crea y cambia; tu carpeta siempre refleja la rama actual.
  • git merge se hace desde la rama que recibe. Si la otra solo va por delante, es un avance rápido; si las dos avanzaron, se crea un commit de fusión. Un conflicto se resuelve editando el archivo, borrando las marcas, git add y git commit.
  • push envía, fetch descarga sin tocar tus archivos y pull descarga y fusiona. Si push se niega, primero pull. GitHub se autentica con HTTPS (gestor de credenciales, gh o token) o con claves SSH, nunca con tu contraseña.
  • GitHub flow: rama desde main, commits, pull request, revisión, fusión y borrar la rama. Con un fork contribuyes a proyectos donde no puedes escribir. Los issues organizan el trabajo.
  • GitHub Pages publica gratis una web estática desde una rama: index.html en la raíz, rutas relativas y nombres exactos.

// Imitación simplificada de cómo decide Git (no hace falta tocarla).
function aExpresion(patron) {
  const r = patron.replace(/[.+^${}()|[\]\\]/g, "\\$&")
    .replace(/\*\*/g, "\u0000").replace(/\*/g, "[^/]*").replace(/\?/g, "[^/]").replace(/\u0000/g, ".*");
  return new RegExp("^" + r + "$");
}
function ignorado(ruta, texto) {
  const partes = ruta.split("/");
  let resultado = false;
  for (let linea of texto.split("\n")) {
    linea = linea.trim();
    if (!linea || linea.startsWith("#")) continue;
    const negar = linea.startsWith("!");
    if (negar) linea = linea.slice(1);
    const soloCarpetas = linea.endsWith("/");
    if (soloCarpetas) linea = linea.slice(0, -1);
    const anclada = linea.includes("/");
    if (linea.startsWith("/")) linea = linea.slice(1);
    const expresion = aExpresion(linea);
    const tope = soloCarpetas ? partes.length - 1 : partes.length;
    for (let i = 0; i < tope; i++) {
      const candidato = anclada ? partes.slice(0, i + 1).join("/") : partes[i];
      if (expresion.test(candidato)) resultado = !negar;
    }
  }
  return resultado;
}

¿Es un mensaje convencional?

Escribe la función esConvencional(mensaje), que devuelve true si el mensaje sigue la forma tipo(ámbito opcional)!opcional: descripción con uno de los tipos de la lista, y false si no. Reglas: el tipo va en minúsculas; el ámbito, si hay, va entre paréntesis y no está vacío; después de los dos puntos hay un espacio y una descripción no vacía.

Pista 1

Busca dónde está ": " (dos puntos y espacio) con indexOf. Si no está, el mensaje no es válido. Lo de la izquierda es la cabecera (tipo, ámbito y !) y lo de la derecha, la descripción.

Pista 2

Limpia la cabecera por partes: si termina en !, quítalo. Si tiene (, comprueba que termine en ) y que haya algo dentro, y quédate con lo que hay antes del paréntesis. Lo que quede debe estar en TIPOS (usa includes).

Ver una solución 
const TIPOS = ["feat", "fix", "docs", "style", "refactor", "perf", "test", "build", "ci", "chore"];

function esConvencional(mensaje) {
  const pos = mensaje.indexOf(": ");
  if (pos === -1) return false;
  let cabecera = mensaje.slice(0, pos);
  const descripcion = mensaje.slice(pos + 2).trim();
  if (descripcion === "") return false;
  if (cabecera.endsWith("!")) cabecera = cabecera.slice(0, -1);
  const parentesis = cabecera.indexOf("(");
  if (parentesis !== -1) {
    const ambito = cabecera.slice(parentesis + 1, -1);
    if (!cabecera.endsWith(")") || ambito === "") return false;
    cabecera = cabecera.slice(0, parentesis);
  }
  return TIPOS.includes(cabecera);
}

¿Avance rápido o commit de fusión?

Vas a programar la decisión que toma git merge. Los commits están en un objeto: cada clave es un commit y su valor, la lista de sus padres (un commit de fusión tiene dos). Escribe esAncestro(commits, posible, desde), que dice si se puede llegar a posible siguiendo padres desde desde (un commit cuenta como ancestro de sí mismo), y úsala en tipoDeFusion, que devuelve "ya actualizado" si la otra rama ya está contenida en la actual, "avance rápido" si la actual está contenida en la otra y "commit de fusión" en otro caso.

Pista 1

Es un recorrido de grafo como los de la Estación 19: una lista de pendientes que empieza con desde; sacas uno, si es posible devuelves true, y si no, añades sus padres a la lista. Usa un Set de visitados para no repetir.

Pista 2

Si otra es ancestro de actual, no hay nada que traer: «ya actualizado». Si actual es ancestro de otra, basta con mover la etiqueta: «avance rápido». Pregunta en ese orden.

Ver una solución 
// La historia: A, B, C y D en fila. De B sale otra rama con X e Y.
// M es un commit de fusión: sus padres son D e Y.
const commits = { A: [], B: ["A"], C: ["B"], D: ["C"], X: ["B"], Y: ["X"], M: ["D", "Y"] };

function esAncestro(commits, posible, desde) {
  const pendientes = [desde];
  const vistos = new Set();
  while (pendientes.length > 0) {
    const id = pendientes.pop();
    if (id === posible) return true;
    if (vistos.has(id)) continue;
    vistos.add(id);
    for (const padre of commits[id]) pendientes.push(padre);
  }
  return false;
}

function tipoDeFusion(commits, actual, otra) {
  if (esAncestro(commits, otra, actual)) return "ya actualizado";
  if (esAncestro(commits, actual, otra)) return "avance rápido";
  return "commit de fusión";
}

console.log(tipoDeFusion(commits, "C", "D"));
console.log(tipoDeFusion(commits, "D", "C"));
console.log(tipoDeFusion(commits, "D", "Y"));
console.log(tipoDeFusion(commits, "Y", "M"));
console.log(tipoDeFusion(commits, "M", "X"));
console.log(tipoDeFusion(commits, "C", "C"));

El caso "Y", "M" comprueba que sigues todos los padres: a Y solo se llega desde M por su segundo padre. Git hace este mismo recorrido, con millones de commits y muchas optimizaciones, cada vez que fusionas.

La siguiente versión

Escribe siguienteVersion(version, mensajes): recibe la versión actual ("1.4.2") y los mensajes de commit desde la última publicación, y devuelve la siguiente versión según SemVer y Conventional Commits. Si algún mensaje rompe compatibilidad (! antes de los dos puntos, o una línea BREAKING CHANGE:), sube el mayor y pone los otros dos a 0. Si no, y hay algún feat, sube el menor y pone el parche a 0. Si no, y hay algún fix, sube el parche. Si no hay nada de eso, la versión no cambia.

Pista 1

Separa la versión con version.split(".").map(Number): obtienes [1, 4, 2]. Al final, únela con join("."). Ojo: 1.9.9 más un feat es 1.10.0, no 2.0.0. Son números, no dígitos.

Pista 2

Recorre los mensajes una vez y anota tres booleanos: rompe, hayFeat y hayFix. La cabecera es lo que hay antes del primer ":"; rompe si termina en ! o si el mensaje incluye "BREAKING CHANGE:". Es feat si la cabecera empieza por "feat".

Ver una solución 
function siguienteVersion(version, mensajes) {
  let [mayor, menor, parche] = version.split(".").map(Number);
  let rompe = false, hayFeat = false, hayFix = false;
  for (const mensaje of mensajes) {
    const cabecera = mensaje.split(":")[0];
    if (cabecera.endsWith("!") || mensaje.includes("BREAKING CHANGE:")) rompe = true;
    if (cabecera.startsWith("feat")) hayFeat = true;
    if (cabecera.startsWith("fix")) hayFix = true;
  }
  if (rompe) return [mayor + 1, 0, 0].join(".");
  if (hayFeat) return [mayor, menor + 1, 0].join(".");
  if (hayFix) return [mayor, menor, parche + 1].join(".");
  return version;
}

console.log(siguienteVersion("1.4.2", ["feat(guardado)!: nuevo formato de partidas", "fix: corrige el menú"]));

¿Qué afirmación sobre Git y GitHub es correcta?

  1. GitHub es la versión nueva de Git.

    No. Son dos cosas distintas: un programa (Git) y un servicio web que lo usa (GitHub). También existen GitLab, Codeberg o Bitbucket.

  2. Git funciona en tu computadora, sin internet; GitHub es un servicio que guarda copias de repositorios y añade herramientas para colaborar.

    Correcto. Puedes usar Git toda la vida sin GitHub; GitHub te da una copia en internet, pull requests, issues y Pages.

  3. Sin cuenta de GitHub no puedes hacer commits.

    No. Los commits los hace Git en tu computadora. La cuenta solo hace falta para subirlos a GitHub.

  4. GitHub guarda la historia y tu computadora solo los archivos actuales.

    No. Git es distribuido: cada copia del repositorio, también la tuya, tiene la historia completa.

    Git no da error. Hace el commit con lo preparado.

  3. juego.js tal como estaba al hacer git add; los cambios posteriores quedan pendientes.

    Correcto. git status mostraría el archivo como modificado otra vez. Te falta otro git add si también querías esos cambios.

    Git hace un solo commit, con lo que estaba preparado.

Subiste a un repositorio público un .env con una clave de una API. ¿Qué es lo más importante?

  1. Anular esa clave en el servicio que la emitió y crear otra; además, sacar .env del repositorio (git rm --cached .env) y añadirlo al .gitignore.

    Correcto. Lo publicado hay que darlo por copiado. Anular la clave es lo único que la vuelve inútil.

  2. Añadir .env al .gitignore: así desaparece del historial.

    No. .gitignore solo afecta a archivos que Git todavía no sigue, y nunca cambia el historial.

  3. Borrar el archivo en un commit nuevo.

    El archivo sigue en los commits anteriores, y cualquiera puede verlo en el historial.

  4. Hacer el repositorio privado.

    Ayuda para el futuro, pero quien la copió mientras era público ya la tiene. Hay que anularla.

¿Qué muestra git diff --staged?

  1. Los cambios que todavía no preparaste.

    Eso es git diff sin opciones: compara tu carpeta con lo preparado.

  2. La lista de commits de la rama.

    Eso es git log.

  3. Las diferencias entre tu repositorio y GitHub.

    Para eso tendrías que comparar con origin/main, por ejemplo git diff origin/main después de un fetch.

  4. Lo que preparaste y entrará en el próximo commit, comparado con el último commit.

    Correcto. Es la última revisión antes de hacer commit.

Un commit que ya subiste y que tu equipo ya descargó rompió el juego. ¿Cómo lo deshaces?

  1. git reset --hard HEAD~1 y git push --force.

    Reescribe historia compartida: el resto del equipo tendrá un commit que ya no existe en GitHub, y el force puede borrar trabajo ajeno.

  2. git revert con el hash de ese commit, y git push.

    Correcto. revert añade un commit que deshace el otro, sin reescribir nada. Es seguro con historia compartida.

  3. git restore juego.js.

    restore descarta cambios de tu carpeta que no están en un commit. No deshace commits.

  4. Borrar el repositorio de GitHub y subirlo otra vez.

    Perderías issues, pull requests y el trabajo de los demás. Nunca hace falta.

¿Qué es una rama en Git?

  1. Una copia completa de los archivos del proyecto en otra carpeta.

    Es la confusión más común. Crear una rama no copia nada.

  2. Un repositorio distinto en GitHub.

    Eso se parece más a un fork. Una rama vive dentro del mismo repositorio.

  3. Un nombre que apunta a un commit y avanza cuando haces commits estando en ella.

    Correcto. Por eso crearla es instantáneo y cuesta casi nada.

  4. Un commit especial que no se puede borrar.

    Las ramas se crean y se borran con facilidad; los commits no son ramas.

En la rama nivel-2 creaste nivel2.js e hiciste commit. Haces git switch main y el archivo desaparece de la carpeta. ¿Qué pasó?

  1. Nada grave: en main ese archivo no existe. Está guardado en el commit de nivel-2 y vuelve al cambiar a esa rama.

    Correcto. Tu carpeta siempre refleja la rama en la que estás.

  2. Git lo borró para siempre.

    No. Lo que está en un commit no se pierde al cambiar de rama.

  3. Se movió a la papelera del sistema.

    Git no usa la papelera. El archivo sigue dentro de .git, en el commit.

  4. Es un error: había que fusionar antes de cambiar de rama.

    No hace falta fusionar para cambiar de rama. Se fusiona cuando el trabajo está listo.

¿Cuándo una fusión es un avance rápido (fast-forward)?

  1. Cuando las dos ramas tienen commits nuevos.

    En ese caso Git crea un commit de fusión con dos padres.

  2. Cuando hay conflictos.

    Los conflictos solo pueden aparecer cuando las dos ramas cambiaron cosas; en un avance rápido solo cambió una.

  3. Siempre que fusionas en main.

    Depende de la historia, no del nombre de la rama.

  4. Cuando la rama que recibe no tiene commits nuevos desde que salió la otra: basta con mover su etiqueta.

    Correcto. No hay nada que combinar.

Estás en main, fusionas nivel-2 y un archivo queda así: <<<<<<< HEAD / vidas = 5 / ======= / vidas = 3 / >>>>>>> nivel-2. ¿Qué es cierto?

  1. vidas = 3 es tu versión.

    Al revés: lo que va entre <<<<<<< HEAD y ======= es la versión de la rama donde estás.

  2. Git ya eligió vidas = 5 y el resto es informativo.

    Git no elige en un conflicto. Si dejas las marcas, quedan dentro del archivo.

  3. vidas = 5 es la versión de main y vidas = 3 la de nivel-2; tienes que dejar el valor correcto, borrar las marcas, hacer git add y git commit.

    Correcto. Esos son los pasos para resolver.

  4. Basta con git commit: Git quita las marcas solo.

    Git guarda el archivo tal como esté. Si tiene marcas, el programa se romperá.

¿Cuál es la diferencia entre git fetch y git pull?

  1. Ninguna: pull es el nombre antiguo.

    Son comandos distintos que se usan los dos hoy.

  2. fetch descarga los commits nuevos y actualiza origin/main sin tocar tu rama; pull hace fetch y además los fusiona con tu rama.

    Correcto. Por eso fetch es seguro en cualquier momento.

  3. fetch sube tus commits y pull los baja.

    Para subir se usa push. fetch también baja.

  4. fetch solo funciona con SSH y pull con HTTPS.

    Los dos funcionan con cualquier forma de conexión.

git push responde ! [rejected] main -> main (fetch first). ¿Qué haces?

  1. git push --force para que lo acepte.

    Borrarías de GitHub los commits que otra persona subió. En ramas compartidas, nunca.

  2. Borras tu carpeta y vuelves a clonar.

    Perderías tus commits nuevos, que todavía no están en GitHub.

  3. Esperas: GitHub está saturado.

    El mensaje no habla de saturación: dice que GitHub tiene commits que tú no tienes.

  4. git pull para traer y fusionar los commits nuevos, resuelves los conflictos si los hay, y vuelves a hacer git push.

    Correcto. Es exactamente lo que sugiere el mensaje.

Quieres corregir una falta en un proyecto de código abierto donde no tienes permiso de escritura. ¿Cómo lo haces?

  1. Fork del proyecto, clonas tu fork, rama, commit, push a tu fork y pull request al original.

    Correcto. Es el flujo estándar para contribuir a proyectos ajenos.

  2. Clonas el original y haces push a su main.

    GitHub rechazará el push: no tienes permiso. Y aunque lo tuvieras, en main se entra con PR.

  3. Envías el archivo corregido por correo a quien mantiene el proyecto.

    Es mucho más trabajo para esa persona: tendría que buscar qué cambió. El PR le muestra el diff y le deja fusionar con un clic.

  4. Le pides a quien lo mantiene la contraseña de su cuenta.

    Nunca se comparten contraseñas. Los permisos se dan invitando a colaboradores, y para contribuir basta un fork.

Glosario

Control de versiones
Sistema que guarda la historia de los cambios de un proyecto y permite consultarla, volver atrás y trabajar en equipo. Git es el más usado.
Repositorio
Proyecto cuya historia gestiona Git. La historia vive en la carpeta oculta .git.
Commit
Foto guardada del proyecto, con autor, fecha, mensaje y un puntero al commit anterior (su padre).
Hash
Identificador único de un commit, calculado a partir de su contenido. Se suele mostrar con sus 7 primeros dígitos, como a3f9c2e.
Área de preparación (staging area)
Zona intermedia donde git add deja los cambios que entrarán en el próximo commit.
.gitignore
Archivo con reglas que indican qué archivos no debe seguir Git, como dependencias, archivos generados o secretos.
Conventional Commits
Convención para escribir mensajes de commit con un tipo al principio, como feat: o fix:, que entienden las personas y las herramientas.
HEAD
Marca que indica en qué punto de la historia estás; normalmente apunta a la rama actual.
Rama (branch)
Nombre que apunta a un commit y avanza con cada commit nuevo hecho en ella. Permite líneas de trabajo paralelas.
Fusión (merge)
Juntar en una rama los cambios de otra. Puede ser un avance rápido o crear un commit de fusión.
Avance rápido (fast-forward)
Fusión en la que la rama que recibe no tenía commits nuevos, así que Git solo mueve su etiqueta.
Conflicto
Situación en una fusión en la que las dos ramas cambiaron las mismas líneas y Git necesita que una persona decida el resultado.
Rebase
Forma de juntar ramas que reaplica tus commits encima de otra rama, creando commits nuevos. No debe usarse con commits compartidos.
Remoto
Otra copia del repositorio, normalmente en GitHub, registrada con un nombre corto como origin.
Clonar
Descargar una copia completa de un repositorio remoto, con toda su historia, usando git clone.
Push
Enviar tus commits nuevos a un remoto.
Fetch
Descargar los commits nuevos de un remoto sin cambiar tus ramas ni tus archivos.
Pull
Descargar los commits nuevos de un remoto y fusionarlos con tu rama actual (fetch más merge).
Token de acceso personal
Clave que se crea en GitHub, con permisos limitados y fecha de caducidad, para autenticarse en lugar de la contraseña.
Pull request
Propuesta en GitHub para fusionar una rama en otra, con conversación, revisión y diff de los cambios.
Revisión de código (code review)
Lectura y comentario de los cambios de otra persona antes de fusionarlos.
Fork
Copia de un repositorio ajeno en tu cuenta de GitHub, desde la que puedes proponer cambios al original.
Issue
Ficha numerada en GitHub para anotar un error, una petición o una tarea, con conversación, etiquetas y responsables.
GitHub flow
Flujo de trabajo en el que cada cambio se hace en una rama, se propone con un pull request, se revisa y se fusiona en main.
GitHub Pages
Servicio de GitHub que publica gratis una web estática a partir de los archivos de un repositorio.
