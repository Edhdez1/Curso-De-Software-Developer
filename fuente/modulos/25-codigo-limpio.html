Lo que vas a lograr

Que un programa funcione es solo la mitad del trabajo. La otra mitad es que alguien pueda leerlo mañana, entender qué hace y cambiarlo sin romper nada. Ese alguien casi siempre eres tú, meses después, sin recordar por qué escribiste lo que escribiste. En esta estación vas a aprender las costumbres, los principios y los patrones que usan los equipos profesionales para que su código siga siendo fácil de cambiar cuando el proyecto crece.

  • Elegir nombres que revelan intención y escribir funciones cortas, con un solo nivel de detalle y pocos parámetros.
  • Distinguir un comentario útil (el porqué) de un comentario que solo hace ruido.
  • Instalar y configurar Prettier y ESLint en un proyecto, con un archivo de configuración de ejemplo, y corregir lo que señalan.
  • Aplicar los principios DRY, KISS y YAGNI sin caer en sus excesos, y reconocer cuándo dos partes del código están demasiado acopladas.
  • Explicar los cinco principios SOLID con ejemplos en JavaScript.
  • Detectar olores de código y refactorizar en pasos pequeños, con pruebas que confirman que el comportamiento no cambió.
  • Usar los patrones Strategy, Observer, State y Command para resolver problemas típicos de juegos y apps.
  • Usar los patrones Factory, Module, Adapter y Decorator, y explicar por qué Singleton casi siempre sobra.
  • Reconocer antipatrones, incluido el de meter patrones donde no hacen falta.

Vas a leer y reorganizar mucho código, así que necesitas manejar con soltura las funciones (Estación 10), los arrays y objetos (Estación 11) y las clases y la composición (Estación 21). Para la parte de herramientas necesitas Node.js y VS Code con las extensiones de Prettier y ESLint (Estación 5). Y para refactorizar sin miedo te conviene saber hacer commits y deshacer cambios con Git (Estación 24).

Por qué importa que el código se entienda

Empieza con un experimento. La función de abajo funciona y no tiene ningún error. Antes de ejecutarla, intenta averiguar qué hace y qué número va a imprimir. Cronométrate si quieres.

Imprime 366. Seguramente acabaste deduciendo que p es un precio, c una cantidad y que hay un descuento del 10 % en los productos de 100 o más. Pero tuviste que hacer de detective. Ahora lee esta otra versión, que hace exactamente lo mismo:

const DESCUENTO_POR_VOLUMEN = 0.9;          // se paga el 90 %
const PRECIO_MINIMO_PARA_DESCUENTO = 100;

function totalDelCarrito(productos) {
  return productos.reduce((total, producto) => total + subtotal(producto), 0);
}

function subtotal({ precio, cantidad }) {
  const importe = precio * cantidad;
  const tieneDescuento = precio >= PRECIO_MINIMO_PARA_DESCUENTO;
  return tieneDescuento ? importe * DESCUENTO_POR_VOLUMEN : importe;
}

console.log(totalDelCarrito([
  { precio: 120, cantidad: 2 },
  { precio: 50, cantidad: 3 },
  { precio: 300, cantidad: 0 },
]));   // 366

La computadora ejecuta las dos igual de bien. La diferencia está en ti: la segunda se lee como una explicación. No necesitas adivinar qué es cada cosa, y si mañana el descuento cambia al 15 %, sabes en qué línea tocar. Eso es, en una frase, el código limpio: código que otra persona puede leer, entender y cambiar con confianza. El término se hizo famoso con el libro Clean Code (2008) de Robert C. Martin, pero la idea es mucho más antigua.

El objetivo no es que el código sea bonito. Es que sea barato de cambiar. Un programa que nadie se atreve a tocar está muerto, aunque funcione.

El código se lee muchas más veces de las que se escribe

La guía de estilo oficial de Python (PEP 8) lo dice así: «el código se lee mucho más a menudo de lo que se escribe». Lo escribes una vez, pero lo vas a leer cada vez que busques un error, cada vez que añadas una función nueva y cada vez que alguien del equipo revise tus cambios. Martin Fowler, autor del libro Refactoring (1999), lo resumió con una frase que verás citada en muchos equipos: «Cualquier tonto puede escribir código que una computadora entienda. Los buenos programadores escriben código que los humanos pueden entender».

Cuando un proyecto crece, casi todo el tiempo se va en cambiar código que ya existe: corregir errores, añadir un nivel nuevo al juego, cambiar el cálculo de envíos de la tienda. Si cada cambio obliga a leer media hora de código confuso, el proyecto se vuelve cada vez más lento de mover.

Deuda técnica: los atajos se pagan con intereses

En 1992, el programador Ward Cunningham comparó el código escrito con prisas con pedir un préstamo. Salir del paso rápido está bien, siempre que después lo arregles. Si no lo arreglas, pagas «intereses» cada vez que tocas ese código: tardas más, te equivocas más y te da miedo cambiarlo. A esto se le llama deuda técnica (en inglés, technical debt).

La deuda técnica funciona como una tarjeta de crédito. Usarla en un momento concreto puede ser buena idea: en una game jam de 48 horas nadie escribe código perfecto, y está bien. El problema llega cuando nunca pagas y los intereses se acumulan. El límite de la analogía: la deuda técnica no llega con un estado de cuenta. Nadie te avisa de cuánto debes; lo notas cuando cada cambio pequeño empieza a costar un día entero.

Reglas, no leyes

Todo lo que vas a ver en esta estación son heurísticas: reglas prácticas que suelen funcionar, no leyes de la física. Personas con mucha experiencia discrepan en los detalles. Entre 2024 y 2025, Robert C. Martin (Clean Code) y John Ousterhout (profesor de Stanford y autor de A Philosophy of Software Design) publicaron un debate por escrito sobre cuán cortas deben ser las funciones y cuánto hay que comentar. Coincidieron en lo importante: el código se escribe para que otras personas lo lean, la complejidad es el enemigo, y el criterio pesa más que cualquier regla aplicada a ciegas. Discreparon en cuánto partir el código en funciones y en el valor de los comentarios.

En un equipo, la costumbre del equipo gana a tus preferencias personales. Si el proyecto usa comillas simples y nombres en inglés, escribe con comillas simples y nombres en inglés. Un código coherente, aunque no sea tu estilo favorito, es más fácil de leer que uno donde cada archivo parece escrito por una persona distinta. Por eso los equipos dejan que las herramientas automáticas decidan el formato, como verás en la sección Comentarios, formato y linters.

Números mágicos

Un número mágico es un valor escrito tal cual en medio del código, sin nombre que explique qué significa: if (puntos > 1500). ¿Qué es 1500? ¿El récord? ¿Lo necesario para subir de nivel? Si ese número aparece en tres sitios y cambia, tendrás que encontrar los tres, y distinguirlos de otros 1500 que significan otra cosa. La solución es darle nombre con una constante:

const PUNTOS_PARA_SUBIR_DE_NIVEL = 1500;

if (puntos > PUNTOS_PARA_SUBIR_DE_NIVEL) {
  subirDeNivel(jugador);
}

Escribir en MAYÚSCULAS_CON_GUIONES_BAJOS las constantes que representan valores fijos del programa es una convención muy extendida, no una regla del lenguaje. Los valores evidentes no necesitan nombre: el 0 de un contador que empieza, el 1 de sumar uno o el 2 de «el doble» se entienden solos.

Ahora te toca. Este taller no pide que cambie lo que el programa hace, sino cómo se lee. Cuando lo ejecutes, la verificación comprobará dos cosas: que la salida sigue siendo exactamente la misma y que el código cumple las reglas. Así funcionan todos los talleres de refactorización de esta estación.

const UMBRAL_DESCUENTO = 500;

  let total = precioUnitario * cantidad;

Un solo nivel de abstracción por función

En la Estación 4 viste que abstraer es esconder detalles detrás de un nombre. Una función se lee bien cuando todas sus líneas están al mismo nivel de abstracción, es decir, al mismo nivel de detalle. Si una línea dice «calcula el total» y la siguiente multiplica precios uno a uno, tu cabeza tiene que saltar entre el «qué» y el «cómo» a cada paso.

Mezcla el qué y el cómo

function procesarPedido(pedido) {
  if (pedido.productos.length === 0) {

    total += p.precio * p.cantidad;

  console.log("Pedido de " + pedido.cliente);
  console.log("Total: $" + total.toFixed(2));

Parámetros: pocos y claros

Cada parámetro es algo más que quien llama a la función tiene que recordar, y en el orden correcto. Mira esta llamada:

crearPersonaje("Gorak", "guerrero", 20, true, false);

¿Qué significa true? ¿Y false? Imposible saberlo sin abrir la función. Hay dos problemas juntos:

  • Demasiados parámetros. Hasta dos se recuerdan bien; tres ya exigen atención; con cinco es fácil intercambiar dos por error. ESLint tiene una regla, max-params, que avisa cuando pasas del límite que elijas.
  • Parámetros bandera. Un parámetro bandera (en inglés, flag argument) es un booleano que cambia lo que hace la función. Delata que la función hace dos cosas distintas según el valor. A veces conviene partirla en dos (crearJefe y crearEnemigo); otras, pasar un objeto con nombres.

La solución más usada en JavaScript es recibir un objeto de opciones y desestructurarlo, con valores por defecto para lo opcional (la desestructuración la viste en la Estación 11). Así cada dato llega con su nombre y el orden deja de importar. Predice las tres líneas:

En la segunda llamada las propiedades van en otro orden y no pasa nada. En la tercera, todo lo que falta toma su valor por defecto. Y quien lee esJefe: true sabe qué significa sin abrir la función. Modifica el programa: añade una opción vuela (por defecto false) que, si es verdadera, añada « (vuela)» al final del texto.

Si una función recibe un objeto y lo modifica (pedido.total = 0), quien la llamó se encuentra su objeto cambiado sin haberlo pedido. Es un efecto secundario escondido, como viste en la Estación 10. Si necesitas un resultado nuevo, devuélvelo con return o crea una copia, como en la sección de inmutabilidad de la Estación 21.

Salir pronto: cláusulas de guarda

Cuando una función comprueba varios casos especiales con if dentro de if, el caso normal acaba escondido al fondo, muy a la derecha. A ese código con forma de punta de flecha se le llama código flecha. La solución es una cláusula de guarda: un if al principio que atiende un caso especial y sale de inmediato con return.

Código flecha

function atacar(atacante, objetivo) {
  if (atacante.estaVivo) {
    if (objetivo.estaVivo) {
      if (atacante.energia >= 10) {
        objetivo.vida -= atacante.fuerza;
        return "¡Golpe!";
      } else {
        return "Sin energía";
      }
    } else {
      return "El objetivo ya cayó";
    }
  } else {
    return "No puedes atacar";
  }
}

Guardas primero, caso normal al final

const ENERGIA_POR_ATAQUE = 10;

function atacar(atacante, objetivo) {
  if (!atacante.estaVivo) return "No puedes atacar";
  if (!objetivo.estaVivo) return "El objetivo ya cayó";
  if (atacante.energia < ENERGIA_POR_ATAQUE) return "Sin energía";

  objetivo.vida -= atacante.fuerza;
  return "¡Golpe!";
}

Las dos hacen lo mismo. En la derecha, cada condición está al lado de su respuesta y el caso normal queda al final, sin sangría. Hay una pauta más, llamada separación entre órdenes y consultas: una función debería hacer algo (cambiar un estado) o responder algo (devolver un dato), pero no las dos cosas a la vez. estaVivo(jugador) no debería quitarle vida a nadie. La propuso Bertrand Meyer, el mismo autor que conocerás en los principios SOLID.

Comentarios, formato y linters

Hay partes de la limpieza del código que dependen de tu criterio, como los nombres o qué comentar. Y hay otras tan mecánicas que sería un desperdicio hacerlas a mano: las sangrías, las comillas o encontrar un == que debería ser ===. Esta sección trata las dos.

Comentarios: el porqué, no el qué

El código ya dice qué hace y cómo lo hace. Un buen comentario cuenta lo que el código no puede decir: por qué se hizo así, qué decisión se tomó, qué trampa hay que evitar. Compara:

Ruido

// suma 1 a intentos
intentos++;

// función que calcula el envío
function calcularEnvio(pedido) { … }

// const total = precio * 1.21;
// console.log("probando", total);

// 12/03: Ana cambió el 5 por un 7
const REINTENTOS = 7;

Información que el código no da

// La API de pagos corta la conexión a los 10 s:
// con 7 reintentos cubrimos su caída habitual.
const REINTENTOS = 7;

// Math.floor y no Math.round: el diseño del juego
// dice que un golpe nunca puede hacer más daño
// del que muestra la barra.
const danio = Math.floor(fuerza * multiplicador);

// OJO: el orden importa. Hay que guardar antes de
// cerrar la sesión o se pierde la partida.

Los comentarios de la izquierda tienen cuatro defectos típicos:

  • Repiten el código. // suma 1 a intentos no añade nada, y hay que mantenerlo.
  • Envejecen y mienten. Si alguien cambia el código y no el comentario, el comentario pasa a decir algo falso. Un comentario falso es peor que ninguno.
  • Guardan código comentado. Nadie se atreve a borrarlo («¿y si hace falta?») y se queda para siempre. Bórralo sin miedo: Git recuerda todas las versiones anteriores (Estación 24).
  • Hacen de diario. Quién cambió qué y cuándo ya lo guarda git log, con más detalle y sin ensuciar el archivo.

Antes de escribir un comentario que explica qué hace un bloque, prueba a extraer ese bloque a una función cuyo nombre lo diga. Pero no conviertas esto en dogma: hay comentarios que sí hacen falta. Los que explican una decisión, los que advierten de un peligro, los que describen una expresión regular difícil y los comentarios JSDoc de las funciones que otras personas van a usar (los viste en la Estación 10).

Muchos equipos permiten comentarios // TODO: para marcar trabajo pendiente, y VS Code tiene extensiones que los reúnen en una lista. Úsalos con cuidado: un TODO sin responsable ni fecha tiende a quedarse para siempre. Si la tarea importa, lo habitual es abrir una incidencia (issue) en GitHub y enlazarla desde el comentario.

Formato automático con Prettier

En la Estación 5 instalaste la extensión de Prettier y activaste el formato al guardar. Eso funciona en tu computadora, con tu configuración. En un equipo hace falta algo más: que todas las personas formateen igual, con la misma versión y las mismas opciones, aunque usen editores distintos. Para eso Prettier se instala dentro de cada proyecto.

Vas a usar npm, el gestor de paquetes que viene con Node.js (lo conociste en la Estación 5 y lo usarás a fondo en la Estación 29). Solo necesitas saber tres cosas:

  • npm init -y crea el archivo package.json, la «ficha» del proyecto, donde se apunta qué herramientas usa y en qué versión.
  • npm install --save-dev paquete descarga una herramienta en la carpeta node_modules y la apunta como dependencia de desarrollo: algo que usas mientras programas, pero que el programa terminado no necesita. La carpeta node_modules no se sube a Git; se regenera con npm install.
  • npx herramienta ejecuta una herramienta instalada en el proyecto.

Con eso, así se prepara Prettier según su documentación oficial:

$ npm init -y
$ npm install --save-dev --save-exact prettier
$ node --eval "fs.writeFileSync('.prettierrc','{}\n')"
$ npx prettier --version
3.9.9

La opción --save-exact fija la versión exacta. Dos versiones distintas de Prettier pueden formatear algún detalle de otra manera, y entonces cada persona del equipo «reformatearía» los archivos de las demás en cada commit. La tercera línea crea un archivo .prettierrc que contiene {}: la configuración vacía, que significa «usa las opciones por defecto». Su sola presencia también le indica a tu editor que el proyecto usa Prettier. La versión que ves es la de septiembre de 2026; la tuya puede ser más nueva.

Las opciones por defecto son razonables: líneas de unos 80 caracteres, sangría de 2 espacios, comillas dobles, punto y coma al final y coma después del último elemento de las listas que ocupan varias líneas. Si el equipo prefiere otra cosa, se escribe en .prettierrc:

{
  "singleQuote": true,
  "printWidth": 100
}

Prettier tiene pocas opciones a propósito. Su documentación explica que, cuantas más opciones hay, más se discute: «los debates sobre estilo se convierten en debates sobre qué opciones de Prettier usar». Desde hace años no aceptan opciones nuevas. La idea es que el formato deje de ser un tema de conversación.

Con el proyecto preparado, dos órdenes hacen todo el trabajo. --check solo revisa y avisa; --write reescribe los archivos:

$ npx prettier . --check
Checking formatting...
[warn] feo.js
[warn] Code style issues found in the above file. Run Prettier with --write to fix.
$ npx prettier . --write
feo.js 39ms

Este es el antes y el después de feo.js. Prettier no cambió nada de lo que el código hace, solo su aspecto:

Antes

const personaje={nombre:'Lyra',vida:100,
  ataque:12}
function atacar(a,b){ if(a.ataque>b.defensa){return a.ataque-b.defensa}else{return 1} }
console.log( atacar(personaje,{defensa:4}) )

Después de prettier --write

const personaje = { nombre: "Lyra", vida: 100, ataque: 12 };
function atacar(a, b) {
  if (a.ataque > b.defensa) {
    return a.ataque - b.defensa;
  } else {
    return 1;
  }
}
console.log(atacar(personaje, { defensa: 4 }));

Fíjate en lo que no hizo: no renombró a ni b, ni quitó el else innecesario. Un formateador cambia la forma, nunca el significado. Para lo demás está el linter. Si hay carpetas que Prettier no debe tocar, se listan en un archivo .prettierignore; Prettier ya respeta lo que diga tu .gitignore.

Un linter: ESLint

En la Estación 5 viste que un linter revisa el código en busca de errores probables y malas prácticas sin ejecutarlo. El de JavaScript es ESLint. Funciona con reglas: cada regla detecta un problema concreto y tiene un nombre, como no-unused-vars (variables que nunca se usan) o eqeqeq (usar == en vez de ===). Tú eliges qué reglas activar y con qué gravedad:

DRY, KISS, YAGNI y el arte de separar

Los nombres y las funciones se deciden línea a línea. Ahora sube un nivel: ¿cómo repartes el código entre funciones, objetos y archivos? Hay cuatro ideas que vas a oír en cualquier equipo. Tienen nombres en inglés, casi siempre siglas, y conviene conocerlas por su nombre.

DRY: no te repitas

En la Estación 10 conociste DRY (Don't Repeat Yourself, «no te repitas») como la razón de ser de las funciones. Su definición original, del libro The Pragmatic Programmer (1999) de Andy Hunt y Dave Thomas, es más precisa de lo que parece: «cada pieza de conocimiento debe tener una representación única, inequívoca y autorizada dentro de un sistema».

Fíjate en que habla de conocimiento, no de líneas de texto. La regla «el IVA es del 16 %» es un conocimiento: si está escrita en cinco sitios y cambia, tienes que encontrar los cinco. Pero dos líneas idénticas que representan reglas distintas no son una repetición. Si el máximo de vidas es 3 y el máximo de objetos en el inventario también es 3, son dos datos distintos que casualmente coinciden. Si los unes en una sola constante, el día que el inventario crezca a 5 le darás cinco vidas al jugador sin querer.

Este programa de una tienda repite la regla del impuesto. Refactorízalo para que esa regla viva en un solo lugar:

Ver una solución 
const TASA_IMPUESTO = 0.16;

const carrito = [
  { nombre: "Mando", precio: 40 },
  { nombre: "Juego", precio: 60 },
];

function precioConImpuesto(precio) {
  return precio + precio * TASA_IMPUESTO;
}

for (const producto of carrito) {
  console.log(producto.nombre + ": $" + precioConImpuesto(producto.precio).toFixed(2));
}

let total = 0;
for (const producto of carrito) {
  total += precioConImpuesto(producto.precio);
}

Si mañana el impuesto cambia o se añade un impuesto distinto para los juegos, solo hay que tocar precioConImpuesto.

¿Cuándo eliminar una repetición? Martin Fowler recoge en Refactoring una pauta de Don Roberts: la primera vez que haces algo, lo haces; la segunda vez que haces algo parecido, notas la repetición pero la haces igual; a la tercera, refactorizas. Con dos casos todavía no sabes qué es igual de verdad y qué es casualidad. Sandi Metz, autora de libros de diseño orientado a objetos, lo resumió así en 2016: «la duplicación es mucho más barata que la abstracción equivocada».

KISS: mantenlo simple

KISS viene de Keep It Simple, Stupid («hazlo simple, tonto»). Se atribuye a Kelly Johnson, un ingeniero aeronáutico de Lockheed que pedía diseñar aviones que un mecánico corriente pudiera reparar en el campo con herramientas básicas. En software significa: entre dos soluciones que funcionan, elige la que se entiende antes.

Ingenioso

const esVocal = (c) => !!~"aeiou".indexOf(c);

const nivel = puntos > 900 ? "oro"
  : puntos > 500 ? "plata"
  : puntos > 100 ? "bronce" : "ninguno";

Simple

const esVocal = (letra) => "aeiou".includes(letra);

function medallaPara(puntos) {
  if (puntos > 900) return "oro";
  if (puntos > 500) return "plata";
  if (puntos > 100) return "bronce";
  return "ninguno";
}

Simple no significa corto. La versión de la izquierda tiene menos líneas, pero para entender !!~ hay que saber qué hace el operador ~ con el -1 que devuelve indexOf. Simple significa que se entiende sin trucos.

Escribir código simple no es fácil: suele llegar después de una primera versión complicada que luego limpias. Y simple tampoco es simplista. Si tu juego necesita guardar partidas en la nube, la solución simple no es ignorar los errores de red: es manejarlos de la forma más clara posible.

YAGNI: no lo vas a necesitar

YAGNI significa You Aren't Gonna Need It, «no lo vas a necesitar». Nació en la Programación Extrema (Extreme Programming, una forma de trabajo ágil de finales de los noventa) y dice: no construyas hoy una capacidad que crees que necesitarás mañana. Construye lo que necesitas ahora.

Imagina que tu juego tiene una sola arma y decides preparar un «sistema de armas con plugins, rarezas, mejoras y comercio entre jugadores», por si acaso. Pagas tres veces: el tiempo de construirlo, el de mantenerlo (cada cambio en el juego tiene que respetar ese sistema) y el retraso de lo que de verdad importaba. Y cuando por fin necesites armas nuevas, lo más probable es que las necesites de otra forma que la que imaginaste.

Martin Fowler añade un matiz importante: YAGNI se aplica a las funciones del programa que aún nadie pidió, no al esfuerzo por mantener el código fácil de cambiar. Refactorizar, poner buenos nombres o escribir pruebas no viola YAGNI. Al contrario: YAGNI solo funciona si el código es fácil de cambiar, porque así, cuando la necesidad llegue, la añades sin sufrir.

DRY, KISS y YAGNI tiran en direcciones distintas. DRY te empuja a crear abstracciones para no repetirte; KISS y YAGNI te frenan para que no crees abstracciones que todavía no necesitas. El equilibrio se aprende con práctica, y la refactorización es lo que te permite corregir el rumbo cuando te pasas hacia un lado.

Robert C. Martin popularizó una costumbre sencilla, tomada de los boy scouts: «deja el campamento más limpio de lo que lo encontraste». Cada vez que tocas un archivo para otra cosa, mejora algo pequeño: un nombre confuso, una función demasiado larga. No hace falta pedir permiso para una gran limpieza; el código mejora un poco cada día.

Cohesión y acoplamiento

Dos palabras, acuñadas en los años sesenta y setenta por Larry Constantine para el diseño estructurado, miden si has repartido bien el código:

  • Cohesión: cuánto tienen que ver entre sí las cosas que están juntas en una misma función, objeto o archivo. Un módulo sonido.js que solo contiene cosas de sonido tiene alta cohesión. Un utilidades.js con una función de fechas, otra de colores y otra de sonido tiene baja cohesión.
  • Acoplamiento: cuánto depende una parte del código de los detalles internos de otra. Si cambiar cómo se guarda la puntuación obliga a tocar el código del sonido, del menú y de la pantalla de fin, hay alto acoplamiento.

Lo que se busca es alta cohesión y bajo acoplamiento: cada pieza se ocupa de un tema, y las piezas se hablan poco y por puertas bien definidas.

Una señal práctica de acoplamiento son las cadenas largas de puntos que atraviesan las entrañas de otros objetos:

Conoce demasiado

// La pantalla sabe cómo está guardado el inventario por dentro
const danio = jugador.inventario.armas[0].estadisticas.danio;

Pregunta a quien sabe

// El jugador decide cómo calcularlo
const danio = jugador.danioDelArmaEquipada();

Si mañana el inventario pasa de un array a un Map, la versión de la izquierda se rompe en cada pantalla que la use; la de la derecha solo obliga a cambiar el método del jugador. Esta pauta se conoce como ley de Deméter o «no hables con extraños»: un objeto debería hablar con sus colaboradores directos, no con los colaboradores de sus colaboradores. Es una pauta, no una ley: en datos sencillos, como pedido.cliente.nombre, un par de puntos no hace daño.

Piensa en los aparatos de tu casa. Todos se conectan a la pared con un enchufe estándar: puedes cambiar la tostadora sin llamar a un electricista. Eso es bajo acoplamiento, y el enchufe es la «puerta bien definida». Si cada aparato estuviera soldado a los cables de la pared, cambiar uno obligaría a abrir la pared. El límite de la analogía: en el código, la «puerta» (los nombres de las funciones y lo que reciben) la diseñas tú, y diseñarla bien es la parte difícil.

SOLID es un acrónimo que reúne cinco principios de diseño orientado a objetos. Robert C. Martin los recopiló alrededor del año 2000, a partir de ideas de varios autores, y Michael Feathers les dio el acrónimo unos años después. Nacieron pensando en lenguajes con clases, como Java o C++, pero sus ideas sirven igual para funciones y módulos de JavaScript. Todos persiguen lo mismo que la sección anterior: poder cambiar una parte del programa sin romper las demás.

S: responsabilidad única

La formulación clásica dice que una clase debería tener «una sola razón para cambiar». Martin la aclaró después, porque mucha gente la entendía como «una clase debe hacer una sola cosa diminuta». Lo que propone es: reúne las cosas que cambian por las mismas razones y separa las que cambian por razones distintas. Y añade que las razones para cambiar son personas: quién va a pedir el cambio.

class Partida {
  constructor() {
    this.puntos = 0;
  }
  derrotar(enemigo) {                    // regla del juego: la decide quien diseña el juego
    this.puntos += enemigo.esJefe ? 500 : 100;
  }
  textoDelMarcador() {                   // presentación: la decide quien diseña la interfaz
    return `PUNTOS ${String(this.puntos).padStart(6, "0")}`;
  }
  guardar() {                            // almacenamiento: lo decide quien mantiene la técnica
    localStorage.setItem("puntos", JSON.stringify(this.puntos));
  }
}

Tres personas distintas pueden pedir cambios en esta clase por motivos que no tienen nada que ver entre sí. Si quien diseña la interfaz pide otro formato de marcador y, al tocarlo, rompes sin querer la regla de los puntos, has estropeado algo que nadie te pidió cambiar. Separando cada responsabilidad, cada cambio queda contenido en su sitio:

// Reglas del juego
const PUNTOS_POR_ENEMIGO = 100;
const PUNTOS_POR_JEFE = 500;
const puntosPor = (enemigo) => (enemigo.esJefe ? PUNTOS_POR_JEFE : PUNTOS_POR_ENEMIGO);

class Partida {
  constructor() {
    this.puntos = 0;
  }
  derrotar(enemigo) {
    this.puntos += puntosPor(enemigo);
  }
}

// Presentación
function textoDelMarcador(puntos) {
  return `PUNTOS ${String(puntos).padStart(6, "0")}`;
}

// Almacenamiento
const almacen = {
  guardar(clave, valor) {
    localStorage.setItem(clave, JSON.stringify(valor));
  },
};

No lleves la responsabilidad única al extremo de crear una clase por cada línea. Si separas cosas que siempre cambian juntas, cada cambio te obligará a abrir cinco archivos. Pregúntate: ¿quién pediría cambiar esto y por qué? Lo que cambia por el mismo motivo, va junto.

O: abierto a la extensión, cerrado a la modificación

Lo formuló Bertrand Meyer en 1988: un módulo debería poder ampliarse con comportamientos nuevos sin tener que modificar su código, que ya funciona y ya está probado. El ejemplo típico es un switch que crece cada vez que aparece un tipo nuevo:

function calcularEnvio(pedido) {
  switch (pedido.envio) {
    case "normal": return 5;
    case "express": return 12;
    case "gratis": return 0;
    // ¿Envío por dron? Hay que volver a abrir esta función…
    // …y cualquier otro switch del programa que pregunte por el tipo de envío.
  }
}

Qué cambios son previsibles lo decide la experiencia con tu proyecto, y aquí YAGNI vuelve a mandar: no prepares puntos de extensión para cosas que nadie ha pedido.

L: sustitución de Liskov

Barbara Liskov, que recibió el premio Turing en 2008, lo presentó en 1987: si una clase hija extiende a una madre, cualquier parte del programa que funciona con la madre debe seguir funcionando si le das la hija. El ejemplo clásico de los libros es el cuadrado: en geometría un cuadrado «es un» rectángulo, pero si Cuadrado extends Rectangulo y alguien cambia solo el ancho, o el cuadrado deja de ser cuadrado o el rectángulo deja de comportarse como se esperaba. «Es un» en el mundo real no siempre significa «es un» en el código.

I: segregación de interfaces

Una interfaz, en diseño, es el conjunto de métodos que un objeto promete ofrecer. El principio dice que es mejor tener varias interfaces pequeñas que una enorme, para que nadie tenga que prometer lo que no puede cumplir:

// Un contrato gigante: toda entidad del juego debe saber hacer de todo
class Entidad {
  mover() {}
  atacar() {}
  hablar() {}
  abrir() {}
}

class Cofre extends Entidad {
  mover() { throw new Error("Un cofre no se mueve"); }
  atacar() { throw new Error("Un cofre no ataca"); }
  hablar() { throw new Error("Un cofre no habla"); }
  abrir() { return "Encuentras 50 monedas"; }
}

El cofre solo tiene sentido con abrir; los otros tres métodos son promesas vacías que, además, rompen Liskov. Con capacidades pequeñas, cada objeto tiene solo lo que usa: un cofre es algo que se abre; un aldeano, algo que se mueve y habla; un orco, algo que se mueve y ataca. JavaScript no tiene una palabra interface: aquí las interfaces son un acuerdo sobre qué métodos existen. TypeScript sí las escribe explícitamente (Estación 23) y te avisa si un objeto no cumple la suya.

D: inversión de dependencias

El último principio dice que los módulos de alto nivel (las reglas importantes de tu programa: vender, puntuar, reservar) no deberían depender de los de bajo nivel (los detalles: cómo se manda un correo, en qué base de datos se guarda). Los dos deberían depender de una abstracción: un acuerdo intermedio sobre qué se necesita, sin decir cómo se hace.

La técnica más común para conseguirlo se llama inyección de dependencias (en inglés, dependency injection): en lugar de que un objeto cree por dentro lo que necesita, se lo pasas desde fuera, por ejemplo en el constructor. Suena técnico, pero es solo un parámetro más. Predice la salida:

Olores de código y refactorización segura

Hasta aquí has visto cómo se ve el código limpio. Pero casi nunca escribes código limpio a la primera, y casi siempre trabajas sobre código que ya existe. La pregunta real es otra: ¿cómo se mejora un programa que funciona sin romperlo por el camino?

Como un olor raro en la cocina: lo notas enseguida y no siempre es grave, pero conviene mirar de dónde viene. Qué es refactorizar (y qué no)

Fowler define refactorizar como «cambiar la estructura interna del software para que sea más fácil de entender y más barato de modificar, sin cambiar su comportamiento observable». La última parte es la esencial: después de refactorizar, el programa hace exactamente lo mismo que antes. Si cambia lo que hace, no es una refactorización, es otra cosa.

  • No es reescribir. Reescribir desde cero tira el conocimiento acumulado (los casos raros que el código viejo ya resolvía) y durante semanas no tienes nada que funcione. Refactorizar son muchos cambios pequeños; tras cada uno, el programa sigue funcionando.
  • No es añadir funciones. Kent Beck lo explica con la metáfora de los dos sombreros: cuando llevas el de «añadir funcionalidad», no reestructuras; cuando llevas el de «refactorizar», no añades nada nuevo. Puedes cambiar de sombrero cada pocos minutos, pero nunca los lleves los dos a la vez: si algo se rompe, no sabrás cuál de los dos cambios fue.
  • No es optimizar. Hacer el código más rápido puede volverlo más difícil de leer. Son objetivos distintos, y se mide antes de optimizar (lo viste en la Estación 20).

La red de seguridad: pruebas y commits

¿Cómo sabes que el comportamiento no cambió? No mirándolo «a ojo». Necesitas una comprobación automática que puedas repetir después de cada paso: una prueba. Las pruebas tienen su propia estación, la 26. Aquí te basta con una herramienta que ya conoces de la Estación 12: console.assert(condición, "mensaje"). Si la condición es verdadera, no hace nada. Si es falsa, escribe un error:

> console.assert(2 + 2 === 4, "las sumas funcionan")
> console.assert(2 + 2 === 5, "las sumas funcionan")
Assertion failed: las sumas funcionan

¿Y si el código que vas a refactorizar no tiene pruebas? Es lo más habitual. Michael Feathers, en Working Effectively with Legacy Code (2004), propone escribir primero pruebas de caracterización: pruebas que no comprueban lo que el código debería hacer, sino lo que hace hoy. Ejecutas la función con varios datos, anotas lo que devuelve y lo conviertes en pruebas. Si algún resultado te parece un error, anótalo aparte: arreglarlo será otro cambio, con el otro sombrero.

  1. Comprueba que hay pruebas y que todas pasan (si no las hay, escribe pruebas de caracterización)

  3. Simula un paso que sale mal: cp cambio-arriesgado.js juego.js, y vuelve a ejecutar node juego.js. Mira qué cambió con git diff.

Patrones de diseño (I): organizar el comportamiento

Al programar juegos y apps aparecen una y otra vez los mismos problemas: «este enemigo tiene que poder cambiar de táctica», «cuando pasa algo, cinco partes del programa tienen que enterarse», «quiero un botón de deshacer». Un patrón de diseño es una solución probada a uno de esos problemas recurrentes, con nombre propio. No es código para copiar: es una idea de cómo repartir las responsabilidades, que adaptas a tu caso.

La idea viene de la arquitectura de edificios. Christopher Alexander describió en A Pattern Language (1977) soluciones que se repiten en casas y ciudades. En 1994, Erich Gamma, Richard Helm, Ralph Johnson y John Vlissides, la «Banda de los Cuatro» que ya conociste en la Estación 21, publicaron Design Patterns con 23 patrones para software orientado a objetos, agrupados en tres familias:

FamiliaQué resuelvePatrones de esta estación

CreacionalesCómo se crean los objetosFactory, Singleton
EstructuralesCómo se combinan objetos para formar estructuras mayoresAdapter, Decorator

El patrón Module, que verás en la sección siguiente, no está en ese libro: es propio de JavaScript. Y un aviso honesto: muchos de los 23 patrones se inventaron para lenguajes donde las funciones no se pueden guardar en variables. En 1996, Peter Norvig mostró que 16 de ellos se vuelven invisibles o mucho más sencillos en lenguajes dinámicos. JavaScript es uno de esos lenguajes: a menudo el patrón se reduce a «pasa una función».

El mayor valor de los patrones es el vocabulario. Decir «el sonido es un observador de los eventos del juego» le explica a otra persona, en seis palabras, cómo está organizado el código. Por eso conviene conocer sus nombres en inglés: así aparecen en la documentación, en las entrevistas y en las conversaciones de cualquier equipo.

Problema: cuando el héroe derrota a un enemigo, tienen que pasar muchas cosas: sumar puntos, sonar un efecto, comprobar logros, actualizar estadísticas. State: el personaje como máquina de estados

Programa un personaje de plataformas con booleanos y verás el problema. Empiezas con estaSaltando; luego añades estaAgachado; luego estaCorriendo. Robert Nystrom lo cuenta en su libro Game Programming Patterns: con banderas sueltas, tarde o temprano el personaje acaba agachado en pleno salto o corriendo mientras está agachado, combinaciones que no deberían existir. Cada bandera nueva multiplica los casos que debes vigilar.

La solución es una máquina de estados finita, que Nystrom define con cuatro condiciones:

  • Hay un conjunto fijo de estados en los que puede estar la máquina.
  • La máquina está en un solo estado a la vez.
  • Le llegan entradas o eventos, uno tras otro.
  • Cada estado tiene sus transiciones: para cada entrada, a qué estado pasa. Si una entrada no tiene transición en ese estado, se ignora.

La forma más directa de programarla es una tabla de transiciones: un objeto que, para cada estado, dice a qué estado lleva cada entrada. El patrón State de la Banda de los Cuatro va un paso más allá y convierte cada estado en un objeto con su propio comportamiento (qué animación usa, a qué velocidad se mueve), pero la tabla es el corazón de todo. Command: acciones que se pueden guardar y deshacer

Problema: quieres un botón de deshacer, o grabar las jugadas para una repetición, o que la persona pueda reasignar qué tecla hace cada acción. Si las acciones son llamadas directas (oro -= 30), desaparecen en cuanto se ejecutan. Solución: convertir cada acción en un objeto comando que sabe ejecutarse y, si hace falta, deshacerse. Como es un objeto, se puede guardar en una lista, repetir, enviar por la red o asignar a una tecla. Sigue este programa paso a paso:

let oro = 100;
const historial = [];
const comprarPocion = {
  ejecutar() { oro -= 30; },
  deshacer() { oro += 30; },
};
function ejecutar(comando) {
  comando.ejecutar();
  historial.push(comando);
}
function deshacerUltimo() {
  const ultimo = historial.pop();
  if (ultimo) ultimo.deshacer();
}
ejecutar(comprarPocion);
ejecutar(comprarPocion);
deshacerUltimo();
console.log(oro, historial.length);

Para deshacer, cada comando necesita saber revertir lo que hizo. En acciones sencillas es la operación contraria (restar y sumar). En otras, el comando guarda lo que había antes: un comando «mover pieza» recuerda la casilla de origen. Hay una alternativa que ya conoces de la Estación 21: guardar una copia completa e inmutable de cada estado y volver a la anterior. Los comandos gastan menos memoria cuando el estado es grande; las copias son más simples cuando es pequeño.

En un juego, Command también sirve para separar las teclas de las acciones: en lugar de «si pulsa X, salta», tienes un objeto { X: comandoSaltar, Z: comandoAtacar }. Cambiar los controles es cambiar ese objeto. Y como la misma lista de comandos puede venir del teclado, de un mando o de la inteligencia artificial, el personaje no necesita saber quién lo controla.

Patrones de diseño (II): crear, conectar y envolver

Los patrones de la sección anterior organizan qué hace cada objeto. Los de esta resuelven otras tres preguntas: cómo se crean los objetos (Factory y Singleton), cómo se esconde lo interno (Module) y cómo se conectan o amplían piezas que ya existen (Adapter y Decorator). Al final verás lo contrario de un patrón: los antipatrones.

Factory: un solo lugar sabe cómo se fabrica cada cosa

Problema: tu juego lee los niveles de un archivo que dice «slime, slime, orco». Si en cada sitio donde aparece un enemigo escribes new Enemigo("Orco", 80, 12), los números de cada tipo quedan repartidos por todo el código, y quien crea enemigos tiene que saber qué clase usar para cada uno. Solución: una fábrica (en inglés, factory), una función que recibe una descripción y devuelve el objeto ya construido. Quien la llama no sabe ni le importa cómo se hace.

Modifica: añade un murcielago (vida 15, ataque 6) a las plantillas y ponlo en el nivel. Añadir un tipo de enemigo es añadir datos, no código nuevo. La fábrica también puede decidir qué clase crear: si mañana los jefes son una clase Jefe con más métodos, crearEnemigo("dragon") puede devolver un new Jefe(...) y el resto del juego no se entera. Los libros distinguen variantes (Factory Method, Abstract Factory), pero en JavaScript casi siempre basta con una función como esta.

Singleton, y por qué evitarlo casi siempre

El patrón Singleton garantiza que de una clase exista una sola instancia y da un punto de acceso global a ella. Se suele usar para la configuración, el registro de mensajes (log) o el gestor de sonido de un juego:

class Configuracion {
  static #instancia = null;
  volumen = 80;

  static obtener() {
    if (!Configuracion.#instancia) {
      Configuracion.#instancia = new Configuracion();
    }
    return Configuracion.#instancia;
  }
}

const a = Configuracion.obtener();
const b = Configuracion.obtener();
console.log(a === b);   // true: es el mismo objeto

Parece práctico: desde cualquier archivo escribes Configuracion.obtener() y ya está. Ese es justamente el problema. Es una variable global con otro nombre, y trae sus mismos males:

  • Dependencias escondidas. Mirando cómo se llama a una función no sabes que, por dentro, lee o cambia la configuración. Es lo contrario de la inyección de dependencias de la sección SOLID.
  • Pruebas que se contaminan. Si una prueba cambia el volumen a 0, la siguiente prueba empieza con volumen 0. Los resultados dependen del orden en que se ejecuten.
  • Cualquiera puede cambiarlo desde cualquier sitio. Cuando algo sale mal, el culpable puede estar en cualquier archivo del proyecto.
  • Suele ser innecesario. En JavaScript, un módulo se evalúa una sola vez: si un archivo exporta un objeto, todos los que lo importan reciben el mismo objeto. La «instancia única» ya la tienes gratis, sin clase especial.

El problema del Singleton no es que haya un solo objeto: tener una sola configuración es normal. El problema es el acceso global. La alternativa es crear ese único objeto al arrancar el programa y pasárselo a quien lo necesite, como hiciste con el notificador de la tienda. Robert Nystrom dedica un capítulo entero de Game Programming Patterns a explicar por qué casi nunca hace falta, incluso en videojuegos. Es el patrón de la Banda de los Cuatro que más se desaconseja hoy.

Problema: quieres agrupar datos y funciones relacionados, y que desde fuera nadie pueda tocar los datos internos, solo usar lo que tú decidas. Solución: el patrón Module. Antes de que JavaScript tuviera módulos propios, se escribía con una función que se ejecuta en el mismo momento en que se define. Se llama IIFE (Immediately Invoked Function Expression, «expresión de función invocada inmediatamente»): la función se envuelve entre paréntesis y se llama con () al final. Adapter: un traductor entre dos formas

Problema: tu juego muestra el ranking con objetos { nombre, puntos }, pero el servicio externo de puntuaciones que contrataste devuelve { player_name, pts }, con los puntos como texto. No puedes cambiar el servicio, y no quieres llenar tu juego de player_name. Solución: un adaptador, una pieza pequeña que traduce de la forma ajena a la tuya en un único lugar.

Si el servicio cambia de formato mañana, o lo sustituyes por otro, solo cambia adaptarRanking: mostrarRanking y el resto del juego ni se enteran. Modifica: haz que el adaptador ponga la primera letra de cada nombre en mayúscula («Lyra», «Kai»). Los adaptadores aparecen en cuanto tu programa habla con algo que no controlas: una API, una librería, un mando de consola que llama a sus botones de otra forma. Son también la forma habitual de envolver una librería para poder cambiarla por otra algún día.

Es el adaptador de enchufes que llevas de viaje: ni tu cargador ni la pared cambian; el adaptador hace que encajen. El límite: un adaptador de enchufes no cambia el voltaje, y uno de código tampoco arregla diferencias de fondo. Si el servicio no guarda un dato que tu juego necesita, ningún adaptador lo inventa.

Decorator: envolver para añadir

Problema: tu espada puede recibir mejoras (fuego, filo, hielo) que se combinan en cualquier orden. Con herencia necesitarías una clase por combinación: EspadaDeFuego, EspadaAfiladaDeFuego… Solución: un decorador, un objeto que envuelve a otro, tiene su misma forma (los mismos métodos) y añade algo antes o después de delegar en él. Como la forma no cambia, los decoradores se pueden apilar. Predice las tres líneas y fíjate en la última:

conFilo(conFuego(espada)) calcula (10 + 5) × 2 = 30; al revés, 10 × 2 + 5 = 25. El orden de las envolturas importa, como el orden de las capas de ropa. La espada original sigue intacta: los decoradores no la modifican, la envuelven. Es composición (Estación 21) aplicada a añadir comportamiento.

Con funciones, la idea es la misma: una función que recibe otra función y devuelve una versión «decorada». Esta añade un mensaje de registro a cualquier función sin tocarla (...argumentos recoge todos los argumentos en un array, sean cuantos sean):

function conRegistro(funcion) {
  return (...argumentos) => {
    console.log(`Llamando a ${funcion.name} con`, argumentos);
    return funcion(...argumentos);
  };
}

const calcularDanioConRegistro = conRegistro(calcularDanio);
calcularDanioConRegistro(20, 8);   // Llamando a calcularDanio con [ 20, 8 ]

En TypeScript y en frameworks como Angular verás una sintaxis con arroba, @Component(...), que también se llama «decorador». Está inspirada en la misma idea, pero es una característica del lenguaje, no el patrón. Existe una propuesta para añadirla a JavaScript que en septiembre de 2026 todavía no forma parte del estándar.

Antipatrones

Un antipatrón es lo contrario de un patrón: una respuesta frecuente a un problema que parece buena idea, pero que trae más problemas que soluciones. El término lo propuso Andrew Koenig en 1995. Conocer sus nombres ayuda tanto como conocer los patrones, porque te permite decir «esto se está convirtiendo en un objeto dios» antes de que sea tarde:

Sobre la optimización prematura, la cita completa de Donald Knuth (1974) es más matizada que el eslogan: «deberíamos olvidarnos de las pequeñas eficiencias, digamos, el 97 % del tiempo: la optimización prematura es la raíz de todos los males. Pero no deberíamos dejar pasar nuestras oportunidades en ese crítico 3 %». No dice que el rendimiento no importe; dice que primero hay que saber dónde importa.

Los patrones son un vocabulario, no una lista de tareas. No empieces un proyecto preguntándote qué patrones vas a usar. Empieza con lo más simple que funcione y, cuando sientas el dolor (un switch que crece, diez funciones que avisan a mano a otras diez), refactoriza hacia el patrón que lo alivia. Joshua Kerievsky escribió un libro entero sobre esta idea: Refactoring to Patterns (2004).

El código se escribe una vez, pero lo heredan otras personas: compañeras que llegan al equipo, voluntarios de un proyecto de código abierto, quien mantenga tu app cuando tú ya no estés. Un código claro abre la puerta a que más gente pueda contribuir, incluidas personas que empiezan, como tú ahora. Un código que solo entiende su autor la cierra. Escribir limpio también es una forma de ser amable con el equipo.

Resumen

  • Código limpio es código que otra persona puede leer, entender y cambiar con confianza. El objetivo no es la belleza, sino que cambiarlo sea barato. Los atajos que no se pagan se acumulan como deuda técnica.
  • Los nombres revelan intención: qué es, para qué sirve, cómo se usa. Los números mágicos se convierten en constantes con nombre. Los booleanos se leen como preguntas y las funciones empiezan con un verbo.
  • Cada función hace una cosa, a un solo nivel de detalle, con pocos parámetros (un objeto de opciones si son muchos), sin parámetros bandera y con cláusulas de guarda para los casos especiales.
  • Los comentarios explican el porqué; el qué lo cuentan los nombres. El formato lo decide Prettier y los errores probables los señala ESLint, configurado en eslint.config.mjs y ejecutado con npx eslint ..
  • DRY: cada conocimiento en un solo lugar (a la tercera repetición, abstrae). KISS: la solución que se entiende antes. YAGNI: no construyas lo que nadie ha pedido. Busca alta cohesión y bajo acoplamiento.
  • SOLID: una razón para cambiar por módulo; extender sin modificar; las subclases cumplen las promesas de la madre; interfaces pequeñas; depender de acuerdos, no de detalles (inyección de dependencias).
  • Un olor de código es una pista de un problema. Refactorizar es cambiar la estructura sin cambiar el comportamiento: en pasos pequeños, con pruebas después de cada paso y un commit cuando pasan. Si fallan, vuelve atrás.
  • Strategy intercambia comportamientos; Observer avisa a quien se suscribe; State evita estados imposibles con una tabla de transiciones; Command convierte acciones en objetos que se guardan y se deshacen.
  • Factory centraliza la creación; Module separa lo privado de lo público; Adapter traduce entre formas; Decorator envuelve para añadir. Singleton es estado global disfrazado: mejor crear una instancia y pasarla.
  • Los patrones son vocabulario, no una lista de tareas. Los antipatrones (objeto dios, espagueti, patronitis, optimización prematura) te ayudan a nombrar lo que va mal. Refactoriza hacia un patrón cuando aparezca el dolor.

Tu propio emisor de eventos

Completa crearEmisor para que funcione como el patrón Observer, y suscribe dos oyentes a partida: uno que imprima Nivel X alcanzado y otro que imprima ¡Logro: Veterana! solo cuando el nivel sea 10 o más. La salida debe ser:

Nivel 2 alcanzado
Nivel 10 alcanzado
¡Logro: Veterana!
Pista 1

suscribir solo tiene que hacer oyentes.push(oyente);. emitir recorre la lista: for (const oyente of oyentes) oyente(datos);

Pista 2

Un oyente es una función que recibe los datos: partida.suscribir((datos) => console.log(`Nivel ${datos.nivel} alcanzado`));. El del logro lleva un if dentro.

const NIVEL_VETERANA = 10;

function crearEmisor() {
  const oyentes = [];
  return {
    suscribir(oyente) {
      oyentes.push(oyente);
    },
    emitir(datos) {
      for (const oyente of oyentes) {
        oyente(datos);
      }
    },
  };
}

const partida = crearEmisor();

partida.suscribir((datos) => console.log(`Nivel ${datos.nivel} alcanzado`));
partida.suscribir((datos) => {
  if (datos.nivel >= NIVEL_VETERANA) console.log("¡Logro: Veterana!");
});

// Pruebas (no las cambies)
partida.emitir({ nivel: 2 });
partida.emitir({ nivel: 10 });

La máquina de estados de un pedido

Un pedido de una tienda pasa por estos estados: pendiente → (pagar) → pagado → (enviar) → enviado → (entregar) → entregado. Mientras está pendiente o pagado se puede cancelar (pasa a cancelado); una vez enviado, ya no. Completa la tabla de transiciones y el método recibir, sin comparar el estado con ===: toda la lógica tiene que salir de la tabla. La salida esperada es:

enviar: no permitido desde pendiente
pagar: pagado
enviar: enviado
cancelar: no permitido desde enviado
entregar: entregado
pagar: pagado
cancelar: cancelado
pagar: no permitido desde cancelado
Pista 1

La fila de pendiente queda así: pendiente: { pagar: "pagado", cancelar: "cancelado" },. Los estados finales (entregado y cancelado) se quedan con un objeto vacío: no aceptan ningún evento.

Pista 2

Dentro de recibir: const siguiente = transiciones[estado][evento];. Si siguiente no existe, devuelve el texto de «no permitido»; si existe, asígnalo a estado y devuélvelo.

Ver una solución 
const transiciones = {
  pendiente: { pagar: "pagado", cancelar: "cancelado" },
  pagado: { enviar: "enviado", cancelar: "cancelado" },
  enviado: { entregar: "entregado" },
  entregado: {},
  cancelado: {},
};

function crearPedido() {
  let estado = "pendiente";
  return {
    recibir(evento) {
      const siguiente = transiciones[estado][evento];
      if (!siguiente) return "no permitido desde " + estado;
      estado = siguiente;
      return estado;
    },
  };
}

// Pruebas (no las cambies)
const pedidoA = crearPedido();
for (const evento of ["enviar", "pagar", "enviar", "cancelar", "entregar"]) {
  console.log(`${evento}: ${pedidoA.recibir(evento)}`);
}
const pedidoB = crearPedido();
for (const evento of ["pagar", "cancelar", "pagar"]) {
  console.log(`${evento}: ${pedidoB.recibir(evento)}`);
}

Toda la política de la tienda está en seis líneas de datos. Si mañana se permite cancelar un pedido enviado (con devolución), se cambia la tabla y nada más.

Deshacer y rehacer con comandos

Completa el patrón Command para un inventario con deshacer y rehacer. Hay dos pilas: hechos (lo que se puede deshacer) y deshechos (lo que se puede rehacer). Escribe el método deshacer del comando y las funciones deshacer() y rehacer(). Si no hay nada que deshacer o rehacer, no deben fallar. La salida esperada es:

espada, escudo, poción
espada
espada, escudo
0
Pista 1

El método del comando es el contrario de ejecutar: deshacer() { inventario.pop(); }. No olvides la coma entre los dos métodos del objeto.

Pista 2

En la función deshacer(): const comando = hechos.pop(); if (!comando) return;. Después, comando.deshacer() y deshechos.push(comando). rehacer() es simétrica. El tercer deshacer() seguido encuentra la pila vacía: por eso la guarda.

Ver una solución 
const inventario = [];
const hechos = [];      // comandos ejecutados (para deshacer)
const deshechos = [];   // comandos deshechos (para rehacer)

function crearComandoAgregar(objeto) {
  return {
    ejecutar() {
      inventario.push(objeto);
    },
    deshacer() {
      inventario.pop();
    },
  };
}

function ejecutar(comando) {
  comando.ejecutar();
  hechos.push(comando);
  deshechos.length = 0;   // una acción nueva borra lo que se podía rehacer
}

function deshacer() {
  const comando = hechos.pop();
  if (!comando) return;
  comando.deshacer();
  deshechos.push(comando);
}

function rehacer() {
  const comando = deshechos.pop();
  if (!comando) return;
  comando.ejecutar();
  hechos.push(comando);
}

// Pruebas (no las cambies)
ejecutar(crearComandoAgregar("espada"));
ejecutar(crearComandoAgregar("escudo"));
ejecutar(crearComandoAgregar("poción"));
console.log(inventario.join(", "));
deshacer();
deshacer();
console.log(inventario.join(", "));
rehacer();
console.log(inventario.join(", "));
deshacer();
deshacer();
deshacer();
console.log(inventario.length);

Añadir otro tipo de acción, como «equipar» o «vender», es crear otro comando con su ejecutar y su deshacer: deshacer() y rehacer() no cambian, porque no saben qué hace cada comando.

Una cafetería con decoradores

Una bebida es cualquier objeto con los métodos descripcion() y precio(). Escribe tres decoradores (funciones que reciben una bebida y devuelven otra con la misma forma), sin usar clases ni herencia:

  • conLeche: añade « con leche» a la descripción y 0.5 al precio.
  • conCaramelo: añade « con caramelo» y 0.75.
  • doble: añade « (doble)» al final y multiplica el precio por 2.

La bebida original no debe cambiar. La salida esperada es:

Café con leche: $2.50
Café con leche con caramelo: $3.25
Café con caramelo (doble): $5.50
2
Pista 1

Un decorador devuelve un objeto nuevo que delega en la bebida que envuelve: descripcion: () => bebida.descripcion() + " con leche".

Pista 2

Si tu salida da $2.00 o el último número no es 2, probablemente estás modificando la bebida recibida (bebida.precio = …) en lugar de devolver un objeto nuevo.

Ver una solución 
const cafe = {
  descripcion: () => "Café",
  precio: () => 2,
};

function conLeche(bebida) {
  return {
    descripcion: () => `${bebida.descripcion()} con leche`,
    precio: () => bebida.precio() + 0.5,
  };
}

function conCaramelo(bebida) {
  return {
    descripcion: () => `${bebida.descripcion()} con caramelo`,
    precio: () => bebida.precio() + 0.75,
  };
}

function doble(bebida) {
  return {
    descripcion: () => `${bebida.descripcion()} (doble)`,
    precio: () => bebida.precio() * 2,
  };
}

// Pruebas (no las cambies)
const pedidos = [conLeche(cafe), conCaramelo(conLeche(cafe)), doble(conCaramelo(cafe))];
for (const bebida of pedidos) {
  console.log(`${bebida.descripcion()}: $${bebida.precio().toFixed(2)}`);
}
console.log(cafe.precio());

Con tres decoradores puedes crear cualquier combinación sin escribir una sola clase nueva. Con herencia necesitarías CafeConLeche, CafeConLecheYCaramelo, CafeDobleConCaramelo… una por combinación.

¿Qué es refactorizar?

  1. Reescribir el programa desde cero con mejores ideas.

    No. Reescribir tira el conocimiento acumulado y te deja semanas sin nada que funcione. Refactorizar son muchos cambios pequeños sobre código que sigue funcionando.

  2. Cambiar la estructura interna del código sin cambiar su comportamiento observable.

    Correcto. Es la definición de Martin Fowler: el programa hace exactamente lo mismo, pero es más fácil de entender y de cambiar.

  3. Añadir funciones nuevas mientras se limpia el código.

    Eso es llevar los dos sombreros a la vez. Si algo se rompe, no sabrás si fue la limpieza o la función nueva. Se hacen por separado.

  4. Hacer que el programa sea más rápido.

    Eso es optimizar, un objetivo distinto que a veces hace el código más difícil de leer.

¿Cuál de estos comentarios aporta más información?

  1. // incrementa el contador, encima de contador++.

    Repite lo que el código ya dice. Solo añade algo que mantener.

  2. // función que calcula el total, encima de function calcularTotal().

    El nombre de la función ya lo dice. Es ruido.

  3. // Redondeamos hacia abajo: la pasarela de pago rechaza céntimos de más.

    Correcto. Explica un porqué que el código no puede expresar: una decisión y su motivo.

  4. // const total = precio * 2;, código comentado «por si acaso».

    El código comentado se queda para siempre y confunde. Git ya guarda todas las versiones anteriores: bórralo.

Tu código tiene const MAX_VIDAS = 3; y const MAX_OBJETOS = 3;. Alguien propone unirlos en const TRES = 3; «para cumplir DRY». ¿Qué respondes?

  1. Que no: son dos conocimientos distintos que coinciden por casualidad.

    Correcto. DRY habla de conocimiento, no de valores iguales. El día que el inventario crezca, no quieres cambiar también las vidas.

  2. Que sí: DRY prohíbe escribir dos veces el mismo valor.

    DRY dice que cada conocimiento debe estar en un solo lugar. Dos reglas distintas pueden tener el mismo valor hoy.

  3. Que sí, pero con un nombre mejor, como MAXIMO.

    El nombre mejora, pero sigue mezclando dos reglas que cambiarán por motivos distintos.

  4. Que da igual, porque el programa funciona igual.

    Hoy sí. El problema llega cuando una de las dos reglas cambie y la otra cambie con ella sin que nadie lo quiera.

La clase Torreta extends Enemigo lanza un error en mover() porque las torretas no se mueven. ¿Qué principio incumple?

  1. Responsabilidad única.

    Ese principio trata de cuántas razones tiene un módulo para cambiar, no de si una subclase cumple lo que promete su madre.

  2. Abierto/cerrado.

    Ese trata de ampliar sin modificar. Aquí el problema es que la subclase no puede usarse donde se espera un enemigo.

  3. Inversión de dependencias.

    Ese trata de depender de abstracciones y no de detalles.

  4. Sustitución de Liskov.

    Correcto. Cualquier código que mueve enemigos se rompe si le das una torreta: la subclase no cumple la promesa de la clase madre.

Cada vez que añades un tipo de envío tienes que editar un switch en tres funciones distintas. ¿Qué cambio ayuda más?

  1. Poner un comentario en cada switch recordando que hay otros dos.

    Documenta el problema, pero no lo resuelve. El próximo cambio seguirá tocando tres sitios.

  2. Un objeto de estrategias con una función por tipo de envío.

    Correcto. Cada tipo vive en un solo lugar y añadir uno nuevo es añadir una entrada, sin tocar lo que ya funciona (principio abierto/cerrado).

  3. Convertir cada switch en una cadena de if/else.

    Es el mismo problema con otra sintaxis: siguen siendo tres lugares que editar.

  4. Un Singleton que guarde todos los tipos de envío.

    Añade estado global y no resuelve la dispersión de la lógica.

«Cuando la jugadora sube de nivel se actualizan el marcador, el sonido y los logros, y queremos añadir más reacciones sin tocar el código que sube de nivel». ¿Qué patrón encaja?

  1. Singleton.

    Garantiza una sola instancia, pero no organiza quién reacciona a un suceso.

  2. Adapter.

    Traduce entre dos formas incompatibles. Aquí nada es incompatible.

  3. Observer.

    Correcto. El código del nivel emite un evento y cada parte interesada se suscribe. Una reacción nueva es un suscriptor nuevo.

  4. Factory.

    Sirve para crear objetos, no para avisar de sucesos.

¿Cuál es el problema principal del patrón Singleton?

  1. Es estado global: crea dependencias escondidas y hace que las pruebas se contaminen entre sí.

    Correcto. El problema no es tener un solo objeto, sino que cualquiera pueda leerlo y cambiarlo desde cualquier sitio.

  2. Gasta mucha memoria porque crea muchas instancias.

    Es al revés: su objetivo es que exista una sola instancia.

  3. JavaScript no permite escribirlo.

    Sí se puede, por ejemplo con un campo estático privado. Y un módulo ya se evalúa una sola vez.

  4. Solo funciona en videojuegos.

    Se usa (y se abusa) en todo tipo de programas.

¿Qué herramienta te avisa de que escribiste == donde debía ir ===?

  1. Prettier.

    Prettier solo cambia el aspecto del código (espacios, comillas, saltos de línea), nunca su significado.

  2. Git.

    Git guarda versiones, pero no analiza lo que escribes.

  3. Node.js, al ejecutar el archivo.

    == es válido en JavaScript: Node lo ejecuta sin quejarse, con sus conversiones implícitas.

  4. ESLint, con la regla eqeqeq.

    Correcto. Es un linter: detecta malas prácticas y errores probables sin ejecutar el código.

Estás refactorizando y, después de un paso, dos pruebas fallan. ¿Qué haces?

  1. Cambias los valores esperados de las pruebas para que pasen.

    Las pruebas describen el comportamiento que debías conservar. Cambiarlas es esconder que lo rompiste.

  2. Sigues refactorizando y lo arreglas todo al final.

    Cuantos más cambios acumules, más difícil será saber cuál rompió qué.

  3. Vuelves al último commit en verde y das un paso más pequeño.

    Correcto. Deshacer cuesta segundos; depurar un cambio grande puede costar horas.

  4. Borras las pruebas que fallan.

    Te quedas sin red de seguridad justo cuando te estaba avisando de algo.

Tu personaje tiene estaSaltando, estaAgachado y estaCorriendo, y a veces aparece agachado en el aire. ¿Qué propones?

Tu app solo está en español y nadie ha pedido otro idioma. Alguien quiere preparar «por si acaso» un sistema de traducción a doce idiomas. ¿Qué principio lo desaconseja?

  1. DRY.

    DRY trata de no repetir conocimiento, no de si construir algo que nadie pidió.

  2. Sustitución de Liskov.

    Trata de subclases y promesas de la clase madre.

  3. La regla del boy scout.

    Habla de dejar el código un poco mejor cada vez que lo tocas, no de añadir funciones.

  4. YAGNI.

    Correcto. No construyas capacidades para necesidades que imaginas. Si el código es fácil de cambiar, lo añadirás cuando haga falta, y sabrás mejor cómo.

En el patrón Command, ¿qué hace posible el botón de deshacer?

  1. Que cada acción es un objeto que sabe ejecutarse y deshacerse, y los ejecutados se guardan en una pila.

    Correcto. Deshacer es sacar el último comando de la pila y pedirle que se deshaga.

  2. Que las funciones se ejecutan dos veces para comprobar el resultado.

    No hay nada de eso en el patrón.

  3. Que el estado del programa es global.

    El estado global no ayuda a deshacer; ayuda a romper cosas.

  4. Que cada acción imprime en la consola lo que hizo.

    Un registro de texto no sabe revertir nada. El comando sí.

Glosario

Código limpio
Código que otra persona puede leer, entender y cambiar con confianza. El término se popularizó con el libro Clean Code (2008) de Robert C. Martin.
Deuda técnica
Coste futuro de los atajos tomados al escribir código: cada vez que tocas ese código pagas «intereses» en tiempo y errores, hasta que lo arreglas.
Refactorizar
Cambiar la estructura interna del código para que sea más fácil de entender y modificar, sin cambiar su comportamiento observable.
Olor de código
Señal en la superficie del código que suele indicar un problema de diseño más profundo, como una función muy larga o código duplicado. En inglés, code smell.
Número mágico
Valor escrito tal cual en el código sin un nombre que explique qué significa. Se sustituye por una constante con nombre.
Cláusula de guarda
Condición al principio de una función que atiende un caso especial y sale con return, para que el caso normal quede al final sin anidar.
Parámetro bandera
Parámetro booleano que cambia lo que hace una función. Suele indicar que la función hace dos cosas. En inglés, flag argument.
DRY
Don't Repeat Yourself: cada pieza de conocimiento debe tener una representación única en el sistema.
KISS
Keep It Simple, Stupid: entre dos soluciones que funcionan, elige la que se entiende antes.
YAGNI
You Aren't Gonna Need It: no construyas capacidades para necesidades que todavía nadie ha pedido.
Cohesión
Grado en que las cosas agrupadas en una misma función, clase o archivo tienen que ver entre sí. Se busca que sea alta.
Acoplamiento
Grado en que una parte del código depende de los detalles internos de otra. Se busca que sea bajo.
SOLID
Acrónimo de cinco principios de diseño: responsabilidad única, abierto/cerrado, sustitución de Liskov, segregación de interfaces e inversión de dependencias.
Inyección de dependencias
Técnica que consiste en pasar a un objeto o función lo que necesita (por ejemplo, un notificador) en lugar de que lo cree por dentro.
Prueba de caracterización
Prueba que registra lo que un código hace hoy, sin juzgar si es correcto, para detectar cualquier cambio de comportamiento al refactorizarlo.
Patrón de diseño
Solución probada y con nombre a un problema de diseño que aparece una y otra vez, como Observer o Strategy.
Antipatrón
Respuesta frecuente a un problema que parece buena idea pero trae más problemas que soluciones, como el objeto dios.
Strategy (Estrategia)
Patrón que encapsula cada variante de un comportamiento en una pieza intercambiable con la misma forma.
Observer (Observador)
Patrón en el que un emisor mantiene una lista de suscriptores y los avisa cuando ocurre algo, sin saber quiénes son.
Máquina de estados finita
Modelo con un conjunto fijo de estados, uno activo a la vez, y transiciones que indican a qué estado lleva cada entrada. Es la base del patrón State.
Command (Comando)
Patrón que convierte una acción en un objeto que sabe ejecutarse (y a menudo deshacerse), para poder guardarla, repetirla o revertirla.
Factory (Fábrica)
Función u objeto que crea otros objetos a partir de una descripción, escondiendo cómo se construyen y qué clase se usa.
Singleton
Patrón que garantiza una sola instancia de una clase con acceso global. Hoy se desaconseja casi siempre porque equivale a estado global.
Adapter (Adaptador)
Pieza que traduce la forma de un objeto o servicio ajeno a la forma que espera tu código.
Decorator (Decorador)
Objeto o función que envuelve a otro con la misma forma y le añade comportamiento. Los decoradores se pueden apilar.
