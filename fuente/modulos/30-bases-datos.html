Lo que vas a lograr

Cierra una app y vuelve a abrirla: tus mensajes, tus compras y tu progreso en el juego siguen ahí. Detrás de casi todas las aplicaciones hay una base de datos que guarda la información de forma ordenada, segura y rápida de consultar. En esta estación aprenderás a diseñarlas y a hablarles en SQL, el mismo lenguaje que usan desde una app de tareas hasta un banco.

  • Explicar qué es una base de datos y qué problemas resuelve frente a guardar todo en un archivo.
  • Leer y crear tablas con columnas, tipos, clave primaria y restricciones.

  • Resumir datos con GROUP BY, funciones de agregación, HAVING y subconsultas.

Por qué una base de datos

En la Estación 29 tu API guardaba los datos en un array, dentro de la memoria del servidor. Funciona hasta que el servidor se reinicia: la memoria RAM se borra al apagar, como viste en la Estación 2, y con ella todas las puntuaciones. Necesitas que los datos sobrevivan. A eso se le llama persistencia: que la información quede guardada de forma permanente, en disco.

La primera idea suele ser guardar todo en un archivo JSON: leerlo al arrancar y reescribirlo en cada cambio. Para un proyecto de fin de semana, sirve. Pero en cuanto la app tiene personas usándola de verdad aparecen cinco problemas:

  1. Dos personas a la vez. Si dos peticiones leen y reescriben el archivo al mismo tiempo, una borra el cambio de la otra.
  2. Un apagón a mitad. Si el servidor se apaga mientras escribe, el archivo queda a medias y puedes perderlo entero, no solo el último cambio.
  3. Buscar es lento. Para encontrar a una persona entre un millón tienes que leer y recorrer el archivo completo cada vez.
  4. Nadie vigila las reglas. Nada impide guardar un precio negativo o una compra de un cliente que no existe.
  5. Cada pregunta nueva es un programa nuevo. «¿Cuánto vendimos por género este mes?» te obliga a escribir bucles y acumuladores para cada consulta.

Qué es una base de datos

Una base de datos es una colección de datos organizada y guardada de forma permanente, pensada para consultarse y modificarse de forma segura. El programa que la administra se llama sistema gestor de bases de datos (SGBD; en inglés, database management system, DBMS). SQLite, PostgreSQL y MySQL son sistemas gestores. En el día a día casi todo el mundo dice «la base de datos» para las dos cosas, y aquí haremos lo mismo.

Un archivo JSON es como un cuaderno compartido sobre una mesa: cualquiera lo abre, tacha y escribe, y si dos personas escriben en la misma página a la vez, se pisan. Una base de datos es como un archivo con una bibliotecaria en el mostrador. Tú no tocas las fichas: le pides lo que quieres. Ella atiende las escrituras de una en una, anota cada cambio en un registro antes de hacerlo, encuentra una ficha entre un millón en un instante y se niega a archivar una ficha que rompe las reglas. La analogía tiene un límite: la bibliotecaria no entiende qué significan tus datos. Solo hace cumplir las reglas que tú le das.

ProblemaArchivo JSONBase de datos

Buscar un dato entre millonesLeer y recorrer todoSalta directo con un índice
Datos que rompen las reglasSe guardan sin avisoLos rechaza con un error

¿Cómo sobrevive una base de datos a un apagón? Antes de cambiar nada, anota lo que va a hacer en un registro aparte. Si la luz se va a mitad, al arrancar lee ese registro y deshace o termina el cambio, de modo que nunca queda a medias. SQLite llama a ese registro diario (en inglés, journal) y PostgreSQL, registro de escritura anticipada (write-ahead log, WAL). Tú no tienes que programarlo: viene incluido.

Una base de datos no solo guarda: garantiza. Garantiza que dos cambios simultáneos no se pisan, que un apagón no deja datos a medias y que nada que rompa tus reglas entra. Programar esas garantías a mano sobre archivos es dificilísimo; por eso casi nadie lo hace.

¿Y cuándo basta con un archivo?

No todo necesita una base de datos. Un archivo sigue siendo la mejor opción para la configuración de un programa, para exportar datos que otra persona va a abrir en una hoja de cálculo o para la partida guardada de un juego de un solo jugador, donde solo un programa escribe y nunca a la vez. La pregunta útil es: ¿varias personas o procesos van a escribir a la vez, o voy a necesitar buscar y combinar datos de muchas formas? Si la respuesta es sí, usa una base de datos.

La documentación de SQLite lo resume con una frase famosa: SQLite no compite con las bases de datos cliente-servidor, compite con fopen(), la función con la que un programa en C abre un archivo. Muchas aplicaciones usan SQLite como un «archivo con superpoderes»: Android e iOS la incluyen, y navegadores como Firefox y Chrome guardan en ella tu historial. Si tu juego necesita guardar muchas cosas y buscarlas, SQLite puede ser tu formato de partida guardada.

El lenguaje: SQL

La familia de bases de datos más usada es la relacional: guarda los datos en tablas y se consulta con SQL (de Structured Query Language, «lenguaje de consultas estructurado»; se pronuncia «ese-cu-ele» o, a la inglesa, «sícuel»). Nació en IBM en los años setenta y es un estándar internacional desde 1986; la edición más reciente es SQL:2023. Hay otras familias, que se agrupan bajo el nombre NoSQL; las verás en la sección SQLite, PostgreSQL y NoSQL.

En la Estación 21 viste que SQL es declarativo: describes qué datos quieres y la base de datos decide cómo buscarlos. No escribes bucles. Cada motor habla su propio dialecto, con pequeñas diferencias, pero lo básico es igual en todos. En esta estación usarás el de SQLite, y te avisaremos cuando algo cambie en PostgreSQL o MySQL.

Tres convenciones que verás en todos los ejemplos:

  • Las palabras del lenguaje (SELECT, FROM, WHERE) se escriben en MAYÚSCULAS por costumbre, para distinguirlas de tus nombres. SQL no distingue mayúsculas en ellas: select también funciona.
  • Cada instrucción termina en punto y coma (;). Una instrucción puede ocupar varias líneas.
  • Los comentarios empiezan con dos guiones: -- esto no se ejecuta.

Tablas, tipos y claves

En 1970, Edgar F. Codd, un matemático que trabajaba en IBM, publicó un artículo que cambió la informática: proponía organizar los datos en tablas y consultarlos con operaciones matemáticas bien definidas, sin que el programa tuviera que saber cómo estaban guardados en el disco. Es el modelo relacional, y más de cincuenta años después sigue siendo la forma más común de guardar datos. Cada tabla guarda un tipo de cosa: una tabla de juegos, otra de clientes, otra de compras.

Estas son las piezas, con los nombres que vas a leer en todas partes:

  • Una fila (en inglés, row; también se dice registro) es una cosa concreta: un juego, un cliente, una compra.
  • Una columna (en inglés, column; también se dice campo) es una propiedad que tienen todas las filas: el título, el precio. Tiene un nombre y un tipo.
  • El esquema (en inglés, schema) es la descripción de las tablas: qué columnas tienen, de qué tipo y con qué reglas. Es el plano de tu base de datos.

Si vienes de la Estación 11, cada fila es como un objeto { id: 1, titulo: "Bosque Eterno", … } y la tabla es como un array de esos objetos, con una diferencia importante: en una tabla todas las filas tienen exactamente las mismas columnas.

Una tabla se parece a una hoja de cálculo, y la comparación sirve para empezar. Pero falla en dos puntos. En una hoja de cálculo puedes escribir cualquier cosa en cualquier celda; en una tabla, cada columna tiene un tipo y unas reglas que la base de datos hace cumplir. Y las filas de una tabla no tienen un orden fijo: si quieres verlas ordenadas, lo pides en cada consulta.

Crear una tabla

La instrucción CREATE TABLE define una tabla nueva: su nombre, sus columnas y las reglas de cada una.

CREATE TABLE juegos (
  id     INTEGER PRIMARY KEY,               -- número que identifica cada juego
  titulo TEXT NOT NULL,                     -- texto obligatorio
  genero TEXT,                              -- texto opcional
  precio REAL NOT NULL CHECK (precio >= 0), -- decimal, obligatorio, nunca negativo
  anio   INTEGER                            -- año de salida, opcional
);

Cada línea dentro de los paréntesis es una columna: primero el nombre, después el tipo y, al final, las restricciones. Los nombres suelen escribirse en minúsculas, sin tildes ni espacios, con guion bajo para separar palabras (precio_pagado). Esa forma se llama snake_case. La columna se llama anio y no año porque la ñ y las tildes funcionan en muchos motores, pero dan problemas en algunas herramientas; es más seguro evitarlas en los nombres, aunque sí puedes usarlas dentro de los datos.

Cada motor tiene su lista de tipos. SQLite tiene muy pocos; PostgreSQL, muchos. Esta tabla muestra los más comunes:

SQLite no tiene tipo de fecha: guarda las fechas como texto con el formato internacional ISO 8601, año-mes-día ('2026-09-30'). Ese orden tiene una ventaja: al ordenar los textos alfabéticamente, quedan ordenados por fecha.

En la Estación 7 viste que 0.1 + 0.2 no da exactamente 0.3. REAL tiene el mismo problema. Para dinero de verdad, guarda los céntimos como enteros (1999 para 19,99) o usa numeric en PostgreSQL, que guarda decimales exactos. En esta estación los precios son redondos para que los ejemplos se lean fácil.

La clave primaria

La clave primaria (en inglés, primary key) es la columna cuyo valor identifica cada fila: no puede repetirse y no puede faltar. ¿Por qué no usar el nombre? Porque dos clientas pueden llamarse Ana. ¿Y el correo? Porque la gente cambia de correo, y entonces habría que cambiarlo en todas partes. Lo habitual es añadir una columna id con un número que no significa nada más: una clave sustituta (en inglés, surrogate key). Una clave que sí tiene significado, como un DNI, se llama clave natural.

En SQLite, una columna INTEGER PRIMARY KEY se numera sola: si insertas una fila sin id, recibe el siguiente número libre. Cada motor lo escribe a su manera:

-- SQLite
id INTEGER PRIMARY KEY
-- PostgreSQL (forma moderna; en tutoriales antiguos verás SERIAL)
id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY
-- MySQL
id INT AUTO_INCREMENT PRIMARY KEY

En tutoriales de SQLite verás INTEGER PRIMARY KEY AUTOINCREMENT. No hace falta para que el número se ponga solo: solo impide reutilizar los números de filas borradas. La documentación de SQLite recomienda no usarlo si no lo necesitas, porque gasta más recursos.

Una restricción (en inglés, constraint) es una regla que la base de datos comprueba en cada inserción y en cada cambio. Si una fila la rompe, la operación entera se rechaza con un error.

Insertar filas

Con INSERT INTO añades filas. Primero nombras las columnas que vas a rellenar y después, en VALUES, los valores en el mismo orden. Puedes insertar varias filas en una sola instrucción separándolas con comas:

INSERT INTO juegos (titulo, genero, precio, anio)
VALUES ('Bosque Eterno', 'aventura', 20, 2021),
       ('Cohete Loco', 'carreras', 10, 2019);

Los textos van entre comillas simples. Si el texto contiene un apóstrofo, se escribe doble: 'Bernardo O''Higgins'. Los números van sin comillas. No hace falta dar el id: la base de datos lo asigna.

La rareza de SQLite: tipos flexibles

SQLite tiene una particularidad que sorprende a casi todo el mundo. Predice qué guardará en cada fila:

La función typeof dice el tipo real de cada valor. El texto '31' se convirtió en el número 31, porque parecía un número. Pero 'treinta' se guardó como texto en una columna de enteros, sin ningún error. SQLite trata el tipo de la columna como una preferencia, no como una obligación; la documentación lo llama afinidad de tipo. Lo hace para ser compatible con programas antiguos.

Desde la versión 3.37 (2021) existe la opción STRICT, que hace que SQLite se comporte como los demás motores. Cambia la primera línea del taller por CREATE TABLE prueba (edad INTEGER) STRICT; y ejecuta: ahora el texto 'treinta' se rechaza con un error. '31', en cambio, se sigue aceptando convertido en número, porque la conversión no pierde nada.

Confiar en que SQLite comprueba los tipos. Sin STRICT, una columna INTEGER acepta 'treinta' y el error aparece mucho después, cuando una suma da un resultado raro. En proyectos nuevos con SQLite, usa tablas STRICT o valida los datos antes de guardarlos. PostgreSQL y MySQL, en su configuración habitual, rechazan el valor desde el principio.

Consultar con SELECT

En casi todas las apps se lee mucho más de lo que se escribe: una tienda muestra su catálogo miles de veces por cada juego nuevo que añade. Por eso la instrucción que más vas a escribir es SELECT («seleccionar»). Su forma general, con las partes opcionales entre corchetes, es:

SELECT columnas
FROM tabla
[WHERE condición]
[ORDER BY columna]
[LIMIT cantidad];

Cada parte recibe el nombre de su palabra clave: la cláusula WHERE, la cláusula ORDER BY… Una consulta que lee datos se llama, en general, una consulta (en inglés, query). Los talleres de esta sección usan esta tabla juegos de una tienda en línea. Tenla a la vista para predecir los resultados:

Elegir columnas

Después de SELECT escribes las columnas que quieres, separadas por comas. También puedes calcular columnas nuevas y ponerles un nombre con AS, que se llama alias:

SELECT titulo, precio FROM juegos;                      -- solo dos columnas
SELECT titulo, precio * 0.8 AS rebajado FROM juegos;    -- columna calculada: 20 % menos
SELECT titulo || ' (' || anio || ')' AS ficha FROM juegos; -- une textos: Bosque Eterno (2021)
SELECT DISTINCT genero FROM juegos;                     -- cada género una sola vez

En SQL los textos se unen con ||, no con +. Y DISTINCT quita las filas repetidas del resultado: «rpg» aparece dos veces en la tabla, pero una sola en la respuesta. Las columnas calculadas no cambian nada en la tabla: solo existen en la respuesta.

SELECT * es cómodo para explorar, pero en el código de una app escribe las columnas que necesitas. Traes menos datos por la red, y si mañana alguien añade a la tabla una columna enorme (una imagen, un texto largo) o una columna privada, tu programa no la recibirá sin querer.

Con paréntesis: lo que querías

WHERE (genero = 'rpg' OR genero = 'puzle')
  AND precio < 28;
-- Mazmorra 64, Puzle Cuántico

En SQLite, = distingue mayúsculas: 'rpg' no es igual a 'RPG'. LIKE no las distingue, pero solo para las letras sin tilde del alfabeto inglés: 'Ábaco' LIKE 'á%' es falso. En PostgreSQL, LIKE sí distingue mayúsculas y existe ILIKE para ignorarlas. Cuando busques nombres escritos por personas, guarda o compara todo en minúsculas, y comprueba cómo trata tu motor las tildes.

Usar comillas dobles para los textos. En SQL, las comillas simples son para textos ('rpg') y las dobles, para nombres de columnas o tablas ("genero"). SQLite, por compatibilidad, acepta "rpg" como texto si no hay una columna con ese nombre, así que parece funcionar. Pero WHERE genero = "genero" compara la columna consigo misma y devuelve todas las filas, sin error. PostgreSQL rechaza "rpg" diciendo que esa columna no existe. Acostúmbrate a las simples.

Ordenar y limitar

ORDER BY ordena el resultado por una o varias columnas: de menor a mayor por defecto (ASC, ascendente) o de mayor a menor con DESC (descendente). LIMIT se queda con las primeras filas y OFFSET se salta unas cuantas antes de empezar. Con los dos juntos se hace la paginación: mostrar los resultados de 10 en 10, como las páginas de una tienda.

SELECT titulo, precio FROM juegos ORDER BY precio DESC;          -- del más caro al más barato
SELECT titulo, genero, precio FROM juegos ORDER BY genero, precio; -- por género y, dentro de cada género, por precio
SELECT titulo FROM juegos ORDER BY titulo LIMIT 3;                -- los 3 primeros por orden alfabético
SELECT titulo FROM juegos ORDER BY titulo LIMIT 3 OFFSET 3;       -- la «página 2»: del 4.º al 6.º

Haz tres cambios, ejecutando después de cada uno: muestra los 3 más baratos; después la segunda página de 3 (añade OFFSET 3); por último, los 4 juegos más recientes, usando la columna anio.

Si no escribes ORDER BY, la base de datos devuelve las filas en el orden que le resulte más cómodo. Hoy puede coincidir con el orden en que las insertaste y mañana, tras un cambio interno, no. Un LIMIT sin ORDER BY te da «unas filas cualesquiera». Si el orden importa, pídelo siempre.

NULL: el valor que no es un valor

NULL significa «no se sabe» o «no hay dato». No es cero ni un texto vacío: un cliente con el correo vacío ('') te dio un correo en blanco; un cliente con el correo NULL no te lo dio. Y aquí viene la trampa: cualquier comparación con algo desconocido da como resultado «desconocido». ¿Es un correo desconocido igual a otro correo desconocido? No se sabe. Por eso email = NULL nunca es verdadero, ni siquiera cuando el correo es NULL, y WHERE solo deja pasar las filas cuya condición es verdadera.

Escribir = NULL o <> NULL. No dan error: simplemente no devuelven nada, y crees que no hay datos. Para preguntar por la falta de valor usa siempre IS NULL o IS NOT NULL.

NULL también se contagia en los cálculos: 5 + NULL es NULL, y 'Hola ' || NULL también. Tiene sentido: si no sabes cuánto vale algo, tampoco sabes cuánto vale ese algo más 5. Al ordenar, SQLite y MySQL ponen los NULL al principio en orden ascendente y PostgreSQL, al final. Si te importa, dilo tú: ORDER BY email NULLS LAST funciona en SQLite y en PostgreSQL.

Decide columna por columna si un dato puede faltar. Si no puede, márcala NOT NULL desde el principio: cada columna que admite NULL es una pregunta más que tendrás que responder en cada consulta y en cada línea de código que lea ese dato.
